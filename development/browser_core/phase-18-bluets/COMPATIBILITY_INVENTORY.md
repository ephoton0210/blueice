# BlueTS compatibility inventory against pinned TypeScript 5.9.3 (J.6.1)

**Status: full `tsc` parity is not claimed and must not be advertised.** BlueTS is a checked,
emitting TypeScript front end for a defined subset of the language. Every form in that subset is
compared with the pinned 5.9.3 compiler by the differential suites in section 1, and everything
outside it is refused with a diagnostic (section 4) or is listed as an open gap (section 3). The
claim "full parity" is the conjunction of J.6.1 to J.6.3 *and* no open required gap; section 3
has required gaps open, so it stays closed.

K.1–K.14 are complete within their measured subsets and decision scope. K.13.2 confirms the four
hosted oracle legs (Ubuntu, macOS, Windows x86_64 and Windows arm64) in
[run 38877729768](https://github.com/ephoton0210/blueice/actions/runs/38877729768)
at `d4b13ff5e`; this is an oracle result, not a claim that the entire workflow
or the later K.13.4 source has passed that run. AC-K14.2's versioned case-rate
measurement is complete. AC-K14.3 uses the user's accepted Windows VM/local gates.
AC-K14.4 row accounting, AC-K14.5's scoped decision and AC-K14.6's four-document
consistency verification are complete. Broader required G-* gaps remain open.

The authority for every expectation is the pinned `typescript@5.9.3` executable (`BLUEICE_BLUETSC_ORACLE`),
not documentation. Section 1 is generated from one committed Git tree using a
Rust syntax parser, including tests in external modules, not a grep over text.
Section 4 is `python3 tools/inventory_refusals.py` over production source.
CI runs the ignored suites on four oracle platforms; the Windows legs report
their Unix-only exclusions explicitly (`.github/workflows/ci.yml`, job
`typescript-oracle`). Suite/function counts in section 1 are not a substitute
for K.14.2's versioned program/configuration denominators or agreement rates.
An agreement is limited to the properties asserted by that named suite
(for example diagnostics, execution, declarations or source-map metadata),
not universal byte-for-byte output or language-wide equivalence.
Broader unmeasured gaps in section 3 remain outside this finite case set;
the agreement percentage does not close them.

### Row accounting maintenance (AC-K14.4)

The two suite tables are views of the same source-matched suite records, not
separate programs. Schema 2 of `COMPATIBILITY_CASES.json` labels every suite
and case `closed`, `open` or `refused`. A case's assertion selector and its
measurement JSON pointer identify the evidence; the referenced suite also
retains the raw log digest. Reference-only and owner-only controls are closed
only within their named control scope and never become direct agreements.
Broad feature rows below stay open even where the measured suite is closed.

The Rust generator owns both generated tables and the case JSON. After its
suite/case regeneration, `tools/account_inventory_rows.py --write` refreshes
the reviewed feature labels, direct-profile label and source-derived refusal
list. Missing/duplicate feature IDs and stale/foreign case evidence are errors.
From the repository root, check all four boundaries without editing data:

```sh
cargo run -p blueice-bluets --example compatibility_inventory -- --check
cargo run -p blueice-bluets --example compatibility_inventory -- --check-cases
python3 development/browser_core/phase-18-bluets/tools/account_inventory_rows.py --check
python3 development/browser_core/phase-18-bluets/tools/check_compatibility_status.py --check
```

with classes, enums, functions); `.tsx` JSX in every `jsx` mode; standard and legacy decorators; installed
