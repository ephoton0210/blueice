# Phase 10 — Built-in Download Manager

[← Back to plan](../BROWSER_CORE_PLAN.md)

**Status**: Design resolved (see "Wiring design (resolved 2026-09-20)" below); implementation is in progress. Done so far: the `blueice-ipc` contract (the `downloads` wire protocol with its shared client, and the gatekeeper's `CheckDownload` stage) and the transfer engine in `blueice-net::download` (probe, segmentation with dynamic re-splitting, retries, stall watchdog, pause/resume/cancel, resume validation, atomic completion, and the gatekeeper clearance typestate). The `downloads` process, the MCP tools, and `about:downloads` are not started. The first slice's work items are tracked in [`TODO.md`](TODO.md).

## Objective

A full built-in file-transfer subsystem: chunked, resumable, multi-threaded downloads, comparable in capability to Free Download Manager — not just "save this HTTP response to disk."

Like the rest of BlueIce, it must expose one piece of state through both representations: a human sees a visual downloads page, and an AI agent reads the same transfers' progress and processing status over MCP — not a second, separately tracked copy of it (`BROWSER_CORE_PLAN.md`'s core goal).

## Design sketch

**Process design**: `backend/downloads/` as its own isolated OS process, a peer to `extension` and `ai-gatekeeper` rather than a child of either, speaking the same length-prefixed-JSON IPC family (`blueice-ipc`) as the rest of plan §1's architecture. The transfer *engine* itself (probing, segmentation, retries, resume) is a library in `backend/net` (`blueice-net::download`); the process wraps it with queueing, persistence, gatekeeper review, and the wire protocol. See "Wiring design" below for why the split sits there.

**Chunking algorithm** (the well-understood part): probe the resource to learn its total size and whether byte ranges work; if they do, split it into N concurrent `Range: bytes=start-end` requests, each writing straight into its byte range of a pre-allocated destination file (`File::set_len` + positioned writes — no N temp files to stitch together afterward); when a connection finishes early, it splits the largest remaining segment instead of going idle (dynamic re-splitting — the technique that keeps all connections busy on uneven servers); fall back to a single sequential stream when range requests aren't supported.

**Resume**: a sidecar metadata file next to the in-progress download (URL, total size, per-segment progress, `ETag`/`Last-Modified`). On resume, validate the remote resource is unchanged before continuing byte-for-byte — restart from scratch if it changed (or if there is nothing to validate against), rather than silently splicing old and new content together.

**State/UI surface**: the process exposes a list of `TransferInfo` records over IPC and pushes updates to subscribers rather than making clients poll. The human-facing view is a built-in `about:downloads` page rendered by BlueIce's own engine; the AI-facing view is a set of MCP tools over the same records.

## Wiring design (resolved 2026-09-20)

Resolved by reading the surrounding phases' plans and code (Phase 7's gatekeeper wiring, Phase 8's process registry, Phase 12's MCP adapter, the existing `about:credits` built-in page) plus explicit user direction on scope: **the engine, the process, the MCP tools, and the visualization all land in this first slice**, and the visualization is a built-in engine-rendered page, not a native `frontend` panel.

**Layering and process shape.** Two layers, deliberately separated:

- `backend/net` (`blueice-net::download`) — the transfer engine, a plain library. Everything that is hard to get right (segment planning, retries, resume validation, atomic completion) lives here, so it can be test-driven against a local HTTP server without any process, socket, or gatekeeper involved beyond the clearance token it requires.
- `backend/downloads` (`blueice-downloads`, lib + bin) — the isolated process: a `TransferManager` (ids, queueing, lifecycle, persistence), the download-directory policy, the gatekeeper calls, and a Unix-socket server speaking a new `blueice_ipc::downloads` protocol.

The process is registered in `blueice-launcher`'s `ProcessRegistry` as an `IdleTeardown` slot — typed but not yet wired to an automatic spawn path, exactly how `mcp-server` was registered (`phase-8-live-core-hotswap/PLAN.md`'s "Minimal first slice: fleet memory supervisor"); wiring automatic teardown is Phase 8 work this slice does not widen. Until then, every client uses connect-or-spawn: connect to the well-known socket, and if nothing is listening, spawn the sibling `blueice-downloads` binary (the same shape `frontend-reference` uses to find `blueice-core`). Idle teardown is scoped as `research/multi-process-memory.md` recommends: safe only with no active or queued transfers, and history must survive it (see "Persistence" below).

**HTTP client: `ureq` 3, not `reqwest`.** The codebase is synchronous + threads (`blueice_engine::session`, `gatekeeper_client`, the MCP server's `spawn_blocking`), `blueice-net` already depends on `ureq`, and pulling tokio into the engine path would buy nothing here: the engine uses one thread per segment. Facts checked against `ureq` 3.4.1's source:

- `Body::into_reader()` is unlimited by default — correct for streaming to disk, since the body is never buffered in memory — and errors if the connection closes before `Content-Length` bytes arrive, which the engine treats as a retryable truncation.
- `ureq`'s timeouts are per-phase budgets; in particular `timeout_recv_body` is "not restarted for each read," so there is no idle-read timeout. **Stall detection is therefore the engine's own job**: the coordinator thread revokes a segment that has made no progress for the stall timeout and reassigns it. A worker thread blocked in a dead `read()` can outlive that (until the TCP layer errors) but can never affect correctness, because a revoked worker's writes are discarded (see "Segmentation").
- `ResponseExt::get_uri()` exposes the post-redirect URL, which the probe records and segment requests use, so redirects are followed once rather than per segment.

**Probe: a ranged `GET`, not `HEAD`.** The probe sends `GET` with `Range: bytes=0-0`. A `206` with `Content-Range: bytes 0-0/TOTAL` proves ranges actually work and yields the total size; a `200` means the server ignores `Range` (single-stream mode; `Content-Length` may or may not be present). This tests the server's real behavior rather than what `Accept-Ranges` advertises, and it works for servers that reject `HEAD`. The probe also records the final URL, `ETag`, `Last-Modified`, and `Content-Type`, and derives a file-name hint from `Content-Disposition`.

**Segmentation.** With total size `T` and minimum split size `S`, the initial plan is `n = min(max_connections, ceil(T / S))` contiguous segments (the remainder goes to the last one). Each segment tracks `start`, `end`, `pos` (the next byte to fetch), an `owner` token, and its retry state. A worker claims a pending segment; if none is pending, it splits the running segment with the most remaining bytes (when at least `2 × S` remain) — the new segment takes the back half, and the victim's `end` shrinks so it stops when it reaches it. A worker checks its `owner` token before committing any progress, so a revoked (stalled, paused, or cancelled) worker's late writes are ignored. Because a split victim may already have a buffer in flight past its new `end`, up to one buffer of bytes can be written twice; the bytes are identical and progress is counted as `Σ (min(pos, end) − start)`, so this is harmless and never double-counted.

**Coordinator.** One thread per transfer ticks periodically: it samples throughput (an exponential moving average, with time injected so it is unit-testable), publishes a snapshot, tops up workers to `max_connections` when segments are claimable, runs the stall watchdog, and checkpoints. A checkpoint is `sync_data` on the data file followed by an atomic write of the sidecar, so the sidecar never claims bytes that are not durable.

**Retries and failure classification.**

- Retryable: network errors, truncated bodies, `408`, `429`, `5xx`. Backoff is exponential (0.5 s doubling to 8 s), the consecutive-failure counter resets whenever a segment makes progress, and exceeding the retry budget fails the transfer with the last error.
- Fatal: any other `4xx`, `416`, and **resource changed** — a `200` in reply to a `Range` request, a response `ETag`/`Last-Modified` that no longer matches the probe's, or a `Content-Range` that doesn't start where requested. The transfer fails rather than splicing content from two versions of the file.
- Range requests carry `If-Range` with the probe's validator, so a server-side change also shows up as a `200` instead of a mismatched `206`. The validator is the strong `ETag` if there is one, else `Last-Modified`; a weak `ETag` alone does not count (RFC 9110 forbids weak comparison in `If-Range`).

**Files, sidecar, and resume.** Data is written to a pre-allocated `<dest>.blueice-part`; progress lives in `<dest>.blueice-part.json`:

```json
{ "version": 1, "url": "…", "final_url": "…", "total": 123456,
  "etag": "\"…\"", "last_modified": "…", "content_type": "…",
  "segments": [ { "start": 0, "end": 61728, "pos": 40000 }, … ] }
```

On completion the engine `fsync`s, checks the length, atomically renames the data file to `dest`, and deletes the sidecar, so `dest` never holds a partial file. An existing `dest` is not overwritten unless the caller says so (checked at start and again at completion).

**There is one resume path.** Pause stops the workers and checkpoints; resume — in the same session or after a browser restart — rebuilds the transfer from the sidecar exactly as a restart would. A transfer resumes from the sidecar only if all of these hold: the sidecar version is supported; the data file exists with length `T`; the segments are contiguous, non-overlapping, and cover `[0, T)` with each `pos` within its segment; a fresh probe reports the same total; and the stored validator matches the fresh probe's. If anything fails — including a server that supplied no usable validator (`resume_safe: false` in the snapshot) — the transfer restarts from byte 0 and records why in its `events`. Never continuing without a validator is deliberate: silent splicing of two file versions is the failure mode this design exists to avoid. It also means every ordinary resume exercises the restart-resume path.

**Single-stream mode.** When the server ignores `Range` (or the total is unknown), the engine downloads one sequential stream into the same `.blueice-part` file. A truncated body restarts from byte 0 within the retry budget. Pausing such a transfer discards its progress and resuming restarts from 0; the snapshot's `mode` and `events` say so up front, so an AI agent or a human isn't surprised.

**Gatekeeper integration (typestate, fail-closed).** Both reference engines' weakest link was the download path (`research/safe-browsing-enforcement.md`), and `phase-7-local-ai/PLAN.md` requires the decision to *start* a transfer to need proof of review. Two stages, mirroring navigation's:

1. **URL stage** — `GatekeeperRequest::CheckUrl { url }`, before any network I/O, including the probe.
2. **Download stage** — a new `GatekeeperRequest::CheckDownload { url, file_name, content_type, total_bytes }`, after the probe (which is what makes the file type and size known) and before any bytes are downloaded. This is where "downloading an executable or otherwise dangerous file type" (Phase 7's risk taxonomy) gets its hook.

The stages are chained by types, not convention. `blueice-net`'s `clearance` module owns `Reviewer` (the gatekeeper client), `UrlCleared`, and `DownloadClearance` — privately constructed, not `Clone`, fields private to that module. `probe()` requires a `UrlCleared`; `Transfer::begin()` requires a `DownloadClearance`, which can only be obtained by clearing the download stage with a `UrlCleared` in hand. Skipping review is a compile error, not a review-time miss. This is why `blueice-net` depends on `blueice-ipc`: the engine itself, not just its caller, requires the token. A rejected review ends in a `Blocked { reason, category }` transfer, and an unreachable, dropped, or malformed gatekeeper reply is treated exactly like a rejection (fail-closed, as `blueice_engine::gatekeeper_client` already does for navigation). Every resume re-runs both stages — verdicts can change between a pause and a resume, so a clearance is never carried across one.

The compile-time guarantee holds only inside one process. Because `mcp-server` and `frontend` are separate processes, the **downloads process performs the review itself** and never trusts a caller (the MCP adapter included) to have done it. IPC-wire-level clearance enforcement remains the open Phase 9 item and is not solved here. `ai-gatekeeper` is still an always-clear stub, so the "blocked" path is tested with a fake gatekeeper, which proves the mechanism, not real review content.

**Transfer states and records.** Beyond the originally sketched Queued/Active/Paused/Completed/Failed, the state set is `Queued`, `AwaitingClearance`, `Active`, `Paused`, `Completed`, `Failed`, `Cancelled`, and `Blocked` — `AwaitingClearance`/`Blocked` because "waiting on (or stopped by) the gatekeeper" is otherwise indistinguishable from "queued" or "failed," and `Cancelled` so a cancelled transfer stays visible instead of vanishing. Transitions: `Queued → AwaitingClearance → Active ⇄ Paused`, then `Active → Completed | Failed | Cancelled`; `AwaitingClearance → Blocked | Failed | Cancelled`; `Paused → AwaitingClearance` (a resume re-enters review).

`TransferInfo` — the one record every consumer reads — carries `id`, `url`, `final_url`, `dest_path`, `state`, `total_bytes`, `completed_bytes`, `speed_bps`, `eta_secs`, `connections` (active workers), `segments[]` (range, completed bytes, state), `retries`, `last_error`, `blocked { reason, category }`, `mode` (segmented, or single-stream with the reason), `resume_safe`, `content_type`, timestamps, a `generation` counter (so a client can drop stale updates), and `events[]` — a bounded log of the last 32 notable events ("probe: server supports ranges, 8 connections", "segment 3 retry 2/5 after connection reset", "resumed from 41.2 MiB", "server changed since the last run; restarted from the beginning"). The `events` log is what lets an AI agent see not just *that* a transfer is slow or failed but *why*.

**Wire protocol** (`blueice_ipc::downloads`, a new module in `blueice-ipc` for the same reason `gatekeeper` and `extension` live there: reusing the private framing primitives). A long-lived connection with the `Hello`/`protocol_version` handshake and an envelope carrying `request_id`, like the client-facing protocol, because pushed updates interleave with replies. Requests: `Hello`, `Start { url, dest?, overwrite }`, `List { state? }`, `Get`, `Pause`, `Resume`, `Cancel`, `Remove` (drop a finished transfer from history), `Subscribe`, `Shutdown`. Replies: `Started(TransferInfo)` (as soon as the transfer is queued), `Transfers`, `Transfer` (the transfer as it now stands, for `Get`/`Pause`/`Resume`/`Cancel`), `Ok`, `Error { code, message }` (`code` is one of `not_found`, `invalid_request`, `invalid_state`, `unsupported_version`, `internal`), and the pushed `Updated(TransferInfo)`. Unknown variants fail soft, as in `ClientMessage`, and so does an unrecognized enum *value* inside a record (it reads as `Unknown` instead of losing the record). Enum values are snake_case strings on the wire, since an AI agent reads them verbatim in MCP results and passes `state` filters back. A subscriber that doesn't drain only delays itself, never other clients (the same per-client-writer lesson as `blueice-launcher`'s broker). A generic blocking client over `Read + Write` lives beside the types and is shared by the MCP server, `core`, and `frontend`.

**Destination policy.** Downloads land under `$BLUEICE_DOWNLOAD_DIR`, else `<the XDG download directory, or ~/Downloads>/BlueIce`. A caller-supplied `dest` is accepted only as a relative path inside that directory; absolute paths and `..` components are rejected — Phase 7's risk taxonomy names an AI agent reaching the file system outside a downloads directory. File names taken from `Content-Disposition` or the URL are sanitized (path separators, control characters, reserved names, excessive length). A name conflict fails unless the caller opts in to overwriting, and otherwise picks a unique name only when the name was derived rather than requested.

**Persistence.** Each in-progress transfer's sidecar makes it resumable; on top of that, the manager keeps a `transfers.json` index (atomic writes) under `$XDG_DATA_HOME/blueice/downloads/` holding every transfer, including finished ones, so history and resumable items survive a process restart and the process can be torn down when idle. On startup, anything recorded as `Active` becomes `Paused` with an event noting that the process restarted. Whether the whole *browser* restarting resumes automatically is left to the user: transfers come back `Paused`, never auto-started.

**AI observability over MCP.** `blueice-mcp-server` gains `download_file(url, dest?)`, `list_transfers(state?)`, `get_transfer(id)`, `pause_transfer`, `resume_transfer`, `cancel_transfer`, and `remove_transfer` — thin translation onto the downloads protocol, in keeping with Phase 12's adapter-not-parallel-channel principle; `blueice-mcp-server` implements no transfer logic. Every result is the structured `TransferInfo` plus a one-sentence plain-language `summary` ("8 connections, 41%, 12.3 MB/s, about 1 min 20 s left"; "blocked by the gatekeeper: <reason>"). `download_file` returns as soon as the transfer is queued; the agent reads progress with `get_transfer`. Every result carrying server-supplied text — URLs, file names, error messages, `events` — is wrapped with `wrap_untrusted_page_content`, the same "this is data, not instructions" framing every page-derived tool result already gets.

**Visualization: `about:downloads`.** A built-in page generated per request by the engine, following the `about:credits` precedent (`blueice_engine::credits`, recognized in `Page::navigate` without a network fetch), rendered through the normal HTML/CSS/layout/paint pipeline. That is the point: the progress bars a human sees and the accessibility-tree snapshot an AI agent reads through `get_page_representation` come from the same render pass, not from a native panel only one frontend could draw. Each row shows the file name, state, a progress bar, downloaded/total, speed, ETA, a segment block map (per-segment completion, in the style Free Download Manager uses), and any retry, error, or blocked reason. All strings go through `blueice-i18n` (a new `downloads.ftl`, `en` + `zh-TW`). The bar's width uses percentages if layout supports them, otherwise pixels computed by the generator — verified as the first step of M5.

- **Live updates.** The page must move while a download runs, which the static credits page never had to. On `session.rs`'s poll tick, if any tab is on `about:downloads`, `core` fetches a fresh snapshot roughly every 500 ms and re-renders only when it changed. The fetch runs on a background thread and reports through the same completion-channel mechanism gated navigation uses, so a slow or hung downloads process never delays other tabs or clients. The resulting `FrameReady` and the `Representation` that follows it keep sharing one `generation`, preserving the "same render pass" check from Phase 5.
- **Opening the page** connect-or-spawns the downloads process — `research/multi-process-memory.md` names "the frontend opening the downloads panel" as a legitimate respawn trigger — and shows an empty state if that fails, never a navigation error.
- **Starting a download as a human.** `frontend-reference` gains stdin commands `downloads` (navigate to `about:downloads`, like the existing `credits` command) and `download <url>` (talk to the downloads process directly). `ClientMessage` is not extended: `core` needn't learn a downloads command just to relay it.

**Defaults** (all configurable): 8 connections per transfer, 1 MiB minimum split size, 5 retries with 0.5 s → 8 s exponential backoff, a 30 s stall timeout, and 3 transfers running at once (the rest stay `Queued`). These are this design's own starting values, not Free Download Manager's.

**Relationship to Phase 11.** Same subsystem with a pluggable protocol backend (Phase 11's `TransferBackend` sketch), not two separate components: this phase owns the chunking/resume/state machinery and the HTTP backend; Phase 11 supplies FTP/SFTP backends. This slice deliberately does **not** define the trait: with one implementation, the right abstraction is a guess (FTP's `REST` and SFTP's read-at semantics differ from HTTP ranges). Instead the engine's ranged fetch stays behind one internal function boundary, so lifting it into a trait when Phase 11 has a second backend is mechanical.

**Testing approach.** The engine is tested against a hand-rolled local HTTP server (with/without Range support, changing validators, injected 5xx and mid-body disconnects, throttling, per-request logging of `Range` headers and concurrent connection counts, redirects), plus a fake gatekeeper listening on a real Unix socket. The process is tested end to end as a real subprocess, as `core_binary.rs` does for `blueice-core`. See [`TODO.md`](TODO.md) for the full list.

**As built: the transfer engine** (`blueice-net::download`). The public sequence is `Reviewer::review_url` → `probe(&UrlCleared)` → `Reviewer::review_download(UrlCleared, &Probe, file_name)` → `Transfer::begin(DownloadSpec, Probe, DownloadClearance)`, then `snapshot` / `pause` / `cancel` / `wait`. Where building it settled details the design left open:

- `probe` borrows the `UrlCleared` and makes a single attempt, so a caller can retry a transient failure (`DownloadError::is_retryable`) without spending a new review; `review_download` consumes the token.
- The download stage reviews the probe's **final** URL (where a redirect actually led), and a `DownloadClearance` binds the requested URL, the file name, the content type, and the size. `Transfer::begin` refuses a clearance that does not match what it is asked to download, so a token for one file cannot be spent on another. A `Reviewer` gives every check a deadline (default 10 s) that also holds against a gatekeeper that sends half a frame and then stalls; every way a check can fail to say "yes" yields `Blocked` and never a token.
- A URL that does not parse is `InvalidUrl`, not a (retryable) network error — a test caught `ureq` reporting an empty host through its `Http` error variant.
- `Transfer::pause` blocks until the transfer has settled, and dropping a running `Transfer` pauses it, so there is still exactly one resume path: a new `begin` rebuilding from the sidecar. A transfer that fails keeps its partial data and sidecar when resume is safe (a later `begin` can continue it) and discards them when it is not.
- Concurrent requests may overlap after a split — the original request still names its old end and its worker stops reading at the new one — so what the tests check is that the request ranges' *union* covers the file, and that the assembled file is byte-for-byte correct.
- `DownloadOptions` also carries a connect timeout (10 s) and a first-response timeout (30 s), since `ureq` offers no idle-read timeout to cover the rest.

## Open questions

- ~~Process placement~~ — **isolated process, confirmed**, consistent with `extension`'s isolation rationale (plan §1). [`research/multi-process-memory.md`](../research/multi-process-memory.md) additionally flags `downloads` as an idle-teardown candidate (no reason to stay resident with zero active/queued transfers) — the Phase 8 launcher is the proposed owner of that teardown authority once it exists. **Resolved 2026-09-20**: the engine is a `blueice-net` library and the process wraps it; see "Wiring design."
- ~~**Resume-across-restart**~~ — **resolved 2026-09-20**: yes. State persists as a per-transfer sidecar next to the data file plus a `transfers.json` index, and a transfer resumes only when a strong validator confirms the remote file is unchanged; see "Wiring design."
- ~~**Relationship to Phase 11**~~ — **resolved 2026-09-20**: one shared subsystem with pluggable backends; the trait itself is deferred to Phase 11 (see "Wiring design").
- **Private-network URLs** (localhost, RFC 1918, link-local) requested by an AI agent are **not blocked** by this slice — tests need localhost, and blocking them deserves its own design. A known gap, intended for the gatekeeper's rule base (`phase-7-local-ai/PLAN.md`).
- **Real review content for downloads.** `ai-gatekeeper` still always clears; what its rule base and AI layer should say about executables, archives, and oversized files is Phase 7 work. This phase only provides the hook (`CheckDownload`).
- **Redirects are contacted before the download stage sees them.** The probe follows redirects (`ureq` does it transparently), so a redirect's target receives a one-byte ranged request before the download stage reviews the final URL; no file bytes are transferred first. Navigation has the same shape today. Closing it means following redirects by hand with a review per hop.
- **`Retry-After` is not honored**: a `429`/`503` is retried on the ordinary exponential backoff.
- **Write failures are not exercised by a test.** A full disk or a failing `fsync` is reported as a fatal `Io` error, but there is no portable way to provoke one in a test.
- **Navigation-triggered downloads.** A clicked link to a non-HTML resource, or a `Content-Disposition: attachment` response, should hand off to this subsystem. Today `core`'s navigation path fetches everything as text; this slice does not touch that path.
- **Automatic idle teardown** of the downloads process is Phase 8 work (the launcher's registry slot exists after this slice, but no automatic spawn/teardown is wired).
- **IPC-wire-level clearance enforcement** across process boundaries is the shared open item with Phase 7/Phase 9.
- **Not designed here**: a scheduler, bandwidth limits, multi-mirror downloads, cookies/authentication/proxies, and Windows support (the whole workspace currently relies on `UnixStream`).
