# Phase 8 — Live Core Hot-Swap / Seamless Update

[← Back to plan](../BROWSER_CORE_PLAN.md)

**Status**: In progress for this phase's own hot-swap objective — the design is fully resolved (see "Wiring design (resolved 2026-09-08)" below) and its minimal-slice cutover mechanism is now built and tested: a manually/control-socket-triggered, reload-based cutover from a running `core` (v1) to a freshly-spawned `core` (v2), with v1's tabs replayed into v2 and already-connected external clients never dropped. Cutovers are single-flight: a competing control request receives `CutoverBusy` without changing state. Automatic update-detection/scheduling, a bounded-retry policy, and structural per-tab health diffing remain future work. Two other minimal first slices are already done — the rendezvous broker (a human's `frontend` and an AI's `mcp-server` sharing one `core` instance at all), including its `protocol_version`/request-ID follow-up, and a fleet-wide process-supervisor framework wired to the one real, unblocked target (`core`) — see "Minimal first slice" and "Minimal first slice: fleet memory supervisor"

## Objective

Let `core` be updated at runtime without restarting the browser: start a new `core` process (the updated version), verify it's healthy, hand off from the old instance to the new one, then terminate the old instance — invisible to the user, no dropped session.

This generalizes a principle plan §1 already established for window visibility ("AI-controlled visibility, decoupled from process lifecycle") to `core`'s own lifecycle: a process boundary existing is not supposed to mean session continuity breaks when that process cycles.

## Minimal first slice: the rendezvous broker (multi-client sharing, not yet hot-swap)

Raised the same way "Foundation built early" was for Phase 5/`mcp-server` (`phase-12-mcp-server/PLAN.md`): an architecture-wide risk survey found that **today, a human's `frontend` and an AI's `mcp-server` can never observe the same `core` instance at all** — `blueice-mcp-server` spawns its own private `core` subprocess with its own fresh `Page` on every startup (`CoreProcess::spawn`), and `blueice-core`'s own docs state it "accepts exactly one client connection... no multi-frontend support." That's the exact dual-track architecture plan §1's core goal rejects (a human on one instance, an AI driving a separate one), just as fully present internally as the external "human on a real browser, AI on headless Chromium" case the whole project exists to avoid. Waiting for this phase's full hot-swap design (blocked on the reload-vs-migration decision below) to also fix this would block it for no good reason — hot-swapping to a *new core version* and fanning out *one already-running core* to *multiple simultaneous clients* are different problems that happen to want the same rendezvous shape, and the first open question below ("clients connect through a stable point, not to a specific `core` instance") is exactly the piece this slice needs and nothing more.

**Design**: a new, deliberately minimal `blueice-launcher` binary — the same "simpler than `core` itself on purpose" launcher role sketched below, built now for its multi-client-broker job rather than its hot-swap job:

1. **Rendezvous point**: the launcher listens on a well-known Unix domain socket (default `$XDG_RUNTIME_DIR/blueice/core.sock`, falling back to `/tmp/blueice-<uid>/core.sock` if unset — per-user, not system-global; overridable via `--socket`/an env var for tests and for running more than one BlueIce session side by side).
2. **One real `core`, spawned once, never idle-torn-down**: on its own startup, the launcher spawns exactly one `blueice-core` process on a private, internal socket it generates itself (clients never see or connect to this one directly). Per `research/multi-process-memory.md`'s own finding ("`core` — always-resident, no change... nothing suggests treating the always-must-be-up process as an idle-teardown candidate"), this spawned `core` stays up for the launcher's whole lifetime regardless of how many external clients are connected — including zero. Only `mcp-server` (a genuinely stateless adapter, per that same research doc) is an on-demand-spawn candidate; `core` itself never is.
3. **Fan-in / fan-out, not a protocol change to `core`**: `blueice-core`/`session.rs` needs **no changes at all** for this slice. The launcher holds the single internal connection `session.rs` already expects, and does the multi-client work itself: every external client's incoming `ClientMessage`s are forwarded (interleaved, from however many external connections are open) into that one internal stream; a single reader task on the internal stream broadcasts every `ServerMessage` `core` sends back out to *every currently-connected external client*, not just whichever one's action triggered it. This is what actually delivers "same render pass": an AI's `ActOn` produces a `FrameReady` the human's `frontend` receives too, and vice versa, because both are reading the same broadcast off the same one `core` connection.
4. **`mcp-server` changes** (resolves `phase-12-mcp-server/PLAN.md`'s blocked "switch from unconditional spawn to on-demand process spawning" checklist item): `CoreConnection`'s construction tries connecting to the well-known rendezvous socket *first*; only if that fails (nothing listening — no launcher running, e.g. a standalone dev/test workflow) does it fall back to today's behavior, spawning a private `core` via `CoreProcess::spawn`. This is a pure addition — every existing test that relies on today's unconditional-private-spawn behavior (including the real-subprocess integration test) keeps working unchanged, since "nothing listening at the rendezvous path" is exactly the environment those tests already run in.
5. ~~**Known limitation, flagged rather than silently accepted**~~ **Fixed** — see the checklist item below: `ClientMessage`/`ServerMessage` originally had no per-request correlation ID, so with the broadcast in step 3, a `ServerMessage::Error` genuinely caused by *another* client's concurrent action could be misattributed by `mcp-server`'s `send_and_drain` (which loops until it sees *a* `Representation`, treating any `Error` seen along the way as its own) to the tool call currently in flight. A client-generated request ID, echoed back on every reply, closes this.

**What this slice deliberately does not do** (still gated on the open questions below, unchanged): hot-swap `core` to a new *version* (spawning v2 alongside v1, health-checking it, cutting traffic over, tearing down v1). Idle-teardown authority over `mcp-server`/`downloads`/`ai-assistant` — originally listed here too — has its own minimal first slice now; see immediately below.

## Minimal first slice: fleet memory supervisor (framework + `core`, not yet other roles)

Raised the same way the rendezvous broker was: the "Fuller hot-swap work" checklist's "scope the launcher's idle-teardown authority... per `research/multi-process-memory.md`" item doesn't need to wait on the hot-swap design questions below (reload-vs-migration, health-check contract) — supervising a fleet of *other* processes' lifecycles is an independent concern from hot-swapping `core`'s own version, and the launcher already exists as the natural owner (it's already `core`'s supervisor for the rendezvous broker).

**Design**: a generic, policy-driven process registry in `blueice-launcher`, not a special case per role:

```rust
pub enum ProcessPolicy {
    AlwaysResident,                         // core; ai-gatekeeper once Phase 7 exists
    OnDemand { idle_timeout: Duration },     // not yet spawned; spawn on first need
    IdleTeardown { idle_timeout: Duration }, // already resident, eligible once idle
}
pub struct ProcessRegistry { /* HashMap<String, SupervisedProcess>, keyed by role name */ }
```

`ProcessRegistry::mark_active(role)`/`idle_eligible_for_teardown(now: Instant)`/`teardown(role)` — `now` is an injected parameter (not read internally via `Instant::now()`) so idle-timeout tests are deterministic, never a real sleep. A `MemorySource` trait (`fn available_ratio(&self) -> f64`), backed by a new `sysinfo` dependency (`blueice-launcher`'s `Cargo.toml` previously depended only on `blueice-ipc`), is polled on a background thread; below a configurable threshold it calls `idle_eligible_for_teardown` and tears each returned role down. The trait boundary keeps the *decision* logic unit-testable against a fake signal — a test that depends on actually exhausting host memory would be flaky/dangerous in CI.

**`core` and `ai-gatekeeper` are wired up as fully real always-resident roles**: `blueice-launcher` starts `SpawnedGatekeeper` first on a unique private socket, then starts `SpawnedCore` with that explicit socket; `ProcessRegistry::default_fleet` registers both roles as `AlwaysResident`, while their actual children remain owned and cleaned up by their respective `Spawned*` values rather than duplicated into the registry. Every core v2 spawned for cutover inherits that same live gatekeeper socket. `mcp-server` is registered too, but only as a **typed, inert `IdleTeardown` slot** — present in the data model and exercised in tests against a real (if synthetic) child process standing in for it, but with no automatic spawn-on-first-connection path wired up yet. That's a deliberate, named limit, not an oversight: `blueice-mcp-server` currently only ships a stdio transport (spawned directly by whatever MCP host process invokes it, which already owns that child's lifetime via stdio) — for `blueice-launcher` to genuinely own spawn-timing and idle-teardown of `mcp-server`, it would need to become the thing an MCP host points its command at instead of `blueice-mcp-server` directly, a real, unresolved transport question (`blueice-launcher` as a lazy stdio-spawning proxy? `mcp-server` gaining a socket transport the launcher can listen on and spawn behind?) that isn't a mechanical consequence of the registry existing — tracked as its own follow-up below, matching `phase-12-mcp-server/PLAN.md`'s own already-open "switch `mcp-server` to on-demand process spawning" checklist item.

**Registry ownership (resolved 2026-09-25).** Each of the three remaining roles has one owner, chosen for a reason rather than left open. `ai-assistant` is **launcher-owned** and registered `OnDemand` by `AssistantSupervisor` when an assistant is configured: the launcher owns its public socket, starts it on the first connection, treats every relayed connection as activity, tears it down when idle under memory pressure (the registry's existing rule), kills it over its resident-memory ceiling, and respawns it on the next connection (`phase-7-local-ai/PLAN.md`, R2–R3). The `extension` host is **core-owned** and deliberately never registered: core generates a fresh credential per generation, hands it to the child through its environment only, and accepts only that child's authenticated `HelloAuthenticated` — a launcher-held child would break that binding, and a cutover already gives each new core its own host. `downloads` is **client-owned** (connect-or-spawn) and deliberately absent from `ProcessRegistry::default_fleet`: a time-only teardown could lose an active or queued transfer. Registering it would first need an authoritative idle query from the downloads manager (no active, queued, or resumable-pending transfers) and an orderly shutdown request; until that exists it stays out of the registry.

## Design sketch (the fuller hot-swap shape this phase is ultimately for)

A concrete shape for the supervisor role, assuming (pending confirmation, see open questions) the **reload-based** state-transfer approach — it's the far cheaper of the two options and the sketch below is written against it:

1. A small, deliberately minimal **launcher** binary — simpler than `core` itself on purpose, so it's the least likely thing in the whole system to itself need updating — spawns `core` v1 and hands it a listen socket/named pipe for the control-plane IPC. **This role gets a second job**, per [`research/multi-process-memory.md`](../research/multi-process-memory.md): neither Chromium nor Firefox has a true whole-fleet memory budget (only per-process limits), and BlueIce's own Phase 7 plan flags several of its processes (`ai-assistant`, `mcp-server`, `downloads`) as idle-teardown candidates with nothing currently owning that authority. The launcher, already supervising `core`'s own lifecycle, is the natural place to own idle-teardown of those other processes too, rather than inventing a separate coordinator role.
2. `frontend`/`extension` connect to a stable rendezvous point the launcher owns (a well-known local socket path), not directly to a specific `core` process — so which `core` instance is actually behind that socket can change without either client needing to know.
3. **Update**: the launcher spawns `core` v2 alongside the still-running v1, pointed at the same on-disk profile/state directory (opened read-only by v2 until cutover, to avoid concurrent-write corruption).
4. **Health check**: `frontend` (or the launcher, via `frontend`'s current tab list) replays the session's open URLs into v2 and confirms it renders without crashing; an exact pixel-perfect match against v1 isn't a reasonable bar (font/anti-aliasing can legitimately differ between builds) — a first-pass health bar could be simply "renders without panicking and produces a DOM of comparable structure," tightened later once this phase is actually built.
5. **Cutover**: existing connections are drained/reconnected to v2 (either the launcher starts proxying new rendezvous connections to v2, or it pushes a "reconnect now" signal to already-connected clients — a real design choice for whoever implements this, not resolved by this sketch).
6. **Teardown**: v1 is terminated after a grace period once v2 is confirmed healthy under real traffic, not immediately at cutover.

If reload-based state transfer turns out to be insufficient (see open questions), most of this sketch still holds — only step 4/6 and what "session state" means at handoff would need to change, not the overall supervisor/rendezvous shape.

## Wiring design (resolved 2026-09-08)

Resolved via a research pass grounded in the *actual* current shape of `blueice-launcher`'s broker (`run_broker`/`forward_client_to_core`/`broadcast_core_to_clients`/`core_writer: Arc<Mutex<UnixStream>>`, all real and shipped) and `blueice-engine`'s real multi-tab support (`TabManager`, `ListTabs`/`OpenTab`/`Navigate`), plus explicit user direction to proceed with the recommended design.

**Reload-based, not true state migration — confirmed.** `Page`'s actual fields (doc/styles/fragment, all pure functions of content+viewport, plus transient scroll/hover/focus/highlight state) hold nothing a reload can't cheaply reconstruct, and there is no JS execution state anywhere yet (BlueJS hasn't landed). True migration would buy almost nothing for the cost. Concretely: the launcher captures v1's current tab list via `ListTabs`, spawns v2, and replays it in — `Navigate{url}` for the first (default) tab, `OpenTab{url}` for each subsequent one, `url: None` skipped (leaves that slot blank, same as a fresh tab). Known, accepted cost: scroll position, hover/focus state, and any unsubmitted form input do not survive a cutover — equivalent to "your tabs reloaded," not "your session vanished."

**The launcher captures v1's tab list as a synthetic internal client of its own broker**, not via a side channel — `core` only ever has the one real connection the launcher itself holds (`core_writer`); every external client's traffic is proxied through it. The cutover handler pushes its own `mpsc::Sender<ServerMessage>` onto the same `clients` list `register_client` already uses for real external clients, writes `ListTabs` into `core_writer` tagged with a request ID it generates, and reads its own `Receiver` until the reply with that ID appears — the same request-ID-based filtering `blueice-mcp-server`'s `send_and_drain` already established for picking one reply out of a broadcast stream, reimplemented locally in `blueice-launcher` rather than shared (consistent with this codebase's existing convention of duplicating small, crate-specific helpers rather than adding a shared-dependency for ~10-20 lines).

**Health check for this minimal slice — real, but deliberately narrower than the fuller ambition.** Every replay message (`Navigate`/`OpenTab`) must get a successful reply (`Navigated`/`TabOpened` + `FrameReady`, never `Error`) via the same synthetic-client mechanism above, and a final `ListTabs` against v2 must report the expected tab count and URLs. This is real, checkable, and sufficient to prove the mechanism — structurally diffing each tab's `GetDom`/`GetRepresentation` against v1's own captured state (the fuller ambition, for a genuine version-upgrade health bar) is explicitly deferred, not built in this slice.

**Failure handling for this minimal slice — single attempt, fail closed to v1, no retry loop yet.** If v2 fails to spawn, or any replay message errors, the cutover is abandoned before any swap step ever touches v1's serving state: v2's process (if spawned) is killed and cleaned up, the control client gets `ControlReply::CutoverFailed { reason }`, and v1 keeps serving every already-connected client exactly as before, untouched. A bounded-retry policy is real, deferred future work — flagged as a follow-up, not solved here.

**Concrete cutover mechanism.** Once replay + health check succeed:
1. Retain each replayed tab's v2 `FrameReady` and its actual tab ID, then perform the writer swap under `core_writer`'s mutex. Bump the launcher generation before closing v1; v1's broadcaster checks that generation while holding the same client-list mutex used for handoff, so a late v1 read cannot be queued after a v2 frame.
2. Queue the retained v2 frames to the existing `clients: Arc<Mutex<Vec<Sender<TaggedServerMessage>>>>` list as unsolicited notifications (not replies to the launcher's synthetic replay requests). The human frontend can paint v2 immediately, even though its frame generation counter restarted and no user action has occurred.
3. Close v1's stream before handoff, then start v2's generation-tagged broadcaster on that same client list and reap v1's process/socket/frame directory. The synthetic capture client's dropped receiver self-prunes on broadcast; no explicit removal is needed.
4. Reply `ControlReply::CutoverDone { tabs_migrated }` after v1 teardown.

**A real, pre-existing bug found while grounding this design in the actual broker code (not introduced by this phase's own work, but blocking it and worth fixing regardless)**: `forward_client_to_core`/`broadcast_core_to_clients`/`register_client` currently use the plain (non-`_with_ids`) `blueice_ipc` functions — `write_client_message`/`write_server_message` always write `tab_id: None, request_id: None`, and `read_client_message`/`read_server_message` discard both fields entirely; the client fan-out channel is typed `Sender<ServerMessage>` with no id fields to carry at all. This means **`tab_id` and `request_id` do not actually survive being relayed through the broker today** — every message effectively gets forced onto the default tab, and every reply loses its tab identity, contradicting `phase-16-multi-tab-and-tab-groups/PLAN.md`'s and `CLAUDE.md`'s existing claim that "a client sharing the connection via `blueice-launcher`'s broadcast broker can always tell which tab a reply is about." Existing tests didn't catch this because the broker's own end-to-end test doesn't exercise multi-tab addressing specifically. Fixing this (switching the broker's forwarding/broadcast/fan-out path to the `_with_ids` functions and an id-carrying channel type) is a prerequisite for this phase's own cutover mechanism (the synthetic internal client needs request-ID correlation to actually survive the broker) and a real correctness fix in its own right — tracked as its own checklist item below, done together with the cutover work since it touches the exact same functions.

**A concrete, load-bearing detail the research surfaced**: v2 must be spawned with a *different* `frame_dir` than v1's — both instances' `generation` counters start at 0 independently, so sharing a frame directory would let v2's early frames collide with v1's already-written ones of the same generation number while v1 is still actively serving.

**Trigger mechanism for this minimal slice**: a new, small, launcher-internal control socket (`default_control_socket_path()`, distinct from the client rendezvous socket), speaking one new request/reply pair (`ControlRequest::Cutover` / `ControlReply::{CutoverDone, CutoverFailed, CutoverBusy}`) — a manual, externally-triggered cutover between the launcher's already-running v1 and a v2 it spawns itself on request, proving the mechanism end to end before any automatic update-detection/scheduling policy exists. The broker owns an atomic RAII gate for the full capture/replay/health-check/swap interval, so no two control connections can race a transition; the second request gets `CutoverBusy` and makes no change.

**The concrete, client-observable property to test**: an external client registered *before* cutover is never dropped/disconnected by it, and a message sent to that same still-open connection *after* cutover gets a reply reflecting v2's (replayed) state — the actual "seamless" property this whole phase exists for.

**Installed-extension cutover follow-up (2026-09-24).** The launcher accepts `--extension-manifest` and passes that installed package to v1 and every cutover v2 with a fresh private extension socket and the sibling `blueice-extension-host` executable. Core revalidates the manifest and requires its own newly authenticated host before exposing each generation's frontend socket. The launcher lets a superseded core exit normally and reap its host, with a bounded force-kill fallback. A compiled launcher/core/extension-host test proves that v1's extension socket disappears, v2's appears, and the same external client still sees its replayed tab. A second compiled-process test corrupts the installed manifest after v1 is ready and proves that v2's revalidation fails closed to v1 without dropping its extension socket or an already-connected client. Optional capability grants are process-lifetime state and intentionally are **not** migrated; v2 begins from manifest-declared grants. This is not a full extension state migration or a trusted-consent implementation. If a core exceeds the shutdown grace, the force-kill fallback does not yet guarantee its child was reaped; stronger process-tree containment remains future work.

## Open questions (blocking the fuller hot-swap design; the process-role question is resolved for the minimal slice above)

- ~~**This needs a new process role.**~~ **Resolved for the minimal slice**: `blueice-launcher`, designed above — `frontend`/`mcp-server` connect to its rendezvous socket rather than to a specific `core` instance directly. What's still genuinely open for the *fuller* hot-swap objective is whether that same launcher process (vs. a second, separate role) is also the right owner of spawning/health-checking/handoff between `core` v1 and v2 — the minimal slice gives it exactly one `core` instance to manage, forever; hot-swap needs it to manage a transition between two.
- ~~What state actually needs to transfer from old `core` to new `core`?~~ — **resolved: reload-based**, via `ListTabs`-captured-then-replayed tab URLs against the real `TabManager`/`OpenTab`/`Navigate` messages — see "Wiring design" above. True state migration is not needed: no JS execution state exists anywhere yet, and `Page`'s own fields are all cheaply reconstructible from content + viewport.
- ~~Health verification before cutover~~ — **resolved for the minimal slice**: every replay message must succeed (no `Error`), plus a final `ListTabs` against v2 matching the expected tab count/URLs — see "Wiring design" above. Structurally diffing `GetDom`/`GetRepresentation` per tab against v1's own captured state is explicitly deferred, not this slice's bar.
- ~~Failure handling~~ — **resolved for the minimal slice**: a single attempt, fail closed to v1 (v1 is never touched until replay + health check both succeed), v2 killed and cleaned up on any failure — see "Wiring design" above. A bounded-retry policy is deferred future work.

**Fuller hot-swap (added 2026-09-25).** The minimal-slice cutover is built; these three pieces of the objective were only prose ("future work") and are now checklist items with the design decisions they need. Shared principle: v1 is never touched until v2 has replayed and passed its health check, so every retry or automatic attempt is safe to abandon.

- [x] Bounded retry for a cutover that fails transiently. Decision: a cutover attempt (spawn v2, replay, health check) may be retried up to twice more with a growing pause, but only for failures that leave v1 untouched and can plausibly clear (a v2 that failed to spawn or start, a replay that timed out); `CutoverBusy` is never retried, and a v2 that *ran and failed its health check* is retried at most once (a second identical failure is deterministic). The reply reports how many attempts were made and the last reason. **Built:** `run_with_retries` is the policy as a pure function (three attempts; a pause of 250 ms then 500 ms; `Final` never retried, a health failure retried once), and `attempt_cutover` is one try; every replay and health message this crate produces is pinned by a classification test so rewording cannot change how it is retried. Two hardening fixes fell out of it: a core that exits on startup is noticed at once instead of after the 5 s socket wait, and every v2 read during replay and health check now has a 30 s timeout (a hung v2 used to hang the whole cutover). Compiled-launcher tests use a shell wrapper around the real core that fails chosen invocations: a first-attempt start failure is recovered by the retry on the same open client connection, and a core that never starts gives up after exactly three attempts with v1 still serving and a later cutover still accepted (not stuck busy). The reply carries the attempt count and last reason in `reason` (the wire enum is unchanged). One existing test had to block each attempt's frame directory, because a retry now recovers from the single blocked one — the intended behavior
- [x] Automatic update detection and scheduling. Decision: opt-in (`--auto-update-secs N`; off by default, so an existing deployment never changes behavior on upgrade). The launcher watches the `blueice-core` binary it would spawn; when its identity (modification time and length) differs from what the running core was started from *and has stayed the same for one further poll* (so a half-copied binary is never swapped in), it runs the same single-flight cutover the control socket triggers, with the bounded retry above. Scheduling: immediately, because a cutover never drops a client; there is no quiet-window policy to design. After a success the new binary becomes the baseline; after exhausting retries it gives up until the binary changes again, and reports why on stderr. **Built:** `update_watch.rs` — `UpdateWatch` is the decision logic as a state machine with no I/O and no clock (ten table-driven tests: unchanged never acts; a change must be seen on two consecutive polls; a still-growing file never confirms; an unreadable file forgets a half-confirmed change; a revert is dropped; success re-baselines; a failed build is left alone until it changes again; a busy cutover is simply asked again), and `spawn_update_watcher` runs it against the real cutover with its bounded retry. `blueice-launcher --auto-update-secs N` enables it (off by default; `0` and non-numbers are refused). Four compiled-launcher tests swap a replacement `blueice-core` in atomically under a running launcher: an unchanged core is never restarted; a newer one replaces the running core while the client connection opened *before* the update keeps its tab, and one update is one cutover, not a loop; three versions landing in about a second produce a single cutover; a broken update is tried exactly three times with v1 still serving, is not tried again on later polls, and a fixed build afterwards succeeds. Identity is modification time plus length, not a content hash: a same-length, same-second replacement would be missed, which package managers do not do in practice and a hash would cost a full read of a large binary every poll
- [ ] Structural per-tab health diff. Decision (a first-pass bar, as the design sketch anticipated): for each replayed tab, v2's representation must be non-empty whenever v1's was, and its node count must stay within half to double of v1's. That catches a blank or crashed render without failing on pages whose content legitimately changed. The threshold is a constant with a test, tightened later against real traffic.
