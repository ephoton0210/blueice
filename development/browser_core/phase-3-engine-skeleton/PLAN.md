# Phase 3 — Rust Core Engine Skeleton

[← Back to plan](../BROWSER_CORE_PLAN.md)

**Status**: Done

## Objective

Stand up the minimal end-to-end pipeline in Rust — parse → DOM → CSS cascade → layout → paint — as defined by the Phase 2 scope. This is the first phase that produces actual engine code; everything before it is planning.

## Plan

Structure this as a Cargo workspace with one crate per pipeline stage (rather than one monolith), matching how Servo and similar projects decompose the problem, referenced in plan §4 — and laid out under `backend/core/` per plan §1's process architecture, alongside a stubbed `backend/extension/` and a shared `ipc` crate, so the process boundary exists from the first commit rather than being retrofitted:

1. HTML tokenizer/parser producing a DOM tree
2. CSS parser + cascade producing a styled tree, against the Phase 2 CSS subset
3. A layout pass (block/inline flow at minimum) producing a layout tree
4. A paint stage producing a raster/paint-command output
5. An end-to-end smoke test that runs a small HTML+CSS fixture through all four stages and asserts on the output

`backend/extension/` stays a stub in this phase — no real extension API ships in MVP (plan §4) — but it exists as a separate crate/binary target from day one specifically so `core` never grows an in-process extension-loading code path that would later need ripping out for process isolation. The `ipc` crate similarly starts as a placeholder for the control-plane protocol plan §1 describes (shared by `extension`, the Phase 5 AI-facing API, and the Phase 4 frontend boundary) — not implemented yet, just reserved as a workspace member so its eventual dependents don't need restructuring to adopt it.

Prioritize getting *something* end-to-end working over completeness at any one stage — a skeleton that runs all five stages on a trivial page is more valuable at this point than a highly complete parser with no layout/paint behind it.

Per plan §1, every DOM node must get an explicit, stable ID at creation — this is a property of the DOM data structure itself, not something bolted on later, so it needs to be part of the initial DOM design in stage 1, not retrofitted after Phase 1 settles the AI representation format. [`../research/dom.md`](../research/dom.md) recommends the concrete shape: a monotonic-counter-issued `NodeId` newtype (not a slab/array index, to avoid ABA reuse hazards) assigned eagerly at construction, plus a document-scoped `NodeId → node` lookup table.

[`../research/layout.md`](../research/layout.md) recommends the DOM/layout-tree split follow Blink's LayoutNG design (a persistent DOM-linked box type plus a freshly-built immutable fragment tree per layout pass) rather than Gecko's mutable, back-pointer-heavy frame graph, since the latter fights Rust's ownership model. It also recommends a single `match` on `display` dispatching to per-algorithm implementations (block/inline first; flex/grid as later arms), mirroring how both real engines structure this.

[`../research/css-cascade.md`](../research/css-cascade.md) recommends against vendoring Gecko's Stylo (`style` crate) directly — its `TElement` trait alone has 82 methods to implement against a new DOM — in favor of porting its packed-specificity/cascade-origin design as a lightweight from-scratch implementation, and separately evaluating the standalone `cssparser` crate for tokenization.

Testing policy for everything in this phase (coverage gate, what belongs in unit vs. fixture tests) is defined once in [`../testing/TEST_PLAN.md`](../testing/TEST_PLAN.md), not repeated per checklist item below — each item below is expected to satisfy it, including keeping its crate off the coverage gate's ignore-list once it stops being a stub.

**Post-Done addendum** (`phase-15-chromium-differential-testing/PLAN.md`): running `blueice-html` against the *full* WPT/html5lib-tests tree-construction corpus (not just the handful of hand-picked cases the bullet above mentions) found and fixed over thirty real parser bugs across three triage passes — an unclosed `<script>`/RCDATA element at EOF suppressing the implicit `<body>`, comment-tokenizer edge cases (`<!-->`/`<!--->`/`--!>`) swallowing real markup, a missing "after head" carve-out for `<style>`/`<script>`/`<title>` after an explicit `</head>`, no "in select"/"in select in table" insertion mode at all (so `<select>`/`<option>`/`<input>`/`<hr>` nesting inside a `<select>` was simply wrong), `<script>`'s entire "script data escaped"/"double escaped" state machinery being unimplemented, and — the third pass's specific focus, since it's the highest-risk area for silently wrong output on ordinary (not just adversarial) pages — real bugs in the adoption agency algorithm itself: cloned intervening formatting elements never replaced their *stack* entry (only their active-formatting-list entry), a raw/stale bookmark index instead of one resolved by entry identity, a missing Noah's Ark clause, a missing "clear the stack back to a table context" step several table-insertion rules need, and a missing active-formatting-elements "marker" concept (table cells/captions need one despite the earlier assumption that no supported element did). See `testing/TEST_PLAN.md`'s "WPT tree-construction corpus" section for the full list and current pass-rate numbers (56.4%, 21 unclassified failures remaining, down from 191 at the start of this hardening effort). Recorded here rather than reopening the checklist item above, since the item itself (implement the parser) is still accurately "done" — this is ongoing correctness hardening of a real implementation, the same category as any other bug found after a phase's checklist is checked off.

**Second post-done addendum** (architecture-wide risk survey prompted by the HTML hardening above — the same question asked of `blueice-css`: does the implementation actually match what its own module docs claim to have gotten right, not just what the existing fixture tests happen to cover): found and fixed two real bugs in `cascade.rs`/`selector.rs`.

- [x] **`cascade.rs`'s sort key didn't actually reverse origin precedence when *both* origins declare `!important`.** The module doc states the `(important, origin, specificity, source_order)` tuple is designed so "`!important` reverses origin precedence" — but `Origin::Author`'s higher enum value still sorted after `Origin::Ua` even when both sides were `!important`, so Author's `!important` declaration won over UA's `!important` declaration, the opposite of the real rule (UA `!important` must always win). Verified by hand: `ua = "p{color:red !important}"` vs. `author = "p{color:blue !important}"` computed blue; the correct answer is red. Was dormant — `UA_STYLESHEET_SOURCE` never uses `!important` — but would have been wrong the moment it did (e.g. a future "protect this UA rule from page overrides" feature). The existing `important_reverses_origin_precedence` test only covered important-vs-non-important, a strictly weaker case that passed regardless of this bug. Fixed by inverting the origin comparison specifically when `important` is true; new test `ua_important_beats_author_important` covers the both-important case.
- [x] **`selector.rs`'s `matches` function didn't backtrack across combinator boundaries.** For a chain mixing a `Descendant` step with a later, stricter step (e.g. `x > y z`), the algorithm walked up from the target and committed to the *first* (nearest) ancestor satisfying the `Descendant` compound; if that ancestor then failed the stricter `Child` check, it gave up instead of trying a farther ancestor that would also satisfy the descendant compound. Verified by hand: selector `x > y z` against `<x><y class=outer><div><y class=inner><z/></y></div></y></x>` should match (via `y.outer`, whose parent is `x`) but BlueIce's greedy matcher locked onto `y.inner` (the nearest "y" ancestor of `z`), found its parent is `div` not `x`, and reported no match — a live false negative on a plausible real-world pattern (any repeated-component/nested-wrapper markup using `>` after a descendant combinator). No existing test exercised a mixed-combinator chain with more than one candidate ancestor at the ambiguous step. Fixed with real backtracking (`matches_from`, retrying with the next-farther ancestor on failure instead of a greedy first-match walk); new test `descendant_then_child_backtracks_past_a_nearer_non_matching_ancestor` covers exactly this shape.
