# Phase 9 — BlueIce Extension Protocol

[← Back to plan](../BROWSER_CORE_PLAN.md)

**Status**: In progress (the capability list, manifest model, implementation format, protocol versioning, server-side capability enforcement, per-capability version-window enforcement, manifest parser, manifest-derived identity, exact-origin scopes for DOM read/write, network observation, and declarative interception, core-spawned authenticated host binding, bounded no-WASI WASM execution, core-defined navigation, toolbar-activation, and popup-action events, gatekeeper action-review boundary, core-backed `dom:read`, bounded real `dom:write` bridges for native controls, semantic text leaves, and noninteractive inline textContent, bounded core-owned storage v1, separate durable v2 namespace, and v3 durable-key listing, constrained redirect-aware declarative navigation block and same-origin rewrite rules, committed navigation request/redirect/final-response `network:observe` v2, native `ui:inject` toolbar button, text popup, and one-action popup, a private core-parent optional-grant transport, an opt-in native optional-permission confirmation path, and a tested extension-author [ABI reference](PROTOCOL.md) are implemented; a real person-driven native grant/revoke proof, runtime-ephemeral gesture lifetime, general DOM mutation, subresource observation, general request interception, and arbitrary interactive extension UI remain)

## Objective

Turn the process-isolated `extension` architecture (already settled: separate OS process, IPC boundary, no in-process sandboxing — plan §1) into an actual documented, versioned protocol third parties can build against: a manifest format, a permission model, and a defined API surface. Plan §4 already excludes the extension *ecosystem* from MVP scope — this phase is that ecosystem, once the MVP core exists for it to extend.

The current extension-author contract and a tested no-WASI example package are
in [PROTOCOL.md](PROTOCOL.md). That reference deliberately distinguishes
installed `declared` grants from opt-in native-confirmed `optional` and still-
ungrantable `runtime_ephemeral` declarations, and the guest ABI from the private
host/core socket. It does not claim the unimplemented ecosystem features.

## Design sketch

**Capability list, refined against real prior art by [`research/extension-architecture.md`](../research/extension-architecture.md)** (which studied Chromium's Manifest V3 and Firefox's WebExtensions capability catalogs directly):

- `dom:read` — query the Phase 1 AI-facing representation, read-only
- `dom:write` — mutate specific nodes (content-script-style injection)
- `network:observe` — read request/response metadata
- `network:intercept` — modify or block requests (research note: Chromium's own move away from blocking `webRequest` toward `declarativeNetRequest` — the browser evaluating declarative rules itself rather than an extension parsing untrusted network data in a privileged process — is worth weighing for this capability specifically, not just copying the older blocking-callback model)
- `ui:inject` — ask `frontend` to render extension-provided UI (toolbar button, popup)
- `storage` — a scoped key-value store, one per extension

**Manifest model — a three-tier structure, borrowed from both reference engines' converged design**: `declared` (granted at install, matches Chromium/Firefox's persistent host-permission model), `optional` (available but not granted until requested, matches both engines' `optional_permissions`), and `runtime-ephemeral` (gesture-triggered, non-persistent — the research found Chromium's `activeTab` is exactly this shape, worth a BlueIce equivalent rather than only the binary declared/optional split). Manifest file: a declarative file (`extension.toml` or `.json`) naming `name`, `version`, `blueice_api_version` (for the protocol-versioning/compatibility story), the three-tier `capabilities` structure above, and an `entry_point` (path to the extension's WASM module, per the implementation-format decision below).

**Wire protocol shape**: since `extension` already runs in its own OS process (settled, plan §1), the natural transport is a length-prefixed framed protocol over a Unix domain socket / named pipe, with messages defined via a schema (tying back to `backend/ipc`'s still-open format decision — protobuf/Cap'n Proto are the leading candidates there too). Capability checks are enforced by `core` against what that extension's manifest declared at install time — checked on `core`'s side of the boundary, not trusted from the extension process itself, since not trusting that process is the entire point of the isolation. This is also where Phase 7's `GatekeeperClearance` capability-token pattern needs its server-side counterpart: `core`'s handler for each extension-initiated request must itself reject an unauthorized capability use, not rely solely on the extension process behaving.

**Extension implementation format — decided: WASM.** `research/extension-architecture.md` found both Chromium and Firefox independently carve `'wasm-unsafe-eval'` out of their otherwise-tightened MV3 Content-Security-Policy defaults, while continuing to restrict plain JS `eval` — and neither gives extension code *any* path to native code except as a separate, explicitly-consented native-messaging peer process. Two independent production extension systems converging on the same WASM-over-native stance is a strong, source-grounded signal, not just WASM's general reputation for sandboxability. Native dylibs are dropped from consideration.

## Wiring design (resolved 2026-09-08)

Resolved via a research pass grounded in Phase 7's *actual implemented* shape (not the speculative one this doc originally assumed) plus explicit user direction. Phase 7's `GatekeeperClearance` is a `pub(crate)`, in-process-only Rust typestate token scoped specifically to navigation (`backend/core/engine/src/gatekeeper_client.rs`) — it never crosses a wire and isn't directly reusable by a different process or capability domain. What Phase 9 reuses from Phase 7 is the *pattern* (server-side enforcement, fail-closed, non-blocking background round-trip via `blueice_ipc::gatekeeper`), not the literal type.

**Versioning — two independent layers, not one.** `PROTOCOL_VERSION`/`Hello` (the existing single-integer, all-or-nothing handshake `frontend`/`mcp-server` already use) stays exactly as-is for framing/envelope mechanics — cheap and fine for first-party clients built in lockstep with `core`. Extension capability content gets a *second*, per-capability version layer instead of being folded into that same all-or-nothing gate: a connecting extension declares `capability_versions: { dom_read: 1, network_intercept: 2, ... }` for only the capabilities it actually uses; the host checks each against its own supported inclusive `[min, max]` window per capability and rejects only the unsupported entries, not the whole connection. This matters specifically because third-party WASM extensions will legitimately lag `core`'s own release cadence and use only a subset of capabilities — an all-or-nothing version bump elsewhere in the protocol shouldn't break an extension that never touches the capability that changed. The implementation fixes the granularity at individual capability names: `backend/extension`'s `ExtensionRegistry` owns the windows, `HelloAck { unsupported_capabilities }` reports unknown names or the supported interval for incompatible versions, and each later capability request requires both a manifest grant and a successfully negotiated declaration. `dom:read` supports v1–v2 and `dom:write` supports v1–v9: v1 retains default-tab reads and the protocol-only generic write; v2 adds explicit `DomReadTab { tab_id }` plus `SetTextInputValue { tab_id, node_id, value }`; v3 adds `SetCheckboxChecked { tab_id, node_id, checked }`; v4 adds `SetTextareaValue { tab_id, node_id, value }`; v5 adds selection-only `SetRadioChecked { tab_id, node_id }`, with core deriving group membership; v6 adds selection-only `SelectOption { tab_id, node_id }`, with core deriving the enabled single-select and atomically clearing its other options; v7 adds `SetRangeInputValue { tab_id, node_id, value }`, where `value` is an integer and core derives the target's live range constraints; v8 adds reviewed `SetVisibleLeafText { tab_id, node_id, value }` for a rendered semantic leaf; v9 adds reviewed `SetVisibleTextContent { tab_id, node_id, value }` for a visible semantic target with only noninteractive inline formatting descendants. `network:intercept` supports v1–v6: v1 retains the protocol-only registration proof, v2 adds `RegisterNetworkBlockUrl { url }`, v3 adds `ClearNetworkBlockUrls` for the caller's own connection-scoped rule set, v4 adds `RegisterNetworkBlockHost { host }`, v5 adds `RegisterNetworkBlockPathPrefix { host, path_prefix }`, and v6 adds `RegisterNetworkRedirectUrl { source_url, target_url }` for a reviewed exact same-origin navigation rewrite. A handshake below the request's version cannot use it.

`storage` supports a process-lifetime v1 namespace (`StorageGet`/`StorageSet`/`StorageRemove`) and a separate durable v2 namespace (`DurableStorageGet`/`DurableStorageSet`/`DurableStorageRemove`). The v2 operations require a negotiated `storage` version of at least 2; a v2 negotiation continues to permit v1 imports without making v1 data persistent. Each added operation requires its own explicit capability version.

`storage` v3 now adds `DurableStorageListKeys` and the bounded `durable_storage_keys_utf8` guest import. It requires a negotiated v3 grant, returns this manifest-derived identity's durable keys in deterministic lexical order as at most 40 KiB of JSON, and never includes values or v1 process-lifetime keys. The same private-file validation and nonblocking per-bucket OS lock used for v2 point reads apply, including for an absent bucket. A v2 caller is denied before storage access; a v3 handshake keeps v1/v2 imports usable. Unit, guest ABI, real host subprocess, and compiled-core restart tests cover ordering, scope, version gating, and persistence. Cross-device sync, package-update migration, and richer queries beyond key enumeration remain open.

**Server-side capability enforcement.** `core` gains an in-memory `ExtensionRegistry` (a peer to `TabManager`, not a member of it), keyed by a *derived* `extension_id` (a hash of the manifest + WASM module, not an author-chosen string), holding the three-tier capability grant set from that extension's manifest, each optionally origin-scoped. Extension identity and its granted capabilities are established once at a connection-scoped handshake (`ExtensionHello { extension_id, capability_versions }` → `ExtensionHelloAck`), not re-declared per message — the same "implicit context established once, carried by every later message" discipline `tab_id` already uses on the external envelope, but on its own protocol. Every extension-initiated request is checked against the registry's grant *on `core`'s side* before it's allowed to execute; an unauthorized attempt gets a new `CapabilityDenied { capability, reason }` reply, mirroring `GatekeeperBlocked`'s "structured block, not a bare `Error`" precedent. A hash alone does not authenticate the process presenting it, so the real-core host must also bind the connection to its spawned package.

**Implemented install-time increment (2026-09-23).** `blueice-extension-host --manifest extension.json` parses a strict JSON manifest, constrains its WASM entry point to the package root, validates the WebAssembly v1 header, and derives a domain-separated SHA-256 ID from the exact manifest and module bytes. Its registry grants only the manifest's `declared` capabilities; `optional` and `runtime_ephemeral` declarations carry no authority. The identity makes package membership exact and rejects friendly author-selected IDs, but an explicit development listener without a core-spawned host still treats that ID as a bearer claim and must not be mistaken for the production binding mode below.

**Implemented host-spawned authentication increment (2026-09-23).** `blueice-core --extension-socket <path> --extension-manifest <extension.json> --extension-host <blueice-extension-host>` now generates a fresh 256-bit token from the Unix kernel CSPRNG, creates/validates a user-owned `0700` listener directory, binds a `0600` extension socket, then starts the supplied BlueIce host with `--connect`/`--manifest` and the token only in that child environment. The host validates the package independently and sends `HelloAuthenticated { extension_id, capability_versions, authentication }`; core checks the token without an early content exit, sends no reply for a plain or mismatched handshake, and publishes its frontend socket only after the authenticated child has received `HelloAck`. The token is neither a command-line argument, manifest field, socket reply, nor persisted file. The compiled-core test proves that sequencing, socket privacy, and that a second local peer carrying only the manifest-derived ID receives no `HelloAck`; the real `blueice-extension-host --connect` subprocess test proves its environment-only handshake. The pre-existing `--extension-socket`/`--extension-manifest` path without `--extension-host` remains deliberately available for isolated protocol development and retains its documented bearer-claim semantics, but is still private from other Unix users.

**Implemented restricted WASM execution increment (2026-09-23).** After the authenticated `HelloAck`, the spawned host sends internal `RuntimeReady`; core replies `RuntimeStart` only after it has accepted a frontend and created the live session/`TabManager`. Only then does the host run the exact module bytes that were validated and identity-hashed at install time through Wasmtime 49's core-module API. This prevents a startup-time page request from timing out before core has an owner for page state. The required `blueice_start: () -> ()` export is a one-shot reactor; its only later invocations are fresh instances for the core-owned lifecycle notifications below, never a resident service worker. The linker exposes no WASI, filesystem, process environment, clocks, randomness, sockets, or generic host functions. Its only `blueice` imports are `dom_read_utf8(tab_id, destination, capacity)`, `set_text_input_value(tab_id, node_id, value_ptr, value_len)`, `set_checkbox_checked(tab_id, node_id, checked)`, `set_radio_checked(tab_id, node_id)`, `select_option(tab_id, node_id)`, `set_textarea_value(tab_id, node_id, value_ptr, value_len)`, `register_network_block_url(url_ptr, url_len)`, `clear_network_block_urls()`, `runtime_event_kind()`, and `runtime_event_tab_id()`; each stateful import serializes the corresponding existing extension IPC request on the authenticated stream, so core still checks the manifest grant/version and applies the existing gatekeeper review for writes. Guest memory must be exported as `memory`; text-control payloads are capped at 4 KiB in the WASM ABI, the extension protocol handler, and core's session owner (so manual development clients cannot bypass the bound), exact-network rule URLs are capped at 2 KiB, and representation copies are capped at 64 KiB. Package modules are capped at 1 MiB; every execution gets 1 MiB linear-memory, one instance/memory/table, a 1,024-element table, and one million Wasmtime fuel units. A missing entrypoint, unknown import, invalid guest pointer/UTF-8/bool, resource-limit trap, unavailable core operation, or denied core capability fails the relevant call or terminates the reactor without an ambient fallback. Unit tests prove actual read/text/checkbox/radio/select/textarea/network-rule IPC forwarding, cross-boundary text limits, event context, and fuel exhaustion; the compiled `blueice-extension-host --connect` test proves the authenticated child runs a module that emits `DomReadTab` across a real Unix process boundary; the compiled-core test proves `RuntimeStart` is held until frontend/session setup. The standalone `--socket` protocol-development listener intentionally still does not execute a package module.

**Implemented bounded navigation-event lifecycle increment (2026-09-23).** Once startup invocation returns, the authenticated host issues `NextRuntimeEvent`; this pull boundary is deliberate, so host and core retain one framed request/reply turn and no concurrent socket reader. `session.rs` queues `NavigationCommitted { tab_id }` only after a navigation has passed normal gatekeeper review, committed to the live `TabManager`, and successfully published its frame. The queue has capacity 16 and uses non-blocking `try_send`: it is advisory, so a stalled extension can lose events but can never hold the sole page/render owner or cause unbounded memory growth. On receipt the host creates a new Wasmtime instance and invokes `blueice_start` again; guest code can distinguish startup (`runtime_event_kind() == 0`, tab `-1`) from a committed navigation (`kind == 1`, its opaque tab ID), then must use an independently granted `dom:read` call for actual page content. When the frontend session ends, core closes the producer and replies `RuntimeEventStreamClosed`; a cooperative host exits before the process-containment fallback. Unit, compiled-core, and real-host subprocess tests cover source ordering, wire framing, fresh event invocation, and clean stream close. Other lifecycle events, persistence, retries, scheduling, and reliability/overflow policy remain explicitly unimplemented.

**Implemented core-read/write and declarative-network increment (2026-09-23).** `blueice-core --extension-socket <path> --extension-manifest <extension.json>` validates the package and creates the manifest-derived registry before either its client or extension socket is published. Its private extension worker performs the normal capability/version check, then sends requests through bounded one-shot channels to `session.rs`; that session thread remains the only owner of `TabManager`/`Page`. V1 `DomRead` returns JSON for the actual default tab's `AiSnapshot`; v2 `DomReadTab` makes the tab choice explicit. V2 `SetTextInputValue` carries both tab and stable node ID, always obtains a `CheckExtensionAction` clearance with fixed, non-extension-controlled metadata, then asks core to verify that the live target is a supported text `<input>`. V3 `SetCheckboxChecked` accepts only a live, enabled native checkbox; V4 `SetTextareaValue` accepts only a live, enabled `<textarea>` and changes only that control's child text. V5 `SetRadioChecked` is selection-only: it accepts an enabled named native radio without an external `form` attribute, derives its ordinary ancestor-form scope and group name from the live DOM, then atomically clears the other matching group members. V6 `SelectOption` is also selection-only: `<select>` and its visible `<option>` children are represented so an extension can supply only a live option ID; core derives the owning select, accepts only enabled native single-selects plus enabled options outside disabled optgroups, and atomically clears that select's other options. It never accepts a select owner, sibling list, arbitrary Boolean, or generic attribute mutation; `multiple` selects and disabled controls/groups remain intentionally unsupported. Text control values have one 4 KiB UTF-8 protocol limit, enforced again by core before page mutation even if a manually connected development client bypasses the normal WASM guest ABI. All successful bounded writes update core state, dispatch normal input/change hooks, and push a fresh uncorrelated frame to human observers before replying `DomWriteAck`. V2 `RegisterNetworkBlockUrl` is the first real `network:intercept` effect: after fixed-metadata review it accepts one 2 KiB-or-smaller absolute HTTP(S) URL without credentials, canonicalizes it in core, and blocks a matching initial URL or redirect target before either gatekeeper review or that hop's network connection. V3 `ClearNetworkBlockUrls` requires the same capability/version but no fresh gatekeeper review, because it carries no payload and can only remove the current connection's own rules; it is equivalent in scope to disconnect cleanup, while an in-flight navigation still uses its start-time snapshot. Core snapshots the live connection-scoped rule set when navigation begins, so the background fetch worker never shares `TabManager` state; a disconnect removes rules for future navigations, while an already in-flight navigation uses its captured policy. Core fetches one hop at a time, URL-reviews every redirect target, applies final `CheckContent` only after a non-redirect page response, and bounds chains to ten redirects. The rule still cannot observe or change traffic, run a callback, modify headers/bodies, or use richer rule algebra. Unit, session, and compiled-core tests prove a rule stops a redirect target before a loopback HTTP listener receives a connection, then becomes inactive after the caller clears it. Legacy generic `DomWrite` has no stable target and remains `OperationUnavailable` in core. The standalone host keeps its placeholder handlers for isolated protocol tests.

**Implemented bounded core-owned storage increment (2026-09-23).** `storage` v1 adds `StorageGet`, `StorageSet`, and `StorageRemove` to the capability-separated wire. The already-negotiated manifest-derived identity, never a request field, selects one core-owned in-memory bucket; reconnecting the same extension reaches that bucket, while another identity cannot. Buckets last only for the core process lifetime: v1 does not create a guest-visible filesystem path or imply crash persistence. Keys are nonempty ASCII identifiers (`[A-Za-z0-9._-]`) up to 256 bytes; values are UTF-8 up to 16 KiB; one identity has at most 128 keys and 256 KiB total key/value bytes. The map and quota transition live behind one mutex in core's extension service. Storage operations create no network request, gatekeeper prompt, host path, or cross-extension observation channel, so they need ordinary manifest-grant plus v1 negotiation only. The constrained no-WASI ABI exposes `storage_get_utf8`, `storage_set_utf8`, and `storage_remove_utf8`; a found value is copied into bounded guest memory, missing is distinct from an empty string, and remove reports whether a key existed. Unit tests prove identity isolation and both quotas; runtime, real-host, and compiled-core tests prove the wire/ABI, v1 handshake, and reconnect behavior.

**Storage quota hardening (2026-09-24).** A boundary test found that `StorageSet` counted a new value but not the newly inserted key's bytes when checking the 256 KiB aggregate quota. The core-owned storage calculation now counts both, rejects an over-limit new key without changing the bucket, permits an exact-limit insert, and rejects a subsequent value expansion while preserving the prior value. The test reproduced the old over-limit acceptance before the fix; all extension-host unit tests pass afterward. This does not change storage v1's process-lifetime or grant semantics.

**Separate durable storage v2 (2026-09-24).** Core now selects a private user-data directory (`$XDG_DATA_HOME/blueice/extension-storage-v2`, otherwise `$HOME/.local/share/blueice/extension-storage-v2`) and owns all filesystem operations. The guest supplies only a bounded key/value, never a path or bucket ID. Only a canonical manifest-derived `sha256:` identity can select its hashed bucket filename. Each operation reloads under a nonblocking per-bucket OS lock; reads reject symlinked, non-private, corrupt, wrong-identity, or over-quota data, and writes use a private temporary file, atomic rename, and filesystem sync. The same 128-entry, 16 KiB value, and 256 KiB aggregate quotas apply independently to the durable bucket. Missing or inaccessible durable storage returns an unavailable operation rather than silently falling back to v1. Storage v1 remains a separate process-lifetime map, even after a v2 handshake. Unit tests cover identity isolation, restart, grant/version gating, quota rejection, corrupt/symlink rejection, and guest ABI forwarding; a compiled host subprocess test exercises both v1 and v2 imports over real IPC, and a compiled-core subprocess test verifies v2 survives a full core restart while v1 does not. Because the identity hashes the installed package, an extension update derives a new bucket identity; migration across package updates is not yet designed.

**Implemented integer range-control increment (2026-09-23).** `dom:write` v7 adds `SetRangeInputValue { tab_id, node_id, value }`. The guest supplies only stable core IDs plus a signed integer; after manifest/v7 negotiation, it cannot supply an attribute name, `min`, `max`, `step`, or an alternative form owner. The host uses the fixed `action=set-range-input-value` detail for normal fail-closed Phase 7 review. Core then accepts only a live enabled `<input type=range>`, derives its integer `min`, `max`, and positive `step` values (or the native `0..=100`/step-1 defaults), verifies in-range step alignment, and changes its own `value` attribute. Decimal constraints and `step=any` reject rather than receiving an approximate numeric interpretation. The read representation exposes a range as `Slider` with the core-owned value, so the extension receives the same stable node it can safely target. `set_range_input_value` is a bounded no-WASI ABI import. Page, protocol, review/delegation, downgrade-denial, real-host subprocess, and compiled-core tests cover this path.

**A new, separate `blueice_ipc::extension` module — not new variants on `ClientMessage`/`ServerMessage`.** Reuses the crate's existing `write_framed`/`read_frame_bytes` primitives (the same reason `blueice_ipc::gatekeeper` lives where it does) but defines its own `ExtensionRequest`/`ExtensionReply` enums. Rationale: folding extension messages into the external client protocol would couple extension capability versioning to `PROTOCOL_VERSION`'s own all-or-nothing bumps (exactly what the two-layer versioning design above avoids) and force `frontend`/`mcp-server` to carry match arms for a vocabulary they never speak. One real divergence from the `gatekeeper` module's own shape, worth calling out: `blueice_ipc::gatekeeper` is deliberately handshake-less (one-shot, short-lived, built in lockstep with `core`); an extension connection is long-lived like `frontend`'s, so it needs a `Hello`-handshake shape layered onto `gatekeeper`'s framing style — a genuine hybrid of the two existing precedents, not a mechanical copy of either.

**Composing with the real Phase 7 gatekeeper: not every capability call, only specific high-risk ones.** Manifest authorization (above) is a static, install-time allowlist check — necessary but not sufficient, since it says nothing about whether *this specific call* looks like exfiltration, the risk phase-7's own taxonomy names for `network:intercept`/`dom:write`. Gating *every* capability call through an AI round-trip would make read-heavy usage (a `dom:read` query every few milliseconds) latency-bound on the gatekeeper for no real safety benefit. **Current trigger list**: `network:intercept` rule registration, supported `dom:write` effects, and native `ui:inject` label/popup publication receive mandatory gatekeeper review after capability authorization; read-only capabilities (`dom:read`, `network:observe`, storage reads) do not. The host sends `CheckExtensionAction { extension_id, capability, detail }` over a short-lived gatekeeper socket and fails closed on an unavailable or rejecting reviewer. V1 `DomWriteTarget` derives a bounded ASCII action label without forwarding its untrusted payload; v2 text-input, v3 checkbox, v4 textarea, v5 radio-selection, and v6 select-option writes use fixed respective details, `action=set-text-input-value`, `action=set-checkbox-checked`, `action=set-textarea-value`, `action=set-radio-checked`, and `action=select-option`, so an extension cannot lie about a control type, radio group, or select owner to weaken review. V1 `NetworkIntercept` retains `action=register-intercept`; v2 `RegisterNetworkBlockUrl` uses fixed `action=register-exact-navigation-block`, deliberately withholding the extension-controlled URL from the reviewer. Native UI passes bounded validated visible text for review before publication. Core runs review in its extension connection worker, never the session/render loop; only a cleared action enters the session-owned DOM mutation or native UI path. **Flagged as not fully resolved, an accepted starting point rather than a final answer**: whether this static trigger list is complete (e.g. whether a pattern of many small `dom:read` calls that aggregate into exfiltration needs a rate-heuristic on top of it) is the same open "risk taxonomy completeness" question Phase 7's own doc already flags for navigation — Phase 9 inherits it rather than resolving it independently.

**Minimal first slice.** Replace `backend/extension`'s `todo!()` stub with a hardcoded single extension (no WASM runtime, no manifest file parser yet): a fixed `extension_id`, a fixed capability set of `{dom:read}` only (no `dom:write`). It connects over a real Unix socket and speaks the new `blueice_ipc::extension` module: sends `ExtensionHello`, the standalone host seeds a trivial `ExtensionRegistry` with the matching hardcoded grant (the same "mechanism real, content stub" discipline `ai-gatekeeper`'s always-clears stub already used), replies `ExtensionHelloAck`. The extension then sends one `DomRead` request — checked against the registry, granted, executed against a placeholder instead of real `Page` state, succeeds — and one `DomWrite` request — checked, not granted, rejected with `CapabilityDenied`. The default grant does not reach the gatekeeper; targeted tests add a high-risk grant and prove the subsequent action review, rejection, and fail-closed behavior. This proves handshake-established identity, server-side allow, server-side deny, and the high-risk-review boundary end-to-end before WASM, manifest parsing, or real core integration exist.

**Implemented final-response observation increment (2026-09-24).** `network:observe` v1 adds `ReadNetworkResponse { tab_id }`, authorized independently of `dom:read` and `network:intercept` by the installed manifest grant and negotiated v1 declaration. It reads only the final HTTP response behind the current committed page in that explicit live tab: GET method, final URL, status, and a validated, at-most-256-byte Content-Type. A built-in or blank page returns `None`; a missing tab returns `OperationUnavailable`. Redirect-hop metadata, request headers, response bodies, cookies, and arbitrary response headers remain unavailable. The core session owns the response record, so superseded or rejected navigations cannot publish it; history snapshots retain it only when the existing optional snapshot mode retains the page. The no-WASI `network_response_utf8` ABI copies at most 4 KiB of JSON into guest memory and reports a missing response separately from an error. This read-only effect needs ordinary capability checks but no Phase 7 action review. Host, WASM, page, and live-session tests cover authorization and the committed-state boundary.

**Implemented committed navigation trace increment (2026-09-24).** `network:observe` v2 adds `ReadNetworkTrace { tab_id }` and the bounded `network_trace_utf8` guest import. Core records the initial GET request URL and each reviewed redirect response's request URL, status, and resolved target before the next-hop connection; it publishes that trace only together with the successfully gated final page, alongside the unchanged v1 final response. A rejected, superseded, failed, or built-in navigation never publishes an in-flight trace. The JSON trace is capped at 32 KiB at both host and guest boundaries. The v1 request/reply shape and its 4 KiB bound remain unchanged, and a guest negotiated at v1 cannot call v2. No arbitrary headers, cookies, or bodies are exposed beyond v1's validated Content-Type; URLs themselves may carry sensitive path/query data, so this still requires an explicit manifest grant. This is committed main-frame navigation metadata, not observation of subresource requests, a real-time traffic tap, or an interception callback. Live-session and compiled-core redirect tests verify publication; a real extension-host subprocess test verifies v2 negotiation and the no-WASI import.

**Implemented native toolbar increment (2026-09-24).** `ui:inject` v1 is a separately granted, negotiated capability for one native toolbar button. The guest may set only a 1–20-byte ASCII label (letters, digits, spaces, hyphens, underscores); host and core both validate it, and the reference frontend always prefixes it with `Ext:`. It cannot supply HTML, CSS, coordinates, an icon, a popup, or a script for the frontend. Core owns the label and broadcasts changes to clients; a newly joined frontend uses `GetExtensionToolbar` to recover current state. The guest can clear its own button explicitly; it is also removed when its publishing connection disconnects or renegotiates, and a stale connection cannot clear a newer connection's button. A click sends `ActivateExtensionToolbar` for the selected live tab, queues one bounded `ToolbarActivated` lifecycle event, and invokes the extension in a fresh fuel/memory-limited Wasm instance. External clients can send the same message, so this event is not an authenticated human gesture and grants no ephemeral capability. Host, Wasm, session, native-frontend raster/hit tests, and a compiled-core/authenticated-host subprocess test cover this first UI surface. V1 itself provides no popup or richer extension chrome.

**Implemented native text popup increment (2026-09-24).** `ui:inject` v2 adds `show_popup_utf8`/`clear_popup` Wasm imports and a non-interactive, tab-bound native panel. The guest supplies only a 1–20-byte printable ASCII title and 1–120-byte printable ASCII body, with no HTML, CSS, link, coordinate, or input capability. A popup requires the same connection's live toolbar button and is reviewed by the independent gatekeeper before core publishes it; an unavailable or rejecting reviewer blocks publication. The browser-owned header identifies the text as an extension message. Core checks the live tab and connection ownership, broadcasts show/clear, and clears the popup on dismissal, toolbar removal, tab close, disconnect, or renegotiation. A joining frontend queries the current popup, shows it only for its locally selected tab, and consumes a content click or Escape to dismiss rather than forwarding the click into the page. The reference frontend's pixel test, Wasm/host/session tests, and compiled-core/host/gatekeeper subprocess test cover the path. Richer interactive extension UI remains open.

The v2 popup sends its bounded validated title and body to `CheckExtensionAction`, and the deterministic rule-base rejects known credential, external-URL, and instruction-override phrases. A later mandatory-workflow follow-up also covers v1 toolbar labels: the host reviews the validated label before publication, fails closed if the gatekeeper is unavailable, and rechecks the grant generation after clearance. The compiled ruleset reports `extension-toolbar-before-publish` and a high-precision short-label signature in live `about:settings`; ordinary labels such as `Notes` and `Password manager` remain clear, while `Enter password` and `Disable gatekeeper` are rejected. This is a narrow safety signature, not a complete social-engineering classifier. Host tests cover rejection and reviewer outage without invoking the core publisher, plus a delayed-review revoke/regrant race; compiled-core/host and compiled-gatekeeper tests cover actual enforcement and policy disclosure.

**Implemented one-action popup increment (2026-09-24).** `ui:inject` v3 adds `show_popup_action_utf8` with one short label rendered as a browser-owned button beside the reviewed v2 text. The host requires a negotiated v3 grant and its own toolbar, validates the title/body/label, and sends all three to the mandatory gatekeeper before core publishes anything. Core assigns each popup a fresh ID, validates the live tab and owner, and accepts a click only for that exact current ID; a stale click cannot activate its replacement. A successful click dismisses the popup and queues a `PopupActionActivated` event for a fresh bounded Wasm invocation. The frontend draws one fixed-style hit target and consumes other panel clicks rather than passing them to page content. The ABI and client event are not an authenticated human-gesture channel: AI/MCP clients can send the same client message, so this action confers no `optional` or `runtime_ephemeral` grant. Wasm, host, session, frontend-pixel, and compiled-core/host/gatekeeper tests cover this narrow path. Arbitrary extension layouts, form controls, HTML, links, and trusted consent remain open.

**Popup input isolation and real-host follow-up (2026-09-24).** A visible popup in the selected human tab now consumes keyboard and wheel input instead of letting typing, Backspace, or scrolling affect a focused page behind the panel. Escape dismisses; Enter and Space activate the single action only when its whole browser-owned button fits in the current window. A too-small window never permits invisible keyboard activation; the user can resize or dismiss. Reference-frontend tests cover the keyboard mapping and offscreen guard. A compiled `blueice-extension-host` subprocess now loads an installed `ui:inject` v3 Wasm package and completes startup toolbar publication, toolbar activation, popup-action publication, and popup-action activation over real IPC. This improves the narrow v3 surface but does not turn client messages into trusted consent.

**Implemented declarative host-block increment (2026-09-24).** `network:intercept` v4 adds `RegisterNetworkBlockHost { host }` and the no-WASI `register_network_block_host` import. A guest submits only a bounded ASCII DNS-like hostname, never an executable callback or an opaque URL pattern. The extension host requires a v4 negotiation and manifest grant, obtains fixed-metadata gatekeeper clearance without exposing the guest string to the reviewer, and asks core to validate and store the canonical host. The shared 64-rule connection quota counts both exact URLs and hosts. A host matches itself and dot-boundary subdomains, while IPv4 literals match only exactly; misleading suffixes do not match. `ClearNetworkBlockUrls` and disconnect remove both rule kinds. Core snapshots rules at navigation start and rejects matching initial URLs or redirect targets before network connection. Host, runtime, session, and compiled extension-host tests cover the path; arbitrary response/header interception remains unavailable.

**Implemented literal path-prefix increment (2026-09-24).** `network:intercept` v5 adds `RegisterNetworkBlockPathPrefix { host, path_prefix }` and a bounded no-WASI import. This is a third connection-owned declarative rule kind under the same 64-rule quota. The host requires v5 plus a manifest grant and sends only fixed action metadata to the gatekeeper; core validates an ASCII canonical host and a literal 1–512-byte path with no percent escapes, query, fragment, empty/dot segments, or pattern language. It matches the canonical URL path at a segment boundary on that host or dot-boundary subdomains, including redirect targets before network connection; an IPv4 literal matches only exactly. This is deliberately URL-path matching rather than a claim about a server's percent-decoding or route rewriting. Clear and disconnect remove it alongside v2/v4 rules. Core, host, runtime, and compiled-binary tests cover the path; arbitrary request interception remains unavailable.

**Implemented exact same-origin navigation rewrite increment (2026-09-24).** `network:intercept` v6 adds `RegisterNetworkRedirectUrl { source_url, target_url }` and a bounded no-WASI import. Each credential-free HTTP(S) URL is limited to 2 KiB at the guest, host, and core rule-store boundaries. Core canonicalizes both, requires a different target on the same exact scheme/host/port origin, rejects conflicting source mappings across connections, and counts the rule under the existing 64-rule quota. The host checks the v6 declared grant and obtains mandatory fixed-metadata gatekeeper clearance before registration. An immutable rule snapshot follows each navigation: block rules win; the source receives normal `CheckUrl`, the target is rechecked against block rules and receives its own `CheckUrl`, and only then can the target open a connection. Extension rewrites and HTTP redirects share the ten-hop limit. The v2 network trace reports the first actual GET URL and only real HTTP redirect responses, never a fabricated HTTP status for an extension rewrite. `ClearNetworkBlockUrls` and disconnect remove rewrites for future navigations, while in-flight navigations retain their start-time snapshot. This is static navigation rewriting, not arbitrary header/body editing, callbacks, or subresource interception.

**Implemented semantic text-leaf increment (2026-09-24).** `dom:write` v8 adds `SetVisibleLeafText { tab_id, node_id, value }` and a bounded no-WASI import. The host requires v8 plus a declared grant and submits the exact nonempty, 1 KiB-or-smaller proposed text for gatekeeper review; the compiled rule base rejects credential, external-URL, and instruction-override phrases before the model layer. Core repeats the size/control-character checks and permits only a live rendered `h1`–`h6`, `p`, or `li` on an HTTP(S) page with exactly one existing text child, no separate accessible name, and no hidden ancestor. It mutates that text node in place, so nested links, controls, and unrelated DOM subtrees cannot be deleted by this operation, then publishes the shared frame and AI snapshot. Built-in pages remain immutable to this extension API. This does not grant generic `textContent`, HTML insertion, CSS changes, or arbitrary DOM mutation.

**Implemented noninteractive inline textContent increment (2026-09-24).** `dom:write` v9 adds `SetVisibleTextContent` and a bounded no-WASI import. The host requires a negotiated v9 declared grant and sends the exact proposed value to the mandatory gatekeeper; core separately checks the live tab's origin, target, and 1 KiB text limit. A rendered heading, paragraph, or list item may replace its entire content only when its at-most-128 descendants are text or basic noninteractive inline formatting. Links, controls, scripts, semantic children, element IDs, inline event-handler attributes, hidden/interactive annotations, and separately named or hidden targets are rejected before any DOM node is removed. Successful replacement invalidates the deleted descendants' node IDs and publishes one shared frame and updated AI representation. Arbitrary HTML insertion, attribute/CSS mutation, and unrestricted `textContent` remain open.

**Implemented exact-origin grant scopes (2026-09-24).** A strict manifest may attach `capability_origins` to declared `dom:read`, `dom:write`, or `network:observe` grants. Each entry is an exact canonical HTTP(S) origin, never a host wildcard or URL-path pattern; absent scope preserves the existing global grant. Core retains the install-time validated scopes and compares them against the live tab URL inside the page/session owner immediately before every covered read or mutation, so a redirect, navigation, or stale node cannot reuse authority from an earlier origin. A denied mutation publishes no frame. This does not implement optional or ephemeral consent.

**Extended origin scopes to `network:intercept` (2026-09-24).** A declared interception grant can use the same exact-origin manifest field. Core snapshots its validated scope with each navigation's declarative block rules and checks the target URL at the initial request and every redirect hop before connecting. A broad host/path-prefix rule cannot block a request on another scheme or port outside the grant's precise origins; an omitted scope keeps existing behavior. `ui:inject` and `storage` are not origin-scoped, and optional/ephemeral grant authority remains open.

**Internal optional-grant state, not user consent (2026-09-24).** The installed registry now retains validated `optional` declarations separately from immediate `declared` grants, and its in-process, process-lifetime transition can add or revoke only a declared optional capability. Every subsequent request on an already-negotiated connection rechecks that live state, so revocation denies new operations without reconnecting; unknown package IDs, undeclared capabilities, and `runtime_ephemeral` declarations cannot enter the optional grant set. Core's navigation-rule evaluation additionally checks a grant generation in every captured snapshot: revocation immediately makes old block/rewrite rules inert, including for in-flight navigation snapshots, and regrant cannot resurrect rules from the old generation. Their stale entries are pruned by the session's idle poll or on the next registration. The manifest also accepts exact origin scopes for origin-aware capabilities in any tier, preserving restrictions for a future authenticated grant without granting authority merely because a scope exists. No external IPC, guest ABI, ordinary client message, toolbar activation, or settings control can invoke the internal transition. A separately authenticated human-window approval/revocation channel that calls the private completion barrier, and genuinely gesture-bound ephemeral scope, are still required before optional or ephemeral permissions become user-accessible.

**Negotiate all installed tiers without granting them (2026-09-24).** The core-spawned host now includes `declared`, `optional`, and `runtime_ephemeral` capabilities in its authenticated startup version negotiation, preserving compatibility state for a later live grant on the same connection. The core's separate installed-manifest registry still denies every operation in the two ungranted tiers. Negotiation is never consent, and no guest or ordinary client can turn it into authority.

**Reject stale reviewed network registrations (2026-09-24).** For each persistent v2/v4/v5/v6 `network:intercept` registration, the host captures the grant generation before mandatory Gatekeeper review and rechecks it after clearance. It passes that original generation through the private core request channel; the session owner checks it again under a transition guard at the actual rule write. This final check also rejects a request left in the session queue after the host's one-second acknowledgement timeout, even if the capability was revoked and regranted in the meantime. Core's navigation permission reads use an atomic snapshot, so a waiting revoker cannot deadlock the session during the guarded write. A four-case socket regression deliberately pauses review, revokes and regrants, then proves no delegate ran; a core-state test rejects an old-generation write at the final gate after regrant. Other side effects still need equivalent revocation semantics before user-facing consent.

**Reject stale native UI after optional revoke (2026-09-24).** `ui:inject` toolbar and popup publication now carry the original live-grant generation through the authenticated extension worker to the core session. Core checks that generation at publication under the same transition guard used for network rule registration, so a late reviewed popup cannot publish after revoke/regrant. The session polls the live generation and broadcasts removal of any stale toolbar or popup before accepting another client activation, even when no client command arrives; a queued activation carries its generation and the host discards it before invoking Wasm if the grant changed. This is prompt polling cleanup, not a synchronous user-facing revoke transaction. No extension activation is a trusted human gesture, and the optional-grant transition remains inaccessible through public IPC. Real-process declared-grant UI tests, full-session live optional-revoke tests, and focused revoke/regrant regressions cover these boundaries; person-driven native-window revoke proof remains open.

**Reject stale reviewed DOM writes (2026-09-24).** Every core-backed `dom:write` form-control or visible-text request now captures the live optional-grant generation when the host receives it. After mandatory Gatekeeper review, the host rejects a changed generation with `CapabilityDenied`; it also sends the original generation through the private core channel. The session checks that generation under the registry transition guard at the actual DOM mutation, so a request still queued after the host's acknowledgement timeout cannot borrow a later regrant. A paused-review race test covers both a v2 text input and v9 visible-text write; a core-state test exercises the final gate for all eight supported write shapes and confirms rejected writes publish no frame. The compiled core/host/gatekeeper v9 write test and both crates' full unit suites pass. The opt-in native consent path now uses the private completion barrier; a real person-driven window proof remains open.

**Serialize optional storage effects with revocation (2026-09-24).** The host now captures the `storage` grant generation when it receives each request and runs every v1/v2/v3 storage read, write, removal, and durable-key listing under the registry's stable-capability guard. A concurrent optional revoke cannot finish between the final authorization check and a storage effect, and a revoke/regrant cannot lend an old request the new grant. Existing-connection tests deny all seven storage operations after revoke and confirm a later regrant can read unchanged v1 data; a paused-effect test proves revoke waits until the operation finishes and rejects reuse of the prior generation. This closes the local storage check/use gap, but does not itself create a trusted user-consent path.

**Serialize optional read replies with revocation (2026-09-24).** Both `dom:read` versions and both `network:observe` versions now capture their grant generation at request receipt and keep the registry transition guard through the core-backed read and its bounded reply write. A concurrent revoke therefore waits for an already-authorized reply to finish; after revoke completes, the old request cannot deliver data, and regrant cannot revive its captured generation. Existing-connection tests deny all four read operations after revoke without invoking a reader, then confirm fresh grants restore access. A paused read/reply regression verifies the revoke ordering and stale-generation denial. The opt-in native path now exposes installed optional grants; the person-driven real-window result remains to be checked.

**Retire revoked navigation rules on the idle session poll (2026-09-24).** Rule snapshots already check the live generation and become inert immediately on revoke. The same 25 ms session poll that clears stale native toolbar/popup state now physically prunes connection-owned navigation block and rewrite entries from `TabManager`, even if no frontend or extension message arrives. A live session test registers a real optional rule, revokes its grant, sends no further message, then observes that the store is empty before EOF cleanup; a `TabManager` test covers old snapshots and a later regrant.

**Private revoke completion barrier (2026-09-24).** `revoke_optional_and_wait_for_cleanup` first withdraws an installed optional grant in the registry, then sends a core-internal `SynchronizeRevokedEffects` request and waits up to two seconds. The session prunes revoked navigation rules and writes native toolbar/popup removal messages before acknowledging. If the session is missing or does not acknowledge, the helper reports an error while the grant **remains revoked**; it never reports cleanup success by assuming a timeout is safe. A direct test covers both published effect types and the unavailable-session failure, and a live session test covers UI removal before acknowledgement without another frontend command. No public frontend, MCP, or extension wire message maps to this helper or request. A separately authenticated human-window authority must still own the call. Launcher cutover revalidates the same installed package and creates a fresh authenticated extension host in v2, but intentionally does not migrate process-lifetime optional grants.

**Private core-parent permission channel foundation (2026-09-24).** Core now has a separately framed, bounded `blueice_ipc::permission_control` request/reply protocol over its own stdin/stdout, enabled only by explicit `--permission-control-stdio` together with a core-spawned authenticated extension host. `Inspect` reports the validated package name/version/hash and installed optional capabilities, exact-origin scopes, and current grant state. `Grant` accepts only an installed optional declaration; `Revoke` uses the completion barrier above. Unknown or runtime-ephemeral capabilities cannot be granted through it. The extension-host child receives null stdin/stdout, so it cannot steal parent commands or forge replies; broken/malformed parent transport withdraws all optional grants this channel could have made. A compiled core plus authenticated test-host subprocess proves deny → grant → allow → completed revoke → deny on the *same* host connection, and deny again after parent-pipe EOF. This is a core-parent authority boundary, **not yet a trusted human consent flow**. No general frontend, MCP, guest, or page message reaches it; runtime-ephemeral gesture authority remains separate.

**Launcher-owned permission pipe and read-only operator inspection (2026-09-24).** For an installed extension, each launcher-spawned core generation receives private piped stdin/stdout and the explicit permission-control flag. The launcher owns the pipe, inspects the live authenticated core before admitting v1 or a cutover v2, and offers only bounded read-only inspection on its operator control socket. Inspection reports the actual package identity, installed optional declarations, origin scopes, and current grants; it never changes them. A dedicated worker serializes private core requests with bounded caller deadlines, and dropping the old core generation closes its parent pipe. A real launcher/core/host cutover test proves both generations answer through separate pipes with the same installed package and no optional grant. The shared control/rendezvous sockets still have **no** Grant/Revoke route; only the opt-in launcher-owned native child can request a change.

**Launcher-owned native inspection child (2026-09-24).** Opting into `blueice-launcher --trusted-frontend` starts the exact sibling `blueice-frontend` binary with anonymous stdin/stdout pipes, separate from the shared browser and operator-control sockets. The child requests a live permission `Inspect` only after it has connected to the brokered core and created its native window; the launcher requires a successful private reply before its ten-second startup deadline. The window displays the inspected installed package and optional-capability count in native title chrome. The child cannot read operator stdin commands in this mode. A graphical-session smoke test launches the real sibling window with an installed optional declaration, verifies no spontaneous grant, and kills only that verified child to prove broker/core shutdown and resource cleanup; the subsequent native confirmation implementation is described below.

**Native optional-permission confirmation (2026-09-24; implementation underway).** The trusted frontend's F8 panel now requires a native two-step review/confirmation event before emitting `Change`; it displays the installed package hash, current core generation, exact optional capability, grant state, and every manifest origin-scope line without truncating long origins. Review and Confirm occupy different pointer targets, key auto-repeat cannot confirm, and a window too small to display the panel cannot authorize a keyboard change. While the panel is open, hover, click, wheel, and keyboard events are not forwarded to the page beneath it. The launcher rejects stale generations, changed packages, undeclared capabilities, and changes during cutover under its active-core lock and single-flight gate. A successful private core `Updated` reply is followed by a fresh `Inspect`; an uncertain or inconsistent mutation kills that core generation rather than leaving a late grant serving. Losing the native child pipe stops the broker and core, so human-approved process-local grants cannot outlive their window. The ordinary frontend/MCP and operator-control sockets still have no mutation operation. Unit tests cover two-step confirmation, scope paging, target rejection, cutover exclusion, and pipe-loss shutdown; an opt-in real-core test exercises private Grant→Inspect→Revoke. The existing graphical test verifies window startup and inspection, **not yet a person clicking Grant/Revoke in a real window or the resulting published-effect cleanup**. That full human-window test and runtime-ephemeral gesture lifetime remain open.

**Person-driven proof harness (not yet executed).** The ignored `manual_native_grant_and_revoke_retire_published_toolbar` integration test in `backend/launcher/tests/trusted_native_window.rs` starts a real launcher, core, installed optional `ui:inject` WASM host, and native frontend. Its own control connection only performs read-only `Inspect`; it waits for a person to use the F8 panel to grant, then triggers a local page navigation so the guest publishes a toolbar, and waits for the person to revoke before requiring the toolbar-removal event and clean broker teardown. In a graphical session, first build the sibling binaries with `cargo build -p blueice-launcher -p blueice-frontend-reference -p blueice-engine -p blueice-ai-gatekeeper -p blueice-extension-host -p blueice-bluejs --bins`, then run `cargo test -p blueice-launcher --test trusted_native_window manual_native_grant_and_revoke_retire_published_toolbar -- --ignored --nocapture`. The test prints each F8 action and allows 60 seconds for it. This is a reproducible human-window check, **not** proof until a person actually runs it and records the result. The compiled core test separately proves removal precedes the private revoke acknowledgement; this manual harness observes the resulting removal rather than forging an acknowledgement from the read-only control socket.

**Real-WASM effect preflight (2026-09-24).** The same test target also has an ordinary, non-graphical `real_installed_wasm_toolbar_follows_private_optional_grant_and_revoke` check. It passed against compiled core, extension-host, and gatekeeper binaries: the installed WASM fixture began ungranted, a private parent Grant enabled its navigation-triggered native toolbar, and a private Revoke removed that published toolbar and restored the ungranted inspection state. This validates the manual harness's actual guest/effect path, but because the test itself writes the parent permission pipe, it is expressly **not** evidence of human approval. Like other launcher subprocess tests, it requires the workspace sibling binaries to be built before running a package-only test; CI's workspace build does this before its workspace test command.

**Consent must name a core generation (2026-09-24).** Read-only launcher inspection now returns `core_generation` atomically paired with the active core's private pipe and installed package state. The cutover swap holds the active-core lock while publishing its new writer, process, and generation; an inspection cannot accidentally show v1's grants under v2's generation. Real cutover tests check `0 → 1` both with and without an installed package. A future native-window Grant/Revoke request must carry the inspected generation *and* package hash, and the launcher must compare both under that same lock immediately before using its private pipe. The same package hash across v1/v2 is not permission to replay a pre-cutover click into v2. This groundwork does not add any grant action to the operator control socket.

**Trusted-window protocol and authority boundary (2026-09-24).** `blueice-launcher::trusted_window` defines bounded, separately framed `Inspect` and `Change { expected_core_generation, expected_extension_id, capability, action }` messages, plus current-state and rejection replies. Its validation rejects a stale generation, changed package, absent package, or capability that is not an installed optional declaration. The protocol is accepted only on anonymous pipes of an exact sibling native frontend spawned and owned by the launcher, never on either launcher socket. Trusted mode disables ordinary stdin commands and child descendants do not inherit the request pipe. Only a native F8 panel confirmation emits `Change`; the launcher rechecks generation, package identity, and the optional declaration under its active-core lock immediately before forwarding to core. A timed-out, malformed, or inconsistent mutation reply terminates that core generation so a late grant cannot survive. Losing the native child pipe stops the broker/core. The remaining evidence gap is a real-window person-driven Grant/Revoke demonstration, not the private transport or handler implementation.

**Real-process optional-effect revocation proof (2026-09-24).** A compiled-core test now drives an authenticated installed host over the private parent pipe with optional `ui:inject` and `network:intercept`. Before grant, both publication attempts are denied on the same connection. After grant, the host publishes a native toolbar button and an exact navigation block that prevents any connection to a loopback fixture. The parent then revokes both capabilities and waits for each private completion reply: the toolbar removal is already visible to the frontend when its reply arrives, the old host cannot republish either effect, and a new navigation reaches the formerly blocked fixture. This tests the actual process/IPC/session boundary, not only registry state or a unit-level idle poll. Trusted human approval and ephemeral gesture lifetime are still open.

## Open questions (blocking real design)

- ~~What can an extension actually do?~~ — **draft resolved above**, refined against Chromium/Firefox's real capability catalogs; still needs review for BlueIce-specific gaps neither reference engine has (e.g. anything touching the Phase 1 AI-facing representation specifically).
- ~~Manifest/permission model~~ — **resolved to a three-tier model** (declared/optional/runtime-ephemeral) above, borrowed from both reference engines' converged design.
- ~~Extension implementation format~~ — **resolved: WASM**, see design sketch above.
- ~~Versioning~~ — **resolved: two independent layers** (the existing all-or-nothing `PROTOCOL_VERSION`/`Hello` for framing, plus a new per-capability `[min, max]` version window checked at the extension handshake) — see "Wiring design" above.
- ~~Server-side capability enforcement~~ — **resolved**: an in-memory `ExtensionRegistry` keyed by a derived (non-spoofable) `extension_id`, checked on `core`'s side against a manifest-declared grant established once at connection handshake, with a new `CapabilityDenied` reply on rejection — see "Wiring design" above. Still open: whether the initial gatekeeper-review trigger list (`network:intercept` + form/network-causing `dom:write`) is complete — flagged there as inherited from Phase 7's own still-open "risk taxonomy completeness" question, not resolved independently.
- **Trusted optional/ephemeral grant authority still needs final human-window proof.** The launcher deliberately relays the same client IPC surface for the reference frontend and external AI/MCP clients. Consequently, a plain `ClientMessage::ApproveExtensionCapability` or toolbar-activation event would not prove a human approved anything: an AI client can emit either message. A guest-originated request must likewise never turn its own manifest `optional` declaration into a grant. The opt-in launcher-owned native child now has a separate confirmation UI and private pipe, while normal launcher use remains declared-only. End-to-end evidence of a real person granting and revoking in that window, including published-effect cleanup, is still required; a unit-driven panel event is not that evidence. `runtime_ephemeral` additionally needs a genuine gesture-bound lifetime. A compiled-core subprocess regression test sends successfully negotiated v3 storage and v2 DOM-read requests for capabilities declared only in those two ungranted tiers; core returns `CapabilityDenied` for every attempt, including the v3 key listing, and never creates a durable data directory.
- **Revocation must clear already-published effects.** A live grant generation makes old network block/rewrite rules inert even in captured navigation snapshots and after regrant, and registration is guarded across Gatekeeper review and core acknowledgement. The session's idle poll physically removes stale connection-owned rules as well as stale toolbar/popup state; a private completion barrier waits for that cleanup before acknowledging. New UI publication and DOM mutation reject old generations, the host drops queued UI activation from an older generation, and storage effects plus core-backed read replies are serialized with revoke. Compiled-core parent-pipe tests prove live storage denial and real-process native-toolbar/network-rule cleanup after completed revoke. The opt-in trusted native caller now invokes this barrier, but the same published-effect cleanup still needs a person-driven real-window proof. Launcher cutover's separate compiled-process test verifies a fresh authenticated host for the same installed package, but intentionally does not migrate optional grants.
