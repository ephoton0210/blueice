# Testing strategy

[← Back to plan](../BROWSER_CORE_PLAN.md)

What gets tested, how, and where a human can see current status without reading source. This is a living policy, not a one-time checklist — every phase's Definition of Done includes keeping this accurate, not just this document's own author.

## Definition of Done

Every phase's checklist in `../phase-*/PLAN.md` carries the following as part of each checklist item — not satisfied by a design being settled or code merely compiling:

- **TDD is the development process, not just an outcome.** Write the test first, watch it fail for the right reason, then write the implementation that makes it pass. Tests bolted on after a feature is already fully written are the exception to reach for on legacy code, not the default way to build something new here.
- **Passing tests, not just compiling code.** A settled design, or a function that builds, is not "done" until tests pass against it.
- **An end-to-end test through the feature's real public interface, wherever an end-to-end path exists.** Test the crate's actual public API, not only the internal modules underneath it — an internal-only test can stay green while the feature itself is broken or unreachable from outside. `blueice-html` is the original reference: `backend/core/html/tests/parsing.rs` drives the parser only through `blueice_html::parse`, never through `tokenizer`/`tree_builder` directly. Now that `html`→`css`→`layout`→`paint` are all real, `blueice-engine`'s own `backend/core/engine/tests/fixtures.rs` is the full-pipeline version of this same principle: it drives `blueice_engine::render()` (the crate's real public entry point) directly, reusing the exact fixtures/expectations `blueice-paint`'s own fixture test checks, rather than trusting that composing four independently-tested stages by hand is equivalent to what the actual public entry point does.
- **A complete public interface for tests to drive.** If exercising a feature requires a test to reach into `pub(crate)` or module-private internals, that's a gap in the interface, not something for the test to work around — complete the public surface rather than add test-only backdoors.
- **≥90% line coverage**, per "Coverage policy" below — a feature under the floor isn't finished, whatever else it does.
- **A dedicated test-review pass once the implementation itself is otherwise complete.** TDD's red-green cycle and the coverage floor both guard against *missing* tests, not *wrong* or *stale* ones — a test written first can still end up asserting the wrong thing once the implementation settles, and a test that was correct when written can go stale as the code around it changes. Before calling the checklist item done, re-read the suite's actual content (not just whether it's green or what percentage it reports) and: (a) add cases the incremental TDD cycles didn't happen to surface — edge cases, error paths, interactions between pieces written in separate cycles; (b) update any test whose expectation no longer matches the feature's actual intended behavior; (c) delete tests that no longer exercise anything meaningful. A stale test left passing for the wrong reason is worse than no test — it reads as coverage that isn't real. This review is part of the same checklist item, not a follow-up task to schedule later.

## Test pyramid

- **Unit tests**: per-crate, colocated `#[cfg(test)] mod tests` (standard Rust convention), testing one function/type's behavior in isolation. `blueice-dom`, `blueice-html` (`backend/core/html/src/{tokenizer,tree_builder}.rs`), `blueice-css` (`backend/core/css/src/{tokenizer,selector,value,parser,cascade}.rs`), `blueice-layout` (`backend/core/layout/src/{text,block}.rs`), and `blueice-paint` (`backend/core/paint/src/lib.rs`) are the current reference examples.
- **Integration/fixture tests**: cross-crate, exercising the real pipeline end to end. `blueice-html` has two: a hand-written one (`backend/core/html/tests/parsing.rs`, against the public `parse` API) and the shared-corpus one (`backend/core/html/tests/fixtures.rs`, built on `blueice-testing` — see "Rendering-correctness fixtures" below). `blueice-css`, `blueice-layout`, and `blueice-paint` each have the equivalent shared-corpus test (`tests/fixtures.rs` in each crate). `blueice-engine` has the full-pipeline version — Phase 3's smoke test (`tests/fixtures.rs`, through the real `render()` entry point) — completing the pyramid: every pipeline crate is a real implementation now, checked in isolation and end to end.
- **Rendering-correctness fixtures** (settled design, fully implemented through paint): a single corpus of small HTML(+CSS) fixtures under `development/browser_core/testing/fixtures/*.dat`, closer to how WPT/reftests (and html5lib-tests specifically) work than to unit tests. Each fixture is a `#data` (HTML input) plus one named section per pipeline stage that can check something about it — `#document` (a canonical DOM-tree dump), `#css`+`#styles` (an optional author stylesheet, plus a canonical computed-style dump checked with the UA stylesheet always applied), `#layout` (a canonical fragment-geometry dump), and `#paint` (a canonical paint-command dump — see "UI testing strategy" below) exist today; Phase 5 adds `#ai-representation`, without changing this format, any earlier stage's section, or any already-written fixture file — this is the concrete answer to needing one stable cross-stage interface instead of one rebuilt per phase. `layout.dat`/`paint.dat`'s fixtures are new files; `basic.dat`'s first fixture gained `#styles`, then `#layout`, then `#paint` sections directly, one per stage, proving a fixture written for one stage keeps picking up every later stage's check with zero changes to the sections or tests that already existed. The shared crate `blueice-testing` (`backend/testing/`) owns only the generic format parser and the DOM dump serializer (`dump_dom`); each pipeline crate's own `tests/` directory (`backend/core/{html,css,layout,paint}/tests/fixtures.rs`, plus `blueice-engine`'s own smoke test reusing `#paint`) owns its own section's dump/compare logic and runs every fixture through *that crate's real public API* per the Definition of Done above, so adding a new fixture file (or a new section to an existing one) needs zero new code in `blueice-testing` or in another stage's tests. `blueice-paint`'s `dump_frame` is kept as public library API rather than test-only code specifically so `blueice-engine`'s smoke test can reuse it. The DOM dump format is adapted directly from the html5lib-tests tree-construction corpus (`| `-prefixed, 2-space-per-depth, sorted attributes as their own lines, text as `"content"`) rather than invented, and a handful of fixtures are that corpus's own verbatim cases (from the local Gecko/Chromium checkouts under `reference/`) used as an independent, browser-vendor-verified oracle — not just self-authored expectations. This is also how two real bugs were caught: exact whole-tree-shape comparison surfaced runaway nesting in the adoption agency algorithm (new formatting element inserted on the wrong side of `furthest_block` in the stack, `blueice-html`) that coarser tag/text-only assertions had missed entirely, and building a genuine multi-section fixture (CSS content containing an ID selector like `#x { ... }`) surfaced a bug in the fixture-format parser itself (any bare `#`-prefixed line was assumed to be a new section marker) that a single-section corpus could never have exercised.
- **UI tests**: split into two genuinely different things — see "UI testing strategy" below. The fixture-based geometry/visual layer (`#layout`, `#paint`) is fully built; the core↔frontend IPC-boundary layer is now also built and automated (real `UnixStream` tests in `blueice-ipc` and `blueice-engine::session`); real platform-native UI automation (WinAppDriver/XCUITest/etc.) is still not actionable, since it needs a platform-native frontend and only the `winit`/`softbuffer` reference frontend exists so far.
- **Differential/cross-validation tests**: BlueIce's own output checked against a real, independent oracle rather than trusted to its own test suite alone — the same category, two instances:
  - **BlueJS vs. Node.js** (Phase 13-specific): correctness and performance of the custom JS engine checked against Node.js — run the same script corpus through `node` and through the `bluejs` shell's batch mode, diff stdout/exit codes (correctness, gates the build for in-scope features) and wall-clock time (performance, tracked as a trend, not a pass/fail threshold — parity with Node/V8 isn't the MVP bar). See `../phase-13-bluejs-engine/PLAN.md` for the full design, including the non-determinism-normalization traps this category has to account for.
  - **BlueIce vs. Chromium** (Phase 15): rendering output checked against a real Chromium via Puppeteer — see "Chromium differential testing" below.

## Chromium differential testing

**Objective**: an independent correctness signal for the whole HTML/CSS→layout→paint pipeline, the same "don't trust your own test suite to grade itself" principle Phase 13's BlueJS/Node.js differential testing already established for the JS engine — applied here to rendering instead of script execution, and using a real production browser (Chromium, via Puppeteer) as the oracle instead of a reference JS runtime.

**Why this exists as its own initiative rather than more fixtures**: the shared fixture corpus (`../testing/fixtures/*.dat`, above) checks BlueIce's output against *hand-authored or html5lib-tests-sourced* expectations — correct as far as they go, but never independently checked against what a real, production rendering engine actually does with the same input. Differential testing closes that gap: same HTML in, compare BlueIce's own output against Chromium's, on the same machine, for the same input.

**What gets compared, using capabilities already built for other reasons**:
- **Screenshots**: Puppeteer's own `page.screenshot()` against BlueIce's PNG output (`blueice-raster`'s `Pixmap::save_png`, reachable via `blueice-mcp-server`'s `screenshot` MCP tool or a direct `Page::render_visible` call) — a pixel-level or perceptual-diff comparison (e.g. `pixelmatch`), within a tolerance, not exact-match (see "not exact parity" below).
- **DOM structure**: Chromium's DOM (serialized via `page.evaluate(...)`, or Puppeteer's own accessibility snapshot for a closer analog) against BlueIce's `ClientMessage::GetDom` (added specifically to support this — deliberately the *unfiltered* full tree, not the AI-facing `GetRepresentation` snapshot, which excludes non-semantic nodes on purpose and would make a structural diff meaningless for anything decorative).

**Corpus**: the *same* `development/browser_core/testing/fixtures/*.dat` files the shared fixture interface already uses — each fixture's `#data` HTML section, fed to both Chromium and BlueIce, rather than a separately maintained set of pages. This means every fixture already scoped to what BlueIce's MVP HTML/CSS subset actually supports (`phase-2-mvp-scope/PLAN.md`) is differential-testable for free as the corpus grows, with no separate curation step.

**Not exact parity — tracked as a trend, mirroring Phase 13's own JS-differential philosophy exactly**: BlueIce's MVP scope is deliberately narrower than Chromium's (`phase-2-mvp-scope/PLAN.md`'s non-goals: no Grid, no advanced selectors, no JS execution yet, etc.), so pixel-identical or DOM-identical output is not the bar, and a harness that expected it would report false failures forever. The comparison establishes a baseline and tracks it over successive changes (did this change move rendering *closer* to or *further from* Chromium's output for in-scope features), the same non-goal Phase 13's differential design already states explicitly for BlueJS-vs-Node performance parity.

**Architecture**: a Node.js harness (Puppeteer needs a real Node runtime; this is the one part of the project that isn't Rust, same exception CI's `bluejs-differential` job already carves out for Node.js) that, per fixture: (1) loads the `#data` HTML into a real Chromium tab via Puppeteer, captures a screenshot and serializes the DOM; (2) drives `blueice-mcp-server` over stdio MCP (`navigate` with the fixture written to a temp file or a local static server, then `screenshot` and `get_dom`) to get BlueIce's own versions of the same two artifacts; (3) diffs both and reports. Talking to BlueIce through the MCP server (rather than a bespoke IPC client) means the harness doubles as an integration check of the MCP surface itself, and gives Phase 12's eventual real MCP-client validation a second, automated consumer beyond manual testing.

**Not yet built**: this section is the design; `backend/mcp-server`'s `screenshot`/`get_dom` tools exist and are verified manually and by unit test, but the actual Node.js/Puppeteer harness, its comparison/tolerance logic, and CI wiring are Phase 15's own checklist, tracked there rather than here.

## WPT tree-construction corpus

A second, independent correctness check for `blueice-html` specifically, distinct from the Chromium *rendering* comparison above: the official [WPT](https://github.com/web-platform-tests/wpt) `html/syntax/parsing/resources/*.dat` tree-construction corpus (formerly the standalone `html5lib-tests` repo, which now just points here) run through `blueice_html::parse` and compared against the corpus's own expected `#document` dumps. See `reference/README.md` for how to fetch it (a sparse partial clone, not the whole WPT monorepo) and `backend/core/html/tests/wpt_corpus.rs` (module docs + `--nocapture` output) for the runner itself -- a reporting scratch tool today, not a CI gate.

**Byte-exact comparison against the raw corpus is the wrong bar**: it starts at ~19% pass, almost entirely because of already-decided MVP scope cuts (no Comment/Doctype nodes at all, no SVG/MathML foreign content, no `<template>`, a minimal named-character-reference table, no quirks mode, no scripting) rather than bugs. The runner normalizes away the Comment/Doctype-node difference and classifies the rest by likely cause (element outside the Phase 2 MVP list, foreign content, entity-table gap, ...), leaving only genuinely unexplained failures worth a human reading. That normalized number moved from 39.0% to **54.5%** (956/1753) over two triage passes that together found and fixed over twenty real bugs, all now regression-tested; unclassified (not-an-obvious-scope-cut) failures dropped from 669 to **52**.

First pass (six bugs):

1. **Whitespace either side of `</body>` didn't merge into one Text node** (`blueice-html`'s `insert_text`) -- actually found by the *Chromium* differential test above, not this corpus, but fixed alongside these; listed here since the next two bugs are corrections to the same code path.
2. **An unclosed `<script>`/`<title>`/`<style>`/`<textarea>` at EOF suppressed the implicit `<body>` element entirely** -- the "Text" insertion mode's EOF handling must *reprocess* the EOF in the restored original mode (triggering the normal implicit-`<body>` cascade), not just consume it.
3. **An end-tag-like sequence truncated by EOF (`</script` with no `>`) was wrongly accepted as a real end tag**, silently eating the text instead of keeping it literal -- the "appropriate end tag" check must not treat "hit EOF right after the tag name" as a valid terminator.
4. **A numeric character reference with no digits (`&#BAR`, `&#xZOO`) was replaced with U+FFFD instead of staying literal text** -- "zero digits after `&#`" (not a reference at all) was being conflated with "digits present but resolve to an invalid code point" (where U+FFFD *is* correct).
5. **Text separated only by a comment wrongly merged into one Text node** -- a regression from fix #1's own generalization: since `blueice_dom` never materializes Comment/Doctype nodes, `insert_text` had no way to tell a comment had been dropped between two character runs and merged across it, but a *real* browser's actual Comment node physically blocks that merge. Fixed by tracking "did the immediately-preceding token get dropped as a Comment/Doctype" and refusing to merge across it.
6. **`&#x80;`-`&#x9F;` (the legacy Windows-1252 C1-control compatibility range) resolved to raw control characters or nothing at all**, instead of the specific WHATWG-mandated replacement table (`€`, `"`, `"`, etc.) real browsers still use for historical compatibility.

Bug #5 is worth calling out on its own: it was introduced *by this same testing effort*, on the very same day, by a fix that looked complete when checked against the fixture corpus and unit tests but generalized past what real browsers actually do -- exactly the kind of thing a second, independent, real-browser-derived oracle is for.

Second pass, working through the remaining unclassified failures file-by-file (46.8% -> 54.5%, 191 -> 52 unclassified):

7. **`<hr>` wasn't in the "closes an open `<p>`" element list**, despite already being a supported element -- an oversight, not a deliberate cut.
8. **A stray `</p>` with no matching open `<p>` was ignored outright** instead of inserting (then immediately closing) an empty `<p>` per spec.
9. **`<!-->` and `<!--->`** ("abrupt-closing-of-empty-comment", comment start/start-dash states seeing `>` immediately) **were not recognized as valid closing sequences at all** -- the naive "scan forward for the next `-->`" comment scanner swallowed real markup in between (`<!--><div>--<!-->` lost the entire `<div>`). Same for **`--!>`** ("comment end bang" state, an "incorrectly closed comment" error) later in the same pass.
10. **`<style>`/`<script>`/`<title>`/`<meta>`/`<link>` appearing after an explicit `</head>` wrongly opened an implicit `<body>`** instead of re-entering `<head>` -- the "after head" mode's spec-mandated exception (temporarily re-push the head element, delegate to "in head" rules, remove it again) was missing entirely.
11. **`<style>`/`<script>` directly inside `<table>`** (not inside a cell/caption) **were foster-parented in front of the table** instead of inserted as the table's own child, per the "process using in-head rules" carve-out.
12. **A stray `</thead>`/`</tfoot>`/etc. end tag inside a cell closed the cell anyway**, even when no matching element was actually open -- `step_in_cell` used the general "in scope" algorithm (which stops at `td`/`th`) instead of the narrower "in table scope" the spec actually calls for here, so it could never have found a `<thead>` sitting *outside* the very cell it needed to look past.
13. **A raw U+0000 NULL byte inside `<script>`/`<style>` content was passed through literally** instead of becoming U+FFFD (RAWTEXT/script-data's tokenizer rule); separately, **a raw NUL in ordinary body/select content wasn't dropped** the way "in body"/"in select" tree construction requires (these are two different rules at two different layers, easy to conflate).
14. **`\r`/`\r\n` were never normalized to `\n`** -- spec's input-preprocessing step was missing entirely, which also broke the next bug.
15. **A leading `\n` right after `<pre>`/`<textarea>`'s start tag wasn't stripped** ("newlines at the start of pre blocks are ignored as an authoring convenience").
16. **`<script>` had no "script data escaped"/"script data double escaped" state machinery at all** -- a literal `<!--` inside `<script>` content (used to hide inline script from pre-`<script>`-aware browsers) didn't hide anything, and a genuinely nested `<script>...</script>` pair inside that didn't toggle double-escaped mode either; the single biggest fix of this pass (~50 corpus cases).
17. **No "in select" insertion mode existed at all** -- `<select>` fell through to generic element insertion, so a second `<select>` nested instead of closing the first, `<input>`/`<textarea>` nested inside a `<select>` instead of closing it, and `<hr>` inside `<select>` did nothing instead of closing an open `<option>`/`<optgroup>` and being inserted as `<select>`'s own child.
18. **No "in select in table" mode existed either** -- a `<select>` opened while already inside table structure needs table-structure tags (`<tr>`, `<td>`, ...) to close it outright (unlike plain "in select", which just ignores them); needed extending `reset_insertion_mode` to actually handle table/select frames instead of only `body`/`html` (previously safe only because its two callers had, by construction, already popped past anything else).
19. **`<input type="hidden">` directly inside `<table>` was foster-parented** like any other stray content, instead of being inserted normally as the table's own child (the spec carve-out real pages rely on for hidden CSRF-token-style inputs placed directly inside a table).
20. **`<button>` had no auto-closing behavior at all** -- a second `<button>` nested inside the first instead of closing it, and `</button>` didn't generate implied end tags before popping (so `<button><p></button>x` left "x" nested inside the still-open `<button>` instead of after it).
21. **`<col>`'s attributes were dropped** when it triggered an implicit `<colgroup>` -- the reprocessed token was rebuilt with a hardcoded empty attribute list instead of the original one.
22. **A second, stray `<html>` start tag was ignored outright**, discarding its attributes, instead of merging any attribute not already present onto the existing `<html>` element.

Bugs #16-18 turned "in select"/`<script>` from silently-wrong into spec-correct territory the MVP element list already claimed to support (`select`/`option`/`optgroup` and `script` were both already on the Phase 2 element list) -- these aren't new scope, just closing a gap between "the element renders" and "the element parses correctly when misused the way real pages do."

**What's left in the 52 remaining unclassified failures** (not attempted, in rough order of what they'd need): the WHATWG active-formatting-elements reconstruction/adoption-agency algorithm has real gaps beyond the one Phase 3 bug already fixed, surfacing as misplaced nesting across `<p>`/`<i>`/`<b>`/`<table>` boundaries in deeply misnested real-world-adjacent markup (`tests1.dat`'s largest remaining cluster) -- risky to touch without a much larger, dedicated pass given how central and easy to regress that algorithm is. A couple of `<form>`-directly-inside-`<table>` cases (`tests20.dat#46`/`#47`) look like they need another "insert normally, don't foster-parent" carve-out similar to bug #19's, but weren't confirmed against spec text with enough confidence to risk a wrong change. `tests20.dat#41`'s `<p><table></p>` (no doctype) looks like it depends on quirks-vs-no-quirks-mode-conditional behavior BlueIce doesn't model at all (an existing, deliberate scope cut) rather than a bug. A `<select>` accepting `<div>`/`<button>`/`<img>` as real child content (several `webkit02.dat` cases) doesn't match the current spec text for "in select" as best it could be verified and may reflect that file's older browser-specific quirks rather than current spec.

## Coverage policy

Tool: [`cargo-llvm-cov`](https://github.com/taiki-e/cargo-llvm-cov) (LLVM source-based coverage — more accurate than instrumentation-based tools like tarpaulin, no nightly toolchain required).

- **Crates with real implementation** must hold **≥90% line coverage**, enforced in CI via `--fail-under-lines 90`. Every pipeline crate through Phase 3 (`dom`, `html`, `css`, `layout`, `paint`, `engine`) and every Phase 4 crate (`ipc`, `net`, `font`, `raster`, plus `engine`'s new `page`/`session`/`blueice-core` binary) clears this, along with the shared `testing` fixture harness — held to the same bar as product code, since a bug in the thing everything else is verified against is worse than a bug in any one crate.
- **Excluded from the enforced number via `--ignore-filename-regex`**, both for the same underlying reason (a real process entry point whose reachable logic is already tested elsewhere, leaving only wiring nothing in CI can exercise) rather than "stub code":
  - `extension/src/main.rs` — its body is still `todo!()` (a genuine stub; Phase 9 is its turn to lose this exclusion, per the note below).
  - `frontend-reference/src/main.rs` — NOT a stub, but its windowed `winit` event loop needs a real display no headless CI runner has; its pure helper functions (pixel-format conversion, socket/binary-path resolution) are unit tested in the same file and do count. Manually verified instead, in a real window under WSLg (Phase 4's `PLAN.md`): live resize, a real synthetic click that followed a link to navigate, screenshots confirming no rendering defects.
  - `mcp-server/src/main.rs` and `mcp-server/src/server.rs` — NOT stubs either. `main.rs` is process-spawn + stdio-transport wiring (mirrors why `frontend-reference/src/main.rs` is excluded); `server.rs` is thin `rmcp` macro-generated MCP tool glue, only exercisable by a real MCP client speaking the wire protocol (manually verified instead — a real `initialize`/`tools/list`/`tools/call` session against the compiled binary, see `phase-12-mcp-server/PLAN.md`). Everything with actual logic (`CoreConnection`'s message-sequencing, the pipelining trick, process spawn/cleanup via a real subprocess integration test) lives in `mcp-server/src/lib.rs` instead and holds the same ≥90% bar as any other crate.
  - `blueice-core`'s own binary (`engine/src/bin/blueice-core.rs`) is deliberately **not** on this list, even though it's also a `main.rs`-shaped process entry point — unlike a window, a Unix-socket server has no display dependency, so `engine/tests/core_binary.rs` runs the actual compiled binary as a subprocess and gets real, repeatable coverage of its argument parsing, bind/accept, and shutdown/cleanup in CI. This is the concrete line between "genuinely can't be automated headlessly" (excluded) and "just hasn't been wired into an e2e test yet" (not excluded, fixed instead).
- **When an excluded file gains a way to test it for real, removing it from the ignore-filename-regex list is part of that work's own Definition of Done** — this already happened once outside the original stub-crate list: `blueice-core`'s binary was never excluded to begin with, specifically because `Command`-spawning it as a subprocess was recognized as actionable rather than reached for the exclusion. Phase 3 did the equivalent (losing stub status entirely) for `html`, `css`, `layout`, `paint`, and `engine`; `extension`'s turn is Phase 9.
- Coverage is necessary, not sufficient: a function hit by one happy-path test can show 100% line coverage while missing every edge case. Treat the percentage as a floor that catches accidentally-untested code, not a target to chase for its own sake — reason about what a crate's tests actually need to cover (per the pyramid above) independent of the number.

Run it locally the same way CI does:

```sh
cargo llvm-cov --workspace \
  --ignore-filename-regex 'extension/src/main\.rs$|frontend-reference/src/main\.rs$|mcp-server/src/main\.rs$|mcp-server/src/server\.rs$' \
  --fail-under-lines 90 \
  --summary-only
```

## CI — the automation + human-visible interface

`.github/workflows/ci.yml` runs on every push and pull request to `main`:

- **`build-test`**: `cargo build --workspace --all-targets`, `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`.
- **`coverage`**: the `cargo-llvm-cov` command above, with its summary written to the job's step summary so the numbers are visible directly on the run page, not buried in a log.
- **`bluejs-differential`** (not added yet — part of Phase 13): will need Node.js in the CI environment (`actions/setup-node`) to run the differential corpus against `bluejs`, with correctness gating the build and performance numbers published to the job summary the same way coverage is.
- **`chromium-differential`** (not added yet — part of Phase 15): also needs Node.js (shared setup with the job above) plus a headless Chromium Puppeteer can drive; reports the screenshot/DOM diff trend to the job summary rather than gating the build, per "not exact parity" in "Chromium differential testing" above.

This is the interface: GitHub's own Checks UI shows pass/fail per commit and per PR with no extra dashboard to build or maintain; the coverage job's summary shows real numbers on every run; the README badge links straight to the latest run so current status is visible from the project's front page. A human can also just run the same two commands locally (`cargo test --workspace`, the `cargo llvm-cov` command above) to get the identical result CI would.

## UI testing strategy

"UI testing" for a browser engine splits into two genuinely different concerns, gated on two different things existing — conflating them either overclaims what's tested today or underclaims what's actionable before Phase 4. Both live in the same shared fixture interface described in "Rendering-correctness fixtures" above rather than being invented as a separate mechanism per layer.

**1. Rendered-output verification — gated on the pipeline, not on a frontend. Built in Phase 3, complete through paint.** This is "what would appear on screen," checked automatically against fixtures, with no window, no frontend, and no human looking at anything:

- `#layout` (done): a canonical geometry dump — every box's kind, position, and size — checked via `backend/core/layout/tests/fixtures.rs` against a fixed viewport width. This already pins down the real, load-bearing geometry (block stacking, margin/padding/border boxes, line-wrapping) that any eventual on-screen rendering has to match.
- `#paint` (done): a canonical paint-command dump (background/border rectangles, text runs with color and font size) — checked via `backend/core/paint/tests/fixtures.rs`, and reused verbatim by `blueice-engine`'s end-to-end smoke test (`backend/core/engine/tests/fixtures.rs`) to check the exact same expectation through `render()`. Still a display list, not pixels — actual rasterization needs a real font/2D-drawing backend, which is a Phase 4 `frontend` concern (per-platform), not paint's.
- Phase 5's `#ai-representation` section is this same idea applied to the *other* representation `core`'s render pass produces (plan §3) — not UI in the windowing sense, but the same "what would this pass actually expose" verification pattern.

None of this needs Phase 4. It's the concrete, already-integrated answer to wanting automated UI/visual verification without waiting for a real window to look at — and as of Phase 3's completion, it covers the whole pipeline from HTML input to display-list output.

**2. Real frontend/platform automation — gated on Phase 4's frontend existing.** Two layers, only the first of which is meaningfully automatable across all platforms:

1. **Core↔frontend IPC-boundary tests (done)**: drive the control-plane protocol (`blueice-ipc`'s `ClientMessage`/`ServerMessage`) directly with a test client over a real `UnixStream`, without needing real platform UI automation — `blueice-ipc`'s own round-trip test plus `blueice-engine::session`'s tests (navigate/resize/click/scroll/shutdown, including a real local HTTP server for navigation) are this layer. This is the primary correctness net, since it runs the same on every CI platform regardless of which native frontend is under test. The reference `frontend` binary itself (`backend/frontend-reference`) was additionally checked by hand in a real window under WSLg: real resize, a real synthetic click (via the X server's XTest extension) that navigated through a followed `<a href>`, and visual inspection confirming no rendering defects — this is exploratory/manual verification, not a repeatable automated test, and doesn't need to be one given layer 1 already covers the same logic through the real protocol.
2. **Platform-native UI automation (still not actionable)**, one per real frontend, scoped to what's genuinely platform-specific (does the window actually appear and respond, does native accessibility/menu integration work) rather than re-testing logic layer 1 already covers: WinAppDriver (or successor) for WinUI 3, XCUITest for SwiftUI, `pytest-qt`/`QTest` for PySide6. None of these platform-native frontends exist yet — only the `winit`/`softbuffer` reference frontend does — so this layer has nothing to automate against yet.
