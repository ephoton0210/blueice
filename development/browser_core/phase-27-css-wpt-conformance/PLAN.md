# Phase 27 — CSS WPT Conformance Testing

[← Back to plan](../BROWSER_CORE_PLAN.md)

**Status**: In progress — the harness works end to end against a first pilot corpus (`css/css-color/`, 308 real reftests): 292/308 (94.8%) genuine passes once blank-equivalent (uninformative) passes are excluded from the 306/308 (99.4%) raw count, 2 real failures, both classified as known MVP-scope gaps. See "First real results" below, including two real infrastructure bugs (unrelated to CSS) found and fixed along the way.

## Objective

Give `blueice-css` the same kind of independent, real-corpus correctness oracle Phase 13 built for BlueJS against Node.js and `backend/core/html` already has against the official WPT tree-construction corpus (`backend/core/html/tests/wpt_corpus.rs`): the real, upstream **Web Platform Tests CSS suite**, not just the hand-written MVP fixture corpus (`development/browser_core/testing/fixtures/*.dat`) that already exists. Raised out of the numbered sequence for the same reason Phases 14/15/25/26 were: needed now that `blueice-css` is substantial enough (cascade, selectors, box model, basic flexbox) for a real conformance measurement to be worth taking, not planned from the start.

Explicitly not "CSS3 conformance" as a single number — per the HTML/CSS scope research this phase's own investigation surfaced, `phase-2-mvp-scope/PLAN.md`'s "MVP CSS scope" is an ad-hoc subset cross-checked against Stylo/Blink precedent, not a claim to any one numbered CSS spec level. This phase measures how much of the *real* WPT CSS corpus that subset already satisfies, and tracks the gap the same scope-normalized way Phase 2/`wpt_corpus.rs` already tracks HTML5 tree-construction: a raw pass rate (expected low, since WPT's CSS suite tests far more than BlueIce's MVP scope covers) plus a triage distinguishing "known MVP scope gap" from "real bug in what BlueIce already claims to support."

## Why this needs no second engine (unlike Phase 15)

Phase 15's Chromium differential harness compares BlueIce's rendering against a *different* engine's rendering of the *same* input — it needs Puppeteer and a real Chromium because the whole point is cross-engine agreement. WPT's CSS suite instead uses the **reftest** methodology: a test page and one or more reference pages that a spec-compliant engine must render *identically* (`<link rel="match" href="...">`) or *differently* (`rel="mismatch"`), designed so a single engine's own rendering of the two can prove or disprove a claimed CSS behavior without needing a second, independent implementation to compare against. `background-color-rgb-001.html`'s reference page uses the eventual computed color directly (`background-color: green`), so if BlueIce's `rgb()` parsing (it doesn't have any yet — see "First real results") is correct, rendering the test and its reference produces pixel-identical output *by BlueIce's own renderer alone*. This means the harness needs exactly the capability Phase 4/15 already built — navigate a URL, take a screenshot — plus the same `pixelmatch` comparison Phase 15's `compare.js` already uses, and nothing else new.

## Design

- **Corpus**: a real, unmodified subset of `web-platform-tests/wpt`'s `css/` tree, fetched the same sparse-partial-clone way `development/browser_core/reference/wpt/`'s existing HTML tree-construction corpus already is (see that directory's `README.md`, updated by this phase). Pilot suite: `css/css-color/` (253 real `rel="match"`/`rel="mismatch"` reftests, excluding testharness.js-driven script tests and the reference files themselves), plus the shared `css/support/` and root `fonts/` directories a handful of those reftests need via root-absolute paths (`/css/support/...`, `/fonts/ahem.css`). Widening to further suites (`css/css-backgrounds/`, `css/css-box/`, `css/CSS2/`) is future work once the pilot's own findings are triaged, not a scope commitment of this document.
- **Explicitly out of scope for this phase**: any WPT CSS test driven by `testharness.js` (`test()`/`assert_*` calling `getComputedStyle`, CSSOM property access, etc.) — these need real DOM/CSSOM JavaScript bindings BlueJS does not have yet (`backend/core/dom` is a pure internal Rust tree with no script-facing API at all), which is Phase 20's job, not this one's. Running those tests today would either hang waiting on APIs that don't exist or need a parallel, throwaway scripting shim Phase 20 would later replace. This mirrors the same "genuinely unblocked vs. actually blocked on an earlier phase" distinction Phase 24 (PDF viewer, blocked on Phases 20/22) surfaced.
- **Serving the corpus**: unlike Phase 15's per-fixture throwaway HTTP server (one string of HTML at `/`), WPT reftests reference sibling files and root-absolute shared resources (`/css/support/...`, `/fonts/...`), so the harness runs one static file server rooted at the whole `development/browser_core/reference/wpt/` checkout, matching how the upstream `wpt.py` test runner itself serves the repo from a virtual root.
- **Comparison mechanism**: for each reftest, resolve every `rel="match"`/`rel="mismatch"` link from the test file's own `<head>`, navigate BlueIce to the test URL and each reference URL in turn, screenshot each, and `pixelmatch` the test's screenshot against each reference's. A `match` reference must be pixel-identical (0 differing pixels — no fuzzy-match tolerance in this first slice; WPT's `<meta name=fuzzy>` per-test tolerance metadata is a known future refinement, not implemented yet); a `mismatch` reference must differ by at least one pixel.
- **Reuses, not rebuilds**: `blueice-mcp-server`'s existing `navigate`/`screenshot` tools (no new IPC surface needed, unlike Phase 15's `GetDom` addition — a reftest never needs the DOM tree, only pixels) and the `pixelmatch`/`pngjs` dependencies `differential-testing/` already has. New harness code lives in `differential-testing/src/css-wpt/` (same Node project, since it needs no Puppeteer for this phase's own comparisons — Puppeteer stays a `differential-testing` dependency for Phase 15's unrelated cross-engine work) rather than a second Node project.
- **Pass-rate methodology**: mirrors `backend/core/html/tests/wpt_corpus.rs`'s already-established pattern (`testing/TEST_PLAN.md`'s "WPT tree-construction corpus" section) — report the raw pass rate over the full pilot corpus, then classify every failure into a known MVP-CSS-scope gap (a property/value/selector `phase-2-mvp-scope/PLAN.md` already documents as deferred) or an unclassified failure (something BlueIce claims to support that the corpus shows is actually wrong). Zero unclassified failures is the target for a given corpus slice, the same bar `wpt_corpus.rs` holds itself to; a nonzero unclassified count is real signal to fix, not something to filter out of the report.

## First real results

Running the harness against the full `css/css-color/` pilot corpus (the discoverer found 308 real `rel="match"`/`rel="mismatch"` reftests, more than this document's original 253 estimate, once nested directories like `animation/` were included) found **306 / 308 (99.4%) raw pass**, 2 fail, 0 harness errors.

**That raw number overstates real conformance, and building the harness surfaced exactly why.** `backend/core/css` implements no functional color notation at all — no `rgb()`, `hsl()`, or any other CSS Color 4 function; the MVP scope's color support is keywords, `#rgb`/`#rrggbb` hex, and `currentColor` only. A large fraction of `css/css-color/`'s own reftests deliberately pair a test using one functional-notation spelling against a reference using a *different* spelling of the same computed color (`background-color-rgb-001.html`'s `rgb(10%, 60%, 10%, 20%)` against its reference's `rgba(10%, 60%, 10%, 0.2)`, for example) — exactly the kind of pair where an engine that parses *neither* side still "passes," by rendering the same unstyled default on both, not by computing the same color. A reftest can't distinguish "both sides genuinely agree" from "both sides silently failed to parse, identically" on its own.

To separate the two, the harness screenshots one genuinely blank page once per run and flags any *passing* result whose own test screenshot is pixel-identical to that blank baseline as `blankEquivalent` — a pass that proves nothing about the feature it claims to test. That check found **14 blank-equivalent passes** (`a98rgb-*`, `background-color-{rgb,hsl}-*`, `at-color-profile-001`, and the two `opacity-animation-ending-correctly-*`/`contrast-color-interpolation` animation cases — all pages whose only visible content depended on unsupported color functions or animation), leaving **292 / 308 (94.8%) genuine passes**: results where BlueIce rendered real, non-default content and it matched. This blank-page check is a first-order filter, not an exhaustive one — a text-bearing page whose *specific* color declaration is silently dropped but whose surrounding text still renders identically for unrelated reasons would still count as a "genuine" pass here; a full per-declaration causal classification (which computed property actually drove the compared pixels) is future work, the same kind of refinement `backend/core/html`'s own WPT triage went through across several passes rather than getting right in one run.

The 2 real failures are both classified, not left as unclassified noise:
- `relative-currentcolor-rec2020-01.html` (a `match` test): uses CSS Color 4's *relative color syntax* (`rgb(from currentcolor ...)`) against a wide-gamut `rec2020` reference — a known MVP-scope gap (no functional color notation at all, let alone relative-syntax or wide-gamut color spaces).
- `t31-color-text-a.xht` (a `mismatch` test, so its own test and reference are *supposed* to render differently — this failure means they rendered identically): its `<style>` element wraps the actual CSS in an XHTML `<![CDATA[ ... ]]>` section (`#one { color: green; }`), a construct HTML5's tag-soup `<style>`-as-RAWTEXT tokenization does not treat specially, so `blueice-css`'s tokenizer sees `<![CDATA[` as unparseable garbage ahead of the real declaration. If it discards the whole block rather than recovering past just the CDATA markers, the `color: green` rule is silently lost, `#one` falls back to default black text, and the test then matches its reference (which explicitly sets black) instead of differing from it. A known, narrow scope gap in CSS-in-`<style>` extraction for XHTML-authored `.xht` test files, not a selector/cascade bug.

Zero unclassified failures: both retained failures are explained, matching the bar `backend/core/html/tests/wpt_corpus.rs` already holds itself to. Adapter/regexp-worker-style SHA verification doesn't apply here (this harness renders through the real, already-built `blueice-mcp-server`/`blueice-core` binaries directly, not a separate pinned adapter), but the exact reftest pairs, pass/fail/blank-equivalent classification and diff images for every result are in `differential-testing/output/css-wpt/report.json` (not checked in -- regenerate with `npm run css-wpt` from `differential-testing/`).

**Found and fixed two real, previously-unknown bugs building this harness, unrelated to CSS itself but blocking every navigation-driven MCP tool on this platform:**

1. **`default_gatekeeper_socket_path()`/`rendezvous_socket_dir()`'s non-Linux UID lookup was broken by construction.** Both parsed Linux's `/proc/self/status` for the real UID, falling back to `std::process::id()` — this *process's own PID*, not a UID — everywhere that file doesn't exist, every non-Linux Unix included (macOS, where this was found). Two different processes (`core` and a separately started `ai-gatekeeper`, or `core` and `blueice-launcher`) computed two different, unshared socket paths and could never find each other, so gatekeeper review was unreachable and every gated navigation failed closed silently — no error surfaced to the client, since the async pipeline (see below) had already returned before the eventual `GatekeeperBlocked`/fetch outcome even arrived. Fixed in `backend/ipc/src/gatekeeper.rs` and `backend/launcher/src/lib.rs` (the two crates deliberately duplicate this helper) by declaring the real POSIX `getuid()` directly via `extern "C"` rather than parsing a Linux-only file, verified against a real independent process (`id -u`) in a new regression test in each crate.
2. **`blueice-mcp-server`'s reply-draining loops discarded a `FrameReady` tagged with any request id but their own.** `phase-7-local-ai/PLAN.md`'s non-blocking navigation dispatch means a gated navigation's own completion (its `Navigated`/`FrameReady`, produced by a background thread on its own schedule) can easily still be in flight when a *pipelined* `GetRepresentation` sent right after it gets its own answer back first and returns — at which point nothing re-reads the connection until some later, unrelated call does. That later call's own loop filtered out *every* message not tagged with its own request id via a blanket `continue`, including the earlier navigation's now-arrived `FrameReady`, so it was never cached — a subsequent `screenshot` call then failed with "no frame has been rendered yet," indefinitely (retrying more of the same kind of call never surfaced a `FrameReady` tagged with someone else's id either). Fixed in `send_and_drain`/`representation`/`dom` (`backend/mcp-server/src/lib.rs`) by recording a `FrameReady` unconditionally, regardless of which request produced it, before applying the "is this reply mine" filter to every other message type (which still must not misattribute another client's broadcasted traffic on a shared `blueice-launcher` connection — the existing `send_and_drain_ignores_a_reply_carrying_a_different_requests_id` test still passes unchanged). A new regression test, `a_frame_ready_tagged_with_an_earlier_calls_request_id_is_still_cached_by_a_later_call`, reproduces the exact scenario against a real (fake-core-backed) connection.

Both bugs meant `blueice-mcp-server`'s `navigate`+`screenshot` sequence — the mechanism this harness (and Phase 15's differential-testing harness, which uses the same shared `blueice-client.js`) depends on — was silently non-functional on this development machine before this phase's work, with no error message pointing at the cause. `differential-testing/src/blueice-client.js` also gained a small `screenshotPngWhenReady` retry helper and untrusted-content-marker stripping (`wrap_untrusted_page_content`, added to `navigate`/`get_dom`'s output after Phase 15 last verified this client against a real subprocess) — both real, needed fixes surfaced the same way.

## Explicit non-goals

- A single "CSS3 pass rate" headline number — CSS has no such unified conformance suite even upstream; WPT's `css/` tree is dozens of independently versioned suites (`css-color`, `css-backgrounds`, `css-flexbox`, ...), each tracked and reported on its own, the same way this document reports `css-color` on its own rather than inventing an aggregate.
- Script-driven (`testharness.js`) CSS conformance, CSSOM (`getComputedStyle`, `element.style`), and anything else needing a live DOM/script binding — deferred to whenever Phase 20 exists; adding a throwaway scripting shim here to force those tests to run would duplicate work Phase 20 will replace.
- Fuzzy-match tolerance (`<meta name=fuzzy>`), `@font-face`/custom web font loading (the Ahem test font WPT commonly relies on for exact pixel measurements is out of scope until BlueIce's font system loads fonts other than its bundled DejaVu Sans/Noto Sans TC), and per-`.headers`-file HTTP header overrides the static server does not yet honor — each is a known simplification of this first slice, not a silent gap.
