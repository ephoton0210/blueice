# Intl, regex deadlines and Test262

Requested 2026-09-09, continuing from `2519fc1`. This document records the design before implementation and will record actual validation outcomes.

## Regex isolation

Run the standalone regress algorithm in a sibling `bluejs-regexp-worker` process. Both compilation (including parser literal validation) and matching use a bounded request/reply channel. A parent deadline covers worker IO and algorithm execution; timeout kills and reaps the worker and joins its IO thread before returning a resource error. Later operations start a fresh worker. Do not use detached matching threads or cooperative cancellation as a hard timeout. UTF-16 input and capture ranges/names cross the protocol losslessly. Cache one compiled pattern per worker; no compiled regex executes in the BlueJS process. Discover the installed sibling binary or an explicitly configured `BLUEJS_REGEXP_WORKER` path; fail closed if unavailable. The host must ship the helper beside its executable. Defaults and configurable VM limits will be tested through the public pipeline, including catastrophic backtracking and recovery.

## Internationalization

Target published ECMA-402 edition 13 (June 2026), verified at the [official publication page](https://ecma-international.org/publications-and-standards/standards/ecma-402/), rather than the living 2027 draft. ICU supplies locale/case/collation algorithms and data; BlueJS implements observable argument conversions, option order, builtin objects/descriptors and exceptions. Scope follows the preceding String task: Intl.Collator, Intl.getCanonicalLocales, Intl.Locale, its Locale-info query methods and the three locale-sensitive String methods. A deliberately bounded finite-decimal `Intl.NumberFormat` adapter now delegates to the host-neutral Phase 25 service for `format`, `resolvedOptions` and `supportedLocalesOf`; it is not full NumberFormat. `Intl.DateTimeFormat` now owns its branded service state and implements construction/call, `supportedLocalesOf`, bound `format`, `formatToParts`, `formatRange`, `formatRangeToParts` and `resolvedOptions` through ICU4X date/time semantic skeletons. Its exact requested field set is selected at runtime, including weekday/era, partial calendar fields, hour-only and fractional-second forms; unsupported ICU4X combinations are formed from a semantic superset and remove only unrequested fields while preserving field order. Its direct, versioned Jiff bundle pins IANA TZDB `2026c`, exposes that release at runtime, case-normalizes every bundled IANA Zone-or-Link identifier without silently replacing a Link with its target, accepts and normalizes ECMA-402 `±HH`, `±HHMM` and `±HH:MM` fixed offsets, and calculates offset/DST transitions independently of machine zoneinfo. A valid TimeClip endpoint outside Jiff's civil-year range uses its equivalent position in the Gregorian 400-year cycle to select a named zone's recurring IANA offset; this preserves the ISO fields and weekday rather than rejecting the endpoint, but is not historical zone data for that remote year. `formatRange` and `formatRangeToParts` reject an `undefined` endpoint before either `ToNumber`, retain ordinary `ToNumber` and `TimeClip`, and do not add a start-after-end rejection. For Gregorian ranges containing a date and requesting neither a zone name nor fractional seconds, the production default is ICU4X's CLDR `DateRangeFormatter`. ICU's side spans are normalized to ECMA-402 serialized-part ownership: an equal field emitted once is `shared`, a repeated field remains endpoint-owned, and literals adjacent to a shared field or bridging the endpoints are `shared`. The ECMA-402 whole-pattern branch remains: if the formatted endpoints are identical, every part is `shared`. The bounded compatibility formatter is intentionally separate, not an equivalent ECMA-402 range implementation: it remains in use for requested zone names, time-only and fractional-second skeletons, non-Gregorian calendars, a host's explicit ICU4X opt-out, and Temporal plain values. It preserves current output while ICU4X gains the required input/data paths. `Temporal` has a deliberately bounded typed-value bridge for all four DateTimeFormat formatting entry points: ISO Instant strings are parsed to checked epoch nanoseconds; `Instant` keeps ordinary time-zone formatting while selecting its type-specific defaults; ISO plain date/time types preserve their local calendar fields, ignore the formatter time zone and suppress its zone name; and calendars/types are checked before direct or range formatting. `Temporal.ZonedDateTime` remains rejected by the DateTimeFormat methods, while `Temporal.ZonedDateTime.prototype.toLocaleString` delegates with the value's own time zone. This is not a claim of a complete Temporal API. ICU4X 2.3.0 is consumed through the pinned compatibility fork and remains an implementation slice rather than a claim of full DateTimeFormat or ECMA-402 conformance: localized long zone names and broader Test262 validation remain required. DisplayNames, DurationFormat, ListFormat, PluralRules, RelativeTimeFormat, Segmenter and supportedValuesOf have separate bounded implementation slices; all require broader Test262 validation before conformance can be claimed.

### Range formatter completion (2026-09-14)

This status supersedes the earlier compatibility-boundary description above. `formatRange` and `formatRangeToParts` always construct ICU4X's dynamic CLDR `DateRangeFormatter`; there is no host policy switch or string-level endpoint-concatenation path. The range input carries a stable empty zone when no zone field was requested, avoiding a false DST-driven fallback, and carries the actual IANA identifier, offset and name timestamp when it was. The adapter keeps ICU's source spans, normalizes them to ECMA-402 serialized-part ownership and performs the narrow typed fractional-time punctuation repair documented below.

### Resolved formatting core (2026-09-14)

DateTimeFormat now resolves the `ca`, `nu` and `hc` Unicode locale keys together with their explicit options, with option precedence reflected both in the selected ICU locale and in the observable `resolvedOptions()` values. Calendar aliases and supported-value fallback are resolved before formatting; ICU4X therefore receives the actual selected calendar rather than an ISO date decorated after the fact. The bridge preserves `iso8601` as the ECMA-402-visible calendar while using Gregorian formatting data where ICU's `iso8601` keyword would otherwise follow a locale default.

The typed-part boundary supplies the remaining public-format details that ICU4X's dynamic formatter does not currently expose: Arabic fractional seconds use `U+066B` rather than an ASCII decimal marker; `hanidec` keeps its CLDR digit forms and the en-US AM/PM separator; English flexible day periods have the specified morning/noon/afternoon/evening/night forms; Chinese related year/year-name parts retain their required `年` literal; and short date styles retain a localized two-digit historic year. `dateStyle`/`timeStyle` select their date/time precision, including a short time style without seconds. `Date.prototype.toLocaleString`, `toLocaleDateString` and `toLocaleTimeString` now instantiate this same resolved formatter with the ECMA-402 `any`, `date`, and `time` defaulting rules instead of using fixed English Date text.

`formatMatcher` is validated in the prescribed option order and retained in the host-neutral service state (`basic` or `best fit`). Best fit uses ICU4X's CLDR semantic-skeleton matcher. The BasicFormatMatcher scoring core now implements ECMA-402 §11.5.2 exactly: field iteration order, removal/addition penalties, width and fractional-second distance penalties, time-zone-name offset/name exceptions, and stable first-record tie breaking are tested. DateTimeFormat construction invokes that scorer for `basic` before building the ICU4X pattern. ICU4X's public dynamic API presently supplies the exact requested semantic field set but not its ordered raw CLDR `availableFormats` records, so the production candidate list currently contains that exact generated record; no locale-independent invented fallback is used. Extracting the full ordered CLDR record inventory (including append patterns for otherwise absent field combinations) remains required before this is described as a full locale-data-equivalent BasicFormatMatcher implementation.

### Offset and IANA zone identifiers (2026-09-14)

`CreateDateTimeFormat` now parses fixed-offset identifiers directly instead of forcing them through the inverted-sign, whole-hour-only `Etc/GMT` namespace. It accepts only the ECMA-402 forms `±HH`, `±HHMM` and `±HH:MM`, rejects malformed values and non-ASCII minus signs, bounds values at `23:59`, and stores a normalized `±HH:MM` identifier (including positive zero). Fixed offsets remain valid at both TimeClip endpoints.

Named zones are accepted from the same pinned `jiff-tzdb` inventory used for calculations. Lookup is ASCII-case-insensitive but `resolvedOptions().timeZone` receives the inventory's normalized Zone-or-Link spelling: `asia/calcutta` becomes `Asia/Calcutta`, rather than the target `Asia/Kolkata`; `Etc/GMT`, `Etc/UTC` and `GMT` are likewise preserved when supplied to DateTimeFormat. `Intl.supportedValuesOf("timeZone")` returns a new sorted, de-duplicated inventory on every call; its legacy UTC spellings (including `GMT0`/`Etc/GMT0`) are folded to `UTC` for the enumeration API only. The pinned Test262 zone subset passes **16/16 modes**, including all offset grammar/formatting cases, case normalization over the full available inventory, Link retention and enumeration invariants.

Specific long zone display names are still not localized from ICU zone-name data. The temporary long-name fallback is a GMT offset rather than an IANA identifier, so aliases with identical rules cannot render divergent raw identifier text. This is an explicit compatibility fallback, not completion of `timeZoneName: "long"`.

### Temporal plain-value bridge (2026-09-14)

`format`, `formatToParts`, `formatRange`, and `formatRangeToParts` now first resolve one typed `ToDateTimeFormattable` input at the VM boundary, then call the same host-neutral ECMA-402 bridge. The bridge distinguishes ordinary epoch values, `Instant` values (with their resolved time-zone-aware options), and plain local values (with no TimeClip or zone name); range inputs must have matching kinds and one equal resolved option record. Consequently an `Instant` with default options carries its date-and-time fields through both single-value and range formatting rather than letting the range fall back to the formatter's date-only default. The verified direct Temporal filter selects **31 files / 62 modes** across those two methods and records **62 pass**. It covers `Instant`, every supported ISO plain type, type/calendar mismatches, no-TimeClip plain values, type-specific default components, eras, style pruning, no-overlap errors, and ignored plain-value zones. The two `resolved-time-zone` part fixtures use the bounded native record-array assertion described above; its exact record shape is still checked rather than bypassed.

The normative-optional `ChainDateTimeFormat` constructor path is enabled. A no-`new` call whose object receiver has `%Intl.DateTimeFormat.prototype%` strictly in its prototype chain returns that receiver and stores the actual branded formatter under a unique per-realm `Symbol("IntlLegacyConstructedSymbol")` own property. The property is non-writable, non-enumerable and non-configurable; `Symbol.prototype.description` exposes its required description. Only `format` and `resolvedOptions` unwrap that receiver (including through a Proxy `get` trap); `formatToParts`, `formatRange` and `formatRangeToParts` retain their direct-brand requirement.

The historical verified-corpus `intl402/DateTimeFormat` filter selected **244 files / 488 modes** and recorded **486 pass / 2 fail**. The two strict/sloppy modes of `formatToParts/compare-to-temporal.js` are no longer represented by a calendar label on ISO fields: `PlainDate.from` and `PlainDateTime.from` now resolve a property bag with ICU4X's actual calendar, convert that date back to ISO storage, expose `calendarId`, `year`, ordinal `month`, `monthCode`, `day`, `era`, `eraYear` and `monthsInYear`, and convert an ISO-calendar plain value to a checked UTC epoch through `toZonedDateTime`. The implementation covers every calendar supported by this DateTimeFormat slice, including Chinese, Dangi and Hebrew leap months and Coptic/Ethiopic intercalary months. `month` retains Temporal's ordinal semantics while `monthCode` preserves leap-month identity; a property bag containing both is checked for consistency. The focused regression traverses all twelve non-lunisolar calendars, Chinese's thirteenth month plus `monthCode` round-tripping, Coptic's intercalary month, and `PlainDateTime`'s sub-millisecond fields. The two immutable 100-year Test262 calendar matrices have an exact 10,000,000-dispatch / 360-second runner envelope; a full verified-corpus rerun is required before replacing the historical feature count. This remains a bounded Temporal bridge, not a claim of the complete Temporal API or complete ECMA-402 conformance.

## Implemented behavior and deployment

`VmConfig::regex_timeout` defaults to 250 ms per compilation/match. Parser literal validation uses that same default independently of VM configuration; `ParseError.resource` preserves worker/deadline failures instead of mislabelling them SyntaxErrors. Startup has a separate two-second handshake bound. Parent serialization/deserialization and linear metadata scans are outside the regex algorithm deadline. The protocol limits each frame to 16 MiB, validates capture ranges, and preserves UTF-16. A worker caches one pattern per Rust thread, is killed/reaped after a failed transaction and restarts on demand. A worker IO thread only moves bytes; regex work runs exclusively in the child. Regex process memory and ICU/AST/bytecode/allocator storage are not a managed-heap/RSS guarantee.

Build and install `bluejs-regexp-worker` beside every executable embedding BlueJS, or set `BLUEJS_REGEXP_WORKER` to its trusted path. A missing helper fails closed. The standalone algorithm dependency remains regress 0.12.0. ICU4X Collator/Locale/CaseMap use bundled 2.3.0 data; serde 1.0.229 and serde_json 1.0.151 frame the subprocess protocol.

Collator supports sort/search usage, numeric ordering, caseFirst, sensitivity, ignorePunctuation, locale extension keys and supported collation tailorings. Intl.Locale has a private canonical locale slot, so CanonicalizeLocaleList does not invoke a replaced `toString`. Its constructor requires `new`, supports subclass-selected prototypes, validates and applies language/script/region/variants plus calendar/collation/hourCycle/caseFirst/numeric/numberingSystem/firstDayOfWeek options in specification order, and exposes the corresponding accessors, `toString`, `maximize` and `minimize`. Locale-info supplies `getCalendars`, `getCollations`, `getHourCycles`, `getNumberingSystems`, `getTextInfo`, `getTimeZones` and `getWeekInfo`; requested Unicode extensions take precedence and a small deterministic locale dataset supplies defaults. It is not a complete CLDR data provider. Locale negotiation uses the explicitly advertised language set in `src/intl.rs`, CLDR region/script fallback, and deterministic `en-US` default; best-fit currently uses the same matching policy as lookup. Casing validates every requested locale, uses the first one and preserves lone surrogates. Canonicalization rejects invalid language tags, underscores, duplicate variants and extensions before applying ICU aliases; it also supplies ECMA-402-visible `islamicc` → `islamic-civil` and `ethiopic-amete-alem` → `ethioaa` calendar aliases that ICU leaves to consumers. `Array`, `Array.isArray`, `Array.prototype.forEach`/`includes`, `Function.prototype` linkage, `Object.isExtensible` and the Math constants/functions provide the ordinary runtime surface exercised by Test262. Math covers `NaN`, signed-zero, integer-wrap, variadic and resource-exhaustion behavior. The sparse-array forEach path only fast-tracks large arrays and falls back when indexed prototype properties exist, preserving callback mutation semantics. Bound comparison identity, descriptors, constructor prototype lookup and GC cycles are tested. General global environment semantics remain a broader engine limitation.

The Test262 assertion host also required basic Error/TypeError/RangeError/SyntaxError/ReferenceError/EvalError/URIError constructors, Error.prototype.toString and cause properties. These are not a claim of complete Error builtins or exception/catch semantics. Host-installed names and typeof consult the existing global object; the later P0.2 slice adds a persistent classic-script lexical environment, while multiple realms and complete global-environment semantics remain absent.
