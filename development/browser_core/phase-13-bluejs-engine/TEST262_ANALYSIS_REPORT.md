## Reverse-membrane round-trip cache discards mutations (fixed 2026-09-23)

**Symptom (before the fix):** `staging/sm/TypedArray/slice-bitwise-same.js` (2 modes) constructs a species result through a *reverse* Test262 facade and observes the wrong element values (previously a panic, fixed in `7dce4ee`; then a clean value mismatch — every element read back as `0`).

**Exact mechanism, with code locations:**

1. `arr` is a child-realm TypedArray. Setting `arr.constructor = Float32Array` (the *parent's* own constructor) crosses that constructor value into the child as a live reverse facade (`Test262ReverseValue`, `vm.rs`), created by `test262_transport_value`'s general "else" branch (`foreign.rs`).
2. `arr.slice(0)` dispatches into the child (foreign receiver → `test262_foreign_typed_array_native_call`, `foreign.rs`). `%TypedArray%.prototype.slice`'s `SpeciesConstructor` step reads `arr.constructor` (the reverse facade), then `Get(constructor, Symbol.species)` — forwarded via `test262_reverse_get` (`reverse.rs`) into the *real* parent `Float32Array[Symbol.species]` accessor, which per spec returns `this`. Non-nullish, so the reverse facade itself is used as the species constructor (`typed_array_species_constructor`, `typed_arrays.rs`).
3. `typed_array_create_foreign_target` (`typed_arrays.rs`) recognizes this as cross-realm and calls `Construct` through it. `dispatch_call` (`vm.rs`) routes this to `test262_reverse_call` (`reverse.rs`), which resolves the live parent `Vm` via `resolve_active` and genuinely constructs a fresh, empty `Float32Array` **in the parent's own heap**.
4. `test262_reverse_call` exports that result back into the child via `test262_reverse_export_result` (`reverse.rs`) → `parent.test262_export_foreign_value(child_realm_id, &value)`. Since the value is a TypedArray, this takes `test262_transport_value`'s eager TypedArray-snapshot path (`foreign.rs`, the `typed_array_values` branch): it allocates a **brand-new, independent buffer in the child's own heap** and copies the (currently all-zero) source values into it — a genuine value snapshot, not a live view. This snapshot is registered in the parent's own `imported_values`/`imported_sources` maps (`Test262Realm`, `vm.rs`) as a round-trip stand-in for the real parent object.
5. Back in `typed_array_slice` (still executing as the child), the pre-fix code fell back to an ordinary per-element `typed_array_read_values`/`typed_array_write_values` copy into that local snapshot. Reading the snapshot back immediately after this write showed the correct values.
6. `typed_array_slice` returns; `test262_foreign_typed_array_native_call` calls `test262_import_foreign_result` → `test262_import_foreign_value` (`foreign.rs`) to bring the result back out to the parent. **This is where the data used to be lost.** Its very first check is a round-trip identity cache: `if let Some(value) = realm.imported_values.get(&target) { return Ok(value.value.clone()); }`. Because the constructed object was registered in `imported_values` during step 4 (as a stand-in for the *original, still-empty* parent object `test262_reverse_call` constructed), this check fires and returns that **original, pristine, never-mutated parent object** directly — completely bypassing whatever the local snapshot held.

**The fix:** bypass the round-trip cache entirely instead of working around it, for the one case that actually needs to observe a mutation through it — writing bytes into a freshly-`Construct`ed cross-realm TypedArray result. `Vm::test262_reverse_write_into_real_construction_result` (new, `vm/test262/reverse.rs`) resolves the live parent `Vm` via the same `resolve_active` reentrancy mechanism every other cross-realm call in this membrane already uses (sound here because the parent is still registered active — this call is nested inside `test262_foreign_typed_array_native_call`'s own `register_active` scope), looks up the *real* parent-owned object directly via `parent.test262_realms[child_realm_id].imported_values[local_result]` (the exact map the round-trip cache itself reads — read correctly here instead of fought), and writes bytes straight into that real object's buffer via `heap.array_buffer_write`. `typed_array_slice`'s `attempted_cross_realm_construction` branch (`typed_arrays.rs`) now calls this for the same-element-kind case, restoring the same bitwise, NaN-payload-preserving copy the same-realm and live-foreign-facade branches already used, and also still populates the local snapshot (for any caller that observes the result *before* it round-trips back out). The differing-element-kind sub-case is deliberately left on the older per-element `Get`/`Set`-into-snapshot fallback — not exercised by any known failing test, so not implemented speculatively.

**A second, independent bug found while verifying the first fix against the real corpus fixture (not just this crate's own hand-written regression):** `typed_array_create_foreign_target`'s classification of "is this species constructor cross-realm" checked `test262_foreign_native_function`/`test262_reverse_native_function` — i.e. does the constructor carry a `NativeFunction::TypedArray` tag. `sm/non262-TypedArray-shell.js`'s own `anyTypedArrayConstructors` list includes a **JS-defined subclass** of each native constructor (`class SharedTypedArray extends Object.getPrototypeOf(baseConstructor) { constructor(...) {...} }`), used as a species constructor exactly like the plain intrinsic. Such a subclass has no `NativeFunction` tag of its own, even when it *is* itself a reverse facade whose `[[Construct]]` genuinely crosses into the parent realm — so it was misclassified as "local", skipping the direct-write fix above entirely and falling into the ordinary same-realm bitwise-copy path, which correctly populates the local snapshot and then loses it to the exact same round-trip cache. Fixed by making the classification ask the more general and actually-relevant question — "is this constructor a facade at all" (`test262_foreign_reference(id).is_some() || test262_reverse_reference(id).is_some()`) — rather than "...specifically for a native TypedArray constructor"; the existing `actual.length < length` check below still rejects anything that isn't a valid TypedArray constructor, so broadening this is safe. `test262_reverse_native_function` (only ever used for this one classification) is now dead and was removed.

**Current state:** fixed and verified three ways: (1) `backend/bluejs/tests/test262_reverse_membrane.rs`'s `typed_array_species_slice_via_a_reverse_facade_constructor_preserves_nan_bit_patterns` (the plain-intrinsic case) and `typed_array_species_slice_via_a_reverse_facade_to_a_parent_owned_subclass_preserves_nan_bit_patterns` (the subclass case) both assert exact NaN bit-pattern fidelity, not just shape; (2) the real corpus fixture, `staging/sm/TypedArray/slice-bitwise-same.js`, passes both modes against a freshly rebuilt adapter binary; (3) a `--filter staging/sm/TypedArray` sweep of the full 101-file/195-mode TypedArray corpus subset (which exercises both bugs' harness, `sm/non262-TypedArray-shell.js`) passes in full, with no other regression.

## RegExp deviations fixed in the wrapper layer (fixed 2026-09-23)

The former "`regress` crate RegExp limitation" bucket (4 modes) was two independent deviations of the pinned `regress = "=0.12.0"`, neither of which needed a fork, a patch or a version bump. Both (and a third, related one found while verifying them, item 3) are corrected the same way `regex_escapes.rs` and `regex_group_names.rs` already correct others: by rewriting the pattern on its way into `regress`, inside `bluejs-regexp-worker` (the parent never runs `regress`, and `RegExp.prototype.source`, `flags` and the capture ranges are unaffected).

**1. `u`/`v` backreferences could end inside a surrogate pair** (`staging/sm/RegExp/unicode-back-reference.js`, 2 modes; `backend/bluejs/src/regex_backrefs.rs`). `regress` compares a backreference code unit by code unit, so `/foo(.+)bar\1/u` against `"foo\uD834bar\uD834\uDC00"` matched, the capture being a lone lead surrogate and the match ending between the halves of the pair that follows. The specified BackreferenceMatcher compares code points, so the result is `null`. Only one place can go wrong, a position with a lead surrogate right before it and a trail surrogate right after it, and every other atom leaves the matcher between code points, so each backreference `R` (`\N` and `\k<name>`, outside classes) is rewritten to `(?:GRG)` with `G = (?!(?<=[\u{d800}-\u{dbff}])[\u{dc00}-\u{dfff}])`. The guard is needed on both sides because a reference inside a lookbehind is matched backwards. Non-`u` patterns are untouched (there the subject really is a list of code units).

**2. Non-`u` `ignoreCase` used Unicode case folding instead of `Canonicalize`** (`staging/sm/RegExp/ignoreCase-non-latin1-to-latin1.js`, 2 modes; `backend/bluejs/src/regex_canonicalize.rs`). Without `u` the specification compares two code units through their upper case, except that a non-ASCII unit is never folded to an ASCII one and a unit whose upper case is several units is not folded. `regress` (a) expanded every literal to all units with the same upper case, ignoring the ASCII rule, so `/s/i` matched U+017F and `/i/i` matched U+0131 (its `TO_UPPERCASE` table has exactly two such entries, U+0131 and U+017F); (b) closed every character class under Unicode *simple case folding*, so `/[a-z]/i` and `/\w/i` matched U+017F and U+212A (Kelvin sign), `[^\W]` treated `s` as a non-word character, `[U+1E9E]` matched U+00DF and `[U+1FBC]` matched U+1FB3; and (c) folded backreferences through the upper case table alone. The fixture only reached (a); (b) and (c) are the same defect and were found while checking that the fix for (a) was complete (V8 disagrees with `regress` on all of them). Instead of patching each path, the comparison `Canonicalize(a) = Canonicalize(b)` is moved out of the matcher: a case-insensitive non-`u` pattern is rewritten to the case-sensitive pattern over canonical units (a literal becomes its canonical unit, a class becomes the canonical image of its members with its negation kept, `\d \s \w \b .` and the assertions are unchanged because `Canonicalize` is idempotent and keeps ASCII, non-ASCII, white space and line terminators apart) and matched, without `i`, against the subject mapped one unit to one unit through `Canonicalize` (upper case from Rust's `char::to_uppercase`, which is also what `String.prototype.toUpperCase` uses in this engine). The ranges of a match are therefore ranges of the original subject.

**3. The `v` flag was folded like a non-Unicode pattern** (found by the differential fuzz below; no Test262 fixture in this snapshot exercises it; `regex_worker.rs`, `regex_escapes.rs`). `regress` treats a pattern as Unicode for case folding only when it is given `u`; with `v` alone its literals and backreferences fold through the same upper case table as a non-Unicode pattern, so `/i/iv` matched U+0131, `/k/iv` did not match the Kelvin sign and `/[^\W]/iv` was not the extended word set. `v` implies everything `u` means, so the worker now hands `regress` `u` as well whenever the pattern has `v`, and the existing `\W`-in-a-class rewrite (written for `iu`) now covers `iv` too, with the replacement class wrapped as a class of its own (an operand of a set operation must be one) and with class nesting tracked. Verified by `backend/bluejs/tests/regexp_unicode_sets_ignore_case.rs` (checked against V8) and a fuzz of `u`/`v` patterns (7,500 patterns: 0 new mismatches, 16 fewer).

**Deliberately not rewritten** (these keep the previous matcher and its folding, which is exactly what they did before): patterns with a modifier group (`(?i:...)`, `(?-i:...)`), because they change the flag for part of a pattern while the subject can only be canonicalized as a whole; and syntax that is not valid or that the rewrite does not read (unterminated groups and classes, a reversed range, a trailing backslash, `\k` inside a class of a pattern with named groups), which `regress` then rejects or accepts exactly as before. A pattern without `i`, and every `u`/`v` pattern, is not rewritten for case folding.

**Verification.** The two fixtures pass in both modes. A complete unfiltered inventory (53,582 files / 102,926 modes, macOS, debug adapter) run once with the new `bluejs-regexp-worker` and once with the previous one (same adapter binary, since every behavior change lives in the worker) differs in exactly those 4 modes, `fail` -> `pass` (102,874 -> 102,878 passing, 47 -> 43 failing), and in nothing else; no RegExp-related fixture fails any more. `--filter staging/sm/RegExp,built-ins/RegExp,annexB` (3,077 files, 5,357 modes) went from 5,352 pass / 4 fail / 1 `stale_corpus` to 5,356 pass / 0 fail / 1 `stale_corpus`. New tests: `backend/bluejs/tests/regexp_legacy_ignore_case.rs` and `backend/bluejs/tests/regexp_unicode_backreference.rs` (every expectation also checked against V8 in Node), unit tests in `regex_canonicalize.rs`, `regex_backrefs.rs` and `regex_group_names.rs`. A differential fuzz of `exec` results against Node (patterns over an alphabet of U+017F, U+0131, U+212A, U+00DF, U+1E9E, U+00B5, Greek, U+1FB3/U+1FBC and lone surrogates, spelled raw, `\uXXXX`, `\xXX`, octal and as identity escapes, in classes, ranges, negations, groups, lookarounds and backreferences; 57,000 patterns x 3 subjects) found 0 result or validity mismatches attributable to this change; the same fuzz against the previous matcher found 17-19 mismatching cases per 1,500 patterns. A second fuzz aimed at backreferences over lone and paired surrogates (4,500 patterns x 4 subjects, `u`/`v`/`ug`/`uy`/`ui`) found 0 mismatches after the change and 16-30 per 1,500 patterns before it. What the fuzz did still find is unrelated to case folding and unchanged by this work: `regress` accepts a quantified `\b`/`\B` (V8 rejects it), a backreference from inside its own group matches differently, named groups of a lookbehind enumerate in a different order and (once) map `groups.n` to the wrong capture, and in `u` mode a match may start inside a pair when `lastIndex` points at its trail unit.

## Measurement limits

A passing result is the runner's observation, not proof of complete feature conformance. Unclassified parser rejections cannot establish required negative early errors. Existing adapter records may not distinguish a runtime exception in an include from one in the test body. Missing APIs, assertion mismatches and timeouts require reproduction before assigning a confirmed engine root cause. Staging, Annex B, Intl and host-dependent cases remain visible pending applicability audit.
