# Phase 12 — MCP Server (Standard AI Agent Integration)

[← Back to plan](../BROWSER_CORE_PLAN.md)

**Status**: Done — `backend/mcp-server` is a standard-stdio MCP adapter over BlueIce's real internal IPC. It exposes every safe, implemented external capability at this phase boundary, starts browser/download processes only when their first relevant tool needs them, and is exercised through rmcp's official stdio client against the compiled server.

## Objective

Expose BlueIce's capabilities — browsing/rendering (Phase 1/5's AI-facing API), downloads (Phase 10), file transfer (Phase 11), and whatever else applies — through a standard MCP server, so Claude Code or any other MCP-compatible AI agent can drive BlueIce using the standard protocol instead of a bespoke one.

## Foundation built early

Raised while Phase 5 was fresh, not while working through the numbered sequence: differential testing BlueIce's rendering against a real Chromium (via Puppeteer) needs a stable, external way to drive BlueIce *now*, not once Phases 6-11 are also done — waiting for this phase's original place in the sequence would have blocked that testing work for no good reason, since Phase 5's API was already real. `backend/mcp-server` (`blueice-mcp-server`) is that foundation: a real, working MCP server (stdio transport, via the official `rmcp` Rust SDK — reused rather than hand-rolling JSON-RPC framing, same "solved infrastructure" reasoning as `ureq`/`winit`/`fluent-bundle` elsewhere) exposing exactly Phase 5's API as tools, and nothing beyond it:

- `navigate(url)`, `get_page_representation()` — wrap `ClientMessage::Navigate`/`GetRepresentation` directly.
- `click(node_id)`, `type_text(node_id, text)`, `focus(node_id)`, `scroll_into_view(node_id)` — wrap `ActOn` with each `NodeAction` variant.
- `highlight(node_id)` — wraps `Highlight`.
- `screenshot()` — the one tool with no direct `ClientMessage` equivalent: reads the most recently cached `FrameReady`'s shared-memory frame and PNG-encodes it, since there's no "resend the current frame" message (every frame is the side effect of some state change).
- `get_dom()` — wraps `ClientMessage::GetDom`, added specifically for [Phase 15](../phase-15-chromium-differential-testing/PLAN.md)'s differential-testing harness (needs the *unfiltered* DOM, unlike `get_page_representation`'s AI-facing subset).
- `open_tab(url?)`, `close_tab(tab_id)`, `list_tabs()` — wrap [Phase 16](../phase-16-multi-tab-and-tab-groups/PLAN.md)'s `OpenTab`/`CloseTab`/`ListTabs`; every tool above also gained an optional `tab_id` parameter (`None` = the one default tab, unchanged behavior for a client that never opens a second one). No MCP-server-tracked "current tab" — same reasoning as `core` itself not tracking one (Phase 16's own doc): the calling LLM already has full context across tool calls, so it passes `tab_id` explicitly once more than one tab exists.

- `download_file(url, dest?, overwrite?)`, `list_transfers(state?)`, `get_transfer(id)`, `pause_transfer(id)`, `resume_transfer(id)`, `cancel_transfer(id)`, `remove_transfer(id)` — wrap [Phase 10](../phase-10-download-manager/PLAN.md)'s `blueice_ipc::downloads` protocol through one shared client (`backend/mcp-server/src/downloads.rs`), connected — and the downloads process started — only on first use. Every result opens with a plain-language summary and then the full transfer record (progress, speed, ETA, per-segment state, retries, the gatekeeper's decision, an event log), framed as untrusted data (`wrap_untrusted_transfer_content`). See Phase 10's "As built: the MCP tools."

**A real design problem solved along the way, not glossed over**: several `ClientMessage`s produce a *variable* number of replies (an `ActOn`/coordinate `Click` that doesn't land on a link produces none at all — `blueice_engine::session`'s own documented behavior). An MCP tool call needs a deterministic reply, and a read-timeout heuristic would be flaky. `ActOn` and `Highlight` immediately pipeline a `GetRepresentation` and read until its one deterministic reply appears, collecting any `Error` seen along the way rather than returning early. `Navigate` deliberately does **not** pipeline: an `http(s)` navigation's gatekeeper/fetch work is asynchronous, so it waits for its own `Navigated`, `GatekeeperBlocked`, or `Error` (and the success `FrameReady`) before asking for the representation. This prevents a tool response from describing the previous page, without leaving an unread reply for the next call to misinterpret. See `backend/mcp-server/src/lib.rs`'s module docs and `CoreConnection::send_and_drain`.

**Resolved scope at the Phase 12 boundary.** Phase 11 did not add a remote-files session API: its FTP/FTPS/SFTP capability is the download backend, so the existing `download_file` tool accepts those protocol URLs and the three credential-*removal* tools remove local keychain entries without accepting a secret. There is deliberately no `ftp_connect`/`sftp_connect`: a connect-only tool would invent an unauthorised remote-files capability and a secret-bearing MCP argument would break Phase 11's credential boundary. Phase 7's gatekeeper remains an internal mandatory enforcement point, not an agent-controllable policy override; Phase 9's extension host has no safe, real management API yet, so its placeholder is not exposed. `bluejs_run`/`bluejs_analyze` wait for Phase 13 to provide the internal script IPC they must adapt — Phase 12 creates no parallel shell channel merely to make a future tool name appear early.

**On-demand stdio lifecycle.** The MCP client starts `blueice-mcp-server` when it opens its stdio connection; EOF ends the one-client process, so a separate resident adapter/idle timer would be redundant and less reliable than the transport's ownership boundary. The binary now constructs only its tool router on startup. `initialize` and `tools/list` do not start `core`; the first browser-facing tool attaches to the launcher rendezvous or privately starts `core` on a blocking worker. `DownloadsHandle` retains the analogous first-download-tool behavior. `tests/rmcp_stdio_client.rs` proves this using rmcp's `TokioChildProcess`: an isolated server copy with no sibling `blueice-core` still completes initialization and tool discovery, while the normal compiled binary can navigate `about:credits` through the same official client.

## Design sketch

**Process design**: `backend/mcp-server/` as a thin adapter process — speaks MCP (JSON-RPC based, per the MCP spec) on one side, and BlueIce's own internal IPC protocol on the other. It translates incoming MCP `tools/call` requests into internal IPC requests against `core`/`downloads`/etc., and (where the MCP transport in use supports it) surfaces internal state changes back out as MCP notifications — it does not implement any browsing/download/transfer logic itself, only the translation. Being a stateless adapter, [`research/multi-process-memory.md`](../research/multi-process-memory.md) flags it as the clearest on-demand-spawn candidate in the whole process fleet — no reason for it to run at all when no MCP client is connected, unlike `core`/`ai-gatekeeper` which need to stay resident.

**Tool sketch** (signatures will firm up once the wrapped APIs are real, but the shape — one MCP tool per capability, thin pass-through to internal IPC — is reasonably stable regardless of exactly how Phase 5/10/11 end up looking in detail):

- `navigate(url)`
- `get_page_representation()` — wraps the Phase 1/5 AI-facing representation
- `click(node_id)` / `type(node_id, text)` — act on the stable DOM node IDs plan §1 already requires
- `download_file(url, dest)` / `list_transfers()` — wraps Phase 10
- `download_file(ftp://... | ftps://... | sftp://...)` — wraps Phase 11's download backends without inventing a remote-files session API; credential secrets remain stdin-only local CLI input
- `bluejs_run(code)` — wraps the Phase 13 `bluejs` shell's batch mode, so an MCP client can execute/test a JS snippet directly
- `bluejs_analyze(code)` — wraps Phase 13's AI-facing parse/analysis output (AST plus the capability summary the Phase 7 gatekeeper also consumes), so an MCP client can ask "what does this script do" without executing it

## Resolved questions

- ~~MCP should be an adapter, not a fourth protocol~~ — resolved: `backend/mcp-server` translates MCP calls only into `blueice-ipc` core/downloads exchanges; it owns no browsing, transfer, or prospective script implementation. This preserves the single-source-of-truth control plane shared with the frontend and launcher rather than growing a second browser API.
- ~~Which capabilities become MCP tools, and their shape~~ — resolved at Phase 12 close: browsing/multi-tab, the full Phase 10 manager, and Phase 11's protocol URLs are real and exposed; no remote-files session, secret-setting, safety-policy, or extension-management surface is invented where the wrapped subsystem lacks one.
- ~~Scope of "all of it"~~ — resolved: the adapter exposes externally actionable browsing and download/transfer capabilities. Phase 7 remains enforcement rather than a bypassable agent control, Phase 9 has no completed external management capability, and Phase 13 owns adding its tools after it has a real IPC boundary.

## Checklist

- [x] Confirm MCP is implemented as an adapter over the existing internal IPC protocol, not a parallel channel — `backend/mcp-server` wraps `blueice-ipc` exclusively, no browsing logic of its own
- [x] Design and build MCP tool definitions for the capabilities that are real today (Phase 5's API) — see "Foundation built early" above
- [x] Confirm which of Phase 7/9/10/11's capabilities are in scope beyond Phase 5 — Phase 10's manager and Phase 11's FTP/FTPS/SFTP *download* backends are exposed; Phase 7 is internal enforcement and Phase 9 lacks a complete safe management API, so neither receives a bypass/placeholder MCP tool
- [x] Extend the tool set for every landed, externally actionable capability — Phase 10's `download_file`/`list_transfers`/`get_transfer`/`pause_transfer`/`resume_transfer`/`cancel_transfer`/`remove_transfer`, and Phase 11 through protocol-aware `download_file` plus non-secret credential-removal tools. `bluejs_run`/`bluejs_analyze` remain Phase 13-owned work until that phase lands its internal script IPC, preserving the adapter-not-parallel-channel invariant
- [x] Connect to Phase 8's rendezvous socket first, falling back to a private `CoreProcess::spawn` only if nothing is listening there — the *shared-instance* half of this item (architecture-wide risk survey finding: today, `mcp-server` and `frontend` can never observe the same `core`/`Page` at all, the same dual-track split plan §1's core goal rejects). Built per `phase-8-live-core-hotswap/PLAN.md`'s "Minimal first slice": the first browser-facing MCP tool calls `CoreProcess::connect`, which tries the rendezvous before privately spawning. Existing tests (including the real-subprocess `tests/core_process.rs`) keep exercising the private-spawn fallback path unchanged, since none of them run a launcher alongside.
- [x] Make the stdio adapter on-demand — the MCP client owns the adapter process and EOF tears it down; server startup now builds only its router, the first browser tool lazily attaches/spawns `core`, and the first download tool lazily starts `downloads`. The official-client integration test proves discovery does not need a sibling core binary
- [x] Implement the `protocol_version` handshake Phase 1/5 deferred, once a genuinely independent client makes protocol drift a real risk — done, per `phase-8-live-core-hotswap/PLAN.md`'s minimal-slice checklist: `CoreConnection::handshake` (`blueice_ipc::client_handshake`), called from both `CoreProcess::spawn` and `connect_to`
- [x] Validate against an actual MCP client driving a real BlueIce instance end to end — `tests/rmcp_stdio_client.rs` uses the official `rmcp` Rust SDK's `TokioChildProcess` stdio client to initialize the compiled server, enumerate tools, and navigate `about:credits` through a real `blueice-core`; its isolated-binary companion proves discovery does not start a browser
- [x] Mark every tool result that carries page-derived content as untrusted data, not instructions, before it reaches the driving LLM — `blueice_mcp_server::wrap_untrusted_page_content` (a plain, tested string-formatting function in `lib.rs`, applied in `server.rs`'s `outcome_to_result`/`get_page_representation`/`get_dom`/`screenshot`/`open_tab`/`list_tabs` — every tool whose result can contain page-influenced text, tab URLs included), plus a matching warning in `get_info()`'s server `instructions`. This is a lighter-weight, present-day mitigation for the exact threat `phase-7-local-ai/PLAN.md`'s safety-gatekeeper design already names (hidden, instruction-shaped content aimed at an AI reader) — prompt-level framing, not a hard guarantee, and explicitly not a substitute for Phase 7's independent non-AI rule-base layer once that's built (see that phase's own doc). Raised by the user directly asking whether page content reaching an AI is safely treated as data, not something executable.
- [x] Expose Phase 16's multi-tab support (`open_tab`/`close_tab`/`list_tabs`, `tab_id` on every other tool) — see "Foundation built early" above and `phase-16-multi-tab-and-tab-groups/PLAN.md`'s own "MCP exposure" section. Raised directly by the user asking whether tab switching/full control was already wired up.
- [x] **`navigate` waits for page load.** The MCP adapter now waits for the request's `Navigated`, `GatekeeperBlocked`, or `Error`; on success it also drains the matching `FrameReady`, then requests the representation. A regression test recreates the old order (an immediately pipelined representation of generation 0 before navigation completes) and proves the tool returns the resulting generation instead.
- [x] **Relative link targets resolve against the current page URL.** `Page::click` and ID-based `ActOn { Click }` share RFC 3986 resolution through the standard `url` crate. If a page has no usable hierarchical base (a direct test fixture or built-in page), the raw target is retained and the normal navigation scheme validation reports any invalid target.
