# Layout / box-tree research

Findings from reading `reference/gecko/layout/` (Gecko's frame/reflow model) and `reference/chromium/third_party/blink/renderer/core/layout/` (Blink's LayoutNG), aimed at Phase 2's block/inline-flow scoping and the flexbox/grid in-or-out decision. Both checkouts are large (~475k / ~505k files repo-wide); this note is based on targeted reads of the layout subtrees named in the task, not an exhaustive survey.

## 1. Gecko's layout architecture

Gecko keeps a **separate box tree from the DOM**, called the frame tree, built and kept in sync by a dedicated frame constructor — but unlike Blink's LayoutNG, the frame tree is not a clean value-type output of a pure function; frames are long-lived, mutable, stateful objects that layout (reflow) writes into in place.

- `layout/base/nsCSSFrameConstructor.h` / `.cpp` — the frame constructor. Its own file comment states the job precisely: "construction of a frame tree that is nearly isomorphic to the content tree and updating of that tree in response to dynamic changes." Key entry points found in the header: `ConstructBlock`, `ConstructInline`, `ConstructTable`/`ConstructTableRowOrRowGroup`/`ConstructTableCell`, `ConstructFieldSetFrame`, `ConstructOuterSVG`, plus generic machinery (`AddFrameConstructionItems`, `ConstructFramesFromItemList`, `ProcessChildren`). Construction is driven by a big `FrameConstructionItem`/`nsFrameConstructorState`-based dispatch keyed off the `display` value and element type — structurally the same idea as Blink's per-node algorithm dispatch (§3 below), just at box-tree-construction time rather than layout time.
  - "Nearly isomorphic," not identical: `CreateNeededPseudoContainers` and `CreateNeededAnonFlexOrGridItems` insert anonymous frames (e.g. for CSS table pseudo-structure, or for text/inline content that ends up an implicit flex/grid item) where the DOM tree alone doesn't map 1:1 to boxes. This anonymous-box concept recurs in Blink too (see §2).
- `layout/generic/nsIFrame.h` — the base box type. `class nsIFrame : public nsQueryFrame` (line 690) carries `nsCOMPtr<nsIContent> mContent` (line 5291) and `nsIContent* GetContent() const` (line 879) as the direct, explicit link from box back to DOM content node. Frame ↔ content is a many-to-one-or-more relationship in general (continuations for fragmented content, `IsPrimaryFrame()` distinguishes the frame considered canonical for a given `mContent`).
- Reflow is **virtual dispatch per frame class**, not one shared algorithm: `virtual void Reflow(nsPresContext* aPresContext, ReflowOutput& aReflowOutput, const ReflowInput& aReflowInput, nsReflowStatus& aStatus)` declared on `nsIFrame` (nsIFrame.h:3199) and overridden by every concrete frame type — `nsBlockFrame::Reflow` (nsBlockFrame.cpp:1561), `nsFlexContainerFrame::Reflow` (nsFlexContainerFrame.cpp:4672), `nsGridContainerFrame::Reflow` (nsGridContainerFrame.cpp:9433), etc. `ReflowInput`/`ReflowOutput` (`layout/generic/ReflowInput.{h,cc}`, `ReflowOutput.{h,cc}`) are the input-constraints/output-metrics structs threaded through every call, analogous in role to Blink's `ConstraintSpace`/fragment.
- Top-level reflow driver lives in `layout/base/PresShell.cpp`: `PresShell::Initialize()` (line 1654) triggers the first reflow, `PresShell::DoReflow(nsIFrame* target, bool aInterruptible, ...)` (line 10730) reflows a subtree rooted at a dirty frame, and `PresShell::ProcessReflowCommands(bool aInterruptible)` (line 10929) drains the queue of frames marked dirty, calling `DoReflow` per target. So the overall shape is: DOM mutation → frame(s) marked dirty → `ProcessReflowCommands` walks dirty frames top-down → each frame's own `Reflow()` override does its algorithm and recurses into children's `Reflow()`.
- Block/inline flow specifically lives in `nsBlockFrame` (`layout/generic/nsBlockFrame.{h,cc}`, `BlockReflowState.{h,cc}`) plus `nsLineBox`/`nsLineLayout`/`nsInlineFrame` (`layout/generic/nsLineBox.{h,cc}`, `nsLineLayout.{h,cc}`, `nsInlineFrame.{h,cc}`). `nsBlockFrame` groups inline-level children into `nsLineBox` line objects; per-line reflow methods `ReflowLine`, `ReflowBlockFrame` (nsBlockFrame.cpp:4429), `ReflowInlineFrames`/`ReflowInlineFrame` (nsBlockFrame.cpp:5490) handle the two cases (a block-level child vs. an inline run needing line-breaking) inside the *same* frame class and the *same* Reflow call chain — block and inline flow are not separated into distinct pluggable algorithms in Gecko the way flex/grid are (see §3).

## 2. Blink's LayoutNG architecture

**The legacy pre-NG layout system is effectively gone from this checkout.** There is no `layout/ng/` subdirectory — `third_party/blink/renderer/core/layout/` *is* LayoutNG now; algorithm files (`block_layout_algorithm.cc`, `constraint_space.h`, etc.) live directly at that top level, and box-type classes have dropped the historical `LayoutNG` prefix entirely (e.g. `class CORE_EXPORT LayoutBlockFlow : public LayoutBlock` in `layout_block_flow.h:62`, not `LayoutNGBlockFlow`). `grep` for `LayoutNGBlockFlow` / `RuntimeEnabledFeatures::LayoutNG` / `kLegacyLayout` across the directory returns nothing. The only surviving traces of "legacy" are a handful of stale code comments/TODOs (`layout_text.cc:455` "Remove this branch when legacy layout is removed", `physical_box_fragment.h:356` "delegate to legacy layout for now") — i.e. cleanup debt, not a live parallel system. `layout/layout_ng.md` itself is Blink's own design doc for this and is still the canonical description of the architecture (`See [LayoutNG](layout_ng.md) for the implementation details`, referenced from `layout/README.md:16`).

- **Box tree is explicitly decoupled from the DOM**, more cleanly than Gecko's frame tree, via three distinct layers documented in `layout/layout_ng.md` and `layout/inline/README.md`:
  1. `LayoutObject`/`LayoutBox` (`layout_object.h`, `layout_box.h`) — the persistent, DOM-linked box object. `LayoutObject` holds `Member<Node> node_` (layout_object.h:4113) and exposes it via `Node* GetNode() const` (layout_object.h:1741). This is the rough analog of Gecko's `nsIFrame`/`mContent`, and it is where the *persistent* box tree still lives (long-lived, mutated across relayouts, one object per element/pseudo-box, similar to Gecko's isomorphism story).
  2. `LayoutInputNode` (`layout_input_node.h`) — a lightweight, per-layout-call wrapper around a `LayoutBox*`, typed as `kBlock` or `kInline` (`BlockNode`/`InlineNode`, defined in `block_node.h`/`inline/inline_node.h`). Doc comment: "Represents the input to a layout algorithm for a given node. The layout engine should use the style, node type to determine which type of layout algorithm to use to produce fragments for this node." This is the "same tuple for every kind of layout" input described in `layout_ng.md`: a `BlockNode` (or `InlineNode`) + a `ConstraintSpace` (`constraint_space.h`) + break tokens.
  3. `PhysicalFragment`/`LayoutResult` (`physical_fragment.h`, `layout_result.h`) — the **output** box tree: immutable, physical (post writing-mode-resolution), cacheable fragments produced fresh by each layout pass and assembled via `BoxFragmentBuilder` (`box_fragment_builder.h`). `layout_ng.md` is explicit that paint/hit-test walk this fragment tree, *not* the `LayoutObject` tree, specifically because block fragmentation (multicol, printing) can split one `LayoutObject` into several fragments with no 1:1 correspondence, and some fragments (fragmentainers/columns) have no backing `LayoutObject` at all.
  - `layout/inline/README.md` gives a concrete worked example of all three layers for `<div><span>Hello</span></div>`: DOM → `LayoutInputNode` tree (`BlockNode` → `InlineNode` containing `InlineItem`s for open-tag/text/close-tag) → fragment tree (`PhysicalBoxFragment` → anonymous wrapper → `PhysicalLineBoxFragment` → `PhysicalBoxFragment` for the span → text fragment). This anonymous-wrapper-box pattern is the same idea as Gecko's `CreateNeededPseudoContainers`/`CreateNeededAnonFlexOrGridItems` (§1) — both engines need synthetic boxes with no DOM counterpart to make the tree structurally regular for the algorithm.
- **The algorithm itself is a common template interface with per-display-type subclasses, selected by an explicit dispatch function** — not virtual method dispatch on the box like Gecko's `nsIFrame::Reflow`, but a compile-time template + runtime `if`-chain. `layout_algorithm.h` defines `template <typename InputNodeType, typename BoxFragmentBuilderType, typename BreakTokenType> class LayoutAlgorithm`, documented as requiring every concrete algorithm to implement `MinMaxSizesResult ComputeMinMaxSizes(...)` and `const LayoutResult* Layout()`. The dispatch is `DetermineAlgorithmAndRun()` in `block_node.cc` (~line 156), which inspects the `LayoutBox` and picks one of: `FlexLayoutAlgorithm`, `TableLayoutAlgorithm`/`TableRowLayoutAlgorithm`/`TableSectionLayoutAlgorithm`, `CustomLayoutAlgorithm`, a family of `Math*LayoutAlgorithm`s (dispatched further by `DetermineMathMLAlgorithmAndRun`), `GridLayoutAlgorithm`, `GridLanesLayoutAlgorithm`, `ReplacedLayoutAlgorithm`, `FieldsetLayoutAlgorithm`, `FrameSetLayoutAlgorithm`, `ColumnLayoutAlgorithm` (multicol), `PaginatedRootLayoutAlgorithm`, falling through to `BlockLayoutAlgorithm` (`layout/block_layout_algorithm.{h,cc}`) as the default/base case.
- Block flow's own algorithm is documented in `layout/block_layout.md` (BFC offsets, float positioning via an `ExclusionSpace`, and margin collapsing implemented by "inverting" the naive approach — a fragment produces only an *end* margin strut, with the *start* strut and a BFC-offset estimate passed in as layout inputs, to avoid a layout/positioning circular dependency). Inline content within a block is represented as an `InlineNode` child and is *not* routed through the generic `DetermineAlgorithmAndRun` dispatch; `BlockLayoutAlgorithm::LayoutInlineChild(const InlineNode&)` (`block_layout_algorithm.h:175`) calls directly into `layout/inline/inline_layout_algorithm.{h,cc}`. Comment at `block_layout_algorithm.cc:485`: "we can handle `InlineNode` almost the same as `BlockNode`, because an `InlineNode` includes [an implicit anonymous block wrapper]." So block and inline are two distinct algorithm classes, but wired together with a direct call rather than going through the same generic dispatch flex/grid/table use.

## 3. Flexbox/grid integration: separable module, in both engines

Both engines keep flexbox and grid as **structurally separate algorithms from base block/inline flow**, invoked once per box rather than woven line-by-line into the block/inline algorithm — but the separation is achieved differently, and inline layout is *more* entangled with block layout than flex/grid are with either.

- **Gecko**: `nsFlexContainerFrame` and `nsGridContainerFrame` (`layout/generic/nsFlexContainerFrame.{h,cc}`, `nsGridContainerFrame.{h,cc}`) are their own frame classes — `class nsFlexContainerFrame final : public nsContainerFrame, ...` and `class nsGridContainerFrame final : public nsContainerFrame, ...` (both derive from `nsContainerFrame`, a peer of `nsBlockFrame`, **not** a subclass of it). Each overrides `Reflow()` independently: `nsFlexContainerFrame::Reflow` (nsFlexContainerFrame.cpp:4672) calls its own `DoFlexLayout()` (nsFlexContainerFrame.cpp:5345), operating on its own `FlexLine`/`FlexItem` data structures built by `GenerateFlexItemForChild()` — none of `nsBlockFrame`'s `nsLineBox`/`ReflowLine`/`ReflowInlineFrames` machinery is touched. `nsGridContainerFrame::Reflow` (nsGridContainerFrame.cpp:9433) is likewise self-contained. The only coupling point is at frame-*construction* time: `nsCSSFrameConstructor::NeedsAnonFlexOrGridItem`/`CreateNeededAnonFlexOrGridItems` wrap non-conforming children (e.g. bare text) in anonymous block boxes so the flex/grid frame always sees frame-shaped children — a tree-shape fixup, not a layout-algorithm dependency.
- **Blink**: `FlexLayoutAlgorithm` (`layout/flex/flex_layout_algorithm.h:22`) and `GridLayoutAlgorithm` (`layout/grid/grid_layout_algorithm.h:23`) both explicitly instantiate the same `LayoutAlgorithm<...>` template block layout uses — `class FlexLayoutAlgorithm : public LayoutAlgorithm<BlockNode, BoxFragmentBuilder, BlockBreakToken>` and `class GridLayoutAlgorithm : public LayoutAlgorithm<GridNode, BoxFragmentBuilder, BlockBreakToken>`. They are selected in the same `if`-chain as `BlockLayoutAlgorithm` in `DetermineAlgorithmAndRun()` (§2) — structurally peers, not special cases of block layout, each with its own subdirectory (`layout/flex/`, `layout/grid/`) and private data types (`FlexLine`/`FlexItem` in `flex_item.h`/`flex_line.h`; `GridSizingTree`/`GridTrackCollection`/`GridPlacement` in `grid_sizing_tree.h`/`grid_track_collection.h`/`grid_placement.h`). Nothing in `block_layout_algorithm.cc` calls into flex or grid code, and nothing in flex/grid code calls back into `BlockLayoutAlgorithm` for its core sizing loop — they consume the same `ConstraintSpace`/`BoxFragmentBuilder`/`LayoutResult` plumbing but run an independent algorithm.
- Contrast with **inline layout**, which in both engines is *not* this cleanly separable: Gecko's `nsBlockFrame` directly owns line-breaking (`ReflowInlineFrames`) as part of its own class, and Blink's `BlockLayoutAlgorithm` directly calls `LayoutInlineChild()` → `InlineLayoutAlgorithm` as an intrinsic part of laying out a block container with inline-level children (§2) — block flow cannot be implemented, even minimally, without also implementing at least a basic version of inline flow, whereas it demonstrably *can* be implemented (in both real engines) without flexbox or grid.
- Net signal for Phase 2: flexbox and grid are legitimately excludable as later, additive algorithm modules — real engines treat them that way at the architecture level, selected by a per-box dispatch keyed on `display`, sharing only the constraint/fragment plumbing with block/inline flow. Block and inline flow, by contrast, are not separable from each other; any "minimal but real" layout stage needs both together.

## 4. Assessment and recommendation for BlueIce

**Prefer a LayoutNG-shaped design (box tree as a distinct, DOM-linked-but-separate value produced by layout) over Gecko's frame model, for a from-scratch Rust engine specifically.** Reasoning, not just "newer is better":

- Gecko's `nsIFrame` tree is a large graph of mutable, long-lived, cyclically-linked objects (parent/sibling/continuation pointers, `mContent` back-references, frame properties tables) mutated in place across reflows. That shape fights Rust's ownership model directly — it's the classic "graph of mutable nodes with back-pointers" problem that typically forces `Rc<RefCell<..>>`/arena+index patterns and loses most of the benefit of Rust's aliasing guarantees. It's also why Gecko needs a whole separate arena allocator (`ArenaObjectID.h`, `StackArena.{h,cc}`) and careful dirty-bit bookkeeping (`NeedsLayout()`-equivalent flags) to avoid stale/inconsistent state — complexity that exists to manage mutation, not to solve layout.
- LayoutNG's split — persistent `LayoutObject` (DOM-linked, one per element) producing immutable `PhysicalFragment`/`LayoutResult` trees (freshly built value trees, cached and diffed rather than mutated) — maps far more naturally onto Rust: the fragment tree can be an ordinary owned tree of `enum`/`struct` values (e.g. `Vec<Fragment>` children), rebuilt or incrementally rebuilt per layout pass, with no back-pointers required for layout itself (paint/hit-testing can carry a separate index or generation-based ID back to the originating DOM node, matching the plan's existing "every DOM node has a stable explicit ID" requirement in `BROWSER_CORE_PLAN.md` §1 — fragments can simply carry that ID rather than a live reference).
- Concretely for BlueIce: define a `LayoutBox` (persistent, one per styled DOM node, holds `ComputedStyle` + that stable node ID — Gecko/Blink's `LayoutObject`/`nsIFrame` role) and a separate `Fragment` tree type (the actual positioned/sized output — Blink's `PhysicalFragment` role) produced by a `layout(box: &LayoutBox, constraints: Constraints) -> Fragment` pass. Keep the `Fragment` tree a plain owned value tree (no `Rc`/`RefCell` needed inside it) rebuilt each layout pass; that alone sidesteps the biggest structural pain LayoutNG's design was created to fix in Blink (the old `LayoutObject`-tree-doubles-as-paint-tree entanglement Blink also used to have and moved away from, per `layout_ng.md`'s point about fragmentation needing a fragment tree distinct from the `LayoutObject` tree).

**Simplest correct starting algorithm for block/inline flow (Phase 3), sized to not need a rewrite when flex/grid are added:**

- Scope block/inline flow as its own `display: block` / `display: inline` / anonymous-block-wrapping-inline-runs algorithm, modeled on the shape in `layout/block_layout.md` and the `LayoutInputNode` example in `layout/inline/README.md` — not on Gecko's `nsBlockFrame`'s combined block+float+multicol+column-span machinery, which is far more than an MVP needs. Concretely:
  - A single-pass, top-down, single-constraint-space walk: given an available inline size, lay out block-level children stacked in the block direction, and for runs of inline-level children, do simple line-breaking (greedy fill-then-wrap) producing line boxes — this alone (no BFC offset bubbling, no float exclusion space, no margin-strut inversion trick) is enough to get real pages rendering close to correctly for the non-float, non-multicol case, and is exactly what `layout/block_layout.md`'s "naïve algorithm" section describes before explaining *why* real engines complicate it (floats + margin collapsing interacting with float positioning). Floats and full CSS2 margin collapsing can be named explicitly out-of-scope for the MVP without threatening the basic architecture — they're refinements *within* the block algorithm, not a different algorithm.
  - Follow LayoutNG's `LayoutInputNode` split even at this minimal stage: a `BlockNode`/`InlineNode`-equivalent distinction (as in `layout_input_node.h`'s `enum LayoutInputNodeType { kBlock, kInline }`) is cheap to add now and is exactly the seam flexbox/grid plug into later — Blink's own `DetermineAlgorithmAndRun()` dispatch (§2/§3) is a straightforward `match` on the box's `display` value that BlueIce can start with a single `Block` arm and grow additional arms (`Flex`, `Grid`, `Table`, ...) into, with zero changes to the block/inline arm itself. That is the concrete mechanism by which "won't need a full rewrite" is satisfied: the dispatch function is the extension point, not the block algorithm's internals.
  - Keep the constraint/output types generic from day one even though only block/inline exist initially — an equivalent of `ConstraintSpace` (available inline/block size, writing mode if in scope, containing-block info) in and a `Fragment` (size + child fragments + offsets) out, matching the "same tuple for every kind of layout" input contract `layout_ng.md` calls out explicitly as the thing that made adding flex/grid/table/multicol *not* require touching the block algorithm. This is the single highest-leverage architectural decision from either reference codebase for Phase 3: algorithms differ, the interface between them and their caller does not.
- **Flexbox/grid: explicitly out of Phase 2/3 MVP scope**, deferred to a later phase as an additive algorithm module behind the same dispatch, per §3's evidence that both production engines already treat them this way rather than as extensions of block/inline flow. Given the "AI browsing real websites" goal in `BROWSER_CORE_PLAN.md` §1, flexbox in particular is common enough on real sites that it should be the *next* thing added after block/inline flow is solid, ahead of grid (grid is comparatively rarer on the open web and, per `layout/grid/` file count and `grid_sizing_tree.h`/`grid_track_sizing_algorithm.cc` complexity, meaningfully more algorithmically involved than flex) — but neither belongs in the initial MVP pass if the goal is a minimal-but-real block/inline layout stage first.
