# Extension capability/permission models, execution architecture, and manifest formats in Chromium and Gecko

Findings from reading `../reference/chromium` (Chromium's Manifest V3 extension system, mainly under `extensions/` and `chrome/common/extensions/`) and `../reference/gecko` (Firefox's WebExtensions, mainly under `toolkit/components/extensions/` and `browser/components/extensions/`) directly, aimed at BlueIce's Phase 9 open questions: the extension capability list, the manifest/permission model (install-time vs. runtime), the implementation format (native vs. WASM), and versioning. BlueIce has already settled that extensions run in their own OS process rather than in-process — neither reference browser does that (both run extension code inside a renderer/child process under their own separate sandboxing), so the exact isolation mechanism isn't directly portable, but the *capability catalog*, the *permission-grant lifecycle*, and the *manifest schema shape* are all reusable prior art regardless of the process topology underneath them.

## 1. Chromium's Manifest V3 capability/permission model

`extensions/docs/permissions.md` is Chromium's own internal design doc and is the clearest primary source: it defines three permission classes — **API permissions** (reserved strings like `tabs`, `cookies`, `storage` that gate access to a JS API), **match patterns** (URL patterns, split into *explicit hosts* declared in the manifest's `permissions`/`host_permissions` key, which gate APIs like `cookies`/`webRequest`/`tabs.executeScript`, vs. *scriptable hosts* declared in `content_scripts[].matches`, which only gate content-script injection — the doc notes both are messaged to the user identically as "read and change your data on `<site>`"), and **manifest permissions** (a manifest key itself grants a capability, e.g. `externally_connectable`, page overrides, `bluetooth` device access — the doc says these are treated as equivalent to API permissions for the rest of the design).

The actual API-permission catalog is not one flat list but two layered tables: `extensions/common/permissions/extensions_api_permissions.cc` (`extensions::api_permissions::GetPermissionInfos()`) registers 74 embedder-agnostic permissions keyed by the `extensions::mojom::APIPermissionID` enum — e.g. `kActiveTab→"activeTab"`, `kAlarms→"alarms"`, `kClipboardRead`/`kClipboardWrite`, `kNativeMessaging`, `kSerial`, `kUsb`, `kHid`, `kSocket`, `kProxy`, `kWebRequest`, `kWebRequestBlocking`, `kDeclarativeNetRequest`, `kWebView`, `kStorage`, `kUnlimitedStorage` — while `chrome/common/extensions/permissions/chrome_api_permissions.cc` registers a second, Chrome-product-specific layer of 102 more, including the ones most extension authors actually reach for: `tabs`, `cookies`, `history`, `bookmarks`, `downloads`, `geolocation`, `contextMenus`, `identity`, `fontSettings`, `gcm`, plus a long tail of ChromeOS-only and Chrome-internal `*Private` permissions (`autotestPrivate`, `chromeosInfoPrivate`, `glicPrivate`, etc.). This two-layer split (`//extensions` = reusable base for any Chromium-derived embedder, `//chrome` = product-specific additions) is itself a useful architectural precedent: BlueIce's capability catalog could similarly separate a small core set core `core` always understands from a product-specific extension.

Each permission's `APIPermissionInfo::InitInfo` entry carries bitflags that shape UX/enforcement, not just an on/off bit: `kFlagCannotBeOptional` (must be a required, not optional, permission — e.g. `proxy`, `devtools`, `webview`), `kFlagImpliesFullURLAccess` (`devtools`, `proxy`), `kFlagInternal` (never user-facing, e.g. `devtools`, `newTabPageOverride`), `kFlagRequiresManagementUIWarning`, `kFlagSupportsContentCapabilities`, and `kFlagDoesNotRequireManagedSessionFullLoginWarning`. This flag system is how Chromium gets fine warning-string and install-flow behavior out of a single permission table instead of hand-coding special cases per permission.

Permission *storage and lifecycle* (`extensions/docs/permissions.md` §"Storing Permissions" onward) keeps three separate persisted sets per extension: **granted permissions** (the maximum ever approved by the user, monotonically grows, only shrinks on explicit revoke), **active permissions** (what the extension currently has, computed as `intersection(active, union(required, optional))`), and — with the runtime host permissions feature — **runtime-granted permissions**, a third set specifically for host access the user grants through UI (context menu / `chrome://extensions` controls) or through `chrome.permissions.request()`. With runtime host permissions on, current permissions become `intersection(current_without_feature, runtime_granted)`, and the doc explains a real corner case worth stealing: when a user grants a *broader* host pattern than the extension actually requested (e.g. extension asks for `https://google.com/maps`, user grants `https://*.google.com/*` via the generic "on this site"/"on all sites" UI), Chromium computes the **intersection** of the two patterns rather than either endpoint, so the extension object never ends up privileged beyond what it explicitly asked for even though the user's grant was broader.

`activeTab` is documented as Chromium's one *non-persistent* permission (`extensions/docs/permissions.md` §"Non-Persistent Permissions"): it's never stored, grants temporary access to the current tab only after a user gesture (invoking the extension's toolbar action), and covers `tabs.executeScript`, `webRequest`, tab URL/favicon via `tabs`, and `tabs.captureTab` — access is revoked as soon as the user navigates or closes the tab. This is Chromium's answer to "runtime-granted, not declared upfront" for the single most common case (an extension that only needs to act on the page the user is currently looking at), and it predates the more general runtime-host-permissions system described above.

Manifest schema shape: `manifest_version` is an integer, currently 2 or 3 (`extensions/common/extension.cc:60-61`, `kMinimumSupportedManifestVersion = 2`, `kMaximumSupportedManifestVersion = 3`). MV3 splits what MV2 combined: `manifest_constants.h` defines separate top-level keys `kPermissions = "permissions"` (API permission strings), `kHostPermissions = "host_permissions"` (URL match patterns, required), `kOptionalPermissions`/`kOptionalHostPermissions` (requestable at runtime via `chrome.permissions.request()`, never auto-granted so they never trigger a disable-on-update). A real MV3 manifest found at `chrome/test/data/extensions/blocked_actions/optional_host_permissions/manifest.json`:
```
{
  "name": "Optional Host Permissions with site access changes",
  "manifest_version": 3,
  "version": "0.1",
  "permissions": ["scripting", "webNavigation", "tabs"],
  "optional_host_permissions": ["<all_urls>"],
  "background": { "service_worker": "background.js" }
}
```
and `extensions/test/data/api_test/messaging/stress_test/manifest.json` shows the `content_scripts`/`web_accessible_resources` shape alongside it (`"matches": ["<all_urls>"]`, `"run_at": "document_idle"`). Extension identity is *not* a manifest field the author freely picks: `extensions/common/extension.cc:159-179` derives the extension ID via `crx_file::id_util::GenerateId(public_key_bytes)` from the manifest's `key` (public key) field when present, or `GenerateIdForPath(path)` (hash of install path) for unpacked/keyless extensions — the ID is a derived hash, not a declared string.

## 2. Why Chromium moved from Manifest V2 persistent background pages to V3 service workers

The single best primary source is `extensions/browser/extension_service_workers.md`, an internal design doc, which states the change plainly: "Up until Manifest V2, there were two types of extension background pages, persistent background pages and non-persistent background pages. As part of Manifest V3, we are migrating extensions from the persistent/non-persistent background pages to service workers... an event-driven JavaScript program that runs in a worker thread." So the framing inside Chromium itself is explicitly a *migration*, not a green-field design — MV2 already had a "non-persistent background page" (a page-based approximation of on-demand execution, unloaded when idle and reloaded on the next event), and MV3's service worker is positioned as replacing both the always-resident MV2 persistent page *and* that already-imperfect non-persistent approximation with the browser's own general-purpose Worker-based lifecycle primitive rather than a bespoke page-unload/reload scheme.

The MV2→MV3 manifest-level change is a genuine structural constraint, not just a recommendation: `extensions/common/manifest_handlers/background_info.h`/`.cc` shows `background.service_worker` and `background.persistent` are mutually exclusive paths through the same parser (`is_persistent_` defaults to `true` and is only meaningful for the `background.page`/`background.scripts` form — `LoadBackgroundPersistent` is the MV2 knob; MV3's only background form is `background.service_worker`, with an optional `background.type: "classic" | "module"` for ES-module support, defaulting to classic). There is no way to declare a persistent background page under MV3 in this schema at all — the "opt out of the lifecycle" escape hatch MV2 offered (`"persistent": true`) is gone by construction, not just discouraged.

`background_info.cc` also captures a load-bearing detail about *why* the non-persistent model was already straining under MV2, independent of MV3: `BackgroundManifestHandler::Parse` explicitly rejects the combination of a lazy (non-persistent) background page with the blocking `webRequest` API (`errors::kWebRequestConflictsWithLazyBackground` — "Lazy background pages are incompatible with the webRequest API"). A background context that can be unloaded mid-flight is fundamentally hard to reconcile with an API contract that requires synchronously blocking every matching network request on a handler in that same context. This is the direct root cause visible in the source for MV3's headline API change: `extensions/browser/api/declarative_net_request/README.md` documents `declarativeNetRequest` as a *declarative* replacement — the extension ships JSON rules, and the browser itself parses, indexes them into a flatbuffer (`extension_ruleset.fbs`) via `url_pattern_index`, and evaluates them against every request, with the extension's own code never in the synchronous request path at all. The README explicitly cites the security rationale for doing the JSON→structured-rule parsing outside the browser's own privileged process: "reading untrustworthy JSON using C++ in a privileged process like the browser is dangerous as per the [Rule of 2]... we do this either in the renderer... or in a sandboxed process." In other words, moving network-rule evaluation out of live extension JS solves the lazy-background/webRequest conflict *and* removes a class of privileged-process attack surface in the same move — the service-worker lifecycle change and the declarativeNetRequest API change are two faces of the same underlying decision to stop giving extension background code an assumed-always-resident, synchronously-blocking hook into the browser's own request pipeline.

Once background code genuinely lives in a worker that the content layer can start and stop on its own schedule, `extension_service_workers.md` documents the mechanics Chromium had to build to make "non-persistent" not mean "unreliable": registration goes through `ServiceWorkerTaskQueue::ActivateExtension → ServiceWorkerContext::RegisterServiceWorker`, and — critically — the extensions layer does **not** trust worker-alive notifications to infer liveness; instead `ServiceWorkerTaskQueue` calls `StartWorkerForScope` immediately before *every* dispatch regardless of believed running state, because `OnVersionStoppedRunning` only fires after the worker thread has actually terminated and can't be used predictively. Liveness across a single event dispatch is guaranteed with an explicit begin/end pair — `ServiceWorkerContext::StartingExternalRequest()` before dispatch, `FinishedExternalRequest()` after the renderer's `EventAck` IPC comes back — so the worker is guaranteed alive strictly for the duration of in-flight work, not for any longer. `extensions/browser/service_worker/service_worker_keepalive.cc` implements the actual keepalive token bookkeeping this relies on. This "start on demand, extend liveness only for the duration of an acknowledged unit of work, never trust an idle/stopped signal predictively" pattern is the concrete lesson for BlueIce if it adopts a non-persistent, event-triggered extension execution model: the hard part isn't launching the process on the first event, it's guaranteeing the process isn't torn down *between* dispatching a request to it and receiving that request's acknowledgment.

Chromium is also unambiguous that MV2 is being retired, not just deprecated indefinitely: `manifest_constants.h` defines `kManifestV2IsDeprecatedWarning = "Manifest version 2 is deprecated, and support will be removed in 2025..."`, surfaced by `extension.cc`'s `IsManifestSupported()` specifically for unpacked MV2 extensions.

## 3. Firefox's WebExtensions capability/permission model

Firefox's manifest schema is a literal, machine-readable JSON-Schema-like definition at `toolkit/components/extensions/schemas/manifest.json` (897 lines) — and tellingly, the `schemas/` directory ships a `LICENSE-CHROMIUM` file, confirming this schema-description format (and a large fraction of the API surface it describes) was adopted directly from Chromium's own extension-API schema tooling rather than independently invented; the two ecosystems are convergent by explicit design, not by coincidence. `ManifestBase.manifest_version` is `{"type": "integer", "minimum": 2, "maximum": 3}` (`manifest.json:11-15`), identical bounds to Chromium's `kMinimumSupportedManifestVersion`/`kMaximumSupportedManifestVersion`.

Permission taxonomy (`manifest.json:487-598`) is a set of nested string-enum types: `PermissionNoPrompt` = `{"idle"} ∪ {"mozillaAddons" (PermissionPrivileged)} ∪ {"alarms","storage","unlimitedStorage"}` (permissions granted silently, no install-time warning); `OptionalPermission` = `PermissionNoPrompt ∪ {"clipboardRead","clipboardWrite","geolocation","notifications"}`; `Permission = PermissionNoPrompt ∪ OptionalPermission`. Unlike Chromium's single centralized permission table, Firefox's *full* permission catalog is assembled from many files: every API's own schema declares its own gating string at the namespace level, e.g. `downloads.json` → `"permissions": ["downloads"]`, `web_request.json` → `["webRequest"]`, `declarative_net_request.json` → `["declarativeNetRequest", "declarativeNetRequestWithHostAccess"]`, `activity_log.json` → `["activityLog"]` (verified directly by parsing each file's `namespace`/`permissions` fields). This is a genuinely decentralized design vs. Chromium's centralized `extensions_api_permissions.cc`/`chrome_api_permissions.cc` tables — each API announces what unlocks it, rather than one file enumerating every permission up front. It also means the *product-agnostic* set lives under `toolkit/components/extensions/schemas/` (shared by Firefox, Thunderbird, etc.) while Firefox-desktop-only permissions live separately — `activeTab` specifically was found only in `browser/components/extensions/schemas/tabs.json`, not in `toolkit/`, mirroring Chromium's own `//extensions` vs. `//chrome` product split.

Host permissions underwent the *identical* MV2→MV3 structural change as Chromium, verified directly in the schema: MV2's `permissions` array accepted `PermissionOrOrigin` items (API strings and URL match patterns mixed together, `manifest.json:268-279`), while MV3 splits them — `permissions` becomes `Permission`-only (`manifest.json:280-288`), and new `host_permissions`/`optional_host_permissions` array keys (`min_manifest_version: 3`, `manifest.json:291-317`) hold match patterns exclusively. This is real convergence, not superficial similarity — both browsers independently reached the same "separate API-gating strings from URL grants" schema fix at the same manifest version boundary.

The clearest **real difference** found is Firefox's `data_collection` permission axis, with no Chromium equivalent located anywhere in the reference checkout: `permissions.json`'s `Permissions`/`AnyPermissions` types carry a `data_collection` array of `OptionalDataCollectionPermission`, and `manifest.json:536-576` defines `CommonDataCollectionPermission` as an enum of *data categories*, not API capabilities — `authenticationInfo`, `bookmarksInfo`, `browsingActivity`, `financialAndPaymentInfo`, `healthInfo`, `locationInfo`, `personalCommunications`, `personallyIdentifyingInfo`, `searchTerms`, `websiteActivity`, `websiteContent`, plus `"none"` (required) or `"technicalAndInteraction"` (optional-only). This is declared separately under `browser_specific_settings.gecko.data_collection_permissions.{required,optional}` (`FirefoxSpecificProperties`, `manifest.json:660-679`) — it's a *disclosure* permission (what kinds of data the extension says it collects/transmits), orthogonal to the *access* permissions that gate API calls. Chromium's model conflates "can access X" and "may exfiltrate X" into one permission grant; Firefox's schema treats them as two separate declarations. This is directly relevant to BlueIce's capability-list question — "what an extension can technically do" (DOM/network/storage access) and "what it says it does with what it collects" are separable axes, and BlueIce could adopt the same split cheaply if a future policy/privacy-disclosure story is wanted without redesigning the core capability list.

Firefox's identity story also differs concretely from Chromium's derived-from-public-key ID: `FirefoxSpecificProperties.id` (`manifest.json:639-641`, under `browser_specific_settings.gecko`) is an author-declared `ExtensionID`, validated as either a GUID (`{8-4-4-4-12 hex}`) or an email-like string (`[a-z0-9-._]*@[a-z0-9-._]+`) — a human-chosen, manifest-declared identifier, not a hash Firefox computes on install.

On background-execution architecture, Firefox is the one place the two browsers genuinely diverge rather than converge: `manifest.json:131-176`'s `background` object accepts `page`/`scripts` (the pre-existing event-page model) **and** `service_worker` in the *same* schema, plus a `preferred_environment: ["service_worker","document"]` array letting an extension express a preference rather than being forced into one model — and a schema comment at line 152 flags that the `type: "module"|"classic"` distinction is "Only supported for page/scripts; not for service_worker yet, see bug 1775574." `docs/basics.md` and `docs/webidl_bindings.md` confirm this isn't a documentation gap but a real implementation gap as of this checkout: "we are in the process of generating new WebIDL bindings" to expose WebExtension API bindings inside `background.service_worker`, because existing bindings can't be injected into a worker global that runs off the main thread. Concretely: **Chromium made the service worker the only MV3 background option and removed the persistent-page escape hatch outright; Firefox instead added service workers as an additional, still-maturing option alongside its pre-existing non-persistent event-page model**, which already solved the same "don't keep background code resident forever" problem without requiring a dedicated-Worker-only global. This is a genuinely useful data point for BlueIce: an event-driven, lazily-started background *process* model doesn't strictly require a browser-style Worker/service-worker primitive to get the same non-persistence property — Firefox's own history shows a page-based (or, for BlueIce, plain-process-based) lazy-start/idle-suspend model is a viable, independently-arrived-at alternative to Chromium's worker-centric approach, and is arguably a closer structural match to BlueIce's "extension = separate OS process" model than either browser's in-page/in-worker execution.

Runtime permission grants work the same way at the JS-API level: `permissions.json` defines a `permissions` namespace with `getAll`/`contains`/`request`/`remove` functions and `onAdded`/`onRemoved` events — functionally identical to Chromium's `chrome.permissions` API, including `request` being marked `"requireUserInput": true` (i.e., must originate from a user gesture, matching Chromium's install-prompt-on-request model). `ExtensionPermissions.sys.mjs` stores exactly the same triad Chromium tracks conceptually — `{permissions: [], origins: [], data_collection: []}` per extension (`emptyPermissions()`) — though the storage backend differs (migrating from a JSON prefs file to an `rkv`/`KeyValueService` store, per the `Bug 1646182` comments throughout the file) which is an implementation detail, not a model difference.

## 4. Assessment: a starting capability list and manifest schema for BlueIce, and the native-vs-WASM question

**Capability list.** Both browsers converge on the same handful of *axes* even though their concrete permission counts differ wildly (Chromium: ~176 across its two layers; Firefox: a much smaller enumerated core plus per-API declarations) — the axes, not the exact string list, are the reusable finding: (1) **host/URL access**, always represented as match patterns separate from API permissions since both browsers' MV3 schemas moved to split them; (2) **API-gated capabilities**, individual named strings unlocking specific browser functionality; (3) **content-script/DOM injection scope**, treated by both as its own thing (`content_scripts.matches` in both schemas) even though it overlaps with host access; (4) **a small "no prompt" tier** for genuinely low-risk capabilities (Firefox's `PermissionNoPrompt`: `alarms`, `storage`, `unlimitedStorage`, `idle`; Chromium's messageless-permission concept in `permissions.md`) that shouldn't cost the user a warning dialog. Given the plan's `PLAN.md` draft list (`dom:read`, `dom:write`, `network:observe`, `network:intercept`, `ui:inject`, `storage`), the concrete evidence above suggests two refinements: **split host/target scoping from the capability itself**, the way both browsers do — don't bake "which sites" into the capability string; instead pair each of `dom:read`/`dom:write`/`network:observe`/`network:intercept` with a separate `origins`/`match_patterns`-style scope list, exactly as `host_permissions` does, so an extension can be scoped to specific sites without needing a combinatorial capability per site. And **add an `activeTab`-equivalent**: both browsers found it valuable enough to keep as a distinct, non-declared, gesture-triggered grant (temporary access to just the page the user is currently interacting with) — for BlueIce this maps naturally onto a capability that's runtime-granted per-gesture rather than declared in the manifest at all, letting simple "act on the page I clicked the toolbar button on" extensions skip upfront host-permission prompts entirely.

**Manifest/permission model: declared-upfront and runtime-granted are not actually competing designs in either browser — both run both, simultaneously, for different permission classes.** Required capabilities and required host permissions are declared upfront and shown at install (`permissions`/`host_permissions` in both schemas); *optional* capabilities/hosts are declared upfront (`optional_permissions`/`optional_host_permissions`) but not granted until a runtime `permissions.request()` call the user approves in the moment; and `activeTab` bypasses declaration entirely, granted per-gesture and revoked on navigation. Recommend BlueIce's manifest structure mirror this three-tier shape directly rather than picking one of "declared vs. runtime": a `capabilities` list (required, install-time), an `optional_capabilities` list (declared but not granted until requested), and treat active-tab-style ephemeral access as a special runtime-only case that never needs a manifest entry at all. Also worth stealing verbatim: Chromium's granted/active/runtime-granted three-set storage model and its permission-intersection rule for over-broad runtime grants (§1 above) — this is exactly the kind of subtle correctness bug (an extension silently ending up with more access than it declared, because a user's UI grant was broader than the request) that's easy to get wrong on a first design pass and here is a battle-tested fix.

**Native dylib vs. WASM.** Neither reference browser gives extensions a path to load arbitrary native compiled code into the process that runs their JS/extension logic — the only native-code escape hatch either one has is **native messaging** (`toolkit/components/extensions/schemas/native_manifest.json` in Gecko; `extensions/browser/api/messaging/native_message_host.{h,cc}` in Chromium), which is a categorically different, heavier mechanism: a *separately installed*, OS-registered executable (Firefox's schema requires `type: "pkcs11"|"stdio"` and an `allowed_extensions` allowlist keyed by extension ID) that the extension talks to over a stdio pipe, not something bundled inside the extension package and loaded into its own execution context. That both browsers, independently, drew this exact line — "extension logic itself is never native code; native code is a distinct, explicitly consented, separately-distributed peer process" — is a strong signal against a native-dylib extension format even for BlueIce, where the process-isolation decision is already made at the OS level: a dylib loaded into the per-extension process still leaves BlueIce owning a native-code ABI-compatibility surface across every `core` version (exactly the risk `PLAN.md` already flags), with no comparable precedent in either production browser for shipping that as the primary extension format rather than as an optional, explicitly-separate companion process.

There is also a direct, concrete, and easy-to-miss signal in favor of WASM specifically, found independently in both codebases' Content-Security-Policy defaults: Chromium's CSP validator (`extensions/common/csp_validator.cc`) treats `'wasm-eval'`/`'wasm-unsafe-eval'` (`kWasmEvalSource`/`kWasmUnsafeEvalSource`, lines 47-48) as **unconditionally secure** CSP source tokens — allowed in every extension's CSP regardless of settings — while plain `'unsafe-eval'` (arbitrary JS `eval`) is rejected unless a caller explicitly opts in via `OPTIONS_ALLOW_UNSAFE_EVAL` (`GetSecureDirectiveValues`, csp_validator.cc:262-266), which MV3 extension pages don't get by default. Firefox's `WebExtensionPolicy.cpp` shows the exact same asymmetry baked into its *default* CSPs: `DEFAULT_BASE_CSP_V3 = "script-src 'self' 'wasm-unsafe-eval';"` (line 63) — MV3's default policy explicitly permits WebAssembly compilation/instantiation while saying nothing about (i.e., not permitting) plain JS `eval` — compared to MV2's default (`DEFAULT_BASE_CSP_V2`, line 58) which still included bare `'unsafe-eval'` alongside it. Two independently-engineered browsers both special-cased WebAssembly out of their otherwise-tightened MV3 eval restrictions, treating "load and run a WASM module inside an extension context" as safe enough to allow unconditionally while treating "eval arbitrary JS text" as the thing worth restricting. That is meaningfully different from "WASM is untested" — it's evidence that, in these teams' own threat models, a WASM module's sandboxing properties (no ambient authority, memory-safe by construction, no eval-of-untrusted-strings-style code-injection surface) were judged trustworthy enough to carve out of the exact same tightening pass that killed JS `eval` for extensions. Combined with the native-messaging finding above (native code is never the *extension* itself, only an optional external peer), this is a reasonably strong, source-grounded case for **WASM as BlueIce's primary/only extension implementation format**: it gets the portability and forward-ABI-compatibility properties `PLAN.md` already wants without recreating the native-dylib ABI-coupling risk, and it's consistent with what both production extension ecosystems' own security engineering judged acceptable to allow without restriction, even under their strictest (MV3) CSP posture. Neither reference checkout shows evidence of an actual production *WASM-as-extension-format* system (no `background.service_worker`-style WASM entry point exists in either manifest schema — WASM shows up only as something a JS/worker-hosted extension may load and call into, not as the top-level extension artifact) — so there is no directly analogous "manifest declares a `.wasm` entry point" precedent to copy structurally, and BlueIce would be first to do that in an extension manifest specifically, but the CSP evidence supports the trust judgment underlying that choice.

**Versioning**, briefly, since both browsers give at least partial precedent: Chromium's `manifest_version` integer with a strict min/max range (`extension.cc`'s `IsManifestSupported`) checked against explicit `kMinimumSupportedManifestVersion`/`kMaximumSupportedManifestVersion` constants, a hard failure above the max (unless an explicit `--allow-future-manifest-version` override flag is passed) and a deprecation-warning period below current-but-still-supported (the MV2 warning, with a stated sunset date) is a clean, simple pattern worth copying directly for BlueIce's `blueice_api_version`: a single integer with an enforced `[min, max]` window on the `core` side, an explicit warning state for "supported but deprecated," and a hard-reject state for "below min" or "above max" (with an override flag reserved for `core` development builds, not shipped to users) rather than free-form semver negotiation.
