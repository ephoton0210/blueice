# BlueJS bytecode format and event-loop interleaving: what V8/Ignition, SpiderMonkey, Blink, and Gecko actually do

Findings from reading `reference/gecko` (SpiderMonkey's `js/src/vm/`, Gecko's `xpcom/threads/`, and `layout/base/nsRefreshDriver.cpp`) and `reference/chromium` (Blink's `third_party/blink/renderer/platform/scheduler/` and the script/animation call chain it drives), aimed at Phase 13's two open BlueJS design questions: the bytecode instruction format, and how script execution interleaves with `core`'s render-pass/paint loop. One important caveat up front, stated honestly rather than papered over: **this Chromium checkout does not actually contain V8.** `v8/` is a DEPS-managed external checkout (`grep -n "'v8'," DEPS:4410` and `grep -n "'src/v8':" DEPS:3342` show it's fetched by `gclient sync`, not a git submodule — there's no `.gitmodules` entry for it) and the directory on disk is empty (`find .../chromium/v8 -mindepth 1` returns nothing). So there is no `bytecodes.h`, no `interpreter-generator.cc`, nothing under `src/interpreter/` to read here. The only in-tree trace of Ignition at all is a feature-flag name, `kV8IgnitionElideRedundantTdzChecks` (`chromium/gin/gin_features.h:44`, wired to the `--ignition-elide-redundant-tdz-checks` V8 flag in `chromium/gin/v8_initializer.cc:492-494`), which confirms Ignition exists and is still being tuned but says nothing about its instruction encoding. Section 1 below is therefore drawn from V8's own long-public, stable design record (the bytecode design hasn't changed shape since Ignition shipped in V8 5.9/Chrome 59, 2017) rather than from this checkout, and is flagged as such throughout. Section 2 (SpiderMonkey) and Section 3 (Blink + Gecko event loops) are fully grounded in files actually read in this checkout, with line numbers.

## 1. V8's Ignition bytecode format (not verifiable in this checkout — from V8's public design record)

Ignition is a **register-based, accumulator machine**, not a stack machine: most bytecodes read one or more explicit operands and write their result into an implicit "accumulator" pseudo-register that the next bytecode typically consumes, while additional values live in a flat array of numbered virtual registers (effectively spilled locals/temporaries) addressed by small integer operand indices — expected to be defined in `src/interpreter/bytecodes.h` as an `X`-macro list (the same "macro-table" idiom SpiderMonkey uses, see Section 2) and implemented per-bytecode in `src/interpreter/interpreter-generator.cc`, where each handler is generated code built with V8's CodeStubAssembler rather than hand-written C++.

Encoding is **variable-width but byte-oriented and scaled at runtime**, not stack-based and not a fixed 32/64-bit word: the common bytecode is a single opcode byte followed by one or more small (8-bit) operand bytes, but when an operand value doesn't fit in 8 bits, V8 emits a special `Wide` or `ExtraWide` prefix bytecode immediately before the real one, which tells the dispatch loop to reinterpret the following instruction's operands as 16-bit or 32-bit fields instead of 8-bit — i.e. operand width is a property of a runtime prefix scaling decision made by the bytecode generator per-instruction, not a property baked permanently into a specific opcode identity the way SpiderMonkey does it (Section 2's contrast point).

Opcode count is on the order of roughly 150-200 distinct bytecodes (public V8 reporting has been consistently in that range across versions since 2017) — individual instructions are deliberately low-level and RISC-like (`Add`, `LdaSmi`, `Star`, `Ja`, `CallProperty`, `GetNamedProperty`, and similar), with more complex, hot operations like property access and calls kept simple at the bytecode level by delegating to shared inline-cache/builtin machinery rather than encoding that complexity into the instruction itself — the bytecode stays a thin, close-to-uniform layer, and the sophistication lives in what the handler for each opcode calls into, not in the instruction format.

Expected (unverified in this checkout) file layout for reference if this repo's V8 checkout is ever populated: `src/interpreter/bytecodes.h` (opcode list), `src/interpreter/bytecode-array-builder.{h,cc}` (the AST→bytecode emitter, which is also where V8's register allocation for locals/temporaries lives — a real subsystem of its own), `src/interpreter/interpreter-generator.cc` and `src/interpreter/interpreter-assembler.{h,cc}` (per-bytecode handler codegen).

## 2. SpiderMonkey's bytecode format (grounded — `js/src/vm/Opcodes.h`, `BytecodeFormatFlags.h`, `Interpreter.cpp`)

SpiderMonkey is a **pure operand-stack machine**, confirmed directly in the interpreter loop: `js/src/vm/Interpreter.cpp` keeps an explicit `JS::Value*` stack pointer in `REGS.sp`, and `PUSH_COPY`/`PUSH_COPY_SKIP_CHECK`/`POP_COPY_TO` (`Interpreter.cpp:1346-1375`, e.g. `#define PUSH_COPY_SKIP_CHECK(v) *REGS.sp++ = (v)` and `#define POP_COPY_TO(v) (v) = *--REGS.sp`) are literally push/pop onto that stack — there is no accumulator register and no numbered virtual-register file analogous to Ignition's.

Every opcode is defined once, in one place, via an `X`-macro list: `js/src/vm/Opcodes.h` (3653 lines) invokes `MACRO(op, op_snake, token, length, nuses, ndefs, format)` for each of **256 opcodes** (counted directly: `grep -c '^ *MACRO(' Opcodes.h` → 256), where `length` is the instruction's total byte length including operands, `nuses`/`ndefs` are how many stack slots it consumes/produces (`-1` nuses for variadic ops like `Call`), and `format` is a `JOF_*` flag from `js/src/vm/BytecodeFormatFlags.h` describing the operand's shape. Examples read directly from the file: `MACRO(Undefined, undefined, "", 1, 0, 1, JOF_BYTE)` (push undefined, 1 byte, no operand), `MACRO(Int8, int8, NULL, 2, 0, 1, JOF_INT8)` (2 bytes: opcode + int8 literal), `MACRO(Uint16, uint16, NULL, 3, 0, 1, JOF_UINT16)`, `MACRO(Uint24, uint24, NULL, 4, 0, 1, JOF_UINT24)`, `MACRO(Double, double_, NULL, 9, 0, 1, JOF_DOUBLE)` (9 bytes: opcode + inline `double`), `MACRO(Call, call, NULL, 3, -1, 1, JOF_ARGC|JOF_INVOKE|JOF_IC)`.

`BytecodeFormatFlags.h` lists the full `JOF_*` type space: `JOF_BYTE` (no immediate) through `JOF_UINT8/16/24/32`, `JOF_INT8`/`JOF_INT32`, `JOF_DOUBLE` (inline literal), `JOF_JUMP` (`int32_t` branch offset), `JOF_ATOM`/`JOF_OBJECT`/`JOF_REGEXP`/`JOF_SCOPE`/`JOF_BIGINT`/`JOF_SHAPE`/`JOF_STRING` (all `uint32_t` indices into the script's constant/gcthing tables), `JOF_ARGC`, `JOF_QARG`/`JOF_LOCAL` (argument/local slot number), `JOF_ENVCOORD`/`JOF_RESUMEINDEX`. Critically, **each opcode has exactly one fixed encoding chosen at bytecode-emission time** — there are separate opcodes for the same logical operation at different operand widths (the `Uint8`/`Uint16`/`Uint24`/`Uint32` family above is one clear example) rather than V8's runtime `Wide`/`ExtraWide` prefix-scaling trick; the bytecode emitter picks the right fixed-width opcode once, up front, based on the actual operand value.

Dispatch is **computed-goto threading**, not a plain `switch`: `#define DISPATCH_TO(OP) goto* addresses[(OP)]` (`Interpreter.cpp:1777`), with per-opcode labels generated via `#define CASE(OP) label_##OP:` (`Interpreter.cpp:1774`) and `#define ADVANCE_AND_DISPATCH(N)` advancing `REGS.pc` by the opcode's fixed `length` before jumping to the next label — i.e. the interpreter's own comment (`Interpreter.cpp:1929`, "around computed gotos") and code both confirm this directly.

SpiderMonkey's bytecode is also explicitly the base of a **four-tier pipeline**, not a standalone interpreter: `js/AGENTS.md` (this checkout's own architecture doc) states it outright — "Interpreter -> Baseline Interpreter -> Baseline JIT -> Ion -> Warp. CacheIR is the shared IC representation consumed by all tiers." The exact hook point for that tiering is visible in the bytecode format itself: `JOF_IC = 1 << 24` ("baseline may use an IC for this op", `BytecodeFormatFlags.h:52`) is a flag bit set on many opcodes (`Call`, `Typeof`, `Pos`, `Neg`, `GetProp`-family, etc., all seen with `|JOF_IC` in `Opcodes.h`) — the interpreter tier ignores this flag and just executes the op directly, but it marks exactly the sites later tiers attach inline caches to. This is a direct, concrete precedent for BlueIce's own plan language ("inline-caching sites... are real extension points a future optimization phase adds *onto* the bytecode-interpreter... foundation," `PLAN.md:25`): SpiderMonkey's version of "leave the hook, don't build the machinery" is a single reserved format-flag bit that costs nothing until a later tier reads it.

**Comparison with Ignition (Section 1, caveat about unverified V8 source still applies):** both formats are variable-width and byte-oriented rather than fixed 32/64-bit words, and both are defined from one `X`-macro source of truth that generates the opcode enum, dispatch table, and (in both engines) disassembler/pretty-printer text together — a pattern worth adopting regardless of the stack-vs-register decision, since it's what keeps the opcode list, its handler table, and its length/operand metadata from drifting apart as the engine grows. The real difference is stack-vs-register: SpiderMonkey pushes/pops an explicit `JS::Value` stack and has no accumulator; Ignition keeps values in an accumulator plus a numbered register file, and — the sharper contrast — SpiderMonkey commits to one fixed-width opcode per operand-size variant at compile time while Ignition scales operand width at runtime via `Wide`/`ExtraWide` prefix bytecodes. Opcode counts are the same order of magnitude (SpiderMonkey: 256, counted directly; Ignition: roughly 150-200, per V8's own public reporting) — neither design wins on "fewer opcodes."

## 3. How Blink's scheduler and Gecko's event loop actually interleave script, microtasks, and frame production

**Blink: microtask checkpoint is a generic per-task hook, not a rendering-specific one.** `MainThreadSchedulerImpl::OnTaskCompleted` (`third_party/blink/renderer/platform/scheduler/main_thread/main_thread_scheduler_impl.cc:2618-2619`, comment "Microtasks may detach the task queue and invalidate `|queue|`") calls `PerformMicrotaskCheckpoint()` unconditionally after **every** task the scheduler runs through any of its task queues — this is the concrete implementation of the HTML spec's "perform a microtask checkpoint" step, wired to task completion in general, independent of rendering. `PerformMicrotaskCheckpoint` itself (`main_thread_scheduler_impl.cc:1263-1293`) does two things: calls `EventLoop::PerformIsolateGlobalMicrotasksCheckpoint(isolate())` as an isolate-wide fallback, then iterates every live `AgentGroupScheduler` and calls its own `PerformMicrotaskCheckpoint()` — because the HTML spec defines microtask queues per similar-origin-window-agent-cluster ("agent"), not one global queue. The actual queue is `blink::scheduler::EventLoop` (`platform/scheduler/common/event_loop.cc` / `public/event_loop.h`), which wraps a `v8::MicrotaskQueue` directly (`EnqueueMicrotask` calls `microtask_queue_->EnqueueMicrotask(...)`, `event_loop.cc:60-75`), and `Agent::PerformMicrotaskCheckpoint` (`core/execution_context/agent.cc`) is a one-line delegate: `event_loop_->PerformMicrotaskCheckpoint();`.

**Blink: frame production runs script synchronously, inside the same call that produces the frame, in spec order.** `WebFrameWidgetImpl::BeginMainFrame` (`core/frame/web_frame_widget_impl.cc:3041`), invoked by the compositor on a `viz::BeginFrameArgs` (vsync) signal, calls `GetPage()->Animate(last_frame_time)` (`page.cc:1524`), which calls `PageAnimator::ServiceScriptedAnimations` (`core/page/page_animator.cc`). That function's body is, concretely, a numbered transcription of the spec: its own comments cite `https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model` step numbers directly against the code that implements them — step 6 (`pagereveal`), 7 (flush autofocus candidates), 8 (resize events), 9 (scroll events), 10 (media-query-list change events), 11 (CSS animation events), 12 (fullscreen steps), 14 (`requestAnimationFrame` callbacks, via `active_controllers[i]->ExecuteFrameCallbacks()`). All of this — actual script execution, both event-handler callbacks and rAF callbacks — runs **inside** `BeginMainFrame`, before layout/paint proceed later in the same lifecycle update (the code's own comment, "See `LocalFrameView::RunPostLifecycleSteps()` for 15 and 16," points at where the remaining post-layout spec steps continue). So the per-frame ordering is: compositor requests a frame → `BeginMainFrame` → `Animate`/`ServiceScriptedAnimations` runs pending script synchronously in spec order → style/layout/paint follow, in that same call chain. No explicit extra `PerformMicrotaskCheckpoint()` call was found inside `page_animator.cc` itself, so within a single `BeginMainFrame` call any additional checkpointing beyond what the per-task hook provides rides on V8's own callback-scope behavior rather than an explicit Blink-side call at that granularity — worth flagging as a limit of what this pass confirmed, not asserting more precision than the evidence supports.

**Gecko: the same "checkpoint after every task" rule, wired one layer lower.** `nsThread::ProcessNextEvent` (`xpcom/threads/nsThread.cpp`) wraps every runnable it pulls off the main-thread queue with `mScriptObserver->BeforeProcessTask(reallyWait)` (`nsThread.cpp:1109`) and `mScriptObserver->AfterProcessTask(mNestedEventLoopDepth)` (`nsThread.cpp:1233`), and `mScriptObserver` is typed directly as `mozilla::CycleCollectedJSContext*` (`nsThread.h:275`) — i.e. Gecko wires the JS engine's context object straight into the generic, cross-platform runnable-processing primitive, one layer lower than Blink's separate scheduler-level hook. `CycleCollectedJSContext::AfterProcessTask` (`xpcom/base/CycleCollectedJSContext.cpp:527-533`) calls `PerformMicroTaskCheckPoint()` unconditionally — the identical "after every task, drain microtasks" rule Blink implements, arrived at independently in a structurally different place in the codebase. `CycleCollectedJSContext` itself is declared `class CycleCollectedJSContext : dom::PerThreadAtomCache, public JS::JobQueue` (`xpcom/base/CycleCollectedJSContext.h:348`) — it directly implements SpiderMonkey's own abstract `JS::JobQueue` interface, the same relationship Blink's `EventLoop` has to `v8::MicrotaskQueue`.

**Gecko: frame production is likewise a distinct vsync-driven entry point that runs the spec's rendering-update steps, script included, before layout/paint, in the same call.** `nsRefreshDriver::Tick(VsyncId aId, TimeStamp aNowTime, ...)` (`layout/base/nsRefreshDriver.cpp:2278`) is the vsync-driven equivalent of `BeginMainFrame`, and it runs through a fixed, named `RenderingPhase` sequence via `RunRenderingPhase`/`RunRenderingPhaseLegacy` — `Reveal`, `FlushAutoFocusCandidates`, `ResizeSteps`, `ScrollSteps`, `EvaluateMediaQueriesAndReportChanges`, `UpdateAnimationsAndSendEvents`, `FullscreenSteps`, `AnimationFrameCallbacks`, `Layout`, `ViewTransitionOperations`, `UpdateIntersectionObservations`, `Paint` (phase names and call order read directly from `nsRefreshDriver.cpp:2418-2573` and the `RenderingPhase::*` enum uses in `nsRefreshDriver.h`). `RunRenderingPhase`'s own comment cites the spec directly, `// https://html.spec.whatwg.org/#update-the-rendering step 3` (`nsRefreshDriver.cpp:1296`) — the same "engine code is a near-literal transcription of the spec's step list" pattern found in Blink, independently. Script-running phases (event dispatch for resize/scroll/media-query steps, `AnimationFrameCallbacks`) run interleaved with, and before, `Layout` and `Paint`, all inside the same `Tick` call — structurally identical ordering to Blink's `BeginMainFrame`.

**The upshot, true of both engines and load-bearing for BlueJS's design:** there are exactly two distinct entry points into the JS engine's script/microtask state, not one unified queue. One is the generic macrotask loop (`nsThread::ProcessNextEvent` / Blink's scheduler task queues) — process one task, then unconditionally drain microtasks, repeat. The other is a vsync/compositor-driven, per-frame entry point (`nsRefreshDriver::Tick` / `BeginMainFrame`) that is *not itself* a queued macrotask in either engine — it runs the spec's script-bearing "update the rendering" steps synchronously as the first part of producing a frame, then proceeds to layout and paint in that same call. Both engines converged on this same two-entry-point shape independently (different codebases, different eras of design), which is stronger evidence for BlueJS's design than either engine's choice alone, or than reasoning from the spec's abstract processing model text without seeing how it actually gets implemented.

## 4. Assessment: recommendation for BlueJS

**Bytecode format: stack-based, single-fixed-width-per-opcode, byte-oriented — model it on SpiderMonkey, not Ignition.** This confirms the suspected tradeoff from the task brief. The concrete reason stack-based is simpler to implement *correctly*, not just simpler in the abstract: a stack machine's AST→bytecode lowering never needs a register allocator — every expression's intermediate values push and pop implicitly in tree-evaluation order, so the compiler pass is a direct recursive walk with no "which register currently holds this value" bookkeeping. A register/accumulator machine's emitter has to solve a real allocation problem — Ignition's `BytecodeArrayBuilder` (expected location, per Section 1's caveat) carries actual register-allocation logic as a subsystem of its own. For an MVP with no JIT to feed, that extra compiler complexity buys nothing yet: interpreted execution speed for a plain threaded-dispatch loop is comparable between the two designs, and the real reason production engines moved to register/accumulator machines was to reduce push/pop traffic and hand a later JIT tier cleaner, more analyzable dataflow — an optimization concern BlueIce has explicitly and correctly deferred (`PLAN.md:21-25`). Concretely: one opcode byte, a fixed per-opcode operand shape chosen at emission time mirroring SpiderMonkey's `JOF_*` categories (no operand / `u8` / `u16` / `u32` constant-table index / `i32` jump offset), and a compile-time-constant instruction length per opcode (SpiderMonkey's `length` field in `Opcodes.h`) so the dispatch loop advances the program counter by a lookup, not a runtime computation. Do **not** build Ignition's `Wide`/`ExtraWide` runtime operand-scaling prefix for MVP — it solves a code-size problem BlueJS doesn't have yet, and if it's ever needed, SpiderMonkey's approach (multiple fixed-width variants of the same logical opcode, selected once at emission time) is a strictly simpler retrofit, since it needs zero new dispatch-loop machinery, only additional table entries. Define the opcode list exactly once, as an `X`-macro table (SpiderMonkey's `FOR_EACH_OPCODE(MACRO)` pattern) that generates the opcode enum, the dispatch/handler table, and the operand-length table together from one source of truth, so they cannot drift apart as opcodes are added. Reserve, but do not implement, a per-opcode "may use an inline cache" flag bit analogous to SpiderMonkey's `JOF_IC` (`BytecodeFormatFlags.h:52`) — an unused bit today, and the direct, already-proven hook point for a future optimization tier, matching the plan's own stated principle of leaving extension points rather than building the machinery behind them now.

**Event loop: two structurally separate entry points into the same interpreter/microtask state, exactly as both Blink and Gecko independently converged on — not spec-guessed, evidence-derived.** Concretely for `core`: (1) a generic macrotask queue (timers, message-style callbacks, anything not tied to a specific frame) that `core`'s run loop drains one task at a time — never draining the whole queue before checking on rendering, which is precisely what makes interleaving possible at all — mirroring `nsThread::ProcessNextEvent`'s per-runnable granularity. (2) After every single macrotask, unconditionally drain BlueJS's promise-job/microtask queue to completion (looping since a job can enqueue more jobs) before returning to pick up the next macrotask — this is the one rule both Blink (`OnTaskCompleted` → `PerformMicrotaskCheckpoint`) and Gecko (`AfterProcessTask` → `PerformMicroTaskCheckPoint`) implement identically despite being unrelated codebases, which is exactly the kind of two-engine agreement that should outweigh guessing from the spec's abstract text alone. (3) `core`'s render-pass/paint entry point should be its own distinct call — not a queued macrotask — that, on being invoked (vsync- or timer-driven for BlueIce's MVP), first runs whatever frame-scheduled BlueJS script exists (a `requestAnimationFrame`-equivalent, if in MVP scope; an empty/no-op step if not yet implemented) synchronously, mirroring `BeginMainFrame`/`Tick` running script before layout/paint within the same call rather than as a separately scheduled task before or after it, then drains microtasks once more (script just ran and may have queued promise reactions) before proceeding to layout and paint, so layout/paint always observe a post-microtask-settled state. (4) Keep the macrotask-queue entry point and the render-pass entry point structurally separate call sites rather than unifying them into one priority-tagged queue — both reference engines keep them separate (`cc::Scheduler`-driven `BeginMainFrame` is not a task on Blink's `MainThreadTaskQueue`; Gecko's vsync-driven `Tick` is likewise not a runnable on `nsThread`'s queue), and collapsing them would be exactly the kind of premature unification this project is trying to avoid needing to walk back later. (5) Flag as intentionally out of MVP scope rather than silently ignored: both engines partition microtask queues per "agent" (Blink's `AgentGroupScheduler`, one per similar-origin-window-agent-cluster) rather than using one global queue — for BlueIce's realistic MVP (effectively one document, one agent) a single global microtask queue is a fine simplification, but the seam both engines put at "per agent" rather than "per document" or "global" is worth remembering if multi-document/multi-frame script isolation becomes a later requirement, so that work extends the design rather than reworking it. None of the above resolves Phase 13's separate open question of in-process-vs-out-of-process script execution (`PLAN.md:35`) — the task/microtask/frame ordering rule found here holds either way, since both reference engines run script and rendering in the same process and the ordering rule is about *when* script runs relative to rendering, not *where*.
