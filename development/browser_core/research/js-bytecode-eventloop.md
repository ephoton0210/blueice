# BlueJS bytecode format and event-loop interleaving: what V8/Ignition, SpiderMonkey, Blink, and Gecko actually do

Findings from reading `reference/gecko` (SpiderMonkey's `js/src/vm/`, Gecko's `xpcom/threads/`, and `layout/base/nsRefreshDriver.cpp`), `reference/chromium` (Blink's `third_party/blink/renderer/platform/scheduler/` and the script/animation call chain it drives), and `reference/v8` (V8's own canonical repo, cloned separately from `chromium/` — see the note at the top of Section 1), aimed at Phase 13's two open BlueJS design questions: the bytecode instruction format, and how script execution interleaves with `core`'s render-pass/paint loop. One caveat that still applies, stated honestly rather than papered over: **the Chromium checkout's own `v8/` is not populated.** `v8/` is a DEPS-managed external checkout (`grep -n "'v8'," DEPS:4410` and `grep -n "'src/v8':" DEPS:3342` show it's fetched by `gclient sync`, not a git submodule — there's no `.gitmodules` entry for it) and the directory on disk is empty (`find .../chromium/v8 -mindepth 1` returns nothing). The only in-tree trace of Ignition inside `reference/chromium` itself is a feature-flag name, `kV8IgnitionElideRedundantTdzChecks` (`chromium/gin/gin_features.h:44`, wired to the `--ignition-elide-redundant-tdz-checks` V8 flag in `chromium/gin/v8_initializer.cc:492-494`), which confirms Ignition exists and is still being tuned but says nothing about its instruction encoding. That gap is why Section 1 was originally written from V8's public design record rather than source — see the note at its top for what changed. Section 2 (SpiderMonkey), Section 3 (Blink + Gecko event loops), and now Section 1 (V8/Ignition, revised) are all grounded in files actually read in a checkout, with line numbers.

## 1. V8's Ignition bytecode format (grounded — `reference/v8/src/interpreter/`)

**Revision note:** this section originally drew on V8's public design record only, because at the time `reference/v8` did not exist and `chromium/v8` was an empty DEPS placeholder (see the caveat above) — every claim below was explicitly flagged as unverified against any checkout. `reference/v8` has since been cloned as its own repo (a real, populated `src/` tree — `ls reference/v8/src/interpreter/` returns 52 `.cc`/`.h` implementation files, not zero), and this section has been rewritten from that source. The verified picture confirms the shape of the original claims (register+accumulator machine, `Wide`/`ExtraWide` runtime operand scaling) but corrects specifics that turned out to be off — the opcode count, one invented-looking example opcode, and the assumption that V8's "register allocator" is comparable in complexity to a real one — and adds real architectural detail (how dispatch and handler codegen actually work) that no public summary would have surfaced. Corroborated throughout by V8's own in-tree design doc, `reference/v8/docs/interpreter/interpreter-ignition.md`, which independently confirms the same claims this section verified directly against `bytecodes.h` and the `.cc` files it describes.

Ignition is confirmed as a **register-based, accumulator machine**, not a stack machine, directly from `src/interpreter/bytecode-operands.h:119-128`: `enum class ImplicitRegisterUse : uint8_t { kNone, kReadAccumulator, kWriteAccumulator, kClobberAccumulator, kWriteShortStar, kReadWriteAccumulator, kReadAndClobberAccumulator, kReadAccumulatorWriteShortStar }` is a flag set attached to every bytecode describing how it touches one implicit accumulator slot, and `src/interpreter/interpreter-assembler.h:96-97` declares `TNode<Object> GetAccumulator(); void SetAccumulator(TNode<Object> value);` as primitives every handler can call. Numbered virtual registers are a separate, explicit concept: `src/interpreter/bytecode-register.h:27` defines `class Register final { ... int index() const; ... }` — "An interpreter Register which is located in the function's Register file in its stack-frame. Register hold parameters, this, and expression values" (comment, `bytecode-register.h:25-26`). The opcode list itself is built the same "X-macro table" way SpiderMonkey's is (Section 2): `src/interpreter/bytecodes.h:60` defines `#define BYTECODE_LIST_WITH_UNIQUE_HANDLERS_IMPL(V, V_TSA) ...`, invoked once per bytecode as e.g. `V(Ldar, ImplicitRegisterUse::kWriteAccumulator, OperandType::kReg)` (`bytecodes.h:87`) or `V(Add, ImplicitRegisterUse::kReadWriteAccumulator, OperandType::kReg, OperandType::kEmbeddedFeedback)` (`bytecodes.h:213-214`), and `bytecodes.h:630-641` turns the combined list into `enum class Bytecode : uint8_t { ... kLast = ... }`.

Opcode count is **215, counted precisely, not estimated**: `Bytecodes::kBytecodeCount` is defined as `static_cast<int>(Bytecode::kLast) + 1` (`bytecodes.h:649`), and mechanically expanding the same X-macro chain the enum is built from (`BYTECODE_LIST_WITH_UNIQUE_HANDLERS_IMPL`'s 198 distinct handlers, including the 4-entry `CALL_PROPERTY_BYTECODES` sub-list at `bytecodes.h:42-51`, plus the 16-entry `SHORT_STAR_BYTECODE_LIST` at `bytecodes.h:24-40` for `Star0`..`Star15`, plus the single `Illegal` sentinel at `bytecodes.h:532`) gives 198 + 16 + 1 = 215. This corrects the earlier "roughly 150-200" guess drawn from public reporting — real, but on the low side; the actual number is precise and a bit higher, consistent with this being a current (2024/2025-era) V8 checkout that has accumulated bytecodes like the `LdaContextSlotNoCell`/`LdaCurrentContextSlotNoCell` family (context-slot "no cell" variants, `bytecodes.h:97-108`) that public write-ups from 2017 wouldn't mention. Individual instructions are confirmed low-level and RISC-like — real examples read directly from `bytecodes.h`: `LdaSmi`, `LdaZero`, `Star`, `Ldar`, `Mov`, `Add`, `CallProperty`/`CallProperty0`/`CallProperty1`/`CallProperty2` (`bytecodes.h:42-51`), `GetNamedProperty` (`bytecodes.h:168-170`), `Jump`, `JumpLoop`, `JumpIfTrue`, `JumpIfFalse` (`bytecodes.h:408-459`) — one correction worth flagging plainly: the earlier pass's example list included a bytecode named `Ja`, which does not exist anywhere in `bytecodes.h` (`grep -n 'V(Ja\b' bytecodes.h` returns nothing); it was an unverified guess that happened to look plausible and turned out to be wrong, which is exactly the kind of error reading real source catches. `reference/v8/docs/interpreter/interpreter-ignition.md:54-65` gives a full worked disassembly for a small function (`if (x > 0) { return obj.y + x; } return 0;`) that shows these opcodes in context, e.g. `TestGreaterThan a1, [0]` / `JumpIfFalse [13]` / `GetNamedProperty a0, [0], [1]` / `Star0` / `Add r0, [0]` — independently corroborating both the opcode names and the register+accumulator data flow (accumulator holds the live value between steps; `Star0`/`r0` is where it gets parked when a second operand is needed).

`Wide`/`ExtraWide` runtime operand-scaling prefixes are confirmed exactly as described, with the actual mechanism now visible: `bytecodes.h:62-63` declares `V(Wide, ImplicitRegisterUse::kNone)` and `V(ExtraWide, ImplicitRegisterUse::kNone)` as real bytecodes in the list; `src/interpreter/bytecode-operands.h:69-72` defines `#define OPERAND_SCALE_LIST(V) V(Single, 1) V(Double, 2) V(Quadruple, 4)`, i.e. operand byte-width literally doubles or quadruples per scale; and the emission-time decision is concretely `src/interpreter/bytecode-array-writer.cc:304-314`'s `BytecodeArrayWriter::EmitBytecode`: `if (operand_scale != OperandScale::kSingle) { Bytecode prefix = Bytecodes::OperandScaleToPrefixBytecode(operand_scale); bytecodes()->push_back(Bytecodes::ToByte(prefix)); } bytecodes()->push_back(Bytecodes::ToByte(bytecode));` — the prefix byte is pushed first, then the real opcode byte, exactly the "prefix bytecode read before the real one, changing how its operands are read" design the original note described from public sources, now backed by the actual write path. Only "scalable" operand types (`OperandTypeInfo::kScalableSignedByte`/`kScalableUnsignedByte`, covering `Reg`, `Imm`, `ConstantPoolIndex`, `FeedbackSlot`, etc. — `bytecode-operands.h:17-37`) are affected; fixed-size operand types like `Flag8`/`RuntimeId`/`AbortReason` (`bytecode-operands.h:39-46`) never scale, so `Wide`/`ExtraWide` prefixing is itself opcode-dependent, not universal.

Dispatch is **not a hand-written C++ loop the way SpiderMonkey's is** (Section 2's `goto*`/computed-goto loop in `Interpreter.cpp`) — it is a table of raw machine-code entry points into separately-generated handler builtins. `src/interpreter/interpreter.cc:108-115`'s `Interpreter::SetBytecodeHandler` does `dispatch_table_[index] = handler->instruction_start();` where `handler` is a `Tagged<Code>` of `CodeKind::BYTECODE_HANDLER`, indexed via `GetDispatchTableIndex` (`interpreter.cc:118-124`) by `(bytecode, operand_scale)` pair. `InterpreterAssembler::Dispatch()` (`src/interpreter/interpreter-assembler.cc:1402-1407`) — the code that decides where to jump next — is itself part of each handler's own generated machine code, not a separate interpreter-loop function: it loads the next bytecode, then calls `DispatchToBytecode`, which loads `dispatch_table_[...]` and jumps to it directly (a genuine threaded-dispatch design, confirmed independently by `docs/interpreter/interpreter-ignition.md:24-28`'s "Threaded Dispatch" section: "the dispatch table \[is\] stored in a dedicated CPU register for fast access"). Each handler is written once as CodeStubAssembler (CSA) using the `IGNITION_HANDLER(Name, BaseAssembler)` macro (`src/interpreter/interpreter-generator.cc:44-58`, generating a `Name##Assembler` class), but because operand width is a runtime scale, `src/builtins/generate-bytecodes-builtins-list.cc` is a build-time code generator that explicitly re-walks the *entire* `BYTECODE_LIST` X-macro three times, once per operand scale — `operand_scale = OperandScale::kSingle; BYTECODE_LIST(ADD_BYTECODES, ...); ...kDouble...; ...kQuadruple...` (`generate-bytecodes-builtins-list.cc:71-78`) — and its own `CHECK_EQ(single_count, Bytecodes::kBytecodeCount - Bytecodes::kShortStarCount + 1)` (`generate-bytecodes-builtins-list.cc:82-83`) pins the exact number: 215 − 16 + 1 = **200 distinct `kSingle`-scale handler builtins** (the 16 short-star variants collapse to one shared "ShortStar" handler, per the generator's own comment, `generate-bytecodes-builtins-list.cc:24-26`), plus a further `wide_count` and an equal `extra_wide_count` (`CHECK_EQ(wide_count, extra_wide_count)`, line 84) for the `kDouble`/`kQuadruple` scales — meaning most bytecodes with scalable operands really are compiled into **up to three separate machine-code builtins**, not one, and this is measured directly from the generator's own invariants, not inferred. A newer, parallel handler-codegen path also exists: `src/interpreter/interpreter-generator-tsa.cc`/`.h` implement some handlers with Turboshaft Assembler (TSA) instead of CSA, selected via the `V_TSA(...)` macro slot in the bytecode list (e.g. `V_TSA(BitwiseNot, ImplicitRegisterUse::kReadWriteAccumulator, OperandType::kEmbeddedFeedback)`, `bytecodes.h:277-278`) and gated at build time by `V8_ENABLE_EXPERIMENTAL_TSA_BUILTINS` (`bytecodes.h:514-520`) — evidence V8 is mid-migration to a second code-generation backend for at least some handlers, something no public "Ignition uses CodeStubAssembler" summary would capture.

Register allocation for temporaries turns out to be **simpler than "a real register allocator" implies, but the design has a different, real cost instead**: `src/interpreter/bytecode-register-allocator.h`'s `BytecodeRegisterAllocator` is a bump allocator under strict LIFO discipline — `NewRegister()` (`bytecode-register-allocator.h:37-44`) just increments `next_register_index_`, and `ReleaseRegister(Register reg)` (`bytecode-register-allocator.h:88-94`) asserts `DCHECK_EQ(next_register_index_ - 1, reg.index())` — you can only free the most-recently-allocated register, exactly stack discipline. The AST-walking emitter (`BytecodeGenerator`, see below) uses this via an RAII `RegisterAllocationScope` (`src/interpreter/bytecode-generator.cc:770-790`) that snapshots `next_register_index()` on construction and calls `ReleaseRegisters(outer_next_register_index_)` on destruction — a mark/release stack allocator, structurally close to what a stack machine's implicit push/pop already gives for free. The real extra machinery a register+accumulator design needs, that a stack machine doesn't, is a dedicated peephole pass: `src/interpreter/bytecode-register-optimizer.h:20-23`'s own comment states its purpose plainly — "An optimization stage for eliminating unnecessary transfers between registers. The bytecode generator uses temporary registers liberally for correctness and convenience and this stage removes transfers that are not required." `BytecodeRegisterOptimizer` is a full class (`bytecode-register-optimizer.h`/`.cc`) that observes every register allocate/free event (it implements `BytecodeRegisterAllocator::Observer`, `bytecode-register-optimizer.h:24-25`) and rewrites the naive `Star`/`Ldar`/`Mov` stream after the fact — this pass, not the allocator itself, is the concrete "extra subsystem" a stack-based bytecode never needs to build.

One file-role correction to the earlier pass's expected layout: the AST→bytecode lowering walk is `BytecodeGenerator` (`src/interpreter/bytecode-generator.h`/`.cc` — 701 + 9227 lines, an `AstVisitor<BytecodeGenerator>` implementing `Visit...` for every AST node type, confirmed by `docs/interpreter/interpreter-ignition.md:81-88`), not `BytecodeArrayBuilder` as originally guessed. `BytecodeArrayBuilder` (`src/interpreter/bytecode-array-builder.h`/`.cc` — 732 + 1866 lines) is a lower-level assembler-like API that `BytecodeGenerator` emits into; it owns the register allocator as a plain member (`BytecodeRegisterAllocator register_allocator_;`, `bytecode-array-builder.h:703`) alongside the constant pool builder and jump-table machinery, and `BytecodeGenerator::register_allocator()` (`bytecode-generator.h:596-597`) is a one-line delegate to `builder()->register_allocator()` — the two files divide "what bytecode to emit for this AST node" (`BytecodeGenerator`) from "how to actually write bytecode bytes, constants, and registers" (`BytecodeArrayBuilder`), a real and useful separation BlueJS's own compiler pass can borrow regardless of the stack-vs-register decision.

## 2. SpiderMonkey's bytecode format (grounded — `js/src/vm/Opcodes.h`, `BytecodeFormatFlags.h`, `Interpreter.cpp`)

SpiderMonkey is a **pure operand-stack machine**, confirmed directly in the interpreter loop: `js/src/vm/Interpreter.cpp` keeps an explicit `JS::Value*` stack pointer in `REGS.sp`, and `PUSH_COPY`/`PUSH_COPY_SKIP_CHECK`/`POP_COPY_TO` (`Interpreter.cpp:1346-1375`, e.g. `#define PUSH_COPY_SKIP_CHECK(v) *REGS.sp++ = (v)` and `#define POP_COPY_TO(v) (v) = *--REGS.sp`) are literally push/pop onto that stack — there is no accumulator register and no numbered virtual-register file analogous to Ignition's.

Every opcode is defined once, in one place, via an `X`-macro list: `js/src/vm/Opcodes.h` (3653 lines) invokes `MACRO(op, op_snake, token, length, nuses, ndefs, format)` for each of **256 opcodes** (counted directly: `grep -c '^ *MACRO(' Opcodes.h` → 256), where `length` is the instruction's total byte length including operands, `nuses`/`ndefs` are how many stack slots it consumes/produces (`-1` nuses for variadic ops like `Call`), and `format` is a `JOF_*` flag from `js/src/vm/BytecodeFormatFlags.h` describing the operand's shape. Examples read directly from the file: `MACRO(Undefined, undefined, "", 1, 0, 1, JOF_BYTE)` (push undefined, 1 byte, no operand), `MACRO(Int8, int8, NULL, 2, 0, 1, JOF_INT8)` (2 bytes: opcode + int8 literal), `MACRO(Uint16, uint16, NULL, 3, 0, 1, JOF_UINT16)`, `MACRO(Uint24, uint24, NULL, 4, 0, 1, JOF_UINT24)`, `MACRO(Double, double_, NULL, 9, 0, 1, JOF_DOUBLE)` (9 bytes: opcode + inline `double`), `MACRO(Call, call, NULL, 3, -1, 1, JOF_ARGC|JOF_INVOKE|JOF_IC)`.

`BytecodeFormatFlags.h` lists the full `JOF_*` type space: `JOF_BYTE` (no immediate) through `JOF_UINT8/16/24/32`, `JOF_INT8`/`JOF_INT32`, `JOF_DOUBLE` (inline literal), `JOF_JUMP` (`int32_t` branch offset), `JOF_ATOM`/`JOF_OBJECT`/`JOF_REGEXP`/`JOF_SCOPE`/`JOF_BIGINT`/`JOF_SHAPE`/`JOF_STRING` (all `uint32_t` indices into the script's constant/gcthing tables), `JOF_ARGC`, `JOF_QARG`/`JOF_LOCAL` (argument/local slot number), `JOF_ENVCOORD`/`JOF_RESUMEINDEX`. Critically, **each opcode has exactly one fixed encoding chosen at bytecode-emission time** — there are separate opcodes for the same logical operation at different operand widths (the `Uint8`/`Uint16`/`Uint24`/`Uint32` family above is one clear example) rather than V8's runtime `Wide`/`ExtraWide` prefix-scaling trick; the bytecode emitter picks the right fixed-width opcode once, up front, based on the actual operand value.

Dispatch is **computed-goto threading**, not a plain `switch`: `#define DISPATCH_TO(OP) goto* addresses[(OP)]` (`Interpreter.cpp:1777`), with per-opcode labels generated via `#define CASE(OP) label_##OP:` (`Interpreter.cpp:1774`) and `#define ADVANCE_AND_DISPATCH(N)` advancing `REGS.pc` by the opcode's fixed `length` before jumping to the next label — i.e. the interpreter's own comment (`Interpreter.cpp:1929`, "around computed gotos") and code both confirm this directly.

SpiderMonkey's bytecode is also explicitly the base of a **four-tier pipeline**, not a standalone interpreter: `js/AGENTS.md` (this checkout's own architecture doc) states it outright — "Interpreter -> Baseline Interpreter -> Baseline JIT -> Ion -> Warp. CacheIR is the shared IC representation consumed by all tiers." The exact hook point for that tiering is visible in the bytecode format itself: `JOF_IC = 1 << 24` ("baseline may use an IC for this op", `BytecodeFormatFlags.h:52`) is a flag bit set on many opcodes (`Call`, `Typeof`, `Pos`, `Neg`, `GetProp`-family, etc., all seen with `|JOF_IC` in `Opcodes.h`) — the interpreter tier ignores this flag and just executes the op directly, but it marks exactly the sites later tiers attach inline caches to. This is a direct, concrete precedent for BlueIce's own plan language ("inline-caching sites... are real extension points a future optimization phase adds *onto* the bytecode-interpreter... foundation," `PLAN.md:25`): SpiderMonkey's version of "leave the hook, don't build the machinery" is a single reserved format-flag bit that costs nothing until a later tier reads it.

**Comparison with Ignition (Section 1, now grounded in real V8 source — see the revision note at Section 1's top):** both formats are variable-width and byte-oriented rather than fixed 32/64-bit words, and both are defined from one `X`-macro source of truth that generates the opcode enum, dispatch table, and (in both engines) disassembler/pretty-printer text together — a pattern worth adopting regardless of the stack-vs-register decision, since it's what keeps the opcode list, its handler table, and its length/operand metadata from drifting apart as the engine grows. The real difference is stack-vs-register: SpiderMonkey pushes/pops an explicit `JS::Value` stack and has no accumulator; Ignition keeps values in an accumulator plus a numbered register file, and — the sharper contrast — SpiderMonkey commits to one fixed-width opcode per operand-size variant at compile time while Ignition scales operand width at runtime via `Wide`/`ExtraWide` prefix bytecodes, which in Ignition's case also means most scalable-operand bytecodes are compiled into up to three separate machine-code handler builtins, one per operand scale (Section 1). Opcode counts are the same order of magnitude but now both precisely counted rather than one being a public-record estimate: SpiderMonkey 256 (`grep -c '^ *MACRO(' Opcodes.h`), Ignition 215 (`Bytecodes::kBytecodeCount`, `bytecodes.h:649`, verified by mechanically expanding the same `X`-macro chain the enum is built from) — neither design wins on "fewer opcodes," and SpiderMonkey's dispatch loop is a single hand-written C++ function using computed goto (Section 2 above) where Ignition's is a table of independently-generated machine-code builtins (Section 1) — a difference in interpreter *implementation* effort that doesn't show up in the opcode count at all.

## 3. How Blink's scheduler and Gecko's event loop actually interleave script, microtasks, and frame production

**Blink: microtask checkpoint is a generic per-task hook, not a rendering-specific one.** `MainThreadSchedulerImpl::OnTaskCompleted` (`third_party/blink/renderer/platform/scheduler/main_thread/main_thread_scheduler_impl.cc:2618-2619`, comment "Microtasks may detach the task queue and invalidate `|queue|`") calls `PerformMicrotaskCheckpoint()` unconditionally after **every** task the scheduler runs through any of its task queues — this is the concrete implementation of the HTML spec's "perform a microtask checkpoint" step, wired to task completion in general, independent of rendering. `PerformMicrotaskCheckpoint` itself (`main_thread_scheduler_impl.cc:1263-1293`) does two things: calls `EventLoop::PerformIsolateGlobalMicrotasksCheckpoint(isolate())` as an isolate-wide fallback, then iterates every live `AgentGroupScheduler` and calls its own `PerformMicrotaskCheckpoint()` — because the HTML spec defines microtask queues per similar-origin-window-agent-cluster ("agent"), not one global queue. The actual queue is `blink::scheduler::EventLoop` (`platform/scheduler/common/event_loop.cc` / `public/event_loop.h`), which wraps a `v8::MicrotaskQueue` directly (`EnqueueMicrotask` calls `microtask_queue_->EnqueueMicrotask(...)`, `event_loop.cc:60-75`), and `Agent::PerformMicrotaskCheckpoint` (`core/execution_context/agent.cc`) is a one-line delegate: `event_loop_->PerformMicrotaskCheckpoint();`.

**Blink: frame production runs script synchronously, inside the same call that produces the frame, in spec order.** `WebFrameWidgetImpl::BeginMainFrame` (`core/frame/web_frame_widget_impl.cc:3041`), invoked by the compositor on a `viz::BeginFrameArgs` (vsync) signal, calls `GetPage()->Animate(last_frame_time)` (`page.cc:1524`), which calls `PageAnimator::ServiceScriptedAnimations` (`core/page/page_animator.cc`). That function's body is, concretely, a numbered transcription of the spec: its own comments cite `https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model` step numbers directly against the code that implements them — step 6 (`pagereveal`), 7 (flush autofocus candidates), 8 (resize events), 9 (scroll events), 10 (media-query-list change events), 11 (CSS animation events), 12 (fullscreen steps), 14 (`requestAnimationFrame` callbacks, via `active_controllers[i]->ExecuteFrameCallbacks()`). All of this — actual script execution, both event-handler callbacks and rAF callbacks — runs **inside** `BeginMainFrame`, before layout/paint proceed later in the same lifecycle update (the code's own comment, "See `LocalFrameView::RunPostLifecycleSteps()` for 15 and 16," points at where the remaining post-layout spec steps continue). So the per-frame ordering is: compositor requests a frame → `BeginMainFrame` → `Animate`/`ServiceScriptedAnimations` runs pending script synchronously in spec order → style/layout/paint follow, in that same call chain. No explicit extra `PerformMicrotaskCheckpoint()` call was found inside `page_animator.cc` itself, so within a single `BeginMainFrame` call any additional checkpointing beyond what the per-task hook provides rides on V8's own callback-scope behavior rather than an explicit Blink-side call at that granularity — worth flagging as a limit of what this pass confirmed, not asserting more precision than the evidence supports.

**Gecko: the same "checkpoint after every task" rule, wired one layer lower.** `nsThread::ProcessNextEvent` (`xpcom/threads/nsThread.cpp`) wraps every runnable it pulls off the main-thread queue with `mScriptObserver->BeforeProcessTask(reallyWait)` (`nsThread.cpp:1109`) and `mScriptObserver->AfterProcessTask(mNestedEventLoopDepth)` (`nsThread.cpp:1233`), and `mScriptObserver` is typed directly as `mozilla::CycleCollectedJSContext*` (`nsThread.h:275`) — i.e. Gecko wires the JS engine's context object straight into the generic, cross-platform runnable-processing primitive, one layer lower than Blink's separate scheduler-level hook. `CycleCollectedJSContext::AfterProcessTask` (`xpcom/base/CycleCollectedJSContext.cpp:527-533`) calls `PerformMicroTaskCheckPoint()` unconditionally — the identical "after every task, drain microtasks" rule Blink implements, arrived at independently in a structurally different place in the codebase. `CycleCollectedJSContext` itself is declared `class CycleCollectedJSContext : dom::PerThreadAtomCache, public JS::JobQueue` (`xpcom/base/CycleCollectedJSContext.h:348`) — it directly implements SpiderMonkey's own abstract `JS::JobQueue` interface, the same relationship Blink's `EventLoop` has to `v8::MicrotaskQueue`.

**Gecko: frame production is likewise a distinct vsync-driven entry point that runs the spec's rendering-update steps, script included, before layout/paint, in the same call.** `nsRefreshDriver::Tick(VsyncId aId, TimeStamp aNowTime, ...)` (`layout/base/nsRefreshDriver.cpp:2278`) is the vsync-driven equivalent of `BeginMainFrame`, and it runs through a fixed, named `RenderingPhase` sequence via `RunRenderingPhase`/`RunRenderingPhaseLegacy` — `Reveal`, `FlushAutoFocusCandidates`, `ResizeSteps`, `ScrollSteps`, `EvaluateMediaQueriesAndReportChanges`, `UpdateAnimationsAndSendEvents`, `FullscreenSteps`, `AnimationFrameCallbacks`, `Layout`, `ViewTransitionOperations`, `UpdateIntersectionObservations`, `Paint` (phase names and call order read directly from `nsRefreshDriver.cpp:2418-2573` and the `RenderingPhase::*` enum uses in `nsRefreshDriver.h`). `RunRenderingPhase`'s own comment cites the spec directly, `// https://html.spec.whatwg.org/#update-the-rendering step 3` (`nsRefreshDriver.cpp:1296`) — the same "engine code is a near-literal transcription of the spec's step list" pattern found in Blink, independently. Script-running phases (event dispatch for resize/scroll/media-query steps, `AnimationFrameCallbacks`) run interleaved with, and before, `Layout` and `Paint`, all inside the same `Tick` call — structurally identical ordering to Blink's `BeginMainFrame`.

**The upshot, true of both engines and load-bearing for BlueJS's design:** there are exactly two distinct entry points into the JS engine's script/microtask state, not one unified queue. One is the generic macrotask loop (`nsThread::ProcessNextEvent` / Blink's scheduler task queues) — process one task, then unconditionally drain microtasks, repeat. The other is a vsync/compositor-driven, per-frame entry point (`nsRefreshDriver::Tick` / `BeginMainFrame`) that is *not itself* a queued macrotask in either engine — it runs the spec's script-bearing "update the rendering" steps synchronously as the first part of producing a frame, then proceeds to layout and paint in that same call. Both engines converged on this same two-entry-point shape independently (different codebases, different eras of design), which is stronger evidence for BlueJS's design than either engine's choice alone, or than reasoning from the spec's abstract processing model text without seeing how it actually gets implemented.

## 4. Assessment: recommendation for BlueJS

**Bytecode format: stack-based, single-fixed-width-per-opcode, byte-oriented — model it on SpiderMonkey, not Ignition. The real V8 evidence (Section 1) confirms this holds, though for a more precise reason than originally guessed, and the reason is worth stating explicitly rather than re-asserting the old one uncritically.** The original version of this recommendation assumed a register/accumulator emitter "has to solve a real allocation problem" that a stack machine avoids. Reading `reference/v8/src/interpreter/` shows that specific claim overstated the cost: Ignition's `BytecodeRegisterAllocator` (`src/interpreter/bytecode-register-allocator.h`) is a bump allocator under strict LIFO discipline — `NewRegister()` increments a counter, `ReleaseRegister()` asserts you're freeing the most-recently-allocated one (`bytecode-register-allocator.h:88-94`) — used via an RAII mark/release scope (`BytecodeGenerator::RegisterAllocationScope`, `bytecode-generator.cc:770-790`) that is structurally close to a stack machine's implicit push/pop, just addressed by an integer instead of stack position. So "needs a register allocator" is not, on its own, the argument for stack-based being simpler — a real, working register allocator for temporaries is nearly as cheap as a stack. What the real source shows instead, and what stack-based still avoids: (1) Ignition needs a dedicated peephole pass, `BytecodeRegisterOptimizer`, purely to undo the redundant `Star`/`Ldar`/`Mov` chatter its own emitter "uses liberally, for correctness and convenience" (its own header comment, `bytecode-register-optimizer.h:20-23`) — a whole extra class and dataflow pass with no analog needed when values just live on an implicit stack; (2) Ignition's handlers are not hand-written interpreter code but CodeStubAssembler/Turboshaft-Assembler-generated machine code, built by a real code-generation backend (`interpreter-generator.cc`'s `IGNITION_HANDLER` macro, plus a newer parallel `interpreter-generator-tsa.cc` path) and, because operand width is a runtime scale rather than fixed per opcode, compiled into up to three separate builtins per bytecode — one per `Wide`/`ExtraWide` scale (`src/builtins/generate-bytecodes-builtins-list.cc`, confirmed walking `kOperandScaleCount * kBytecodeCount` = 3 × 215 combinations) — machinery a fixed-width-per-opcode design has no reason to build at all. For an MVP with no JIT to feed, none of that buys BlueJS anything yet: interpreted execution speed for a plain threaded-dispatch loop is comparable between the two designs, and the real reason production engines moved to register/accumulator machines was to reduce push/pop traffic and hand a later JIT tier cleaner, more analyzable dataflow — an optimization concern BlueIce has explicitly and correctly deferred (`PLAN.md:21-25`). Concretely: one opcode byte, a fixed per-opcode operand shape chosen at emission time mirroring SpiderMonkey's `JOF_*` categories (no operand / `u8` / `u16` / `u32` constant-table index / `i32` jump offset), and a compile-time-constant instruction length per opcode (SpiderMonkey's `length` field in `Opcodes.h`) so the dispatch loop advances the program counter by a lookup, not a runtime computation. Do **not** build Ignition's `Wide`/`ExtraWide` runtime operand-scaling prefix for MVP — it solves a code-size problem BlueJS doesn't have yet, and now that it's confirmed to also require generating up to three separate handler bodies per scalable-operand bytecode (Section 1), it's an even worse match for an MVP interpreter than the original guess implied; if BlueJS ever needs wider operands, SpiderMonkey's approach (multiple fixed-width variants of the same logical opcode, selected once at emission time) is a strictly simpler retrofit, since it needs zero new dispatch-loop or handler-codegen machinery, only additional table entries reusing the same handler. Define the opcode list exactly once, as an `X`-macro table (SpiderMonkey's `FOR_EACH_OPCODE(MACRO)` pattern, mirrored by Ignition's own `BYTECODE_LIST` in `bytecodes.h:525-532` — both engines converge on this idiom independently) that generates the opcode enum, the dispatch/handler table, and the operand-length table together from one source of truth, so they cannot drift apart as opcodes are added. Reserve, but do not implement, a per-opcode "may use an inline cache" flag bit analogous to SpiderMonkey's `JOF_IC` (`BytecodeFormatFlags.h:52`) — an unused bit today, and the direct, already-proven hook point for a future optimization tier, matching the plan's own stated principle of leaving extension points rather than building the machinery behind them now.

**Event loop: two structurally separate entry points into the same interpreter/microtask state, exactly as both Blink and Gecko independently converged on — not spec-guessed, evidence-derived.** Concretely for `core`: (1) a generic macrotask queue (timers, message-style callbacks, anything not tied to a specific frame) that `core`'s run loop drains one task at a time — never draining the whole queue before checking on rendering, which is precisely what makes interleaving possible at all — mirroring `nsThread::ProcessNextEvent`'s per-runnable granularity. (2) After every single macrotask, unconditionally drain BlueJS's promise-job/microtask queue to completion (looping since a job can enqueue more jobs) before returning to pick up the next macrotask — this is the one rule both Blink (`OnTaskCompleted` → `PerformMicrotaskCheckpoint`) and Gecko (`AfterProcessTask` → `PerformMicroTaskCheckPoint`) implement identically despite being unrelated codebases, which is exactly the kind of two-engine agreement that should outweigh guessing from the spec's abstract text alone. (3) `core`'s render-pass/paint entry point should be its own distinct call — not a queued macrotask — that, on being invoked (vsync- or timer-driven for BlueIce's MVP), first runs whatever frame-scheduled BlueJS script exists (a `requestAnimationFrame`-equivalent, if in MVP scope; an empty/no-op step if not yet implemented) synchronously, mirroring `BeginMainFrame`/`Tick` running script before layout/paint within the same call rather than as a separately scheduled task before or after it, then drains microtasks once more (script just ran and may have queued promise reactions) before proceeding to layout and paint, so layout/paint always observe a post-microtask-settled state. (4) Keep the macrotask-queue entry point and the render-pass entry point structurally separate call sites rather than unifying them into one priority-tagged queue — both reference engines keep them separate (`cc::Scheduler`-driven `BeginMainFrame` is not a task on Blink's `MainThreadTaskQueue`; Gecko's vsync-driven `Tick` is likewise not a runnable on `nsThread`'s queue), and collapsing them would be exactly the kind of premature unification this project is trying to avoid needing to walk back later. (5) Flag as intentionally out of MVP scope rather than silently ignored: both engines partition microtask queues per "agent" (Blink's `AgentGroupScheduler`, one per similar-origin-window-agent-cluster) rather than using one global queue — for BlueIce's realistic MVP (effectively one document, one agent) a single global microtask queue is a fine simplification, but the seam both engines put at "per agent" rather than "per document" or "global" is worth remembering if multi-document/multi-frame script isolation becomes a later requirement, so that work extends the design rather than reworking it. None of the above resolves Phase 13's separate open question of in-process-vs-out-of-process script execution (`PLAN.md:35`) — the task/microtask/frame ordering rule found here holds either way, since both reference engines run script and rendering in the same process and the ordering rule is about *when* script runs relative to rendering, not *where*.
