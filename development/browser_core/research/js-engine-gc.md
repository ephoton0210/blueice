# JavaScript engine garbage collection: SpiderMonkey and V8/Chromium, and a recommendation for BlueJS

Findings from reading `../reference/gecko` (Firefox/SpiderMonkey) and `../reference/chromium` (Chromium) directly, focused on how each engine's GC algorithm actually works, how collection gets triggered, and — the question that matters most for BlueIce — what concrete mechanisms keep pause time and memory growth bounded rather than merely "eventually correct." BlueJS's GC algorithm is currently an open gap in `phase-13-bluejs-engine/PLAN.md`: the plan has decided objects will be handle/ID-addressed (`PLAN.md:29`, mirroring `blueice-dom`'s `NodeId`-into-a-table design in `backend/core/dom/src/lib.rs`) but not the collection algorithm, timing, or memory-budget behavior, and `core` carries an explicit low-memory, must-not-crash requirement (`BROWSER_CORE_PLAN.md:24`: "kept deliberately low-memory and stable: it is the one thing in the whole system that must not crash").

One important scoping caveat up front: `reference/chromium/v8/` is an **empty directory** in this checkout — `DEPS:3342-3343` shows `src/v8` is pulled from a separate `chromium_git/v8/v8.git` repository that was not fetched into this sparse checkout, so V8's own `src/heap/` (the actual Orinoco implementation — `mark-compact.cc`, `scavenger.cc`, `heap.cc`, `spaces.h`) could not be read directly; a repo-wide search for those filenames and for `mark-compact`/`scavenger` returned nothing. What *is* present and real is Blink's own GC integration surface — `third_party/blink/renderer/platform/heap/` (Oilpan) — which since Chromium's "unified heap" project shares its underlying collector engine, `cppgc`, directly with V8's own C++-managed heap; Blink's code includes and calls into `v8/include/cppgc/*.h` and `v8/include/v8-cppgc.h` throughout. Section 2 below is built on that real, in-checkout evidence rather than on general knowledge of V8, and is explicit about the one place it has to fall back to well-known public V8 facts that weren't independently verified against source in this checkout.

## 1. SpiderMonkey's GC architecture

SpiderMonkey's GC lives entirely under `js/src/gc/` (confirmed by `js/AGENTS.md`'s own architecture summary: "generational, incremental, compacting GC. Nursery + tenured heap of Arenas/Chunks"), and the in-tree doc `js/src/doc/gc.md` states its feature list plainly: precise, incremental, generational, partially concurrent, parallel, compacting, and organized around a partitioned heap (zones). The `[SMDOC] Garbage Collector` comment at the top of `js/src/gc/GC.cpp:5-100` is the canonical description: it is "an incremental mark-and-sweep garbage collector, with most sweeping carried out in the background on a parallel thread," proceeding through explicit states tracked in `JSRuntime::gcIncrementalState` — **Prepare → MarkRoots → Mark → Sweep → Finalize → Compact → Decommit** — where an incremental collection is a sequence of time-boxed *slices* (driven by `js::GCSlice()`) interleaved with mutator execution, each slice picking up wherever the last one left off.

Correctness of interleaving marking with a running mutator rests on a **snapshot-at-the-beginning** invariant (`GC.cpp:102-120`): "if a memory location (except a root) is written to, then the value it previously held must be marked" — enforced via write barriers defined in `gc/Barrier.h`. `Barrier.h:23-70` documents the concrete barrier wrapper types: `HeapPtr` (general pre+post-barrier wrapper), `GCPtr` (optimized for GC-thing fields), `PreBarriered` (pre-barrier only, "necessary when generational GC updates are handled manually"), and `HeapSlot` (optimized for object slots/elements) — i.e. SpiderMonkey already separates the *incremental-marking* barrier purpose from the *generational remembered-set* barrier purpose at the type level, not just conceptually.

**Generational collection**: SpiderMonkey implements exactly one young generation (the nursery, `gc/Nursery.h`/`.cpp`) and one old generation (the tenured heap); collecting the nursery alone is a "minor GC," collecting everything a "major GC" (`doc/gc.md:61-74`). The nursery is chunk-based (`NurseryChunkUsableSize` in `Nursery.cpp:54-59`, chunks sized via `ChunkSize = 1 << ChunkShift` = 1MB, `js/public/HeapAPI.h:55-56`) and grows/shrinks its allocable capacity dynamically (`Nursery::growAllocableSpace`/`shrinkAllocableSpace`, `Nursery.h:508-509`) targeting a **4ms** default minor-GC time goal (`JSGC_NURSERY_MAX_TIME_GOAL_MS`, `Scheduling.h:504-508`, default `TimeDuration::FromMilliseconds(4)`). Old→young cross-generational pointers are tracked by a dedicated remembered set, `gc/StoreBuffer.h`, described at `StoreBuffer.h:37-60` as observing "all writes that occur in the system and perform[ing] efficient filtering of them to derive a remembered set for nursery GC," sized by `JSGC_STORE_BUFFER_ENTRIES` (default 16384, `Scheduling.h:514-515`).

**Pretenuring** (`gc/Pretenuring.h`/`.cpp`) is a lifetime-prediction layer on top of the nursery: `Pretenuring.h:5-15` explains cells that could go in either the nursery or tenured heap are placed based on predicted lifetime, inferred from per-allocation-site statistics gathered by the middle JIT tiers; an `AllocSite` (`Pretenuring.h:56-77`) tracks `State::{Unknown,LongLived,ShortLived}` per bytecode site once it has accumulated `NormalSiteAttentionThreshold = 200` nursery allocations (`Pretenuring.h:44-46`), letting hot long-lived sites skip the nursery/copy step entirely.

**Parallel and concurrent marking**: `GC.cpp:102-131`'s SMDOC flags concurrent marking as "an experimental feature... requires building with the `--enable-gc-concurrent-marking` flag... not fully thread safe, use it at your own risk," using a *separate* `GCMarker` instance for the background thread plus main-thread buffers for work that isn't safe to do concurrently (`GC.cpp:118-127`). Concretely in this checkout, `JSGC_CONCURRENT_MARKING_ENABLED` and `JSGC_PARALLEL_MARKING_ENABLED` both default to **`false`** (`Scheduling.h:556-559`), and even when parallel marking is enabled it only activates above `JSGC_PARALLEL_MARKING_THRESHOLD_MB` (default 4MB, `Scheduling.h:492-495`) — small heaps never pay parallel-marking overhead. `gc/ParallelMarking.{h,cpp}` implements the worker-thread task (`ParallelMarkTask : public GCParallelTask`, `ParallelMarking.h:32-52`) for when it is enabled.

**Sweeping and compaction**: sweeping is broken into zone groups found via Tarjan's SCC algorithm over cross-zone pointers (`GC.cpp:139-155`) so that finalizers run correctly without requiring one giant atomic pause; things without finalizers (most of the heap) are swept on a background thread. Compacting (`gc/Compacting.cpp`) happens "at the end of a major GC as part of the last slice" and is explicitly **not incremental** — `doc/gc.md:100-111`: "Compacting involves tracing the entire heap to update pointers to moved data and is not incremental so it only happens rarely, or in response to memory pressure notifications." The heap is partitioned into independently collectible **zones** (`Zone.h`/`.cpp`), used both for isolation and to incrementalize otherwise-atomic work like compaction one zone at a time (`doc/gc.md:113-123`); atoms get special cross-zone handling via a per-zone bitmap (`gc/AtomMarking.cpp`).

## 2. Chromium/V8 GC architecture — evidence available in this checkout (Oilpan/cppgc), and the gap for V8's own JS heap

As noted above, V8's own JS-object heap implementation is absent from this checkout. What is directly readable is Blink's Oilpan GC (`third_party/blink/renderer/platform/heap/`), which is not a separate toy collector — its own documentation, `BlinkGCAPIReference.md:9-38`, points to `cppgc`, the same C++ garbage collector V8 itself now uses for its embedder-facing heap, and describes Blink-specific extensions on top of it. `ThreadState` (`platform/heap/thread_state.h:36-39`) "manages garbage collections together with V8," owning a `v8::CppHeap` attached to a `v8::Isolate` (`AttachToIsolate`/`DetachFromIsolate`, `thread_state.h:61-68`) with `GcPrologue`/`GcEpilogue` callbacks (`thread_state.h:140-144`) tying Oilpan collections to V8's own unified-heap GC cycles — this is real, direct evidence that Blink's C++ objects and V8's JS objects are collected together as one heap in modern Chromium, not two independent systems.

`BlinkGCAPIReference.md:34-38` states the mode of operation plainly: "Blink uses concurrent garbage collection (marking and sweeping), except for during thread termination and heap destruction. Blink tries to schedule GCs through the message loop where it is known that no objects are referred to from the native stack. When under memory pressure, Blink triggers a conservative GC on allocations." That is three distinct trigger classes evidenced directly in the docs and code: **idle/message-loop scheduling** (avoid stealing time from a frame in progress), **incremental+concurrent marking and sweeping** as the default mode (not opt-in, unlike SpiderMonkey's concurrent marking), and **explicit memory-pressure triggers**. The memory-pressure path is concretely exercised in `blink_gc_memory_dump_provider.cc:96-107`: when a memory dump needs to be precise, it calls `thread_state_->isolate_->LowMemoryNotification()` to "trigger a unified heap GC in V8... to eliminate as much garbage as possible" before measuring.

**Generational and write-barrier evidence**: `write_barrier.h:17-95` shows `cppgc::subtle::HeapConsistency::GetWriteBarrierType` dispatching a store to one of three cases — `kMarking` (`DijkstraWriteBarrier`, an incremental-marking insertion barrier), `kGenerational` (`GenerationalBarrier` / `GenerationalBarrierForUncompressedSlot`, a young-generation remembered-set barrier), or `kNone`. This confirms cppgc/Oilpan, like SpiderMonkey, cleanly separates the *incremental-marking* barrier from the *generational* barrier at the API level, and confirms a young generation exists: `thread_state.h:118-120` exposes `CollectGarbageInYoungGenerationForTesting`, a minor-GC-only collection distinct from `CollectAllGarbageForTesting` (`thread_state.h:112-117`).

**Heap partitioning and compaction scope**: `custom_spaces.h:22-59` defines Blink's own space partitioning on top of cppgc — `CompactableHeapVectorBackingSpace` and `CompactableHeapHashTableBackingSpace` (both `kSupportsCompaction = true`), versus `NodeSpace`, `CSSValueSpace`, `LayoutObjectSpace`, and `ElementSpace` (type-segregated but not marked compactable). This is the same "zones/arenas by kind" idea SpiderMonkey uses, but here compaction is explicitly scoped to only the space types known to fragment badly (vector/hash-table backing stores), not the whole heap — a narrower, cheaper compaction story than SpiderMonkey's zone-wide compacting pass.

**Memory accounting**: `blink_gc_memory_dump_provider.cc:93-244` walks `cppgc::HeapStatistics` and reports, per space and per page, `committed_size_bytes`, `resident_size_bytes`, `used_size_bytes`, a derived `fragmentation` percentage (`GetFragmentation`, `blink_gc_memory_dump_provider.cc:81-89`: unused-but-resident memory as a percent of resident), and per-size-class free-list bucket occupancy (`free_list_stats.bucket_size`/`free_count`/`free_size`, lines 198-218) — concrete evidence of a segregated free-list allocator with first-class fragmentation/budget observability built in for the embedder (Chrome's own memory-pressure and DevTools tooling) to act on.

**The gap, stated explicitly**: V8's own JS-heap collector — publicly documented as "Orinoco," combining a young-generation Scavenger (semispace copying) with an old-generation incremental/concurrent Mark-Compact — is widely known background knowledge but was **not** verified against source in this checkout, since `v8/src/heap/*.cc` is absent. Everything else in this section (idle-scheduling, concurrent marking+sweeping as default, memory-pressure-triggered GC, generational write barriers, scoped compaction, free-list/fragmentation accounting) is drawn from files actually present in `reference/chromium/third_party/blink/renderer/platform/heap/` and is directly relevant because it is the same GC engine (`cppgc`) V8 itself now runs.

## 3. How each engine bounds pause time and memory growth in practice

SpiderMonkey does not hardcode a pause-time target inside the engine itself: `TuningDefaults::DefaultTimeBudgetMS = 0` means "unlimited by default" (`Scheduling.h:540-541`) — the *embedder* (Gecko) is responsible for choosing a real per-slice budget via `JS::SliceBudget`. What SpiderMonkey does provide are escape valves that trade pause-time predictability for guaranteed forward progress when incremental collection is falling behind the mutator's allocation rate: `GCRuntime::maybeIncreaseSliceBudgetForLongCollections` (`GC.cpp:4861-4880`) linearly extends the slice budget from 0ms extra at 1500ms total collection time to 100ms extra at 2500ms, and `maybeIncreaseSliceBudgetForUrgentCollections` (`GC.cpp:4883` onward) extends the budget further based on `incrementalBytesRemaining` — how close each zone is to its hard non-incremental limit. In other words: SpiderMonkey deliberately lets an individual slice run longer, on purpose, rather than letting a collection that can't keep up run forever while the heap keeps growing underneath it.

The heap-growth-triggered path is the primary *memory-growth* bound. `Scheduling.h:380-391` defines `JSGC_SMALL_HEAP_INCREMENTAL_LIMIT` (default **1.70×** the trigger threshold) and `JSGC_LARGE_HEAP_INCREMENTAL_LIMIT` (default **1.10×**) — the multiple of the trigger size at which SpiderMonkey gives up on incremental collection and forces a non-incremental (stop-the-world) GC; large heaps get a tighter margin because absolute bytes matter more for OOM risk, small heaps get a looser margin tuned for responsiveness (the comment notes 1.7 is "at least" what's needed "to maintain performance on splay-latency"). Between GCs, the trigger threshold itself grows adaptively: `JSGC_LOW_FREQUENCY_HEAP_GROWTH` (1.5×, normal case) versus `JSGC_HIGH_FREQUENCY_SMALL_HEAP_GROWTH`/`JSGC_HIGH_FREQUENCY_LARGE_HEAP_GROWTH` (3.0× / 1.5×) when GCs are happening more than once per second (`highFrequencyThreshold`, default 1 second, `Scheduling.h:393-401`) — small heaps are allowed to grow faster between GCs under allocation pressure (fewer, larger GCs) while large heaps stay tightly bounded regardless. The whole scheduling doc (`Scheduling.h:87-260`) frames this explicitly as a cost tradeoff between "GC too soon" (wasted work revisiting a nearly-identical graph) and "GC too late" (OOM, fragmentation, management overhead), with numbered `GCReason`s (`MAYBEGC`, `ALLOC_TRIGGER`, `TOO_MUCH_MALLOC`, `MEM_PRESSURE`, `LAST_DITCH`) each corresponding to a different point on that tradeoff.

Generational collection is itself the largest lever for keeping *typical-case* pauses small: because minor-GC cost scales with nursery-survivor count rather than total heap size, and the nursery is capacity-bounded (chunk-based, adaptively resized against a 4ms time goal, `JSGC_NURSERY_MAX_TIME_GOAL_MS`), the overwhelming majority of allocations (short-lived objects, per the standard generational-GC hypothesis) are reclaimed in a bounded, small, frequent pause rather than ever contributing to a major-GC pause at all. Pretenuring further reduces wasted copying work (and thus pause time) by keeping allocation sites known to be long-lived out of the nursery's copy path entirely. Compaction is the one piece explicitly *not* made incremental — SpiderMonkey accepts an atomic, whole-zone pause for it, but bounds its cost by making it rare (end of a major GC, or on memory-pressure notification, not on every collection). Concurrent and parallel marking are off by default in this checkout and gated behind a heap-size threshold (4MB) when enabled, i.e. SpiderMonkey's own default posture already favors "skip the complexity, keep it single-threaded" below a fairly small heap size — worth noting since it's close to what BlueJS's MVP heap sizes are likely to look like.

Oilpan/cppgc's bounding strategy leans on different mechanisms for the same goal: idle/message-loop scheduling avoids doing GC work during a frame the user is waiting on at all (rather than shrinking the pause once started), concurrent marking+sweeping as the *default* mode moves most of the actual tracing/reclamation work off the main thread so it barely shows up as a "pause" in the traditional sense, and compaction is scoped to only the two space types prone to fragmentation (vector/hash-table backing stores) rather than applied heap-wide, bounding compaction's cost by bounding its scope rather than by making it incremental. `LowMemoryNotification` gives the embedding process (Chrome) an explicit, on-demand hook to force reclamation the moment the OS signals memory pressure, rather than relying purely on internal heap-growth heuristics to notice in time — a defense specifically against the "unbounded growth" failure mode rather than the "long pause" one.

## 4. Assessment: a concrete MVP GC recommendation for BlueJS

**Framing**: `phase-13-bluejs-engine/PLAN.md:17` states the governing constraint for this whole phase explicitly: "designing for high-performance-later is the priority for this phase; actually building that performance is not... pick foundational structure now that makes optimization *additive* later, even while building none of the optimization itself yet." Both reference engines are multi-decade, multi-hundred-engineer optimization targets — SpiderMonkey's own docs flag concurrent marking as still "experimental... use at your own risk" after ~20 years of development, and Oilpan's default concurrent marking+sweeping required the kind of heap-consistency subtleties `cppgc::subtle::HeapConsistency` exists to paper over. None of that is a reasonable MVP target, and the plan is explicit that it shouldn't be. What both engines *do* agree on, and what generalizes cleanly to a from-scratch implementation, is that a small young generation collected cheaply and frequently, sitting in front of a simpler old-generation collector, is the single highest-leverage structural decision — everything past that (incremental slicing, concurrent/parallel marking, adaptive pretenuring, scoped compaction) is refinement on top of it, not a prerequisite for it.

**Recommended MVP shape**: a two-generation collector — a small, fixed-capacity, bump-allocated (or simple semispace-copying) **nursery**, collected by a stop-the-world **minor GC** whenever it fills, promoting all survivors to the tenured generation on their first minor GC (no allocation-site pretenuring — SpiderMonkey's `AllocSite` machinery is exactly the kind of "actual optimization" the plan says to defer); and a **tenured heap** collected by a plain, non-incremental, non-compacting **mark-sweep** major GC, triggered proactively by a heap-growth-factor rule modeled on SpiderMonkey's simplest case (e.g. trigger a major GC once live bytes have grown by roughly 1.5–2× since the last collection — the same order of magnitude as SpiderMonkey's `JSGC_LOW_FREQUENCY_HEAP_GROWTH` default of 1.5×) rather than waiting for an absolute ceiling. Given `core`'s existing low-memory requirement, add an explicit configurable max-heap-bytes ceiling as a hard backstop (SpiderMonkey's `JSGC_MAX_BYTES`/non-incremental-then-OOM escape hatch and Oilpan's `LowMemoryNotification` are the two precedents) so `core`'s own process-level memory monitor can force a collection under pressure rather than relying solely on BlueJS's internal heuristics.

**Only one barrier is needed, not two**: both reference engines' code shows write barriers serve two genuinely separate purposes — an incremental-marking snapshot-at-the-beginning barrier (SpiderMonkey's `PreBarriered`/`HeapPtr`; Oilpan's `DijkstraWriteBarrier`) and a generational remembered-set barrier (SpiderMonkey's `StoreBuffer`; Oilpan's `GenerationalBarrier`). Because the MVP major GC proposed above is fully stop-the-world (never interleaved with mutator execution), it needs **no incremental-marking barrier at all** — that entire class of complexity (and its associated correctness risk, which is exactly what makes concurrent/incremental GC hard to get right) simply doesn't apply yet. The generational barrier is still required, since promoting survivors out of the nursery doesn't eliminate old→young pointers created after promotion — but it can be as simple as an unconditional check on every store of a handle into an object field ("does this old-gen object now point at a nursery handle? if so, record it in a remembered set") rather than a precise per-slot store buffer; a coarse, easy-to-get-right remembered set is an acceptable MVP cost given the plan's own priorities.

**A BlueJS-specific advantage worth designing in now**: because BlueJS objects are already going to be handle/ID-addressed through a table (mirroring `blueice-dom`'s `NodeId`, per `PLAN.md:29`) rather than referenced by raw pointer the way SpiderMonkey's `Cell*`/Oilpan's `Member<T>` are, **compaction becomes structurally cheap later even if MVP never implements it**: moving an object's backing storage only requires updating that one handle-table entry, not tracing the entire heap to rewrite every inbound pointer — which is precisely the expensive, non-incremental step SpiderMonkey's `Compacting.cpp` has to do (`doc/gc.md:109-111`: "tracing the entire heap to update pointers to moved data"). This is a direct, concrete instance of the plan's "additive, not a rewrite" test: shipping a plain non-compacting mark-sweep old generation for MVP does not foreclose adding compaction later, and adding it later should be markedly simpler for BlueJS than it was for either reference engine specifically *because* of the handle-addressing decision already made. Worth stating in the object-model design doc as the reason that decision pays off doubly (DOM/JS reference uniformity *and* cheap future compaction), not just once.

**Deliberately deferred, and why each is safe to defer**: incremental marking/slicing (unnecessary if major GC stays stop-the-world and heap size stays capped low by the growth-factor trigger — the same argument SpiderMonkey's own default-off `JSGC_CONCURRENT_MARKING_ENABLED`/`JSGC_PARALLEL_MARKING_ENABLED` and its 4MB parallel-marking threshold implicitly make: below a fairly modest heap size, none of this machinery earns its complexity); concurrent/parallel marking (both reference engines treat this as their hardest, most failure-prone piece even after decades of engineering — squarely out of scope per the plan's own risk-acceptance framing); allocation-site pretenuring (a pure throughput optimization, not a correctness or bound-safety mechanism); adaptive nursery resizing against a time-goal (start with a fixed nursery capacity on the order of a few MB — SpiderMonkey's own nursery chunks are 1MB each — and revisit only if profiling on real BlueJS workloads shows minor-GC pauses are a problem). What should **not** be deferred is the state-machine shape of the collector itself: even though MVP's major GC runs each phase (mark, then sweep) to completion synchronously, structuring it as explicit, discrete phases operating over an explicit worklist (mirroring SpiderMonkey's `Prepare/MarkRoots/Mark/Sweep` states, `GC.cpp:42-56`) rather than one recursive mark function means a future incremental-slicing pass can time-box between existing phase boundaries instead of requiring the collector to be rewritten — which is exactly the kind of foundational choice `PLAN.md:17`'s "does this block a future optimization tier" test is asking for.

**Net assessment**: unbounded memory growth is avoided the same way SpiderMonkey avoids it in its simplest configuration — a heap-growth-factor trigger that fires proactively rather than waiting for an absolute ceiling, backed by a hard configurable max as a last resort, which fits `core`'s existing low-memory requirement directly rather than fighting it. Unpredictable multi-second pauses are avoided primarily by *keeping the collectible heap deliberately small* (the nursery absorbs the high-frequency short-lived case cheaply, the growth-factor trigger keeps the tenured heap from ever growing large enough for a stop-the-world mark-sweep pass to take seconds) rather than by incremental slicing, which is the right tradeoff for an MVP that is explicitly not chasing V8/SpiderMonkey-class raw performance — and if real-world profiling later shows major-GC pauses are still a problem at BlueJS's actual working-set sizes, the state-machine structure recommended above is what makes adding incremental slicing an additive change rather than the kind of full-engine rewrite the plan calls out V8's Crankshaft→TurboFan and SpiderMonkey's JägerMonkey→IonMonkey→Warp transitions as cautionary precedent for.
