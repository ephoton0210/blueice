# JavaScript engine garbage collection: SpiderMonkey and V8/Chromium, and a recommendation for BlueJS

Findings from reading `../reference/gecko` (Firefox/SpiderMonkey) and `../reference/chromium` (Chromium) directly, focused on how each engine's GC algorithm actually works, how collection gets triggered, and — the question that matters most for BlueIce — what concrete mechanisms keep pause time and memory growth bounded rather than merely "eventually correct." BlueJS's GC algorithm is currently an open gap in `phase-13-bluejs-engine/PLAN.md`: the plan has decided objects will be handle/ID-addressed (`PLAN.md:29`, mirroring `blueice-dom`'s `NodeId`-into-a-table design in `backend/core/dom/src/lib.rs`) but not the collection algorithm, timing, or memory-budget behavior, and `core` carries an explicit low-memory, must-not-crash requirement (`BROWSER_CORE_PLAN.md:24`: "kept deliberately low-memory and stable: it is the one thing in the whole system that must not crash").

One important scoping note, now resolved: earlier drafts of this note found `reference/chromium/v8/` **empty** in the Chromium checkout (`DEPS:3342-3343` shows `src/v8` is pulled from a separate `chromium_git/v8/v8.git` repository not fetched into that sparse checkout), so V8's own `src/heap/` could not be read directly, and section 2 substituted evidence from Blink's Oilpan GC (`third_party/blink/renderer/platform/heap/`, which shares V8's `cppgc` engine under Chromium's "unified heap" project) as a reasoned proxy, explicitly flagged as a substitution rather than real V8 source. V8's own source is now available at `reference/v8` — a separate, independently-cloned checkout of V8's canonical repository, not part of the Chromium checkout — and section 2 below has been rewritten from that real source; see its opening paragraph for how the evidentiary picture changed.

## 1. SpiderMonkey's GC architecture

SpiderMonkey's GC lives entirely under `js/src/gc/` (confirmed by `js/AGENTS.md`'s own architecture summary: "generational, incremental, compacting GC. Nursery + tenured heap of Arenas/Chunks"), and the in-tree doc `js/src/doc/gc.md` states its feature list plainly: precise, incremental, generational, partially concurrent, parallel, compacting, and organized around a partitioned heap (zones). The `[SMDOC] Garbage Collector` comment at the top of `js/src/gc/GC.cpp:5-100` is the canonical description: it is "an incremental mark-and-sweep garbage collector, with most sweeping carried out in the background on a parallel thread," proceeding through explicit states tracked in `JSRuntime::gcIncrementalState` — **Prepare → MarkRoots → Mark → Sweep → Finalize → Compact → Decommit** — where an incremental collection is a sequence of time-boxed *slices* (driven by `js::GCSlice()`) interleaved with mutator execution, each slice picking up wherever the last one left off.

Correctness of interleaving marking with a running mutator rests on a **snapshot-at-the-beginning** invariant (`GC.cpp:102-120`): "if a memory location (except a root) is written to, then the value it previously held must be marked" — enforced via write barriers defined in `gc/Barrier.h`. `Barrier.h:23-70` documents the concrete barrier wrapper types: `HeapPtr` (general pre+post-barrier wrapper), `GCPtr` (optimized for GC-thing fields), `PreBarriered` (pre-barrier only, "necessary when generational GC updates are handled manually"), and `HeapSlot` (optimized for object slots/elements) — i.e. SpiderMonkey already separates the *incremental-marking* barrier purpose from the *generational remembered-set* barrier purpose at the type level, not just conceptually.

**Generational collection**: SpiderMonkey implements exactly one young generation (the nursery, `gc/Nursery.h`/`.cpp`) and one old generation (the tenured heap); collecting the nursery alone is a "minor GC," collecting everything a "major GC" (`doc/gc.md:61-74`). The nursery is chunk-based (`NurseryChunkUsableSize` in `Nursery.cpp:54-59`, chunks sized via `ChunkSize = 1 << ChunkShift` = 1MB, `js/public/HeapAPI.h:55-56`) and grows/shrinks its allocable capacity dynamically (`Nursery::growAllocableSpace`/`shrinkAllocableSpace`, `Nursery.h:508-509`) targeting a **4ms** default minor-GC time goal (`JSGC_NURSERY_MAX_TIME_GOAL_MS`, `Scheduling.h:504-508`, default `TimeDuration::FromMilliseconds(4)`). Old→young cross-generational pointers are tracked by a dedicated remembered set, `gc/StoreBuffer.h`, described at `StoreBuffer.h:37-60` as observing "all writes that occur in the system and perform[ing] efficient filtering of them to derive a remembered set for nursery GC," sized by `JSGC_STORE_BUFFER_ENTRIES` (default 16384, `Scheduling.h:514-515`).

**Pretenuring** (`gc/Pretenuring.h`/`.cpp`) is a lifetime-prediction layer on top of the nursery: `Pretenuring.h:5-15` explains cells that could go in either the nursery or tenured heap are placed based on predicted lifetime, inferred from per-allocation-site statistics gathered by the middle JIT tiers; an `AllocSite` (`Pretenuring.h:56-77`) tracks `State::{Unknown,LongLived,ShortLived}` per bytecode site once it has accumulated `NormalSiteAttentionThreshold = 200` nursery allocations (`Pretenuring.h:44-46`), letting hot long-lived sites skip the nursery/copy step entirely.

**Parallel and concurrent marking**: `GC.cpp:102-131`'s SMDOC flags concurrent marking as "an experimental feature... requires building with the `--enable-gc-concurrent-marking` flag... not fully thread safe, use it at your own risk," using a *separate* `GCMarker` instance for the background thread plus main-thread buffers for work that isn't safe to do concurrently (`GC.cpp:118-127`). Concretely in this checkout, `JSGC_CONCURRENT_MARKING_ENABLED` and `JSGC_PARALLEL_MARKING_ENABLED` both default to **`false`** (`Scheduling.h:556-559`), and even when parallel marking is enabled it only activates above `JSGC_PARALLEL_MARKING_THRESHOLD_MB` (default 4MB, `Scheduling.h:492-495`) — small heaps never pay parallel-marking overhead. `gc/ParallelMarking.{h,cpp}` implements the worker-thread task (`ParallelMarkTask : public GCParallelTask`, `ParallelMarking.h:32-52`) for when it is enabled.

**Sweeping and compaction**: sweeping is broken into zone groups found via Tarjan's SCC algorithm over cross-zone pointers (`GC.cpp:139-155`) so that finalizers run correctly without requiring one giant atomic pause; things without finalizers (most of the heap) are swept on a background thread. Compacting (`gc/Compacting.cpp`) happens "at the end of a major GC as part of the last slice" and is explicitly **not incremental** — `doc/gc.md:100-111`: "Compacting involves tracing the entire heap to update pointers to moved data and is not incremental so it only happens rarely, or in response to memory pressure notifications." The heap is partitioned into independently collectible **zones** (`Zone.h`/`.cpp`), used both for isolation and to incrementalize otherwise-atomic work like compaction one zone at a time (`doc/gc.md:113-123`); atoms get special cross-zone handling via a per-zone bitmap (`gc/AtomMarking.cpp`).

## 2. V8's GC architecture (Orinoco): generational Scavenger + incremental/concurrent/parallel Mark-Sweep-Compact — verified against real V8 source

This section originally substituted evidence from Blink's Oilpan GC (`cppgc`) for V8's own JS-heap collector, because at the time `reference/chromium/v8/` was an empty DEPS-managed placeholder and V8's real `src/heap/` could not be read from this repo; that gap is now closed — `reference/v8` is a real, independently-cloned checkout of V8's own canonical repository, verified directly (`git -C reference/v8 log -1` shows genuine, recent commit history, e.g. an August 2026 `mksnapshot` change carrying `Cr-Commit-Position: refs/heads/main@{#109653}`), with a full `src/heap/` tree present (140+ files under `src/heap/` alone, plus first-party design docs under `docs/heap/`). This section has been rewritten from scratch against that real source, and the earlier Oilpan-substitute content it contained has been replaced, not kept alongside the new evidence.

V8's own JS-heap collector calls itself **Orinoco** in its own source — `src/flags/flag-definitions.h:4263`'s section header reads "// Parallel and concurrent GC (Orinoco) related flags." — and its implementation lives under `reference/v8/src/heap/`, which also ships first-party design docs at `docs/heap/garbage-collection.md`, `docs/heap/heap-overview.md`, `docs/heap/marking-and-sweeping.md`, and `docs/heap/compaction.md` describing the same architecture the `.cc`/`.h` files implement. Like SpiderMonkey, V8 is generational: `docs/heap/garbage-collection.md:3` states it directly ("It is a generational collector, meaning it divides the heap into different generations based on object lifetime"), and the generation-selection logic is real code, not just doc prose — `Heap::YoungGenerationCollector()` (`heap.h:379-382`) returns `GarbageCollector::SCAVENGER` by default, or `GarbageCollector::MINOR_MARK_SWEEPER` only if the experimental, off-by-default `--minor-ms` flag is set, and `Heap::IsYoungGenerationCollector()` (`heap.h:372-375`) treats both as distinct from `GarbageCollector::MARK_COMPACTOR`, which collects the old generation.

The default young generation ("New Space") is collected by the **Scavenger**, a semispace copying collector in the classic Cheney style: `docs/heap/garbage-collection.md:15-22` describes New Space split into To-Space and From-Space, new objects allocated into To-Space, and a Scavenge cycle that traces live objects out of From-Space and copies them into To-Space (or promotes them into Old Space) — "a copying collector, which compacts memory as it goes, leaving no fragmentation in the young generation." The implementation is `src/heap/scavenger.{cc,h}`, with parallel work distributed via `src/heap/parallel-work-item.h` and `src/heap/index-generator.h`, and `parallel_scavenge` defaults **true** (`flag-definitions.h:2582`). An alternative young-generation collector, **Minor Mark-Sweep** ("Minor MS", `src/heap/minor-mark-sweep.cc`), is explicitly experimental and off by default — `DEFINE_EXPERIMENTAL_FEATURE(minor_ms, "perform young generation mark sweep GCs")` (`flag-definitions.h:3821`), and `DEFINE_EXPERIMENTAL_FEATURE` itself expands to a flag defaulting `false` (`flag-definitions.h:271-273`). `docs/heap/garbage-collection.md:24-34` describes Minor MS as non-moving mark-sweep that can promote whole pages instead of copying individual objects — i.e. V8 ships two young-gen strategies and defaults to the simpler copying one, not the mark-sweep one.

The old generation ("Old Space") is collected by `MarkCompactCollector`, whose own class comment reads "Collector for young and old generation" (`mark-compact.h:57-58` — it also drives young-generation root/weak processing during a full GC even though Scavenger is the normal young-gen path). Marking uses a per-page bitmap (`MarkingBitmap`, `src/heap/marking.h`, per `docs/heap/marking-and-sweeping.md:23-26`) plus a worklist-driven traversal (`MarkingVisitor`, `src/heap/marking-visitor.h`) that pops grey objects, visits their fields via `BodyDescriptor`, and marks and pushes newly-discovered objects; the worklist (`src/heap/marking-worklist.{h,cc}`) is segmented per-thread with a shared global pool so idle worker threads can work-steal segments (`docs/heap/marking-and-sweeping.md:37-39`), and weak references are resolved only on the main thread once the transitive closure is known (`docs/heap/marking-and-sweeping.md:19-21`). Sweeping (`src/heap/sweeper.cc`) walks Old Space pages, turns unmarked ranges into `Filler` objects, and feeds them to per-space free lists (`docs/heap/marking-and-sweeping.md:66-76`); `concurrent_sweeping` defaults **true** (`flag-definitions.h:2617`).

This is where V8's default posture diverges sharply from SpiderMonkey's: SpiderMonkey's own SMDOC (section 1 above) calls concurrent marking "experimental... not fully thread safe, use it at your own risk," off by default; V8 ships incremental, concurrent, *and* parallel marking **on by default** in ordinary builds — `incremental_marking` defaults `true` (`flag-definitions.h:2570`), `concurrent_marking` defaults `true` on essentially every real build (`flag-definitions.h:2599`, gated only on the `V8_ATOMIC_OBJECT_FIELD_WRITES` build config that ordinary 64-bit builds have), and `parallel_marking` defaults `true` (`flag-definitions.h:2612`). V8 bounds the *cost* of doing this concurrently rather than avoiding it: `IncrementalMarking::AdvanceOnAllocation` steps are hard-capped by `kMaxStepSizeOnTask = 1ms` and `kMaxStepSizeOnAllocation = 5ms` (`incremental-marking.cc:56-60`), and marking doesn't even start below a small-heap floor — `IncrementalMarking::IsBelowActivationThresholds()` (`incremental-marking.cc:135-138`) bails out while both `OldGenerationConsumedBytes()` and `GlobalConsumedBytes()` stay under `kV8ActivationThreshold`/`kGlobalActivationThreshold`, both `8 * MB` (`incremental-marking.cc:63-64`) — a direct structural analogue of SpiderMonkey's own small-heap bypass (its 4MB parallel-marking threshold, section 1 above), just applied to incremental marking as a whole rather than only to the parallel variant. Concurrency safety costs real, visible engineering: an "on-hold worklist" holds objects a background thread can't safely trace because they sit in the mutator's active allocation buffer (`docs/heap/marking-and-sweeping.md:48-51`, `WRITE_BARRIER.md:29`), and `ObjectLockGuard` (`src/heap/object-lock.h`) gives certain concurrently-transitioning objects (e.g. strings) explicit locks against background-thread races (`docs/heap/marking-and-sweeping.md:61-64`).

Compaction ("Mark-Sweep-Compact") is the old generation's third phase and, like SpiderMonkey's, doesn't interleave arbitrary mutator work mid-move — but unlike SpiderMonkey's whole-zone compacting pass (section 1's `doc/gc.md:100-111`), V8 scopes it to a heuristically-chosen subset of pages: `CollectEvacuationCandidates` picks pages whose free space exceeds a fragmentation threshold, sorts candidates by ascending live-byte count (most-free-space-first) to maximize reclaimed bytes per byte copied, and `ComputeEvacuationHeuristics` caps the total with a `max_evacuated_bytes` budget that varies by mode (`ReduceMemory`, `OptimizeForMemoryUsage`, or ordinary latency-sensitive) — all per `docs/heap/compaction.md:11-16`, backed by the real function names in `src/heap/mark-compact.cc`. Moved objects leave a forwarding address in their old map word (`docs/heap/compaction.md:23-26`, matching the forwarding-pointer mechanism `docs/heap/marking-and-sweeping.md:53-56` also describes for marking), and some young-generation survivors skip copying entirely via **page promotion** — moving an entire page's ownership from New Space to Old Space by updating metadata rather than copying each object (`docs/heap/compaction.md:20`, `docs/heap/garbage-collection.md:32`), gated by `minor_ms_page_promotion_threshold`/`minor_ms_page_promotion_max_lab_threshold` (`flag-definitions.h:988-994`).

`src/heap/WRITE_BARRIER.md` is V8's own barrier design doc, and it states the barrier serves **three** purposes, not the two SpiderMonkey's code (section 1) and Oilpan's code (formerly this section) showed: recording old-to-new references for the generational GC (`OLD_TO_NEW` remembered set, "always enabled"), preventing black-to-white references during incremental/concurrent marking (active only "while incremental/concurrent marking is running"), and recording old-to-old references into evacuation candidates so compaction can update them (`WRITE_BARRIER.md:5-10`) — this third purpose exists specifically *because* compaction here is scoped/selective rather than whole-heap: only pointers into the pages chosen as evacuation candidates need tracking. `WRITE_BARRIER.md:19-29` documents the same "initializing store into the most recent young allocation needs no barrier at all" optimization SpiderMonkey and Oilpan both have, and separately notes the barrier is implemented up to four times over — once per code-generation tier (Turbofan, Maglev, Sparkplug, plus the shared CSA/interpreter builtins) plus a shared C++ slow path (`WRITE_BARRIER.md:31-74`) — a concrete measure of how much engineering surface "inform the GC about a pointer write" touches once concurrency and multiple JIT tiers are involved.

V8's trigger logic is a real state machine, not docs prose: `Heap::IncrementalMarkingLimitReached()` (`heap.cc:5630-5739`) returns one of four `IncrementalMarkingLimit` values — `kNoLimit` ("either incremental marking is disabled or it's too early to start"), `kSoftLimit` ("should be started soon"), `kHardLimit` ("should be started immediately"), and `kFallbackForEmbedderLimit` ("as soon as the embedder does not allocate with high throughput anymore") — driven primarily by comparing `OldGenerationSpaceAvailable()`/`GlobalSpaceAvailable()` against `NewSpaceTargetCapacity()` (`heap.cc:5706-5723`), with explicit early-outs for high memory pressure (`HighMemoryPressure()`, `heap.cc:5654-5658`) and for load-time/input-handling responsiveness modes that deliberately defer GC past the normal limit (`ShouldOptimizeForLoadTime`/`ShouldOptimizeForInputHandlingResponsiveness`, `heap.cc:5729-5736`). Two further trigger paths exist alongside this one: `MemoryReducer` (`src/heap/memory-reducer.cc`) watches for a low mutator allocation rate and schedules a delayed, less-urgent GC to reclaim memory during idle periods (`kShortDelayMs = 500`, `kWatchdogDelayMs = 100000`, `memory-reducer.cc:18-19`) — the closest real V8 analogue to the "schedule through the message loop" idea this section's earlier, Oilpan-based draft inferred from Blink, now grounded in V8's own task-priority scheduling instead; and `MinorGCJob` (`src/heap/minor-gc-job.cc`) schedules a background task for the *young* generation once New Space reaches a percentage of capacity — `YoungGenerationTaskTriggerSize` (`minor-gc-job.cc:21-30`) computes that threshold from `v8_flags.minor_gc_task_trigger`, which defaults to **80** percent (`flag-definitions.h:2584`).

Memory-growth bounding is more mathematically explicit in V8 than SpiderMonkey's fixed-ratio thresholds: `MemoryController<Trait>::GrowingFactor` (`heap-controller.cc:65-94`) computes how much the old-generation allocation limit should grow after each GC, combining a hard cap (`MaxGrowingFactor`, `heap-controller.cc:97+`, up to 4.0x on memory-rich devices) with a dynamic factor (`DynamicGrowingFactor`, `heap-controller.cc:165-182`) derived from the measured ratio of GC speed to mutator (allocation) speed, explicitly tuned toward a **target mutator utilization of 0.97** (`BaseControllerTrait::kTargetMutatorUtilization`, `heap-controller.h:23`) — V8 sizes the heap so that, in steady state, the mutator gets roughly 97% of wall-clock time and GC gets about 3%, rather than reacting only after a slice runs long the way SpiderMonkey's escape valves do. `MemoryController<Trait>::ComputeSqrtLimit` (`heap-controller.cc:40-61`) is a second, alternative growth model based on a published result (the comment cites `https://arxiv.org/abs/2204.10455`) that sets the limit to live-bytes-at-last-GC plus a term proportional to `sqrt(allocation_speed * live_bytes)`, clamped by `sqrt_allocation_limits_min_growing_factor`/`...max_growing_factor` of the prior heap size. V8 also picks its *initial* heap sizes from actual physical memory rather than one fixed default — `Heap::OldGenerationSizeFromPhysicalMemory` (`heap.cc:354-367`) divides physical memory by 2 (64-bit) or 4 (Android/32-bit) and clamps the result between `kDefaultMinHeapSize = 256 * MB` (`heap.h:320`) and a platform-scaled maximum, and `Heap::HeapLimitMultiplier`/`DefaultInitialOldGenerationSize` (`heap.cc:4819-4836`) scale the ceiling further by pointer size — a layer of physical-memory-aware adaptivity SpiderMonkey's fixed `Scheduling.h` constants (section 1 above) don't have.

The earlier Oilpan-substitution version of this section inferred, from Blink's side (`ThreadState` owning a `v8::CppHeap` attached to a `v8::Isolate`), that Blink's C++ objects and V8's JS objects are collected together as one heap in modern Chromium; V8's own source directly confirms this from the other side — `src/heap/cppgc-js/` contains `cpp-heap.{cc,h}` (V8's embedding of the `cppgc` engine as `v8::CppHeap`), `unified-heap-marking-visitor.{h,cc}`/`unified-heap-marking-state.{h,cc}` (marking that walks both heaps as one graph), and `cross-heap-remembered-set.{h,cc}` (a remembered set for references crossing between the JS heap and the C++ `cppgc` heap). That confirms the earlier inference was directionally correct, but `cppgc` is a *separate* collector for embedder/C++-managed objects, unified at the marking/remembered-set level with the JS-object collector documented above (`Scavenger`/`MarkCompactCollector`, V8's own heap proper) — not the same code, and not something BlueJS needs to replicate, since BlueJS has no analogous "two type systems sharing one GC" problem to solve.

## 3. How each engine bounds pause time and memory growth in practice

SpiderMonkey does not hardcode a pause-time target inside the engine itself: `TuningDefaults::DefaultTimeBudgetMS = 0` means "unlimited by default" (`Scheduling.h:540-541`) — the *embedder* (Gecko) is responsible for choosing a real per-slice budget via `JS::SliceBudget`. What SpiderMonkey does provide are escape valves that trade pause-time predictability for guaranteed forward progress when incremental collection is falling behind the mutator's allocation rate: `GCRuntime::maybeIncreaseSliceBudgetForLongCollections` (`GC.cpp:4861-4880`) linearly extends the slice budget from 0ms extra at 1500ms total collection time to 100ms extra at 2500ms, and `maybeIncreaseSliceBudgetForUrgentCollections` (`GC.cpp:4883` onward) extends the budget further based on `incrementalBytesRemaining` — how close each zone is to its hard non-incremental limit. In other words: SpiderMonkey deliberately lets an individual slice run longer, on purpose, rather than letting a collection that can't keep up run forever while the heap keeps growing underneath it.

The heap-growth-triggered path is the primary *memory-growth* bound. `Scheduling.h:380-391` defines `JSGC_SMALL_HEAP_INCREMENTAL_LIMIT` (default **1.70×** the trigger threshold) and `JSGC_LARGE_HEAP_INCREMENTAL_LIMIT` (default **1.10×**) — the multiple of the trigger size at which SpiderMonkey gives up on incremental collection and forces a non-incremental (stop-the-world) GC; large heaps get a tighter margin because absolute bytes matter more for OOM risk, small heaps get a looser margin tuned for responsiveness (the comment notes 1.7 is "at least" what's needed "to maintain performance on splay-latency"). Between GCs, the trigger threshold itself grows adaptively: `JSGC_LOW_FREQUENCY_HEAP_GROWTH` (1.5×, normal case) versus `JSGC_HIGH_FREQUENCY_SMALL_HEAP_GROWTH`/`JSGC_HIGH_FREQUENCY_LARGE_HEAP_GROWTH` (3.0× / 1.5×) when GCs are happening more than once per second (`highFrequencyThreshold`, default 1 second, `Scheduling.h:393-401`) — small heaps are allowed to grow faster between GCs under allocation pressure (fewer, larger GCs) while large heaps stay tightly bounded regardless. The whole scheduling doc (`Scheduling.h:87-260`) frames this explicitly as a cost tradeoff between "GC too soon" (wasted work revisiting a nearly-identical graph) and "GC too late" (OOM, fragmentation, management overhead), with numbered `GCReason`s (`MAYBEGC`, `ALLOC_TRIGGER`, `TOO_MUCH_MALLOC`, `MEM_PRESSURE`, `LAST_DITCH`) each corresponding to a different point on that tradeoff.

Generational collection is itself the largest lever for keeping *typical-case* pauses small: because minor-GC cost scales with nursery-survivor count rather than total heap size, and the nursery is capacity-bounded (chunk-based, adaptively resized against a 4ms time goal, `JSGC_NURSERY_MAX_TIME_GOAL_MS`), the overwhelming majority of allocations (short-lived objects, per the standard generational-GC hypothesis) are reclaimed in a bounded, small, frequent pause rather than ever contributing to a major-GC pause at all. Pretenuring further reduces wasted copying work (and thus pause time) by keeping allocation sites known to be long-lived out of the nursery's copy path entirely. Compaction is the one piece explicitly *not* made incremental — SpiderMonkey accepts an atomic, whole-zone pause for it, but bounds its cost by making it rare (end of a major GC, or on memory-pressure notification, not on every collection). Concurrent and parallel marking are off by default in this checkout and gated behind a heap-size threshold (4MB) when enabled, i.e. SpiderMonkey's own default posture already favors "skip the complexity, keep it single-threaded" below a fairly small heap size — worth noting since it's close to what BlueJS's MVP heap sizes are likely to look like; V8, with real source now readable (section 2 above), takes the opposite default posture — incremental, concurrent, and parallel marking all ship **on** by default — but bounds *its* small-heap case the same structural way, just at a different layer: `IncrementalMarking::IsBelowActivationThresholds()` skips incremental marking entirely below an 8MB old-generation/global floor (`incremental-marking.cc:63-64,135-138`), so both engines agree that below some modest heap size the entire concurrent/incremental machinery just doesn't turn on, they only disagree on where the *default* sits above that floor.

V8/Orinoco's bounding strategy, now readable directly rather than inferred from Oilpan, differs from SpiderMonkey's in one important structural way: rather than treating concurrency as an opt-in escape hatch, V8 bounds pause time by making concurrency the *default* and then hard-capping the cost of whatever must still run synchronously on the main thread. `kMaxStepSizeOnTask = 1ms`/`kMaxStepSizeOnAllocation = 5ms` (`incremental-marking.cc:56-60`) bound every incremental-marking step actually taken on the main thread regardless of how far behind the collector is — a harder, unconditional guarantee than SpiderMonkey's own escape valves (section 1's `maybeIncreaseSliceBudgetForLongCollections`/`...ForUrgentCollections`), which deliberately let a slice run *longer* when a collection can't keep up rather than capping it. Memory growth is bounded by the same `IncrementalMarkingLimitReached` state machine that triggers marking (section 2 above) plus `AllocationLimitOvershotByLargeMargin` (`heap.cc:5392-5422`) as its own escape valve: once consumed bytes overshoot the allocation limit by more than `old_generation_overshoot_margin()`/`global_overshoot_margin()`, V8 treats this as urgent regardless of whatever mode (load-time, input-handling, memory-reducer-driven idle collection) it was otherwise optimizing for — V8's version of the same "stop negotiating and just collect" fallback SpiderMonkey's small-heap-vs-large-heap incremental-limit multipliers (section 1's `JSGC_SMALL_HEAP_INCREMENTAL_LIMIT`/`..._LARGE_HEAP_INCREMENTAL_LIMIT`) provide. Compaction is bounded the same way in spirit as the earlier Oilpan-based reading of this section suggested — scoped to a heuristically-chosen subset of pages (`CollectEvacuationCandidates`/`ComputeEvacuationHeuristics`, section 2 above) rather than applied heap-wide — so that inference from Blink's behavior turns out to have generalized correctly to V8's own JS heap, even though the underlying code (`mark-compact.cc`, entirely separate from `cppgc`) wasn't actually visible when it was written. `MemoryReducer`'s idle/low-allocation-rate-triggered collection (section 2 above) is V8's concrete, source-verified version of the "schedule GC when nothing is stealing time from a frame" idea, now grounded in V8's own task-priority scheduling rather than in Oilpan's message-loop integration.

## 4. Assessment: a concrete MVP GC recommendation for BlueJS

**Framing**: `phase-13-bluejs-engine/PLAN.md:17` states the governing constraint for this whole phase explicitly: "designing for high-performance-later is the priority for this phase; actually building that performance is not... pick foundational structure now that makes optimization *additive* later, even while building none of the optimization itself yet." Both reference engines are multi-decade, multi-hundred-engineer optimization targets — SpiderMonkey's own docs flag concurrent marking as still "experimental... use at your own risk" after ~20 years of development, and V8's own `WRITE_BARRIER.md` (section 2 above) documents a write barrier reimplemented across four separate code-generation tiers just to make its default-on concurrent/incremental marking safe. None of that is a reasonable MVP target, and the plan is explicit that it shouldn't be. What both engines *do* agree on, and what generalizes cleanly to a from-scratch implementation, is that a small young generation collected cheaply and frequently, sitting in front of a simpler old-generation collector, is the single highest-leverage structural decision — everything past that (incremental slicing, concurrent/parallel marking, adaptive pretenuring, scoped compaction) is refinement on top of it, not a prerequisite for it.

**Does the real V8 evidence change this recommendation? No — worth saying explicitly rather than leaving this section untouched with no comment.** The recommendation below was originally built from real SpiderMonkey source plus an Oilpan-based proxy for V8; now that V8's actual GC source is readable (section 2 above), the case is if anything stronger, not weaker. V8 doesn't merely support concurrent/incremental/parallel marking the way SpiderMonkey does, as an off-by-default, flagged-experimental option — it ships all three **on by default** in production (`incremental_marking`/`concurrent_marking`/`parallel_marking`, `flag-definitions.h:2570,2599,2612`), and the engineering cost of doing that safely turns out to be concretely larger than either engine initially suggested: a write barrier with *three* distinct purposes (not two), each reimplemented per JIT tier (Turbofan, Maglev, Sparkplug, plus a shared CSA/C++ slow path, `WRITE_BARRIER.md:31-74`); a dedicated "on-hold worklist" just to stop background threads from racing the mutator's own bump allocator (`docs/heap/marking-and-sweeping.md:48-51`); and explicit object locking for types that can transition concurrently (`ObjectLockGuard`, `docs/heap/marking-and-sweeping.md:61-64`). That is the cost of shipping concurrent GC in an engine serving billions of pages under Google-scale investment — a strictly stronger illustration of "not a reasonable MVP target" than the SpiderMonkey-experimental-flag framing or the Oilpan-proxy framing this note originally had to rely on. Where the real V8 evidence does add something genuinely new is a more principled version of the growth-factor idea already recommended below — V8's target-mutator-utilization heap-growing formula (section 3 above) — noted in the deferred list further down as a documented refinement path, not a reason to change course now.

**Recommended MVP shape**: a two-generation collector — a small, fixed-capacity, bump-allocated (or simple semispace-copying) **nursery**, collected by a stop-the-world **minor GC** whenever it fills, promoting all survivors to the tenured generation on their first minor GC (no allocation-site pretenuring — SpiderMonkey's `AllocSite` machinery is exactly the kind of "actual optimization" the plan says to defer); and a **tenured heap** collected by a plain, non-incremental, non-compacting **mark-sweep** major GC, triggered proactively by a heap-growth-factor rule modeled on SpiderMonkey's simplest case (e.g. trigger a major GC once live bytes have grown by roughly 1.5–2× since the last collection — the same order of magnitude as SpiderMonkey's `JSGC_LOW_FREQUENCY_HEAP_GROWTH` default of 1.5×) rather than waiting for an absolute ceiling. Given `core`'s existing low-memory requirement, add an explicit configurable max-heap-bytes ceiling as a hard backstop (SpiderMonkey's `JSGC_MAX_BYTES`/non-incremental-then-OOM escape hatch and V8's own `v8::Isolate::LowMemoryNotification()` — real V8 API, `include/v8-isolate.h:1506`, "Optional notification that the system is running low on memory. V8 uses these notifications to attempt to free memory," which is what Blink's `blink_gc_memory_dump_provider.cc` calls into — are the two precedents) so `core`'s own process-level memory monitor can force a collection under pressure rather than relying solely on BlueJS's internal heuristics.

**Only one barrier is needed, not two or three**: SpiderMonkey's code (section 1) shows write barriers serving two genuinely separate purposes — an incremental-marking snapshot-at-the-beginning barrier (`PreBarriered`/`HeapPtr`) and a generational remembered-set barrier (`StoreBuffer`) — and V8's own `WRITE_BARRIER.md` (section 2 above) now confirms a real third purpose beyond those two: an old-to-old "evacuation" barrier that records pointers into compaction candidates so a scoped, selective compactor can update them, active "only while incremental/concurrent marking is running" (`WRITE_BARRIER.md:8-10`). Three independent reference points (SpiderMonkey's two, V8's three) now agree the marking-related and evacuation-related barrier purposes are separable from the generational one, and separable from each other. Because the MVP major GC proposed above is fully stop-the-world (never interleaved with mutator execution) and non-compacting, it needs **neither the incremental-marking barrier nor the evacuation barrier** — both classes of complexity (and the correctness risk that comes with them, which is exactly what makes concurrent/incremental/compacting GC hard to get right) simply don't apply yet. The generational barrier is still required, since promoting survivors out of the nursery doesn't eliminate old→young pointers created after promotion — but it can be as simple as an unconditional check on every store of a handle into an object field ("does this old-gen object now point at a nursery handle? if so, record it in a remembered set") rather than a precise per-slot store buffer; a coarse, easy-to-get-right remembered set is an acceptable MVP cost given the plan's own priorities.

**A BlueJS-specific advantage worth designing in now**: because BlueJS objects are already going to be handle/ID-addressed through a table (mirroring `blueice-dom`'s `NodeId`, per `PLAN.md:29`) rather than referenced by raw pointer the way SpiderMonkey's `Cell*`/Oilpan's `Member<T>` are, **compaction becomes structurally cheap later even if MVP never implements it**: moving an object's backing storage only requires updating that one handle-table entry, not tracing the entire heap to rewrite every inbound pointer — which is precisely the expensive, non-incremental step SpiderMonkey's `Compacting.cpp` has to do (`doc/gc.md:109-111`: "tracing the entire heap to update pointers to moved data"). This is a direct, concrete instance of the plan's "additive, not a rewrite" test: shipping a plain non-compacting mark-sweep old generation for MVP does not foreclose adding compaction later, and adding it later should be markedly simpler for BlueJS than it was for either reference engine specifically *because* of the handle-addressing decision already made. Worth stating in the object-model design doc as the reason that decision pays off doubly (DOM/JS reference uniformity *and* cheap future compaction), not just once.

**Deliberately deferred, and why each is safe to defer**: incremental marking/slicing (unnecessary if major GC stays stop-the-world and heap size stays capped low by the growth-factor trigger — the same argument SpiderMonkey's own default-off `JSGC_CONCURRENT_MARKING_ENABLED`/`JSGC_PARALLEL_MARKING_ENABLED` and its 4MB parallel-marking threshold implicitly make: below a fairly modest heap size, none of this machinery earns its complexity); concurrent/parallel marking (real V8 evidence, section 2 above, shows production engines don't actually avoid this — V8 ships it on by default — but the engineering cost of doing it safely, a three-purpose write barrier reimplemented per JIT tier, on-hold worklists to avoid racing the mutator's bump allocator, object locks for concurrently-transitioning types, is exactly the kind of complexity `PLAN.md:17` says an MVP needs to not foreclose, not build now; SpiderMonkey's own default-off posture and 4MB parallel-marking threshold, and V8's own 8MB incremental-marking activation floor (`incremental-marking.cc:63-64`), are the more directly applicable precedent at BlueJS's MVP scale — both real engines agree it's fine to skip below a modest heap size, they just disagree on where the *default* sits above that floor); allocation-site pretenuring (a pure throughput optimization, not a correctness or bound-safety mechanism); adaptive nursery resizing against a time-goal (start with a fixed nursery capacity on the order of a few MB — SpiderMonkey's own nursery chunks are 1MB each — and revisit only if profiling on real BlueJS workloads shows minor-GC pauses are a problem); and V8's more principled, target-mutator-utilization heap-growing formula (`MemoryController<Trait>::GrowingFactor`, section 3 above, tuned toward `kTargetMutatorUtilization = 0.97`) — a more sophisticated version of the same fixed-ratio growth-trigger idea already recommended above, worth adopting only if profiling on real BlueJS workloads later shows the simple 1.5–2x fixed ratio is measurably wrong, not before. What should **not** be deferred is the state-machine shape of the collector itself: even though MVP's major GC runs each phase (mark, then sweep) to completion synchronously, structuring it as explicit, discrete phases operating over an explicit worklist (mirroring SpiderMonkey's `Prepare/MarkRoots/Mark/Sweep` states, `GC.cpp:42-56`, and V8's own segmented `MarkingWorklist`, `src/heap/marking-worklist.{h,cc}`, section 2 above) rather than one recursive mark function means a future incremental-slicing pass can time-box between existing phase boundaries instead of requiring the collector to be rewritten — which is exactly the kind of foundational choice `PLAN.md:17`'s "does this block a future optimization tier" test is asking for.

**Net assessment**: unbounded memory growth is avoided the same way SpiderMonkey avoids it in its simplest configuration — a heap-growth-factor trigger that fires proactively rather than waiting for an absolute ceiling, backed by a hard configurable max as a last resort, which fits `core`'s existing low-memory requirement directly rather than fighting it. Unpredictable multi-second pauses are avoided primarily by *keeping the collectible heap deliberately small* (the nursery absorbs the high-frequency short-lived case cheaply, the growth-factor trigger keeps the tenured heap from ever growing large enough for a stop-the-world mark-sweep pass to take seconds) rather than by incremental slicing, which is the right tradeoff for an MVP that is explicitly not chasing V8/SpiderMonkey-class raw performance — and if real-world profiling later shows major-GC pauses are still a problem at BlueJS's actual working-set sizes, the state-machine structure recommended above is what makes adding incremental slicing an additive change rather than the kind of full-engine rewrite the plan calls out V8's Crankshaft→TurboFan and SpiderMonkey's JägerMonkey→IonMonkey→Warp transitions as cautionary precedent for.
