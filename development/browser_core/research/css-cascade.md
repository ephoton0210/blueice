# CSS parsing and cascade — Gecko/Stylo and Blink

Findings from reading `reference/gecko` and `reference/chromium` (see [`../reference/README.md`](../reference/README.md) for how these checkouts were obtained), feeding the Phase 2 MVP-CSS-subset decision and the flexbox/grid in-or-out call described in [`../BROWSER_CORE_PLAN.md`](../BROWSER_CORE_PLAN.md).

All paths below are relative to `reference/gecko/` or `reference/chromium/` unless stated otherwise. Line numbers are as of this checkout's snapshot and will drift on re-clone.

## 1. Gecko/Stylo's CSS parsing and cascade architecture

Gecko's own `layout/style/` directory (e.g. `CSSFontFaceRule.cpp`, `CSSMediaRule.cpp`, `CSS.cpp`) is almost entirely C++ CSSOM glue — DOM-facing rule objects, `nsCSS*` bindings — not the cascade algorithm itself. The actual selector matching and cascade computation is the Rust "Stylo" engine, vendored at `servo/components/style` (the `style` crate) plus a companion `servo/components/selectors` crate. Its own `Cargo.toml` is unambiguous about identity and portability: `name = "style"`, `description = "The Stylo CSS engine"`, `repository = "https://github.com/servo/stylo"` — i.e. this checkout vendors a snapshot of an independently-repo'd, embedder-agnostic project, not Gecko-only code. The crate has separate `gecko` and `servo` Cargo features (`servo/components/style/Cargo.toml` lines ~20-46) that pull in different transitive dependencies (`nsstring`/`mozbuild`/`bindgen` for Gecko vs. `string_cache`/`servo_config`/`url` for Servo) — direct structural proof it already serves two different embedders from one codebase.

Sibling vendored crates under `servo/components/`: `selectors` (selector parsing/matching, engine-agnostic), `style_traits`, `style_derive` (proc-macros used heavily by `style`), `servo_arc`, `malloc_size_of`, `to_shmem`/`to_shmem_derive`. Notably `cssparser` (the low-level CSS tokenizer, implementing the CSS Syntax spec) is **not** vendored here at all — `style`'s `Cargo.toml` pulls it as an ordinary external dependency (`cssparser = "0.38"`), and `servo/components/style/README.md` says outright: "Style system for Servo, using rust-cssparser for parsing." So the tokenizer is a third, even-more-generic, independently-versioned crate one layer below `selectors`/`style`.

Selector parsing and matching (`servo/components/selectors/`):

- `parser.rs` — `Selector<Impl>` (a selector list, generic over a `SelectorImpl` trait so the same code parses both Gecko's and Servo's pseudo-class/pseudo-element vocabularies), `Component` enum (one variant per simple selector kind: `ID`, `Class`, `LocalName`, `AttributeInNoNamespace`, `Is`/`Where`/`Negation`/`Has`/`NthOf` for the functional pseudo-classes, `Host`/`Slotted`/`Part`/`Scope` for shadow-DOM/`@scope` selectors).
- `builder.rs:246` — `struct Specificity { id_selectors: u32, class_like_selectors: u32, element_selectors: u32 }`, packed to/from a single `u32` via `From<u32>`/`From<Specificity>` impls using 10-bit fields (`MAX_10BIT = (1u32 << 10) - 1`, so `id << 20 | class << 10 | element`) — the textbook (a,b,c) specificity tuple, computed once per selector and cached inline in `SpecificityAndFlags` (`parser.rs` around line 863, `Specificity::single_class_like()`). `component_specificity()` (`builder.rs` ~lines 285-400) walks each `Component` and increments the right bucket — `Component::ID` → id bucket; `Component::Class`/attribute selectors/`Component::Root`/`Component::Nth`/non-tree-structural pseudo-classes → class-like bucket; `Component::LocalName` → element bucket; `:is()`/`:where()`/`:not()`/`:has()` recurse and take the *max* specificity of their selector-list argument per the spec, with `:where()` explicitly excluded from contributing (its own comment cites `https://drafts.csswg.org/selectors/#specificity-rules`).
- `matching.rs` — the matcher: `matches_selector_list` → `matches_selector` → `matches_complex_selector` → `matches_compound_selector` → `matches_simple_selector`, i.e. a selector list is OR'd, a complex selector (combinator-separated compounds) is matched right-to-left walking up/across the tree, and each compound is an AND of simple selectors. `AncestorHashes` + `BloomFilter` (`bloom.rs`, `selector_may_match()` at `matching.rs:146`) give a fast-reject path before the real recursive match, which is why real engines don't naively re-walk the DOM for every selector on every element.

Cascade ordering and storage (`servo/components/style/rule_tree/`):

- `level.rs` — `CascadeLevel` is an 8-bit bitflags value packing origin (3 bits), an `IMPORTANT` bit, and 4 bits of shadow-tree cascade order (`ShadowCascadeOrder`, for `:host`/`::slotted` interactions across shadow boundaries). `CascadeOrigin` is a `#[repr(u8)]` enum whose **declaration order is the precedence order** (the doc comment says so explicitly): `UA = 0, User, PresHints, Author, PositionFallback, SMILOverride, Animations, Transitions`. `PresHints` (HTML/SVG presentational attributes, e.g. `<img width>`) sits between `User` and `Author` per the CSS Cascade spec's "author-level zero-specificity" rule, matching the comment at the top of the file almost verbatim.
- `mod.rs` — `RuleTree`/`StrongRuleNode`, a shared trie of matched rules keyed by insertion order; `insert_ordered_rules_with_important()` (doc comment: "Inserts the given rules, that must be in proper order by specifity[sic]... !important rules are detected and inserted into the appropriate position in the rule tree") separates `important_author`/`important_user`/`important_ua` buckets so that `!important` reordering (author-normal < user-normal < UA-normal < UA-important < user-important < author-important, per spec) doesn't require re-sorting matched declarations, just re-walking the tree in a different order.

The cascade algorithm proper is `servo/components/style/properties/cascade.rs` (2704 lines) — `pub fn cascade<E>(stylist, pseudo, rule_node, guards, parent_style, ...)`, doc-commented "Performs the CSS cascade, computing new styles for an element from its parent style." It's driven by a `DeclarationIterator` that walks the `StrongRuleNode` chain plus `CascadePriority`/`RevertKind` (for the `revert`/`revert-layer` CSS-wide keywords) to decide, per longhand, which declaration wins. Two details worth carrying into BlueIce's design: (1) custom properties (`custom-properties.rs`) are substituted *before* anything else, since `var()` references can appear inside any other property's value; (2) a small set of "prioritary" properties are cascaded before the rest, defined declaratively in `properties/data.py`'s `PRIORITARY_PROPERTY_DEPENDENCIES` dict (e.g. `font-size` depends on `zoom`/`math-depth`/`-x-text-scale`; `font-family` depends on `-x-lang`; `color-scheme` depends on `forced-color-adjust`) — i.e. even a "minimal" cascade can't treat all properties as independent key/value pairs, because relative units (`em`, keyword font sizes) make some properties' *computed* values inputs to others' resolution, and Stylo represents that as an explicit small dependency graph rather than ad hoc ordering.

Declarative property definitions live in `properties/longhands.toml` (**434** `[property-name]` entries) and `properties/shorthands.toml` (**94** entries), consumed by `properties/build.py` + the `.mako.rs` templates (`properties.mako.rs`, `gecko.mako.rs`) to code-generate the Rust property structs — this is a real code-generation pipeline, not hand-written per-property code. Each longhand entry declares a `struct` grouping (23 distinct groups found, top ones by count: `box` 61, `position` 60, `border` 47, `ui`/`inherited_text` 38 each, `font` 32, `svg` 25) and an `affects` tag (`"layout"`/`"paint"`/`"overflow"`/`""`). `flex-basis`/`flex-grow`/`flex-shrink` (`longhands.toml:798-832`) and the `grid-*` properties (`longhands.toml:1032+`) are declared exactly like any other longhand — `struct = "position"`, `affects = "layout"` — with no cascade-level special-casing; the grid ones additionally carry `servo_pref = "layout.grid.enabled"`, i.e. even Servo itself historically gated grid support behind a feature flag while the cascade mechanism underneath stayed unified. `display` itself (`longhands.toml:757`, `struct = "box"`) is likewise a plain enum-valued longhand.

Tying selector matching + rule tree + cascade together is `stylist.rs` (98 `pub fn`s): `Stylist::push_applicable_declarations` (collects matching rules for an element into an `ApplicableDeclarationList`), `Stylist::cascade_style_and_visited` (line 1486, runs `cascade()` for the element and its `:visited` shadow style), `Stylist::compute_for_declarations` (line 1995, cascades a bare declaration block with no selectors — used for inline `style="…"`). Computed-value resolution is the `values/{specified,computed,generics,animated,resolved}` module split, with the actual contract at `values/computed/mod.rs:598`: `pub trait ToComputedValue { fn to_computed_value(&self, context: &Context) -> Self::ComputedValue; }` — specified values (what the parser produces, e.g. `1.5em`) implement this to become computed values (resolved against `Context`, which carries the parent style, font metrics, root font size, etc.).

The FFI boundary back into Gecko's C++ layout engine is `layout/style/ServoStyleSet.{h,cpp}` and `layout/style/ServoBindings.{h,toml}` — C++ code (`nsIFrame`-family layout objects) calls into the Rust crate through a defined C ABI to get back `ComputedValues`; the layout algorithms themselves (`layout/generic/nsBlockFrame.cpp`, `nsInlineFrame.cpp`, `nsFlexContainerFrame.cpp`, `nsGridContainerFrame.cpp`) are plain C++ consumers of that output and know nothing about Rust. This is the cleanest evidence in the checkout that "cascade" and "layout" are already a hard architectural seam in a real engine, not just a conceptual one.

**Reusability as a Rust dependency**: the crate is real, general Rust — not Gecko-internal glue — and its `gecko`/`servo` dual-feature setup proves it already supports being embedded by two unrelated consumers. But adopting it means implementing its DOM abstraction: `dom.rs` defines `TDocument` (line 119), `TNode` (line 153), and `TElement` (line 409) traits that any embedder's DOM must implement for the crate to operate on it; `TElement` alone has **82** `fn`/`type` items (attribute access, style-attribute access, pseudo-element enumeration, shadow-DOM traversal, animation hooks, `#[cfg(feature = "gecko")]`-gated methods, etc.). That's a real, non-trivial integration surface — implementing it faithfully for a from-scratch DOM is a project in itself, not a `Cargo.toml` one-liner, though it is far smaller than reimplementing selector matching, specificity, rule-tree cascade ordering, and computed-value resolution from scratch.

## 2. Blink's CSS parsing and cascade architecture

Parsing lives under `third_party/blink/renderer/core/css/parser/`. `css_tokenizer.h` — `class CORE_EXPORT CSSTokenizer` — implements CSS Syntax-level tokenization, mirroring the role of Servo's separate `cssparser` crate. `css_parser.h` — `class CORE_EXPORT CSSParser` — is the static-method entry point: `ParseSheet`, `ParseRule`, `ParseSelector`, `ParseDeclarationList`, `ParseValue`, `ParseInlineStyleDeclaration`, `ParseSupportsCondition`, etc. (all declared `static`, `css_parser.h:44-150`). Actual recursive-descent work is split by concern into `css_parser_impl.cc` (rules/at-rules), `css_selector_parser.cc` (selector lists), and `css_property_parser.cc` (property values) — the same three-way split (tokenize / parse selectors / parse property values) that Servo's `cssparser` + `selectors` + `style::properties` stack has, just as three files in one C++ target instead of three Rust crates.

Selectors and specificity: `css_selector.h`/`css_selector.cc` define `class CSSSelector` with `static constexpr unsigned kIdSpecificity = 0x010000; kClassLikeSpecificity = 0x000100; kTagSpecificity = 0x000001;` (`css_selector.h:172-174`) — the identical base-1024, three-tier packed specificity encoding Stylo uses, just written as raw hex constants on a flat `unsigned` rather than a `Specificity{id,class,element}` struct. `CSSSelector::Specificity()` (`css_selector.cc:199`) and `SpecificityForOneSelector()` (`:234`) walk the selector the same way — `:is()`/`:where()`/`:has()` handled via `MaximumSpecificity()` (`css_selector.cc:66,78`, `:where()` excluded from contributing, mirrored in `css_selector.cc:275`). Matching is `selector_checker.h`/`selector_checker.cc`: `SelectorChecker::Match()` (`:515`) delegates to `MatchSelector()` (`:861`), which recurses through combinators exactly like Stylo's `matches_complex_selector` → `matches_compound_selector` chain (there's an explicit `DCHECK(!inside_match_) << "Do not re-enter Match: use MatchSelector instead"` guarding the entry point at `:520`). `:has()` gets a dedicated, much larger code path (`CheckPseudoHas`, `selector_checker.cc:2114-2246`) — evidence that relative/subject-changing selectors like `:has()` are meaningfully more expensive to implement correctly than the base selector grammar.

Rule collection and sorting: `element_rule_collector.h`/`.cc` — `class ElementRuleCollector`, `CollectMatchingRules()`, `SortMatchedRules()` (`:1504`). The comparator is `struct ElementRuleCollector::CompareRules` (`:1487-1502`), which packs each matched rule's `SortKey()` (layer order + specificity, per `cascade_priority.h`'s doc comment) and its source position into one 128-bit (or `std::pair` fallback) integer and does a single `<` comparison — i.e. "layer, then specificity, then source order" is implemented as one packed-integer sort key rather than a multi-key comparator, for speed. The doc comment at `cascade_priority.h` spells out the full spec-mandated tuple: "Origin/importance; tree order... inline style...; layer order...; rule_index/declaration_index."

Cascade origin and priority: `resolver/cascade_origin.h` — `enum class CascadeOrigin : uint8_t { kNone = 0, kUserAgent = 0b0001, kUser = 0b0010, kAuthorPresentationalHint = 0b0011, kAuthor = 0b0100, kAnimation = 0b0101, kTransition = 0b10000 }` — the same UA < User < presentational-hints < Author < Animations < Transitions ordering as Stylo's `CascadeOrigin`, down to presentational hints sitting between User and Author. `resolver/cascade_priority.h` — `CascadePriority`, built via `EncodeOriginImportance()`/`EncodeTreeOrder()`/`EncodeLayerOrder()`, each of which XORs its bits when `important` is true (e.g. `EncodeOriginImportance`: `static_cast<uint32_t>(origin) ^ 0xF` when important) so that a single integer comparison reproduces the spec's "important reverses everything except layer order stays in the same relative order" rule, again mirroring Stylo's bit-packed `CascadeLevel`.

The cascade algorithm itself is `resolver/style_cascade.h`/`.cc` — `class CORE_EXPORT StyleCascade`, whose class comment states its contract directly: "StyleCascade collects declarations provided by CSS rules and animations, and figures out which declarations should be skipped, and which should be applied (and in which order)." Usage shown in the header comment: construct with a `StyleResolverState&`, repeatedly call `cascade.MutableMatchResult().AddMatchedProperties(...)` per matched rule, then `cascade.Apply()`. It leans on sibling types in `resolver/`: `CascadeResolver`, `CascadeMap`, `CascadeFilter`, `CascadeInterpolations`, `MatchResult` — a comparable decomposition to Stylo's `RuleTree` + `ApplicableDeclarationList` + `cascade()`, just as more, smaller C++ classes.

The overall entry point is `resolver/style_resolver.h`/`.cc` — `class StyleResolver`, `StyleResolver::ResolveStyle()` (`:1377`), `MatchAllRules()` (`:1278`), plus specialized paths `StyleForViewport()`, `StyleForPage()`, `StyleForText()`, `StyleForInterpolations()`, `CreateInitialStyle()`. Unlike Stylo's `Stylist`, `StyleResolver` is written directly against Blink's own `Element`/`LayoutObject`/`ComputedStyle` C++ types — there's no embedder-agnostic trait boundary the way `TElement` gives Stylo one; Blink's cascade code is not designed to be lifted out and reused against a different DOM implementation the way Stylo already demonstrably is (gecko/servo dual-feature). `resolver/style_builder.cc` applies matched `CSSValue`s onto a mutable style builder, and `resolver/style_adjuster.cc` runs post-cascade fixups (e.g. forcing block-level `display` on floated/absolutely-positioned elements) — directly parallel to Stylo's `style_adjuster.rs`, which `cascade.rs` also calls at the end of its own algorithm.

## 3. Where flexbox/grid support sits — separable or entangled?

**Cascade level: cleanly separable, in both engines.** In Stylo, `flex-grow`/`flex-shrink`/`flex-basis` and every `grid-*` longhand are declared in `longhands.toml` with the same shape as any other property (`struct = "position"`, `affects = "layout"`) — no special code path in `cascade.rs`, `rule_tree/`, or `selectors/` treats them differently from `margin-top` or `color`. `display: flex`/`display: grid` are just two more values of the ordinary `display` longhand (`longhands.toml:757`). In Blink, likewise, `css_property_parser.cc`/`css_selector_parser.cc` don't branch on flex/grid at all — those properties parse and cascade through the exact same `StyleCascade`/`CascadePriority` machinery as everything else. Concretely: supporting the flex/grid *properties* in a BlueIce cascade (parsing them, storing them, letting them win/lose by specificity and origin like any other declaration) is close to free once the base cascade exists — it's a handful of extra property definitions, not new cascade logic.

**Layout level: not separable — each is a real, large, dedicated subsystem.** Gecko keeps flex and grid in their own C++ frame classes, distinct from block/inline layout: `layout/generic/nsFlexContainerFrame.{h,cpp}` and `layout/generic/nsGridContainerFrame.{h,cpp}` vs. `layout/generic/nsBlockFrame.{h,cpp}`/`nsInlineFrame.{h,cpp}`. Blink is even more explicit about it as a subsystem boundary: `third_party/blink/renderer/core/layout/flex/` is a dedicated directory — `flex_layout_algorithm.{h,cc}`, `flex_line.h`, `flex_line_breaker.{h,cc}`, `flex_item_iterator.{h,cc}`, `flex_child_iterator.{h,cc}`, `line_flexer.{h,cc}`, `flex_gap_accumulator.{h,cc}` — a dozen-plus files implementing line-breaking, flexing (the "resolve flexible lengths" algorithm), gap handling, and iteration order (which differs between layout order and DOM order once `order` is involved) as their own concerns. Grid is larger still: `third_party/blink/renderer/core/layout/grid/` has its own `README.md` describing a `GridTree`/`GridSizingTree`/`GridLayoutTree` data-structure design built specifically to support subgrid (`grid_subtree.h`, `grid_sizing_tree.{h,cc}`), a dedicated track-sizing algorithm (`grid_track_sizing_algorithm.h`), named-line resolution (`grid_line_resolver.{h,cc}`, `grid_named_line_collection.{h,cc}`), and placement (`grid_placement.{h,cc}`) — plus a newer, actively-developed sibling directory `layout/grid_lanes/` (2024-dated files, `grid_lanes_layout_algorithm.cc` etc.) building CSS Masonry layout on top of grid's data structures, i.e. the grid family is still growing even in a mature, ~20-year-old engine.

**Implication for the Phase 2 decision**: flex/grid are separable from the cascade problem BlueIce needs to solve first, so *deferring layout support* doesn't require deferring the properties — the parser/cascade can accept and store `flex-*`/`grid-*` declarations from day one at negligible cost, they just won't do anything until a flex/grid layout algorithm exists. But actually laying out flex or grid containers is a substantial, self-contained project each (real engines dedicate a directory with 10+ files and, for grid, a bespoke tree data structure to it) — comparable in scope to block/inline layout itself, not an incremental extension of it.

## 4. Recommendations for BlueIce

**MVP CSS subset — selectors.** Include: type selectors, class selectors, ID selectors, the universal selector, descendant combinator (` `), child combinator (`>`), attribute-presence and attribute-equality selectors (`[attr]`, `[attr=val]`), and specificity computed the standard (id, class-like, type) way (Stylo's own encoding — three small counters packed into an integer, `servo/components/selectors/builder.rs:246-283` — is cheap enough to copy as a design, whether or not the crate itself is reused). This is load-bearing: essentially all real-world CSS relies on class-beats-type / id-beats-class ordering, so skipping specificity isn't a scope cut, it's cascade incorrectness that will visibly break real pages. Defer: `:has()` (Blink gives it ~130 lines of dedicated matching code at `selector_checker.cc:2114-2246` specifically because it requires the "check ancestors/siblings for a match" direction reversal that plain selectors don't), `:is()`/`:where()`/`:not()` with complex arguments, `:nth-child()`/`:nth-of-type()` (real but rarer on "simple" pages and non-trivial to get right — see `matches_generic_nth_child`/`nth_child_index` in Stylo's `matching.rs:1405-1590`), shadow-DOM selectors (`::part`, `::slotted`, `:host`), and `@scope`.

**MVP CSS subset — cascade.** Include: two origins only (UA default stylesheet, author stylesheet/`<style>`/`style=""`) in that precedence — both engines agree UA < User < PresHints < Author < Animations < Transitions is the correct order (`servo/components/style/rule_tree/level.rs` and `chromium/.../resolver/cascade_origin.h` converge on the identical ordering independently), so a from-scratch two-tier version of that ordering is a safe, spec-faithful simplification, not a guess. Include `!important` — it's a single bit in both real implementations (`CascadeLevel::IMPORTANT` / `CascadeOrigin` XOR trick) and common enough in real author CSS to be load-bearing. Include a minimal computed-value pipeline that at least resolves `em`/percentage-of-parent-font-size and `currentColor`/inherited `color`, because Stylo's own "prioritary properties" dependency list (`properties/data.py`, `PRIORITARY_PROPERTY_DEPENDENCIES`) shows that even a minimal cascade can't treat `font-size`/`color` as independent of their ancestors — inheritance-with-relative-units is not an optional refinement, it's what makes basic typography render correctly at all. Defer: CSS custom properties/`var()` (real complexity — substitution happens before every other property resolves, per `cascade.rs`'s ordering — but not needed to render "simple" pages that don't use them; revisit as soon as MVP pages that do use them show up), `@layer`/cascade layers, container queries, `@starting-style`, `revert`/`revert-layer` CSS-wide keywords, and animations/transitions as cascade origins (keep `transition`/`animation` as a Phase-3+ feature entirely, not just a cascade-origin stub).

**MVP CSS subset — properties.** Recommend covering, at minimum: the box model (`display: none|block|inline|inline-block`, `width`/`height`, `margin`/`padding`/`border-*`, `box-sizing`), typography (`font-family`/`font-size`/`font-weight`/`color`/`line-height`/`text-align`), `background-color`, and basic positioning (`position: static|relative|absolute` plus `top`/`right`/`bottom`/`left`). Recommend including a *basic single-axis flexbox* (`display: flex`, `flex-direction`, `justify-content`, `align-items`, `flex-grow`/`flex-shrink`/`flex-basis`) in MVP scope despite the layout cost noted in §3 — simple real-world pages (nav bars, centered content, basic card rows) lean on exactly this subset of flexbox heavily enough that excluding it entirely risks failing the "renders real, simple pages" bar the plan sets. Recommend explicitly deferring CSS Grid past MVP: it's rarer on genuinely simple pages than flexbox, and even Chromium's grid implementation — after years of investment, a bespoke `GridTree` design, and a README documenting subgrid support — is still growing an actively-developed sibling subsystem (`layout/grid_lanes/`) in this snapshot, which is a strong signal against taking it on early.

**Cascade implementation strategy — is Stylo/`style` reusable?** Structurally reusable as a *design reference*, and plausibly reusable as an actual dependency, but not as a drop-in. In favor: it's already a real, independently-repo'd, general-purpose Rust crate (`github.com/servo/stylo`) built to be embedded by two unrelated consumers (Gecko and Servo, via its `gecko`/`servo` Cargo features), its lower layers (`cssparser` for tokenization, `selectors` for matching) are even more generic and already factored out as separate crates, and — via `layout/style/ServoStyleSet.{h,cpp}` — Gecko itself proves the cascade/layout boundary is real by crossing it over a C FFI, meaning BlueIce doesn't need to invent that seam, just replicate it in-process (no FFI needed, since BlueIce's layout code will also be Rust). Against: full reuse means implementing the `TDocument`/`TNode`/`TElement` trait surface (`servo/components/style/dom.rs:119,153,409` — `TElement` alone has 82 methods/associated types) against BlueIce's own DOM, pulling in a dependency tree built around Gecko/Servo-specific infra (`malloc_size_of`, `to_shmem`, mako-templated code generation for all 434 longhand + 94 shorthand properties, `bindgen`-based Gecko bindings even when the `gecko` feature is off) that's substantially heavier than an MVP needs. **Recommendation**: don't vendor the `style` crate for MVP — the integration and build-system cost isn't justified for a ~30-40 property, two-origin cascade — but do (a) design BlueIce's own specificity/cascade-order types as direct ports of the packed-integer schemes both engines independently converged on (`Specificity{id,class,element}` packed to a u32; `CascadeOrigin` as a small ordered enum; sort key = `(origin/important, specificity, source order)` as one comparable tuple), since that's proven, spec-correct, and cheap to reimplement from scratch in an afternoon, and (b) seriously evaluate pulling in the standalone `cssparser` crate (an external crates.io dependency in this checkout, not vendored alongside `selectors`/`style` under `servo/components/`, and not Gecko-specific — check its license terms before adopting) for CSS tokenization specifically — it's the one layer in this stack that's already fully general, small, well-isolated from both Gecko and Servo internals, and exactly the kind of "don't reinvent a spec-compliant tokenizer" reuse that's low-risk. Revisit adopting the full `style` crate later if BlueIce's cascade needs grow toward real-world completeness (custom properties, `@layer`, more selector functions) and the `TElement`-trait integration cost starts looking cheaper than maintaining a growing hand-rolled cascade.
