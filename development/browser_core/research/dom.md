# DOM tree structure and node identity in Gecko and Blink

Findings from reading `../reference/gecko` (Firefox) and `../reference/chromium` (Chromium/Blink) directly, focused on two questions: how each engine structures its core DOM node/element/document types and parent/child/sibling links, and — the question that actually matters for BlueIce — how each engine assigns identity to a node, especially the identity used by the accessibility-tree subsystem to reference DOM nodes stably across mutations.

## 1. Gecko's core DOM types and file locations

Gecko's DOM class hierarchy lives under `dom/base/` and `dom/html/` and is a fairly deep C++ interface chain: `nsINode` (`dom/base/nsINode.h:417`, `class nsINode : public mozilla::dom::EventTarget`) is the root of everything nodelike, `nsIContent` (`dom/base/nsIContent.h:54`, `class nsIContent : public nsINode`) adds content-node behavior, `FragmentOrElement` (`dom/base/FragmentOrElement.h:81`, `class FragmentOrElement : public nsIContent`) is the shared base for elements and fragments, and `Element` (`dom/base/Element.h:303`, `class Element : public FragmentOrElement`) is the actual DOM `Element`. `Document` (`dom/base/Document.h:561`, `class Document : public nsINode, ...`) inherits `nsINode` directly (multiple inheritance with several other interfaces), so a `Document` is itself walkable as a node. Concrete HTML element types live in `dom/html/` — e.g. `HTMLDivElement.h`, `HTMLAnchorElement.h`, `HTMLInputElement.h`, one pair of `.h`/`.cpp` files per tag, all ultimately deriving from `Element`.

Tree structure is a classic intrusive doubly-linked list, stored directly as fields on `nsINode` (`dom/base/nsINode.h:3212-3238`): `nsINode* MOZ_OWNING_REF mParent`, `nsCOMPtr<nsIContent> mFirstChild`, `nsCOMPtr<nsIContent> mNextSibling`, and a same-named-but-different-role `mPreviousOrLastSibling` which is a *weak* ref — the sibling list is circular in the backward direction (last child's "next" pointer wraps to first child) purely so the doubly-linked list doesn't need a separate `mLastChild` owning pointer; `GetPreviousSibling()` has to special-case this. There is no array-of-children representation and no index-based child access at this layer — child N is only reachable by walking `mFirstChild` → `mNextSibling` N times.

Node naming/type identity (element tag, namespace) is factored out into a separate interned, refcounted `NodeInfo` object (`dom/base/NodeInfo.h:37`, `class NodeInfo final`), managed and deduplicated per-document by `nsNodeInfoManager` (`dom/base/nsNodeInfoManager.h`, "a class for handing out nodeinfos and ensuring sharing of them as needed"). This is a memory-sharing optimization (many `<div>` elements share one `NodeInfo`), not a node-identity mechanism — it identifies a *kind* of node, not a specific node instance.

## 2. Blink's core DOM types and file locations

Blink's DOM code lives under `third_party/blink/renderer/core/dom/`. The hierarchy is shallower and more linear than Gecko's: `Node` (`node.h:165`, `class CORE_EXPORT Node : public EventTarget`) is the root, `ContainerNode` (`container_node.h:97`, `class CORE_EXPORT ContainerNode : public Node`) adds child-list management, `Element` (`element.h:311`, `class CORE_EXPORT Element : public ContainerNode`) is the DOM element type, and `Document` (`document.h:369`, `class CORE_EXPORT Document : public ContainerNode, ...`) also derives from the node hierarchy directly, same pattern as Gecko. Concrete HTML elements aren't under `core/dom/` — they live in `core/html/` (`html_div_element.h`, `html_anchor_element.h`, etc.), mirroring Gecko's split.

Tree structure is also an intrusive doubly-linked list, but split across two classes: sibling pointers (`Member<Node> previous_`, `Member<Node> next_`) live on `Node` itself (`node.h:1428-1429`), while the child-list head/tail (`Member<Node> first_child_` — `container_node.h:560`) lives on `ContainerNode`, since leaf nodes (text, comments) never have children and don't need that slot. Like Gecko, the backward direction is a circular trick, not a `last_child_` field: the comment at `node.h:1425-1427` explains "`previous_` on the first child of a node will return the last child" — the doubly-linked list is genuinely the same design decision independently made by both engines. `Member<>`/`WeakMember<>` are Blink's Oilpan-GC smart pointer wrappers (roughly Gecko's `nsCOMPtr`/refcounting equivalent, but tracing-GC-managed rather than refcounted). Again, no array/index-based child storage at this layer, and no `NodeInfo`-equivalent — Blink stores tag/namespace via `QualifiedName` directly, interned globally rather than per-document.

## 3. How each assigns/exposes stable node identity

**Neither engine's core `Node`/`nsINode` type carries an engine-assigned "logical ID" as a first-class field.** In both engines, day-to-day node identity *is* pointer identity — `nsINode*` / `Node*` (Gecko's GC/refcounting and Blink's Oilpan both just mean the pointer stays valid while referenced; neither is a stable, serializable, cross-process identifier). Any concept of a stable ID had to be built as a layer on top, and in both cases the clearest evidence of why is the accessibility-tree subsystem, which cannot use raw pointers because it must survive across process boundaries and be able to say "this is still node X" after mutation.

**Gecko: still literally the pointer, even where the code claims otherwise.** `LocalAccessible::UniqueID()` (`accessible/generic/LocalAccessible.h:137`) is `void* UniqueID() { return static_cast<void*>(this); }` — the accessible object's own address. The supposedly more portable `ID()` (`accessible/generic/LocalAccessible.h:139-141`) is `virtual uint64_t ID() const override { return IsDoc() ? 0 : reinterpret_cast<uintptr_t>(this); }` — it's the same pointer, just reinterpreted as an integer so it can be serialized. This value is what actually crosses the content-process/parent-process IPC boundary in Gecko's Fission architecture: `accessible/ipc/RemoteAccessible.h:302` (`uint64_t ID() const override { return mID; }`) and the `DocAccessibleChild`/`DocAccessibleParent` IPDL protocol (`accessible/ipc/PDocAccessible.ipdl`, `DocAccessibleChild.h`) pass `uint64_t aID` on essentially every message (`RecvTakeFocus`, `RecvScrollTo`, `RecvDoActionAsync`, etc.). So the "ID" that Gecko's accessibility IPC treats as an opaque stable identifier is, concretely, a raw C++ object address smuggled across a process boundary as an integer (`accessible/base/EventQueue.cpp:425`, `accessible/generic/DocAccessible.cpp:1717` both do the same `reinterpret_cast<uint64_t>(item->UniqueID())`). It "works" only because the parent process treats it as an opaque hashtable key, never dereferences it as a real address, and the ID is invalidated and a fresh one is minted whenever the underlying `LocalAccessible` C++ object is destroyed and recreated (which happens on many DOM/layout changes, not just node removal). Separately, `DocAccessible` maps *DOM* nodes to their accessible objects via `nsTHashMap<nsPtrHashKey<const nsINode>, LocalAccessible*> mNodeToAccessibleMap` (`accessible/generic/DocAccessible.h:744-745`, used at `DocAccessible.cpp:3215-3218`) — again keyed by raw node pointer, not by any stable ID. The one place Gecko does mint real small-integer stable IDs decoupled from pointers is `accessible/base/IDSet.h`, a bitmap-based ID allocator — but its own doc comment says why: "On windows an accessible's id must be a negative 32 bit integer" for the MSAA/UIA platform API (used by `MsaaIdGenerator`), i.e. it exists to satisfy a Windows platform constraint, not as a general design choice. Gecko's DevTools inspector protocol (`devtools/server/actors/inspector/node.js`, `class NodeActor`) is a third, independent case: `NodeActor` gets its `actorID` from the generic `Actor` base class's own ID generator, not from anything on the DOM node — devtools had to invent yet another ID scheme because neither the pointer nor the a11y ID was suitable for a JSON-RPC-style remote protocol.

**Blink: a real, dedicated, engine-level node-ID facility — `DOMNodeId`.** This is the strongest and most directly relevant find. `third_party/blink/renderer/core/dom/dom_node_ids.h`/`.cc` define `class CORE_EXPORT DOMNodeIds` (`STATIC_ONLY`) with `IdForNode(Node*)` / `ExistingIdForNode(Node*)` / `NodeForId(DOMNodeId)`. `DOMNodeId` itself (`platform/graphics/dom_node_id.h`) is `using DOMNodeId = int;` with `kInvalidDOMNodeId = 0`, and the header comment says explicitly: "The DevTools protocol requires the type to be int, see renderer/core/inspector/browser_protocol-*.json" — this ID *is* Chrome DevTools Protocol's `DOM.NodeId`/`backendNodeId`, the exact identifier that Puppeteer/Playwright/CDP-based automation (i.e. today's AI-browser-agent tooling) uses to reference elements. Mechanically, `DOMNodeIds::IdForNode` (`dom_node_ids.cc:48-61`) is lazy and on-demand: it calls `node->EnsureNodeID(...)`, and only if that's still `kInvalidDOMNodeId` does it mint a new one from a process-global monotonic counter (`DOMNodeId g_last_id`, wrapping at `INT_MAX`) and insert it into a global `GCedHeapHashMap<DOMNodeId, WeakMember<Node>>`. Storage-wise, the ID is not a field on every `Node` — it lives in `NodeRareData` (`node_rare_data.h:185-190`, field `FieldId::kDOMNodeId = 49`), Blink's lazily-allocated side-table for uncommonly-needed per-node data, so most nodes never pay for it. `Node::GetDomNodeId()` (`node.cc:354-356`) is the public accessor, and `Node::FromDomNodeId` (`node.cc:359-361`) does the reverse lookup — both go straight through `DOMNodeIds`.

Critically, Blink's accessibility tree now *reuses* `DOMNodeId` as the accessibility node ID rather than maintaining a parallel identity scheme: `AXObjectCacheImpl::CreateAndInit` (`third_party/blink/renderer/modules/accessibility/ax_object_cache_impl.cc:1592-1602`) does `axid = static_cast<AXID>(node->GetDomNodeId());` whenever the `AXObject` has a backing DOM node, and only falls back to a separately-generated ID (`GenerateAXID()`, `ax_object_cache_impl.cc:2240-2262`) for AX nodes with no DOM node at all (e.g. layout-generated pseudo-content). The two ID spaces are deliberately partitioned by sign to avoid collisions — the comment at `ax_object_cache_impl.cc:2236-2239` states it outright: "All generated AXIDs are negative, ranging from `kFirstGeneratedRendererNodeID` to `kLastGeneratedRendererNodeID`, in order to avoid conflict with the ids reused from `dom_node_ids`, which are positive." `AXObjectCacheImpl::AssociateAXID` (`ax_object_cache_impl.cc:2270-2283`) even asserts this invariant: `DCHECK_EQ(should_have_node_id, IsDOMNodeID(new_axid))` where `IsDOMNodeID(AXID axid) { return axid > 0; }` (`ax_object_cache_impl.h:958`). `kFirstGeneratedRendererNodeID = -1000000001` and `kLastGeneratedRendererNodeID = INT_MIN` are defined in `ui/accessibility/ax_node_id_forward.h:42-43`. In other words: as of this checkout, Blink's accessibility subsystem and its general-purpose DOM node identity are the *same* namespace, not two independently-bolted-on schemes — this appears to be the result of Blink consolidating what used to be a separate `AXID` generator onto the pre-existing `DOMNodeId` facility.

The same `DOMNodeId` facility is also, concretely, what Chromium's own emerging AI-agent-facing DOM APIs are built on — direct evidence this is treated as the general "stable external handle to a node" mechanism, not an accessibility-only concept: `modules/content_extraction/ai_page_content_agent.cc` (an "AI page content" extraction agent) calls `DOMNodeIds::IdForNode`/`NodeForId` throughout (e.g. lines 857, 1988, 2192, 2419) to build its content tree and resolve targets by ID, and `core/html/forms/form_mcp_schema.cc` (Model Context Protocol form-tool schema — file literally named `*_mcp_*`, alongside a `html_form_mcp_tool_test.cc`) uses `DOMNodeIds::IdForNode(&element->ToHTMLElement())` to report which form control an MCP tool call is complaining about. This is close to a direct precedent for BlueIce's stated goal: a real, production engine already uses one lazily-assigned, process-wide-unique, pointer-independent integer ID as the shared reference key for DevTools, accessibility, and an AI/MCP-facing tool API simultaneously.

One important caveat for both engines: none of this is the HTML `id` *content attribute* (`<div id="foo">`). That's a separate, author-controlled, non-unique-in-practice string stored as a normal attribute (Gecko: `nsIContent::GetID()`, `dom/base/nsIContent.h:494`, backed by `AttrArray`; Blink: `Element::GetIdAttribute()`, `core/dom/element.h:537`) and looked up via each document's id-to-element map for `getElementById` — it is not, and cannot be, used as the engine's own node-identity mechanism, since pages routinely have duplicate, missing, or dynamically-changing `id` attributes.

## 4. Assessment: implications and recommendations for BlueIce's DOM design

**BlueIce's requirement is consistent with where both engines ended up, but neither engine ended up there by design — it's a retrofit, and the retrofit quality differs a lot between them.** Gecko's answer to "how do you stably reference a node across a process boundary" is, concretely, still a raw memory address reinterpreted as an integer (`reinterpret_cast<uintptr_t>(this)` on the *accessible* object, itself keyed off the DOM node only via a `nsPtrHashKey<const nsINode>` pointer-hashed map). That is exactly the anti-pattern BlueIce's plan (§1) calls out — "not an implicit array index or an ephemeral pointer/address" — and Gecko's own IPC protocol shows the cost: the ID is only as stable as the C++ object's lifetime, gets invalidated and reissued across many ordinary DOM/layout changes (not just node removal), and required a second, independent, platform-specific ID allocator (`IDSet.h`) purely to satisfy Windows MSAA's "must be a negative 32-bit int" constraint, plus a *third*, unrelated ID scheme in the DevTools actor layer. Three different ad hoc identity systems for three different consumers, none of them the DOM layer's own concept, is what "not designing this in from day one" costs a mature engine in the long run.

Blink's `DOMNodeId` is a much better precedent and validates BlueIce's instinct directly: a single, engine-level, monotonically-issued, pointer-independent integer, deliberately designed to be process-wide unique and small enough to satisfy an external wire protocol (CDP's `int` requirement), that the accessibility tree, DevTools, and now an AI-facing content/MCP layer all key off of. The main thing to *not* copy is the laziness: Blink assigns `DOMNodeId` only on first request (`EnsureNodeID`, stored in the lazily-allocated `NodeRareData`) precisely because most of Blink's billions of ephemeral `Node` objects across the web never need one, and paying an eager per-node cost across all of Chromium's DOM would be wasteful. BlueIce's plan explicitly wants the opposite trade: ID assignment *at creation*, unconditionally, specifically so the AI-facing API can assume every node it can ever observe already has one, with no "does this node have an ID yet" branch and no distinction between nodes that "needed" identity and nodes that didn't. Given BlueIce is being designed for this from day one rather than retrofitted onto an existing multi-billion-node install base, eager assignment is both simpler to implement (no lazy-init path, no rare-data indirection to reach the ID field) and removes an entire class of bugs the retrofit designs above had to work around.

Concretely, for BlueIce's Phase 2 minimal DOM: give every `Node` (or whatever the base type is called) a plain, non-optional `id: NodeId` field (a newtype over an integer, not a `usize` array index and not a pointer/reference) assigned by a single engine-owned monotonic counter at construction time — mirroring Blink's counter-and-hashmap shape (`DOMNodeId`/`IdToNodeMap`) rather than Gecko's per-subsystem pointer-reinterpretation shape, but made unconditional and eager instead of lazy. Keep a document- or engine-scoped `NodeId -> node handle` table (Blink's `IdToNodeMap`, a `HashMap<DOMNodeId, WeakMember<Node>>`, is the direct template) so the AI-facing API and any future accessibility-tree/highlight-state layer can resolve an ID back to a live node without re-walking the tree, and so a stale ID (node since removed) resolves to "not found" rather than a dangling pointer — this is also the reason to key it as an owned/weak table lookup rather than exposing the ID as literally embeddable-pointer-adjacent. Follow Blink's AXID-vs-DOMNodeId split as precedent if BlueIce's semantic/accessibility layer ever needs IDs for synthetic nodes that don't correspond 1:1 to a DOM node (e.g. a generated `::before`/`::after`-equivalent, or an AI-facing "virtual" grouping node) — reserve a disjoint sub-range or sign rather than inventing a fully separate ID space and lookup table, exactly as Blink's positive-DOMNodeId/negative-generated-AXID partition does, so one API surface can accept "any node-like ID" without the caller needing to know which subsystem minted it. Do not reuse Rust's `Vec` index or slab index as the public ID even if a slab/arena is the underlying storage — an index gets reused after removal (a classic ABA hazard) whereas a monotonic counter, as both `DOMNodeId` and Gecko's `IDSet`/`MsaaIdGenerator` demonstrate in different ways, does not, and BlueIce's cross-mutation stability requirement specifically depends on an ID never silently referring to a different, unrelated node later.
