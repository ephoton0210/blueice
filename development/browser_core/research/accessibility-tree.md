# Accessibility tree — Gecko and Blink

Findings from reading `reference/gecko/accessible/` (Firefox/Gecko) and `reference/chromium/third_party/blink/renderer/modules/accessibility/` + `reference/chromium/ui/accessibility/` (Chromium/Blink), aimed at testing the Plan §3 assumption that the Accessibility Tree candidate "misses purely visual information (color, hover, animation)" and at learning how each engine keeps AX-node identity stable across DOM mutations, since that's the closest existing prior art for BlueIce's own stable-DOM-ID requirement (Plan §1).

## 1. Gecko's accessibility tree

**Core types.** `accessible/basetypes/Accessible.h` defines the abstract base `class Accessible` (namespace `mozilla::a11y`), explicitly designed to work on both sides of the process split — its own doc comment says methods here "are available in both the content process and the parent process," with overrides living in the two concrete implementations: `accessible/generic/LocalAccessible.h`/`.cpp` (one per DOM node, in the content process, wraps `nsIContent* mContent` and an `nsIFrame*`) and `accessible/ipc/RemoteAccessible.h`/`.cpp` (a parent-process proxy standing in for a `LocalAccessible` that lives in a different content process, e.g. an out-of-process iframe). `accessible/generic/DocAccessible.h`/`.cpp` is the per-document owner that builds and mutates the tree (`ContentInserted`, `ContentRemoved`, `RecreateAccessible`) and holds the id→object cache. Concrete leaf/container subclasses include `HyperTextAccessible`, `TextLeafAccessible`, `ImageAccessible`, `FormControlAccessible`, `ARIAGridAccessible`, `OuterDocAccessible`.

**Role.** `accessible/base/RoleMap.inc` is an X-macro table, one row per role, mapping a single internal role to every platform AT API's role constant simultaneously: `ROLE(geckoRole, stringRole, ariaRole, atkRole, macRole, macSubrole, msaaRole, ia2Role, iosIsElement, uiaControlType, nameRule)`. The `nameRule` column (e.g. `eNameFromSubtreeIfReqRule`, `eNoNameRule`) drives name computation per role. Role is purely semantic — no visual data folded in.

**State.** `accessible/base/States.h` defines a flat `uint64_t` bitfield namespace `states::` with flags like `FOCUSED`, `SELECTED`, `CHECKED`, `EXPANDED`/`COLLAPSED`, `HASPOPUP`, `INVALID`, `CURRENT`, `INVISIBLE`, `OFFSCREEN`, plus two that look visual on paper but are effectively dead: `HOTTRACKED` (mouse-over highlight) is documented in-source as "currently unused" and has zero real call sites; `ANIMATED` is used only by `generic/ImageAccessible.cpp` to flag animated GIFs, not general CSS animation/transition state. There is no `:hover` state at all (the only "hover" hits in `accessible/` are Android touch-exploration code, unrelated to CSS hover), no z-index/paint-order/occlusion flag anywhere, and no opacity flag.

**Visibility vs. presence.** `LocalAccessible::VisibilityState()` (`generic/LocalAccessible.cpp:268-349`) is layout-driven, not paint-driven: no frame at all (the common `display:none` case) sets `states::INVISIBLE`, unless `IsDisplayContents()`, which instead yields `states::OFFSCREEN`; a frame whose `StyleVisibility()->IsVisible()` is false (`visibility:hidden`/`collapse`) also sets `states::INVISIBLE` — meaning `visibility:hidden` content still gets a real accessible object, it's merely flagged. Scrolled-out-of-view, background-tab, or under-a-closed-popup content gets `states::OFFSCREEN`. None of this consults actual compositor/paint output: an element fully covered by an opaque overlapping sibling (z-index stacking) or set to `opacity:0` triggers neither flag — it reads as present and visible even though a human wouldn't see it. Tree construction itself (`nsAccessibilityService::CreateAccessible`, `base/nsAccessibilityService.cpp:1269`) generally requires a live frame, so `display:none` elements are usually absent from the tree outright (with a narrow allowlist, `MustBeAccessible()`), while `visibility:hidden` elements are present-but-flagged. Bounding box (`LocalAccessible::RelativeBounds()`/`ParentRelativeBounds()`, `generic/LocalAccessible.cpp:625-790`) unions in-flow layout rects (falling back to ink-overflow rect for zero-area frames) — again layout geometry, with no occlusion test and no `opacity` factor.

**The one real visual-data exception.** `accessible/base/TextAttrs.h`/`.cc` (`TextAttrsMgr`) exposes per-text-run attributes for hypertext accessibles (rich-text editors, `contenteditable`) via IAccessible2/ATK text-attribute APIs: `BGColorTextAttr`/`ColorTextAttr` (both `TTextAttr<nscolor>`, reading actual computed color), plus font family/size/style/weight and text-decoration (with its own color). This is real, computed-style-derived color data — but scoped narrowly to text runs inside hypertext content, not a general per-element field available on buttons, divs, or images.

**Name/description.** `LocalAccessible::Name()` calls `nsTextEquivUtils::GetNameFromSubtree()` (`base/nsTextEquivUtils.h:69`), implementing the W3C accname algorithm, gated by the role's `nameRule`. Returned flags (`ENameValueFlag`, `basetypes/Accessible.h`: `eNameOK`, `eNameFromSubtree`, `eNameFromTooltip`, `eNameFromRelations`) record *how* the name was derived, not just the final string.

**Node identity / stable IDs.** This is the least reusable part of Gecko's design for BlueIce's purposes. `LocalAccessible::UniqueID()` (`generic/LocalAccessible.h:137`) is literally `static_cast<void*>(this)` — the C++ object's own memory address, reinterpreted as an integer (`ID()` at line 139 does `reinterpret_cast<uintptr_t>(this)`). It is not a counter, not derived from the DOM node, not persisted. `DocAccessible::mAccessibleCache` (`generic/DocAccessible.h:743`) keys its hashtable by this pointer-derived ID. Gecko does not keep one `LocalAccessible` alive across every DOM mutation: `DocAccessible::RecreateAccessible(nsIContent*)` (`generic/DocAccessible.cpp:1651`) is an explicit teardown-and-rebuild (`ContentRemoved` then `ContentInserted`) fired on things like ARIA-role-changing attribute edits or `<input type>` changes — which mints a brand-new ID at a new address for the *same* DOM element. Identity is therefore scoped to "does this C++ object still exist," not "does this represent the same DOM node over time," and staleness is handled reactively (AT clients get `Show`/`Hide`/`Reorder` events telling them to re-fetch) rather than through any ID-persistence guarantee. Across the IPC boundary, `RemoteAccessible` (`accessible/ipc/RemoteAccessible.h:302,543`) stores a `uint64_t mID` set at construction and `DocAccessibleParent::GetAccessible(uintptr_t aID)` (`ipc/DocAccessibleParent.h:233`) looks up by that same raw value — the address-based, teardown-on-mutation instability propagates unmodified across the process boundary; there is no separate stable/logical ID layer added at the IPC boundary.

## 2. Blink's accessibility tree

**Core types and the Blink→platform relationship.** Two layers. Blink-side (`third_party/blink/renderer/modules/accessibility/`): `ax_object.h`/`.cc` defines the abstract `class AXObject` (1851-line header) — per-frame, backed by live DOM/layout objects, holding `AXID id_`, and virtuals `GetName()`, `TextAlternative()`, `GetRelativeBounds()`, `IsIgnored()`, `IsHiddenViaStyle()`, `RoleValue()`. `ax_node_object.h`/`.cc` (`class AXNodeObject : public AXObject`) is the concrete subclass backing real DOM element/text nodes. `ax_object_cache_impl.h`/`.cc` (`class AXObjectCacheImpl`, one per `Document`) owns `HeapHashMap<AXID, Member<AXObject>> objects_`, the `GetOrCreate(Node*, AXObject* parent)` factory, and `AXID GenerateAXID()`/`AssociateAXID()`. Platform-side (`ui/accessibility/`): `ax_node_data.h` defines `struct AXNodeData` — its own doc comment calls it "a compact representation of the accessibility information for a single accessible object, in a form that can be serialized and sent from one process to another." `ax_node.h`/`.cc` (`class AXNode`) wraps an `AXNodeData` plus tree-structural parent/child pointers inside a browser-process `ax_tree.h` (`class AXTree`, plus tree-global `AXTreeData`). The Blink-side `AXObject` is the live source; `AXNodeData`/`AXNode` is the serialized snapshot sent renderer→browser over mojo IPC, then reassembled into a browser-process `AXTree` — `content/browser/accessibility/` (outside the two directories studied here, but confirmed to exist) is the browser-side consumer that ultimately talks to platform AT APIs (UIA/MSAA/AT-SPI/NSAccessibility).

**Role.** `ax::mojom::Role`, a large `[Extensible, Stable]` enum in `ui/accessibility/ax_enums.mojom` (lines 123-365) — ARIA roles, DPub roles, ARIA Graphics roles, MathML roles, plus internal-only roles. Purely semantic, as in Gecko.

**State and attributes — the significant divergence from Gecko.** `ax::mojom::State` (`ax_enums.mojom:373-398`) includes `kCollapsed, kDefault, kEditable, kExpanded, kFocusable, kHorizontal, kHovered, kIgnored, kInvisible, kLinked, kMultiline, kMultiselectable, kProtected, kRequired, kRichlyEditable, kVertical, kVisited`, stored in `AXNodeData::state` (`ax_node_data.h:429`, an `AXStates` bitset). **`kHovered` is real and live**: `ax_object.cc:2375-2376` sets it on every serialization pass — `if (IsHovered()) node_data->AddState(...kHovered)` — meaning CSS `:hover` match genuinely reaches the AX tree, directly contradicting the plan's blanket "misses hover" framing for this engine. Keyboard focus, by contrast, is *not* a per-node bit — it's `AXTreeData::focus_id` (`ax_tree_data.h:59`), one tree-global "which node currently has focus" field. Beyond state bits, `AXNodeData` carries sparse typed attribute maps (`ax_node_data.h:431-436`: `string_attributes`, `int_attributes`, `float_attributes`, `bool_attributes`, `intlist_attributes`, `stringlist_attributes`) whose enums (`ax_enums.mojom`) include real visual-style fields: `IntAttribute::kBackgroundColor` (=43) and `kColor` (=44) — "Foreground and background color in RGBA" — plus `kTextAlign`, `kTextDirection`, `kTextPosition`, `kTextStyle` (bold/italic/underline), `kTextOverlineStyle`, `kTextStrikethroughStyle`, `kTextUnderlineStyle`, `kListStyle`, and `kPaintOrder` (=68, "indicates when this node is painted relative to other nodes, larger is later" — a genuine z-order field). `FloatAttribute` has `kFontSize` and `kFontWeight`, `kTextIndent`. `StringAttribute` has `kFontFamily` ("only present when different from parent," a bandwidth-saving delta-encoding choice for IPC) and `kDisplay` (the raw CSS display string).

**But most of that is gated or unpopulated in practice.** `kPaintOrder`'s only call site anywhere in `modules/accessibility/` is `ax_object.cc:1335-1337`: `if (blink::features::IsXrDevice() && GetPaintOrder() > 0) { dst.AddIntAttribute(...kPaintOrder, ...); }` — z-order is populated **only for WebXR/immersive-AR sessions**, not in ordinary desktop/mobile trees. Explicit grep of `ax_object.h`, `ax_node_object.h`, `ax_enums.mojom`, `ax_node_data.h` for "Animation"/"Transition" returns zero matches — no animation or transition state exists anywhere in this layer. There is no `kOpacity` in either `IntAttribute` or `FloatAttribute`. `AXObject::ComputeIsHiddenViaStyle()` (`ax_object.cc:5010-5060`), the function behind `IsHiddenViaStyle()`, collapses `display:none` and `visibility:hidden` into a single boolean and never inspects `opacity` — an `opacity:0` element is not flagged ignored/invisible by this path at all. `display:none`/`visibility:hidden` elements do still get an `AXObject`/`AXNodeData` (kept structurally present, per `kIgnored`'s doc comment "keep its subtree") but marked `kIgnored`/`kInvisible` so platform ATs skip them — a real present-but-ignored vs. present-and-visible vs. absent three-way distinction, more granular than Gecko's two-way invisible/offscreen split, but still no occlusion test against overlapping opaque siblings anywhere in either directory.

**Bounding box.** `AXNodeData::relative_bounds` is `AXRelativeBounds` (`ui/accessibility/ax_relative_bounds.h:35-60`): `AXNodeID offset_container_id`, `gfx::RectF bounds`, `std::unique_ptr<gfx::Transform> transform` — deliberately relative to an ancestor offset container "to require minimal changes to the tree when layers are moved or scrolled" (doc comment). `AXObject::GetBoundsInFrameCoordinates()` (`ax_object.h:1105`) resolves this to actual frame coordinates by walking ancestors and applying transforms/scroll/clip (`clips_children` tracks ancestor `overflow:hidden`) — so screen position is recoverable, but it is still layout/paint-geometry, not an occlusion answer.

**Name/description.** `AXObject::GetName(NameFrom&, AXObjectVector*)`, `ComputedName()`, `TextAlternative()`/`RecursiveTextAlternative()` implement the ARIA/HTML-AAM accessible-name algorithm. `ax::mojom::NameFrom` (`ax_enums.mojom:1330-1386`) records provenance (`kContents`, `kAttribute`, `kPlaceholder`, `kTitle`, `kCssAltText`, `kValue`), not just the resulting string.

**Node identity / stable IDs — the key finding for BlueIce.** For any DOM-backed `AXObject`, the AXID *is* the DOM node's own ID, not a separately minted accessibility identifier. `ui/accessibility/ax_node_id_forward.h:26-31`: `using AXNodeID = int32_t;` with the comment "positive AXNodeIDs match DOM node ids generated by Blink. They are used for objects that contain that matching DOM node" (negative ranges are reserved for synthetic browser-/renderer-generated nodes with no DOM backing). `AXObjectCacheImpl::AssociateAXID` (`ax_object_cache_impl.cc:2272-2287`) asserts this invariant with `DCHECK_EQ(should_have_node_id, IsDOMNodeID(new_axid))`. The underlying DOM node ID comes from `blink::DOMNodeIds` (`third_party/blink/renderer/core/dom/dom_node_ids.cc`, outside the two studied directories but directly referenced from them): `DOMNodeIds::IdForNode(Node*)` is a **lazy, on-first-request** assignment off one global monotonic counter (`DOMNodeId g_last_id = 0`), not something assigned at node construction. `AXObjectCacheImpl` call sites confirm direct reuse, e.g. `ax_object_cache_impl.cc:1595`: `axid = static_cast<AXID>(node->GetDomNodeId());`. Practical consequence: AX identity survives DOM mutation and `AXObject` recreation as long as the same `Node*` persists, because the ID lives on the node itself rather than on AXObject-internal state — a `Remove` followed by `GetOrCreate` for the same node reproduces the same AXID. Tree updates are incremental, not full-rebuild: `ui/accessibility/ax_tree_serializer.h` (`class AXTreeSerializer`) diffs an `AXTreeSource` against a client-side shadow tree keyed by node ID and emits `AXTreeUpdate`s that add/remove/reparent by ID, rather than retransmitting the whole tree on every change.

## 3. Verdict on the plan's "misses visual information" assumption

**Partially true, and the specific ways it's wrong or right matter for the design decision.** The plan's framing ("misses purely visual information (color, hover, animation) — things a human perceives that the semantic tree doesn't necessarily capture") is accurate for Gecko and inaccurate in specific, checkable ways for Blink.

- **Color**: false for Blink in general (`ax::mojom::IntAttribute::kBackgroundColor`/`kColor` carry real computed RGBA), true for Gecko in general (color is only exposed per-text-run inside hypertext/`contenteditable` content via `TextAttrsMgr`, not for arbitrary elements).
- **Hover**: false for Blink specifically — `ax::mojom::State::kHovered` is set from live `:hover` match on every serialization (`ax_object.cc:2375-2376`). True for Gecko — `states::HOTTRACKED` is documented dead code with no real call sites.
- **Focus**: false for both — both engines expose focus, just differently (Gecko as a per-node `states::FOCUSED` bit; Blink as one tree-global `AXTreeData::focus_id` rather than a per-node bit).
- **Animation/transition state**: true for both — confirmed absent by direct grep in both codebases. Gecko's `states::ANIMATED` is a red herring; it flags animated-GIF images only, not CSS animations/transitions in progress.
- **Z-order / stacking / overlap**: true for both, with a caveat — Blink defines `IntAttribute::kPaintOrder` (a real per-node z-order field) but populates it *only* under `blink::features::IsXrDevice()`, so it's absent from every ordinary desktop/mobile AX tree. Gecko has no equivalent field at all.
- **Opacity**: true for both — no opacity attribute exists in either engine's AX data model, and neither engine's "is this hidden" check (`VisibilityState()` in Gecko, `ComputeIsHiddenViaStyle()` in Blink) inspects opacity at all, so an `opacity:0` element reads as fully present and visible in both trees.
- **Painted vs. present (occlusion)**: true for both, and this is the sharpest gap — neither engine computes whether a node is actually unoccluded by an overlapping opaque sibling/ancestor. Both engines' "visible" computations are layout-tree-driven (frame existence, CSS `visibility`/`display`) or, for Blink's paint-order field, XR-only — neither consults real compositor/paint output for general overlap detection.
- **Display:none / visibility:hidden distinction**: both engines *do* capture more nuance here than the plan implies — Gecko distinguishes "no frame, excluded from tree" (typically `display:none`) from "has frame, flagged `INVISIBLE`" (typically `visibility:hidden`); Blink goes further with a three-way present-and-visible / present-but-`kIgnored` / absent-from-tree model. This is a case where the plan's "misses visual info" framing is simply wrong — both trees carry meaningfully more presence/visibility nuance than raw DOM+CSSOM would give for free.

## 4. Recommendation for the Phase 1 §3 decision

**The Accessibility Tree candidate looks meaningfully more viable than the plan's current framing suggests, once "accessibility tree" is understood as "Blink's `AXNodeData` schema" rather than as an abstract ARIA concept.** The plan's con column reads as a single blanket statement ("misses...color, hover, animation"), but the evidence shows the real gap is narrower and more specific: color, hover, and provenance-tagged names are already solved in a shipping production engine's AX schema; the actual gaps are animation/transition state, general-purpose z-order/occlusion, and opacity — three fields, not a whole missing dimension.

**A "custom hybrid" would not need to be a from-scratch design — it would be an accessibility-tree-shaped structure (closely following the `AXNodeData` layout: role, state bitset, typed attribute maps, provenance-tagged name/description, offset-relative bounds) plus a small, enumerable set of additions that neither reference engine exposes generally:**

1. **Opacity** — a float field, computed straight from the style/paint pass BlueIce already runs; absent from both engines' schemas entirely.
2. **Animation/transition state** — a bool ("is currently animating") plus the current interpolated value(s) if useful; absent from both engines, and something Blink explicitly never built even though its `AXNodeData` schema had room for it.
3. **General-purpose paint order / occlusion** — Blink already has the field shape (`kPaintOrder`) and deliberately restricts it to XR because, in Blink's architecture, computing and serializing it costs something across the renderer→browser IPC boundary for every AX-tree consumer, most of whom don't need it. BlueIce doesn't have that constraint: there's no separate AT process to serialize to, and the shared render pass already computes paint/stacking order as a compositing byproduct, so exposing it is much closer to "read a value that's already sitting there" than "add new computation." An actual occlusion test (is this node's bounding box actually covered by an opaque later-painted layer) is genuine net-new work in both reference engines — neither one does this today — but it's a bounded, well-scoped addition (one geometric test per query against the same paint-order data), not an open-ended design problem.
4. **Hover/focus as first-class per-node fields** — both are precedented (Blink's `kHovered` state bit; both engines' focus tracking), just need picking one shape (per-node bit, matching Gecko's `FOCUSED`/Blink's `kHovered`, rather than Blink's single tree-global `focus_id`, since BlueIce likely wants "is this specific node focused" queryable locally).

**On stable IDs, Blink is the concrete mechanism to learn from, not Gecko.** Gecko's AX "unique ID" is a raw C++ object memory address (`LocalAccessible::UniqueID()` returns `static_cast<void*>(this)`), invalidated and reissued whenever the accessible is torn down and rebuilt (`DocAccessible::RecreateAccessible`, which fires on ARIA-role-changing attribute edits, among other things) — this is the opposite of what Plan §1 asks for ("addressed by an explicit identifier assigned at creation... reference a specific element reliably across mutations") and should not be copied. Blink's approach is structurally closer to what BlueIce already requires: the AXID *is* the DOM node ID (`ui/accessibility/ax_node_id_forward.h`: "positive AXNodeIDs match DOM node ids generated by Blink"), so AX-tree identity is inherited from DOM-node identity rather than being a parallel bookkeeping system that can drift out of sync. The one place Blink falls short of BlueIce's own bar is that the underlying `DOMNodeIds::IdForNode()` assigns lazily on first request off a single global counter, not at node construction — BlueIce's stable-ID requirement (assigned at creation) is already a strictly stronger guarantee than what Blink provides today. Practically, this means BlueIce doesn't need to design a separate "AX node ID" scheme at all: if the shared representation layer is keyed directly by the same stable DOM ID the engine already assigns at node creation, AX-tree-style identity stability falls out for free, and Blink's incremental `AXTreeSerializer`-style diff-by-ID update pattern becomes directly reusable as the mutation-to-representation-update mechanism, without an IPC boundary to design around (BlueIce is single-process by construction, per the plan's shared-render-pass premise) and without legacy platform-AT role-table compatibility constraints (Gecko's `RoleMap.inc`, mapping one role to six different platform APIs simultaneously) forcing the schema's shape.

**Concrete recommendation**: adopt an accessibility-tree-shaped base schema (modeled on `AXNodeData`'s field categories: role, state bitset, typed attribute maps, provenance-tagged name/description, offset-relative bounding box) as the AI-facing representation, keyed by BlueIce's existing stable per-node DOM ID rather than inventing a parallel AX-specific ID; extend it with the four items above (opacity, animation/transition state, general paint-order/occlusion, per-node hover+focus). This is a small, well-evidenced delta over prior art, not the "requires custom design; highest maintenance cost" the plan currently assumes for the hybrid option — the maintenance cost the plan is worried about mostly stems from cross-process serialization and multi-platform AT compatibility, neither of which applies to BlueIce's single-process, single-consumer architecture.
