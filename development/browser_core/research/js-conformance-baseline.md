# BlueJS conformance baseline

Checked against official sources on **2026-09-09**; do not infer the current edition from memory or from a Node.js result.

- [Ecma's publication page](https://ecma-international.org/publications-and-standards/standards/ecma-262/) identifies **ECMAScript 2026, ECMA-262 edition 17, June 2026** as the latest published standard. Its [versioned HTML](https://262.ecma-international.org/17.0/) is the normative copy. The HTML was fetched directly and the relevant clauses read; the web reader's size limit on the single-page document is not a reason to substitute an older edition.
- The [TC39 living specification](https://tc39.es/ecma262/multipage/) currently identifies itself as **ECMAScript 2027, draft dated September 8, 2026**. It includes changes after the annual snapshot; it is not the published 2026 edition. Recheck the date and clauses when developing subsequent slices.

## Clauses used by the coverage-hardening slice

1. [2026 §12.9.4, String Literals](https://262.ecma-international.org/17.0/#sec-literals-string-literals), also checked against the [current draft](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-literals-string-literals): hexadecimal escapes consume hexadecimal digits, not a signed integer. Two digits follow `\x`, four follow unbraced `\u`, and the braced form requires a nonempty hexadecimal code point. Reject signed forms such as `\x+1` and `\u{+1}` before Rust's integer parser (which otherwise accepts a leading plus). Keep leading-zero code points valid. That escape-validation slice did not resolve the original UTF-8 storage limitation; the subsequent [UTF-16/String track](../phase-13-bluejs-engine/STRING_BUILTINS.md) now preserves lone surrogates and separately escaped pairs. Their former rejection was an implementation gap, not a standard-required SyntaxError.
2. [2026 §6.1.6.1.20, Number::toString](https://262.ecma-international.org/17.0/#sec-numeric-types-number-tostring), compared with the [current draft's same clause](https://tc39.es/ecma262/multipage/ecmascript-data-types-and-values.html#sec-numeric-types-number-tostring): the published edition requires a shortest round-tripping representation, and **Note 2 recommends** nearest-value/even-significand tie selection. The current draft puts that selection **in normative step 5**. BlueJS keeps the nearest/even behavior, compatible with both the published recommendation and the newer draft requirement. Do not describe the 2026 recommendation as already normative. Fixed/scientific decimal presentation boundaries are checked separately.

The float midpoint implementation compares exact integer ratios, never equality of re-parsed adjacent decimals (both may round to the same binary64). For shortest significand `s` (at most 17 digits), a lower-neighbor midpoint is `(2s-1) * 10^k / 2`. Only `-24 <= k < 0` can qualify: for `k >= 0`, its odd binary factor implies an ULP too small for either adjacent decimal to round back to that midpoint; for `k <= -25`, the necessary factor `5^(-k)` exceeds `2s-1`. Within the remaining range the factor fits `u64`, so divisibility plus quotient equality tests the exact rational without iterative multiplication/overflow branches. This is an implementation proof, not a claim taken from the specification.

## Verification boundaries

Use public `parse -> compile -> Vm::execute` regressions, including malformed escapes and fixed expected decimal boundaries. The opt-in Node.js oracle provides an independent compatibility check with broader deterministic float samples; it is neither the specification nor a runtime dependency. Record its installed version with validation results. A 100% line-coverage report does not establish full ECMAScript conformance, branch coverage, Test262 completion or support for currently deferred language features.
