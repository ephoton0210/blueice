# Cross-process frame delivery and control-plane IPC in Chromium and Gecko

Findings from reading `../reference/chromium` (Chromium/Viz) and `../reference/gecko` (Firefox/WebRender) directly, focused on the two open BlueIce design questions: how a rendered frame actually crosses a process boundary without a full-frame-serialization cost, and how "control" traffic (input, resize, lifecycle, navigation) is kept architecturally separate from that high-bandwidth path. This directly informs Phase 4's `core`↔`frontend` IPC design, since `core` and `frontend` are separate OS processes for BlueIce the same way renderer/GPU/browser are separate processes in both reference engines — except BlueIce's `frontend` is a different native toolkit per platform, which neither reference engine has to deal with (their equivalent of "frontend" is Chrome/Firefox's own C++ browser-chrome code, always the same language and mostly the same graphics stack as the engine itself).

## 1. Chromium's Viz-based cross-process frame delivery

Viz lives under `components/viz/` (`client`, `common`, `host`, `service` subdirectories, per `components/viz/README.md`) with its actual Mojo interface definitions under the sibling `services/viz/public/mojom/` and `services/viz/privileged/mojom/` trees — the split documented in `components/viz/README.md` is: **Host** (privileged, browser process, owns/controls the Viz service), **Client** (renderer or other frame producer), **Service** (where the Mojo implementations actually run, normally the GPU process). The interface a renderer's compositor submits frames through is `viz.mojom.CompositorFrameSink`, defined at `services/viz/public/mojom/compositing/compositor_frame_sink.mojom:61-116`, with the key method `SubmitCompositorFrame(LocalSurfaceId local_surface_id, CompositorFrame frame, HitTestRegionList? hit_test_region_list, uint64 submit_time)` (line 89) — annotated `[EstimateSize, UnlimitedSize]` because a `CompositorFrame` can be large enough to need special handling in Mojo's size-limit machinery, with the code's own TODO (line 85-87) noting this is something they'd like to shrink rather than a settled design choice.

The critical fact is *what* `CompositorFrame` actually contains. `services/viz/public/mojom/compositing/compositor_frame.mojom` defines `struct CompositorFrame { CompositorFrameMetadata metadata; array<TransferableResource> resources; array<CompositorRenderPass> passes; }` — the render passes carry draw-quad geometry/transforms/effects (a scene description), not pixels, and pixel data is referenced indirectly through the `resources` array. `services/viz/public/mojom/compositing/transferable_resource.mojom` defines `struct TransferableResource { ResourceId id; gpu.mojom.ExportedSharedImage shared_image; gpu.mojom.SyncToken sync_token; SynchronizationType synchronization_type; ... }` (lines 61-79) — no pixel buffer field at all. `gpu/ipc/common/exported_shared_image.mojom` defines `ExportedSharedImage` as `gpu.mojom.Mailbox mailbox; gpu.mojom.SharedImageMetadata metadata; gpu.mojom.SyncToken creation_sync_token; ...; gfx.mojom.GpuMemoryBufferHandle? buffer_handle; ...`. `Mailbox` itself (`gpu/ipc/common/mailbox.mojom`, backing C++ comment at `gpu/command_buffer/common/mailbox.h:31-35`) is described in the source as "an unguessable name that references a SharedImage. This name can be passed across processes permitting one process to share a SharedImage with another" — a 16-byte opaque token, not data. In other words: what actually rides through Mojo on every `SubmitCompositorFrame` call is scene geometry plus small opaque handles into GPU-owned memory that both the renderer's and the GPU process's graphics contexts already have access to; the pixels themselves never serialize through the Mojo message.

The handle that ultimately backs a `Mailbox`-named `SharedImage`, when it needs to be described concretely (e.g. for a `GpuMemoryBuffer`-backed image), is `gfx.mojom.GpuMemoryBufferHandle` (`ui/gfx/mojom/buffer_types.mojom:29-34`), which wraps a `GpuMemoryBufferPlatformHandle` union (`ui/gfx/mojom/native_handle_types.mojom:114-127`) with one arm per platform: `mojo_base.mojom.UnsafeSharedMemoryRegion shared_memory_handle` (the CPU/software-compositing fallback), `NativePixmapHandle` (`EnableIf=supports_native_pixmap`, i.e. Linux/ChromeOS — an `array<NativePixmapPlane>` where each plane carries a raw `handle<platform> buffer_handle`, in practice a dma-buf file descriptor), `IOSurfaceHandle` (`EnableIf=is_apple` — a `handle<platform> mach_send_right`, i.e. a Mach port naming an `IOSurface`), `DXGIHandle` (`EnableIf=is_win` — a raw Windows `handle<platform> buffer_handle` plus a `DXGIHandleToken` used because "handles get duplicated and the OS provides no other identifier"), and `AHardwareBufferHandle` (`EnableIf=is_android`). Mojo's handle types here are OS-level handle-passing primitives (an fd gets `dup()`'d across the pipe, a Windows handle gets `DuplicateHandle`'d, a Mach port gets inserted into the receiver's task) — the kernel or GPU driver, not Mojo, is what makes the underlying memory/texture actually visible to the other process; Mojo only carries the small handle value plus metadata (size, stride, format via `SharedImageMetadata`).

The final-mile presentation step — GPU process pixels reaching an actual on-screen platform window — is set up via `components/viz/host/gpu_host_impl.{h,cc}` and `components/viz/host/host_display_client.{h,cc}`, with `components/viz/host/layered_window_updater_impl.{h,cc}` present specifically as a Windows layered-window fallback path (software compositing writing into a bitmap the OS composites), i.e. Chromium keeps essentially the same shared-memory-or-GPU-handle duality all the way to the literal screen surface, not just between renderer and GPU process.

## 2. Firefox's cross-process compositor/WebRender frame delivery — and how it differs from Chromium's approach

Gecko's cross-process compositor IPC lives under `gfx/layers/ipc/`, built on IPDL (`.ipdl`/`.ipdlh` files, Gecko's own IDL-based async-message-passing codegen, analogous in role to Chromium's `.mojom`). The top-level actor pair is `CompositorBridgeParent`/`CompositorBridgeChild` (`gfx/layers/ipc/CompositorBridgeParent.{h,cc}`, `CompositorBridgeChild.{h,cc}`), implementing protocol `PCompositorBridge` (`gfx/layers/ipc/PCompositorBridge.ipdl`). WebRender-specific frame/scene traffic rides a child protocol, `PWebRenderBridge` (`gfx/layers/ipc/PWebRenderBridge.ipdl:35`, `manager PCompositorBridge` at line 36), established per-window via `async PWebRenderBridge(PipelineId pipelineId, LayoutDeviceIntSize aSize, WindowKind aKind)` on the parent protocol (`PCompositorBridge.ipdl:193`).

The architecturally important difference from Chromium shows up in what actually crosses on `PWebRenderBridge`: `async SetDisplayList(DisplayListData displayList, OpDestroy[] toDestroy, ...)` (`PWebRenderBridge.ipdl:47-53`). `DisplayListData` (`gfx/layers/wr/RenderRootTypes.h:17-28`) is `{ IdNamespace mIdNamespace; LayoutDeviceRect mRect; nsTArray<WebRenderParentCommand> mCommands; Maybe<ByteBuf> mDLItems; Maybe<ByteBuf> mDLSpatialTree; BuiltDisplayListDescriptor mDLDesc; nsTArray<OpUpdateResource> mResourceUpdates; nsTArray<RefCountedShmem> mSmallShmems; nsTArray<Shmem> mLargeShmems; Maybe<WebRenderScrollData> mScrollData; }` — this is a **retained-mode display list** (serialized WebRender scene-building commands, i.e. "draw this rect with this style at this position"), not a rendered frame at all. The content process never rasterizes its own compositor frame in the WebRender path; it builds and ships the scene description, and the actual rasterization happens inside `gfx/webrender_bindings/` — `RenderThread` (`RenderThread.h`/`.cc`), `RendererOGL` (`RendererOGL.h`/`.cc`), and platform `RenderCompositor` subclasses (`RenderCompositorANGLE`, `RenderCompositorEGL`, `RenderCompositorD3D11SWGL`, etc.) — which runs, per `CompositorBridgeParent.h:496-500`'s own comment, either in a dedicated GPU/compositor process or, "unless the compositor process is separated," in the parent (browser) process itself; either way it is a process distinct from the content process that built the display list. This means Chromium's "renderer GPU-rasterizes a texture, hands a reference across" model and Gecko's "content process ships a scene description, the compositor process's WebRender instance rasterizes it locally" model are genuinely different strategies for avoiding full-frame serialization — Chromium avoids it by not copying an already-rasterized texture, Gecko (for ordinary DOM content) avoids it by not rasterizing on the sending side in the first place.

Gecko still needs a Chromium-`TransferableResource`-equivalent mechanism for content that *is* rasterized outside the compositor process — decoded video frames, WebGL/canvas surfaces, images — and that mechanism is `gfx/layers/ipc/PTexture.ipdl` (`PTexture`, "the IPDL glue between a TextureClient and a TextureHost", manager `PImageBridge or PCompositorBridge or PVideoBridge`) plus the `SurfaceDescriptor` union in `gfx/layers/ipc/LayersSurfaces.ipdlh:236-251`. That union has exactly the same platform-by-platform shape as Chromium's `GpuMemoryBufferPlatformHandle`: `SurfaceDescriptorDMABuf` (Linux, an `array<FileHandleWrapper> fds` per plane — dma-buf), `SurfaceDescriptorMacIOSurface` (`uint32_t surfaceId`, a global IOSurface lookup ID), `SurfaceDescriptorD3D10`/`SurfaceDescriptorDXGIYCbCr` (Windows, `nullable FileHandleWrapper handle` — a shared D3D handle), `SurfaceTextureDescriptor`/`SurfaceDescriptorAndroidHardwareBuffer` (Android), plus `SurfaceDescriptorBuffer { BufferDescriptor desc; MemoryOrShmem data; }` where `MemoryOrShmem` (`LayersSurfaces.ipdlh:203-206`) is a union of a raw `uintptr_t` (same-process only) or an IPDL `Shmem` (a cross-process shared-memory segment) — the CPU/software fallback, structurally the same role as Chromium's `UnsafeSharedMemoryRegion` arm. `SurfaceDescriptorRemoteTexture`/`SurfaceDescriptorExternalImage` (lines 226-234) are WebRender-specific: they let a `RenderTextureHost` subclass in the compositor process (`RenderDMABUFTextureHost`, `RenderMacIOSurfaceTextureHost`, `RenderD3D11TextureHost`, `RenderAndroidHardwareBufferTextureHost`, all under `gfx/webrender_bindings/`) resolve an `ExternalImageId` straight to the platform-native GPU handle without WebRender's own scene format needing to know the platform details.

The last-mile presentation step is also structurally informative: `gfx/layers/ipc/PCompositorBridge.ipdl:122` has `async PCompositorWidget(CompositorWidgetInitData aInitData)`, and the per-platform `CompositorWidgetInitData` — e.g. `widget/windows/PlatformWidgetTypes.ipdlh:17-21`, `struct WinCompositorWidgetInitData { WindowsHandle hWnd; uintptr_t widgetKey; TransparencyMode transparencyMode; }` — hands the compositor process a raw native window handle (an actual `HWND` on Windows) so it can create its own swap chain and present directly, the same shape macOS (`widget/cocoa/PlatformWidgetTypes.ipdlh`) and GTK (`widget/gtk/PlatformWidgetTypes.ipdlh`) variants follow. Chromium does the analogous thing via a `gpu::SurfaceHandle` passed from the browser process to the GPU process. Both engines' answer to "how does a rendered frame reach the screen" ultimately bottoms out in *the process that has the GPU context owns the actual OS window/swap chain and presents into it directly* — there is no final "send the pixels back to whoever owns the window" step at all in the common case, because the compositor process and the window-owning process are made to be the same process.

## 3. Is the control/frame-plane separation deliberate, and how is it structured

**Chromium: a deliberate, fine-grained multiplexing over one Mojo message-pipe-per-concern**, not a single generic channel. The renderer-side widget's general control interface, `blink.mojom.WidgetHost` (`third_party/blink/public/mojom/widget/platform_widget.mojom:35-...`), carries cursor updates, tooltips, IME/text-input state, selection bounds, etc., and its `CreateFrameSink` method (referenced from `platform_widget.mojom:76` onward) is what *establishes* a separate `pending_receiver<viz.mojom.CompositorFrameSink>` / `pending_receiver<viz.mojom.CompositorFrameSinkClient>` pair — i.e. the frame-submission channel is a distinct Mojo interface/pipe, deliberately spun up as its own thing rather than reusing `WidgetHost`'s pipe, and `InitialFrameSinkParams` (`platform_widget.mojom:21-25`) bundles it together with a `RenderInputRouterClient` receiver at setup time. Input goes through yet another dedicated interface, `blink.mojom.WidgetInputHandler` (`third_party/blink/public/mojom/input/input_handler.mojom`), and resize/screen-geometry/DSF/viewport state goes through the `VisualProperties` struct (`third_party/blink/public/mojom/widget/visual_properties.mojom:16-52`, fields like `new_size_device_px`, `compositor_viewport_pixel_rect`, `screen_infos`) carried on `blink.mojom.FrameWidget`/`FrameWidgetHost` (`third_party/blink/public/mojom/page/widget.mojom`). So at the Mojo layer Chromium runs at least four logically distinct interfaces for one on-screen widget — `WidgetHost` (misc control), `WidgetInputHandler` (input), `FrameWidget`/`FrameWidgetHost` (drag/IME/resize/lifecycle), `CompositorFrameSink`/`CompositorFrameSinkClient` (frames) — all independent Mojo pipes that happen to share the same underlying OS transport (a socket/pipe multiplexed by the Mojo core), so "separate channel" here means separate *logical* interface/message-pipe, not a separate physical transport; the zero-copy property comes entirely from what's carried inside `CompositorFrameSink`'s messages (handles, not pixels), not from the pipe being physically distinct hardware.

**Gecko: also deliberate, but structured as protocol nesting rather than independent siblings.** `PWebRenderBridge` is explicitly a *managed* child of `PCompositorBridge` (`manager PCompositorBridge`, `PWebRenderBridge.ipdl:36`), and resize/lifecycle live as top-level `PCompositorBridge` messages — `Pause`/`Resume`/`ResumeAsync` (`PCompositorBridge.ipdl:136-138`), `WillClose` (line 132), `PCompositorWidget` (line 122) for handing over the native window, `FlushRendering`/`ForcePresent` (lines 165-176) — while scene/frame content (`SetDisplayList`, `UpdateResources`, `ParentCommands`) is scoped to the child `PWebRenderBridge` protocol instance for that specific window/pipeline. Input has its own sibling protocol family entirely, `PAPZCTreeManager`/`PAPZ`/`PAPZInputBridge` (also under `gfx/layers/ipc/`, e.g. `PAPZInputBridge.ipdl`) for the async pan-zoom/input-hit-testing path, independent of both `PCompositorBridge` and `PWebRenderBridge`. So Gecko's separation is real but expressed as IPDL's native manager/child protocol hierarchy (one transport, logically partitioned actors) rather than Chromium's flatter "just spin up another Mojo interface" style — same underlying idea (control traffic and frame traffic are different message types/protocols so one never blocks or is confused with the other), different codegen idiom. Neither engine multiplexes frame-pixel bytes and input/resize events over one generic serialize-everything channel; both treat "the compositor frame" as data with its own dedicated submission path precisely because it's disproportionately large and disproportionately frequent (per-vsync) compared to input/resize/lifecycle traffic.

## 4. Assessment: what shape should BlueIce's `core`↔`frontend` frame channel take

Both reference engines get zero-copy by handing the far process a *reference into memory both sides' graphics stacks already understand* — a GPU driver/OS-level handle (dma-buf fd, IOSurface Mach port, DXGI shared handle, `AHardwareBuffer`) or, as a fallback, a shared-memory region — and both keep that reference-passing path as a distinct interface/protocol from control traffic, specifically because control messages are low-frequency/small and frame submission is per-vsync/large, and coupling them either serializes frames unnecessarily slowly or lets frame backpressure stall input/resize handling. That much of the design — two logically separate channels sharing one transport, control-plane as small structured messages, frame-plane as "handle plus metadata, not bytes" — is safe to treat as a validated pattern for BlueIce's IPC family: the control-plane protocol (shared with `extension` and the AI-facing API, per the plan) should be one interface/pipe family, and frame delivery should be a second, dedicated one, exactly mirroring Chromium's `WidgetHost`+`WidgetInputHandler`+`FrameWidget` vs. `CompositorFrameSink` split or Gecko's `PCompositorBridge` vs. `PWebRenderBridge` split.

Where BlueIce's situation is genuinely harder than either reference engine's is the thing both of them get for free and never had to solve: **in Chromium and Gecko, the process that owns the GPU context and the process that owns the OS-native window are made to be the same process** (`gpu::SurfaceHandle` handed to the GPU process; `CompositorWidgetInitData`'s raw `HWND`/`NSView`/GTK widget handed to the compositor process), so presentation is a local `SwapBuffers`/`Present` call, not a cross-process step at all — there is no "send a finished frame to whoever owns the window" leg in the happy path for either engine. BlueIce's design puts the window-owning process on the *other* side of the boundary from `core`: `frontend` owns the native window (WinUI 3 `SwapChainPanel`, SwiftUI `MTKView`/`CAMetalLayer`-backed view, Qt's own `QRhi`/`QWindow` surface), and `core` is the one producing pixels, which is closer to Chromium's renderer-to-GPU-process leg than to either engine's GPU-process-to-screen leg — so BlueIce cannot skip the cross-process handle-passing step the way either reference engine skips its *last* mile; BlueIce's channel has to do the equivalent of the renderer→GPU-process `TransferableResource`/`Mailbox` leg but deliver all the way to a foreign-toolkit-owned surface.

A single, literally cross-platform-portable zero-copy mechanism is not realistic, for the same reason neither Chromium's `GpuMemoryBufferPlatformHandle` nor Gecko's `SurfaceDescriptor` is a single mechanism: both are per-platform-arm unions (dma-buf vs. IOSurface vs. DXGI vs. AHardwareBuffer) precisely because "a handle to GPU memory" has no OS-portable representation — it's always an OS/driver-specific handle type, and both mature engines converged independently on "one union type, one arm per platform" rather than inventing a portable abstraction over the handle itself. BlueIce's situation adds a second axis of divergence on top of the OS one: even *within* a single OS, the frontend toolkit dictates what kind of handle is importable at all — WinUI 3/DirectX wants a shared `ID3D11Texture2D`/DXGI handle (or a `SwapChainPanel` `ISwapChainPanelNative` surface), SwiftUI/Metal wants an `IOSurface`-backed `MTLTexture` (or a `CVPixelBuffer`), and PySide6/Qt's renderer varies by Qt's own backend selection (`QRhi` can be Metal/D3D11/Vulkan/OpenGL depending on platform and Qt build config, and Qt's own texture-import API differs across `QQuickFramebufferObject`, `QSGTexture::fromNative`, and RHI-native-handle interop depending on Qt version) — so "the platform" alone doesn't even pin down the handle type on the frontend side the way it does for Chromium/Gecko's own first-party compositor.

Concretely, BlueIce should design the frame channel as **a common interface with a per-platform-frontend adapter behind it**, not a single wire format: define the frame-plane protocol's payload the way `TransferableResource`/`SurfaceDescriptor` do — an enum/union of handle *kinds* (e.g. `SharedMemoryRegion`, `DxgiSharedHandle` for WinUI 3, `IOSurfaceHandle` for SwiftUI, and whatever Qt/PySide6's RHI backend actually needs, determined empirically per Qt build rather than assumed) plus common metadata (size, stride/format, a frame-generation/sequence number playing the role of Chromium's `SyncToken`/Gecko's fence for producer/consumer synchronization) — with `core` on each platform producing the one handle kind that platform's `frontend` can actually import, not attempting a lowest-common-denominator format. `core` rendering with `wgpu` (or whatever GPU abstraction it ends up using) already has to target a platform-specific backend (D3D12/Metal/Vulkan) per platform build, so producing a platform-native exportable handle from that backend's output texture is not extra generality on `core`'s side — it's the same "one platform, one concrete backend" reality `core`'s renderer already lives in; the adapter layer belongs entirely in how that handle is *described on the wire* and *imported on the `frontend` side* (WinUI 3's C++/WinRT interop code importing a shared `ID3D11Texture2D` into a `SwapChainPanel`; SwiftUI's Swift/Obj-C interop code wrapping an `IOSurface` in an `MTLTexture` and driving an `MTKView`; PySide6's Python/C++ interop importing whatever handle Qt's active RHI backend accepts). Shared memory should still be kept as the universal fallback path (same role as Chromium's `UnsafeSharedMemoryRegion` and Gecko's `Shmem`/`MemoryOrShmem`) for headless/software-rendering configurations, remote/virtualized frontends, or any platform combination where a GPU handle can't be shared cheaply enough to bother — accepting a CPU copy there rather than adding a fifth handle-kind arm to chase a case where zero-copy isn't achievable anyway.
