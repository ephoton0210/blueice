# Safe Browsing / url-classifier enforcement architecture in Chromium and Gecko

Findings from reading `../reference/chromium` and `../reference/gecko` directly, focused on the question Phase 7's "enforcement architecture" open item actually needs answered: not how URL-reputation checking works, but how the check gets *wired into* the navigation/download pipeline such that it can't be silently skipped by a careless or malicious code path, what happens when the check can't complete in time, and how user override of a block is handled.

## 1. Chromium's Safe Browsing enforcement architecture

**Navigation goes through a single funnel point, but the safety check attached to it is an optional, embedder-supplied policy decision, not a required dependency.** Every navigation's network request is created by `NavigationURLLoaderImpl::CreateThrottlingLoaderAndStart()` (`content/browser/loader/navigation_url_loader_impl.cc:1347`), which unconditionally calls `CreateURLLoaderThrottles()` (`:1983`) before starting the request. That in turn calls `content::CreateContentBrowserURLLoaderThrottles()` (`content/browser/loader/url_loader_throttles.cc:49-52`), which unconditionally calls `GetContentClient()->browser()->CreateURLLoaderThrottles(...)` — a `virtual`, *not* pure-virtual, method on `ContentBrowserClient` (`content/public/browser/content_browser_client.h:1731-1739`) whose default implementation in `content/` returns an empty throttle vector. Chrome's embedder override, `ChromeContentBrowserClient::CreateURLLoaderThrottles` (`chrome/browser/chrome_content_browser_client.cc:5982-5988`), is the thing that actually calls `MaybeCreateSafeBrowsingURLLoaderThrottle(...)` (`:5792`, which itself calls `safe_browsing::BrowserURLLoaderThrottle::Create(...)` at `:5871`) and pushes the result into the vector.

So the "mandatory" part of this architecture is genuinely structural — one funnel every request passes through — but *what* gets attached at that funnel is ordinary runtime policy: `BUILDFLAG(SAFE_BROWSING_AVAILABLE)`, enterprise allowlist checks, and prefs all gate whether the Safe Browsing throttle is actually constructed. A `content/`-level embedder that never overrides `CreateURLLoaderThrottles()` gets zero Safe Browsing, silently, with no compiler warning. Chromium's own code admits at least one real gap in this funnel: `content/public/browser/content_browser_client.h:3340-3345` documents that `CreateURLLoaderThrottles()` is not applied to `content::PrefetchContainer` requests at all, which required a separate, hand-maintained `ShouldAllowPrefetchRedirection`/header-mutation mechanism as a patch around the gap.

**The class named in the task brief, `SafeBrowsingNavigationThrottle`, is a red herring for enforcement — it doesn't perform the check.** Its own doc comment at `components/safe_browsing/content/browser/safe_browsing_navigation_throttle.h:26-42` says so directly: "This NavigationThrottle doesn't actually perform a SafeBrowsing check nor block the navigation. That happens in SafeBrowsing's `BrowserURLLoaderThrottle`... This throttle monitors failed requests... and if blocked by Safe Browsing, creates and displays an interstitial." It's registered into the ordinary, skippable `NavigationThrottleRegistry` list via `MaybeCreateAndAdd()`, and is purely a reactive UI trigger — if it's never registered (or `ui_manager` is null), the navigation is still blocked at the network layer, just with no interstitial shown.

**The actual check runs in the network-loading stack, not the navigation-lifecycle stack.** `BrowserURLLoaderThrottle` (`components/safe_browsing/content/browser/browser_url_loader_throttle.h:44`) is a `blink::URLLoaderThrottle` implementing `WillStartRequest`/`WillRedirectRequest`/`WillProcessResponse`, able to defer or cancel the `ThrottlingURLLoader`. It owns `SafeBrowsingUrlCheckerImpl` instances (via `UrlCheckerHolder`, see `sync_sb_checker_`/`async_sb_checker_` at `browser_url_loader_throttle.h:223-224`). `SafeBrowsingUrlCheckerImpl` (`components/safe_browsing/core/browser/safe_browsing_url_checker_impl.h:53`) implements the Mojo interface `mojom::SafeBrowsingUrlChecker`, so it can be driven either over Mojo from a renderer-side throttle or called directly in-process from the browser — but nothing forces any of this to exist; it's a plain heap object constructed only by code that chooses to construct it, with no type-level requirement that a navigation path hold one.

**Downloads follow the identical "one funnel, optional payload" shape, one layer down.** `content::DownloadManagerDelegate` is a nullable `raw_ptr` on `DownloadManagerImpl`; `ShouldCompleteDownload()` (`content/browser/download/download_manager_impl.cc:672-677`) reads `if (!delegate_ || delegate_->ShouldCompleteDownload(...)) return true;` — a null delegate means downloads complete unconditionally, fail-open by simple absence. The real gate is one level lower, inside the download component's own state machine: `DownloadItemImpl::IsDownloadReadyForCompletion()` (`components/download/internal/common/download_item_impl.cc:2390-2427`) hard-codes `if (IsDangerous()) return false;` *before* ever consulting the delegate — this is the one piece of genuine structural enforcement found anywhere in the pipeline: once any code path has marked a download dangerous, no delegate can complete it without first clearing that state. It protects only downloads that got marked dangerous in the first place, though; nothing forces the marking check itself to run. Chrome's actual reputation check is wired in via `ChromeDownloadManagerDelegate::IsDownloadReadyForCompletion` (`chrome/browser/download/chrome_download_manager_delegate.cc:1002-1029`) calling `DownloadProtectionService::MaybeCheckClientDownload(...)`, and even that can decline to check at all (`MaybeCheckClientDownload` returns `false` if `delegate_->MayCheckClientDownload(item)` is false) — in which case Chrome's fallback code explicitly re-applies a `DANGEROUS_FILE` danger state "in case the service was disabled between the download starting and now" (`chrome_download_manager_delegate.cc:1032-1041`), a manual patch for a gap the architecture itself doesn't close.

**Bottom line:** Chromium's pattern is "a single mandatory call site that every request passes through, into an optional, embedder-supplied, runtime-conditional decision of what to attach there" — not a type-system guarantee that a `NavigationRequest`/download cannot proceed without a safety check. The mandatoriness is architectural convention (one loader class, one delegate slot, always invoked) plus code-review discipline on `chrome_content_browser_client.cc`, not a language-level constraint, and Chromium's own comments document at least two places (prefetch requests, a download-check opt-out) where that convention needed a manual patch because it wasn't actually airtight.

## 2. Chromium's fail-open/fail-closed behavior and user override

**Navigation URL checks fail open on a hardcoded 5-second timeout, explicitly by design.** `components/safe_browsing/core/browser/safe_browsing_lookup_mechanism_runner.cc:13-16` defines `const int kCheckUrlTimeoutMs = 5000;` directly under the comment "Maximum time in milliseconds to wait for the SafeBrowsing service reputation check. After this amount of time the outstanding check will be aborted, and the resource will be treated as if it were safe." On expiry, `OnTimeout()` (`:63-68`) invokes the completion callback with `timed_out=true`, and the consumer, `SafeBrowsingUrlCheckerImpl::OnUrlResultAndMaybeDeleteSelf` (`safe_browsing_url_checker_impl.cc:246-266`), maps that directly to `SBThreatType::SB_THREAT_TYPE_SAFE` — a timeout becomes, from that point on, bit-for-bit indistinguishable from a genuine clean verdict. The class's own header restates this: "If it takes longer than this, then the system defaults to treating the URL as safe" (`safe_browsing_url_checker_impl.h:46-48`). Both citations were verified directly against the checkout.

**Downloads fail open the same way, on a separate timeout, with one partial local mitigation.** `CheckClientDownloadRequestBase::StartTimeout()` (`chrome/browser/safe_browsing/download_protection/check_client_download_request_base.cc:411-421`) schedules a delayed task that finishes the request with `DownloadCheckResult::UNKNOWN` after `service_->GetDownloadRequestTimeout()`. `ChromeDownloadManagerDelegate::CheckClientDownloadDone` maps `UNKNOWN` to `DOWNLOAD_DANGER_TYPE_NOT_DANGEROUS` *unless* a separate, non-network-dependent static check (a file-extension-based "danger level" heuristic) had already independently flagged the file, in which case it stays `DANGEROUS_FILE`. So the server-verdict axis is fail-open on timeout exactly like navigation, but a local, always-available heuristic isn't defeated by the same timeout — a mitigation navigation has no equivalent of.

**User override ("Proceed anyway") is a real, gated decision point, not an unconditional bypass — but the gate is a preference, not a structural block.** `BaseBlockingPage::CommandReceived` (`components/safe_browsing/content/browser/base_blocking_page.cc:107-134`, confirmed against source) checks `interstitial_command == CMD_PROCEED && !sb_error_ui_->is_proceed_anyway_disabled()` before calling `set_proceeded(true)` and notifying `ui_manager()->OnBlockingPageDone(..., true /* proceed */, ...)`; if `is_proceed_anyway_disabled()` is true, the proceed side effect is simply skipped. That flag traces back to an enterprise policy-backed pref, `kSafeBrowsingProceedAnywayDisabled` (`components/safe_browsing/core/common/safe_browsing_prefs.h:71`, `.cc:233-235`, confirmed present and wired from `chrome/browser/policy/configuration_policy_handler_list_factory.cc:360`). Both the interstitial being shown and a user proceeding through it are logged to enterprise reporting connectors regardless of consumer-level "extended reporting" settings — `MaybeTriggerSecurityInterstitialShownEvent`/`...ProceededEvent` (`chrome/browser/interstitials/enterprise_util.cc:104-172`) both fire into `extensions::SafeBrowsingPrivateEventRouter` / `enterprise_connectors::ReportingEventRouter`, and the "shown" event even carries the disabled-pref's own value as a reported field. No click-delay or rate-limit on the Proceed button itself was found; the only delay present (`kThreatDetailsProceedDelayMilliSeconds = 3000`, `base_blocking_page.cc:40-42`) only defers sending the post-proceed telemetry report, not the button's availability.

## 3. Firefox's url-classifier equivalent

**Firefox's structural wiring is tighter than Chromium's for navigation: the check is baked directly into the channel's own lifecycle methods rather than attached through a pluggable throttle list.** The hook class is `nsChannelClassifier` (`netwerk/url-classifier/nsChannelClassifier.h`/`.cpp`), which implements `nsIURIClassifierCallback` and wraps a single call, `uriClassifier->Classify(principal, this, &expectCallback)`, against `nsIUrlClassifierDBService` (`nsChannelClassifier::StartInternal`, `:215`). There are two call sites, both inside a channel's own core open/connect path rather than an optional observer registration: `nsBaseChannel::ClassifyURI()` is called unconditionally at the tail of both `Open()` (`netwerk/base/nsBaseChannel.cpp:646`) and `AsyncOpen()` (`:722`), covering the many non-HTTP protocol channels (ftp, data, blob, resource, view-source); and `nsHttpChannel::BeginConnect()` — reached via `AsyncOpen → AsyncOpenFinal → MaybeResolveProxyAndBeginConnect → BeginConnect` — calls `GetOrCreateChannelClassifier()->Start()` directly (`netwerk/protocol/http/nsHttpChannel.cpp:8461-8468`, confirmed against source). A channel that reaches these lifecycle points cannot skip the call the way a `content/` embedder can skip attaching Chromium's optional `BrowserURLLoaderThrottle`.

Whether classification actually happens for a given request is centralized in one shared policy function, `NS_ShouldClassifyChannel()` (`netwerk/base/nsNetUtil.cpp:3393-3455`), consulted by both call sites — gated by the pref `urlclassifier.enabled_mode` (default `3`, both Safe Browsing and Anti-Tracking on), the explicit `nsIChannel::LOAD_BYPASS_URL_CLASSIFIER` flag, and a `beConservative` escape hatch for critical channels like the updater. `nsUrlClassifierDBService.cpp:2082` states outright in a comment: "nsChannelClassifier is the only consumer of this interface" — one enforcement call site, one shared gating function, rather than Chromium's per-embedder policy decision scattered across an optional throttle list.

**Downloads are the inverse case: convention-based, not structural, unlike Firefox's own navigation path.** Application-reputation checking is invoked from `DownloadIntegration.shouldBlockForReputationCheck()` (`toolkit/components/downloads/DownloadIntegration.sys.mjs:458-500`) via `DownloadCore.sys.mjs`'s `_checkReputationAndMove()`, called manually at the tail of `execute()` in each of the two concrete `DownloadSaver` subclasses — `DownloadCopySaver` (`DownloadCore.sys.mjs:2773`, with the comment "reputation checking is the final step in the saver") and `DownloadLegacySaver` (`:3292`). The abstract base `DownloadSaver.prototype.execute()` (`:2259`) is an unimplemented stub, so nothing forces a third saver implementation to call the reputation check — it holds today only because both shipped subclasses happen to call it, the same "someone remembered" pattern as Chromium's `DownloadManagerDelegate`.

**Firefox is explicitly, deliberately fail-open on timeout, at every layer, and says so in its own comments.** `nsChannelClassifier::Start()` (`netwerk/url-classifier/nsChannelClassifier.cpp:118-125`, confirmed against source) reads: if `StartInternal()` fails for any reason (DB service unavailable, or `Channel::Suspend()` failing on channel types that don't support it — commented "This shouldn't be fatal, but will prevent malware from being blocked on these channels"), it immediately calls `OnClassifyComplete(NS_OK, ""_ns, ""_ns, ""_ns)` — i.e. treats the load as classified-safe rather than blocking or retrying. The full-hash "gethash" confirmation step has its own timeout (`urlclassifier.gethash.timeout_ms`, default 5000ms); on timeout the pending completion is treated as unconfirmed, and `OnAllCompletionsFinished()` explicitly skips unconfirmed results ("Skipping result...(not confirmed)", `nsUrlClassifierDBService.cpp:1430-1437`) — an unresolved local prefix hit due to timeout is treated as no-match. Download application-reputation checking (`toolkit/components/reputationservice/ApplicationReputation.cpp`) initializes `verdict = VERDICT_SAFE` before the network round-trip even starts (`OnStopRequest`, `:1793`), and on any failure — including its own timeout at `browser.safebrowsing.downloads.remote.timeout_ms` (default 10000ms) canceling the channel with `NS_ERROR_NET_TIMEOUT_EXTERNAL` — `OnStopRequestInternal` early-returns without touching `aVerdict` (`:1829-1836`), leaving the default `VERDICT_SAFE` in place. Every timeout path in Firefox's implementation, across both navigation and downloads, resolves to "allow."

**User override is a scoped, auditable permission grant, not a one-shot UI bypass — a meaningfully different mechanism from Chromium's pref-gated button.** `nsDocShell::LoadErrorPage()` appends `&o=1` to the `about:blocked?...` URL only if `browser.safebrowsing.allowOverride` is true (default `true`, `modules/libpref/init/all.js:3386`, confirmed present); `blockedSite.js`'s `getOverride()` uses that to decide whether to render the override link at all. Clicking it (`BlockedSiteParent.sys.mjs:160-169`) records Glean telemetry (`urlclassifier.uiEvents`, bucketed per threat category) and calls `ignoreWarningLink()` (`:173-297`), which does two structurally interesting things rather than just reloading the page: it adds a session-scoped permission-manager entry (`Services.perms.addFromPrincipal(..., "safe-browsing", ALLOW_ACTION, EXPIRE_SESSION)`, `:186-191`) for that principal, then reloads with the official `LOAD_FLAGS_BYPASS_CLASSIFIER` escape hatch. That permission is checked directly inside `nsUrlClassifierDBService::Classify()` itself (`toolkit/components/url-classifier/nsUrlClassifierDBService.cpp:2116-2130`, confirmed against source: `TestPermissionFromPrincipal(..., "safe-browsing"_ns, &perm)`, and if `perm == ALLOW_ACTION`, `*aResult = false` short-circuits classification entirely) — meaning the override is recorded as state in the same permission system that governs geolocation/notifications/etc., auditable and inspectable independent of the interstitial UI, rather than a purely client-side "remember not to warn again" flag, and it naturally expires at session end rather than persisting silently forever.

## 4. Assessment and recommendation for BlueIce's gatekeeper enforcement architecture

**Neither reference engine gets this fully right, and the two failure modes they demonstrate are different and both instructive.** Chromium's failure mode is that its "funnel" is a single call site into an *optional* payload — `ContentBrowserClient::CreateURLLoaderThrottles()` and `DownloadManagerDelegate` are both nullable/overridable hooks with a default empty/absent behavior, so the language and type system permit constructing a fully-functional navigation or download path with zero safety checking attached, and Chromium's own code comments admit at least two real gaps (prefetch, a download-check opt-out) that had to be patched by hand after the fact. Firefox's channel-classifier wiring is structurally tighter — the check is a direct, unconditional call inside the channel's own `AsyncOpen`/`BeginConnect` lifecycle rather than an attachable observer — but Firefox's downloads path reverts to Chromium's weaker "convention, not structure" shape (a stub base-class `execute()` that each saver subclass has to remember to finish with a reputation check), and *both* engines are explicitly, deliberately fail-open on timeout/unreachable-backend at every layer studied — the opposite of BlueIce's settled fail-closed policy (`phase-7-local-ai/PLAN.md:79`). Neither engine uses a compile-time/type-system mechanism anywhere in this pipeline; every enforcement point found, in both codebases, is a runtime call that a differently-written caller could omit — the difference between Chromium's and Firefox's navigation paths is only *how many* callers there are and *how deeply embedded* the call is in code those callers can't route around, not a difference in kind.

**The structural pattern to take from this, generalized:** the strongest real-world approximation of "can't be silently bypassed" found in either codebase is Firefox's channel classifier — a check embedded directly inside the one lifecycle method every instance of a type must pass through to do anything (`AsyncOpen`/`BeginConnect`), rather than a registration list or a nullable delegate slot a caller can simply leave empty. Chromium's own most structural moment, `DownloadItemImpl::IsDownloadReadyForCompletion()`'s hardcoded `if (IsDangerous()) return false;`, works for the same reason: it's an invariant baked into the component-internal state machine that no embedder-level delegate can code around, not a hook an embedder chooses whether to populate. Both of these are still C++ conventions ultimately enforced by "this is the only constructor/only lifecycle method," not by the type system refusing to compile an alternative — but Rust gives BlueIce a strictly stronger version of the same idea that neither reference engine's language could express: a **typestate / required-capability-token pattern**, where the type that represents "a navigation/download/action ready to execute" simply does not exist as a constructible value until a gatekeeper verdict has been produced, so *the compiler*, not code review or a runtime null-check, is what makes bypass impossible.

Concretely: define a token type (e.g. `GatekeeperClearance`) that can only be constructed by the gatekeeper's own IPC client code, returned from a call that submits the action description and gets back either `Clearance(GatekeeperClearance)` or a `Denied` verdict — no other code path in the codebase is able to construct a `GatekeeperClearance` value (private inner fields, no `Default`, no public constructor, defined in a crate only the gatekeeper-client module can construct from). Every function that performs a risky action then takes that token as a required parameter with no default and no way to synthesize one locally: `fn navigate(url: Url, clearance: GatekeeperClearance) -> Result<...>`, `fn begin_download(request: DownloadRequest, clearance: GatekeeperClearance) -> Result<...>`, `fn invoke_extension_capability(call: CapabilityCall, clearance: GatekeeperClearance) -> Result<...>`. This is strictly harder to route around than either reference engine's pattern: Chromium's throttle vector can simply be empty and the loader proceeds anyway (a runtime `if` that silently does nothing), and Firefox's channel classifier, while embedded in the lifecycle method, is still just a function call whose failure path (`nsChannelClassifier::Start()`'s catch-all `OnClassifyComplete(NS_OK, ...)`) fails open rather than refusing to let the channel exist. A typestate token, by contrast, means "call `navigate()` without going through the gatekeeper" is not a bug that ships and gets caught in review or postmortem — it is a compile error, in every current and future call site, including ones not yet written.

Applied to BlueIce's actual components as they exist today (verified against the current early-stage skeleton — `backend/core/engine/src/lib.rs` is currently a stub `render(html, css) -> Frame` pipeline with no navigation entry point yet, `backend/extension/src/main.rs` is a stub process, and `backend/downloads`/`backend/mcp-server` don't exist yet per Phase 10/12's "Not started" status):

- **`core` navigation**: whatever function eventually becomes `core`'s real navigation entry point (the thing that takes a URL and begins loading it) should be designed from the start to require a `GatekeeperClearance` parameter, exactly as plan §1 already frames the requirement ("the components that can *take* a risky action... need to *call through* the gatekeeper as a mandatory step," `phase-7-local-ai/PLAN.md:30`) — since `core` doesn't have a navigation function yet, this is a chance to design it in from day one the way node IDs were (per `research/dom.md`'s finding that retrofitting identity later was expensive for both reference engines), rather than retrofitting a check onto an existing `fn navigate(url: Url)` the way both Chromium and Firefox effectively did.
- **`backend/downloads` (Phase 10)**: given that *both* reference engines' weakest link was specifically the download path (Chromium's nullable `DownloadManagerDelegate`, Firefox's stub-base-class `DownloadSaver::execute()` that each subclass has to remember to finish correctly), this is the component most worth being deliberate about — the planned `Transfer` state machine (`phase-10-download-manager/PLAN.md:19`) should make the `Queued → Active` transition itself require a clearance token, mirroring Chromium's one genuinely structural finding, `DownloadItemImpl::IsDownloadReadyForCompletion()`'s `if (IsDangerous()) return false;`, but applied to the *decision to start*, not just the decision to complete — and unlike both references' fail-open timeout defaults, an expired/unreachable gatekeeper call should return `Denied`, not a default `Clearance`.
- **The `extension` host**: Phase 9's own plan already establishes that extension capability checks are enforced by `core` against the extension's manifest, checked on `core`'s side of the process boundary rather than trusted from the extension process (`phase-9-extension-protocol/PLAN.md:24`: "Capability checks are enforced by `core` against what that extension's manifest declared at install time — checked on `core`'s side of the boundary, not trusted from the extension process itself"). The same reasoning that justifies not trusting the extension process for capability checks applies identically to gatekeeper clearance: the IPC handler on `core`'s side that services an extension's capability-use request should be the thing required to hold a `GatekeeperClearance` before performing the action, not the extension process (which could be compromised or simply not bother asking).
- **The Phase 12 MCP adapter**: Phase 12's own plan already states the adapter should translate MCP `tools/call` requests into calls against BlueIce's existing internal IPC protocol rather than `core` growing a second, parallel API surface (`phase-12-mcp-server/PLAN.md:13`, "it does not implement any browsing/download/transfer logic itself, only the translation"). This is good news for enforcement specifically: if that holds, the MCP adapter has no independent code path into `navigate()`/`begin_download()`/capability calls at all — it can only reach the same `core`/`downloads`/`extension`-host IPC entry points every other caller uses, so if those entry points require a `GatekeeperClearance` at the IPC-handler layer (not just in a Rust function signature client-side, since the MCP adapter is a separate OS process and Rust's compile-time guarantee doesn't cross a process boundary), an external AI agent driving BlueIce via MCP is *structurally* unable to bypass the gatekeeper by construction, the same way a compromised extension can't. The one thing worth being explicit about, since the clearance-token pattern's compile-time guarantee only holds *within* the process that has the type: the IPC message format itself needs to make an unauthorized action-request rejectable at the handler (`core`/`downloads` verify a clearance credential attached to or preceding the request; a request arriving without one is refused, not defaulted to allowed) rather than assuming a well-behaved client always asks first — this is the IPC-boundary equivalent of the in-process token pattern, and it's the piece that has to be designed into the wire protocol Phase 9's IPC format work is still deciding (`phase-9-extension-protocol/PLAN.md:24`), not bolted on after.
