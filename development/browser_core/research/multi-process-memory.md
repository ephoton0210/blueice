# Multi-process memory management — Chromium and Gecko

Findings from reading `reference/chromium/content/browser/` (`RenderProcessHostImpl`, `SiteInstanceImpl`), `reference/chromium/base/memory/` and `reference/chromium/base/memory_coordinator/`, `reference/chromium/chrome/browser/memory/` and `reference/chromium/chrome/browser/performance_manager/`, `reference/chromium/components/site_isolation/` and `reference/chromium/components/memory_pressure/`, plus `reference/gecko/dom/ipc/`, `reference/gecko/xpcom/base/`, and `reference/gecko/browser/components/tabbrowser/` — aimed at the flagged, unresolved gap that BlueIce's process-isolation decisions (plan §1) were each made one at a time for crash-containment reasons, with no pass yet made over the *total* memory footprint of running `core` + `extension`(s) + `ai-gatekeeper` + `ai-assistant` + `downloads` + `mcp-server` + the Phase 8 supervisor simultaneously.

## 1. Chromium's process-count and process-reuse strategy

**Process-count ceiling is RAM-derived, not fixed.** `RenderProcessHost::GetMaxRendererProcessCount()` (`content/browser/renderer_host/render_process_host_impl.cc:1502-1577`) computes a soft cap from installed memory: `AmountOfTotalPhysicalMemory() / 2`, divided by an estimated per-`WebContents` cost (`kEstimatedWebContentsMemoryUsage` = 85 MB on 64-bit, 60 MB on 32-bit), then clamped between `kMinRendererProcessCount` = 3 and a platform ceiling (`GetPlatformMaxRendererProcessCount()`, itself half the OS's raw process-count limit, or a hardcoded fallback of `kMaxRendererProcessCount` = 82 when that limit can't be queried, `render_process_host_impl.cc:1483-1493`). The code comment gives concrete worked values: 512 MB → 3 processes, 4096 MB → 24, 16384 MB → 96 (before platform clamping). Android instead defaults to no cap at all (`std::numeric_limits<size_t>::max()`) unless `features::kRendererProcessLimitOnAndroid` is enabled, in which case it's `memory_mib / 80` on devices with "large process count support" (`render_process_host_impl.cc:1511-1530`). This is the one concrete place Chromium ties process *count* directly to total system memory, rather than to per-process limits.

**Process selection is a fallback chain that trades isolation for the count ceiling.** `RenderProcessHostImpl::GetProcessHostForSiteInstance` (`render_process_host_impl.cc:5378-5510`) tries, in order: a policy-directed reuse per `ProcessReusePolicy` (`content/browser/process_reuse_policy.h`: `kDefault`, `kProcessPerSite`, `kReusePendingOrCommittedSiteSubframe`, `kReusePendingOrCommittedSiteWorker`, `kReusePendingOrCommittedSiteWithMainFrameThreshold`, `kReusePrerenderingProcessForMainFrame`) → an existing process with an unmatched service worker for the site → an empty background host → an embedder-preferred existing process → a pre-warmed "spare" process (`SpareRenderProcessHostManagerImpl::MaybeTakeSpare`) → and only once `IsProcessLimitReached()` is true, it falls back to reusing *any* existing suitable process even without an exact site match (`render_process_host_impl.cc:5483-5491`). That last step is the concrete, coded isolation-vs-count tradeoff: Chromium's default posture is one renderer process per `SiteInstance`, but once the RAM-derived ceiling is hit it explicitly relaxes that guarantee rather than refusing to navigate.

**Site isolation itself is disabled below a RAM floor, but only on Android.** `content/public/browser/site_isolation_policy.h` centralizes the policy (`SiteIsolationPolicy::UseDedicatedProcessesForAllSites()`, `IsSitePerProcessOrStricter()`, etc.); the concrete memory logic lives in `components/site_isolation/site_isolation_policy.cc:54-89`. On Android, if `base::SysInfo::AmountOfTotalPhysicalMemory()` is at or below a threshold (default 1900 MB for `kPartialSiteIsolation`, 3200 MB for `kStrictSiteIsolation`, overridable via the `kSiteIsolationMemoryThresholdsAndroid` field trial's `kStrictSiteIsolationMemoryThresholdParamName`/`kPartialSiteIsolationMemoryThresholdParamName` params), site isolation is disabled outright for that device — the code comment states plainly "Desktop does not enforce a default memory threshold" (line 57). Two more Android-only memory-gated isolation knobs exist in the same header: `ArePreloadedIsolatedOriginsEnabled()` ("apply memory limits to preloaded isolated origins on Android") and `IsProcessIsolationForOriginAgentClusterEnabled()` ("turn off opt-in origin isolation on low-memory Android devices"). Desktop Chrome, in other words, always isolates and manages the resulting process count via the RAM-scaled ceiling above; Android additionally turns isolation off below an absolute RAM floor.

**A pre-warmed "spare" process is Chromium's own count-vs-latency knob.** `content/browser/renderer_host/spare_render_process_host_manager_impl.{h,cc}` keeps one idle, content-less renderer process alive so the next navigation doesn't pay process-launch latency; it is the first thing killed under memory pressure (`kKillSpareRenderOnMemoryPressure` feature, §2 below), confirming Chromium treats "warm but empty" processes as the cheapest thing in the fleet to give up.

## 2. Chromium's memory-pressure response mechanism

**Two broadcast levels, dozens of independent listeners, no central priority order among them.** `base::MemoryPressureLevel` (`base/memory/memory_pressure_level.h`) has exactly two active levels: `MODERATE` ("free buffers that are cheap to re-allocate and not immediately needed") and `CRITICAL` ("free all possible memory... the alternative is to be killed by the system"). `base/memory/memory_pressure_listener.h` defines `MemoryPressureListenerTag`, an enum of ~30 active registrants, each an independent subsystem that frees its own memory on notification with no cross-subsystem ordering: `kSpareRenderProcessHostManagerImpl`, `kPrerenderHostRegistry`, `kBackgroundTabLoadingPolicy`, `kLruRendererCache`, `kBlinkIsolatesPressureListener`, `kSkiaGraphicsPressureListener`, `kDiscardableSharedMemoryManager`, `kSSLClientSessionCache`, `kLevelDb`, `kFontGlobalContext`, `kParkableStringManager`, and more. This is the decentralized, "everyone hears the same signal and reacts on their own" layer — it is not where discard *priority order* comes from.

**Multiple pressure sources are aggregated into one level before dispatch.** `MultiSourceMemoryPressureMonitor` + `MemoryPressureVoteAggregator` (`components/memory_pressure/multi_source_memory_pressure_monitor.h:20-24`) collect votes from several `MemoryPressureVoter`s — the OS-reported signal via a per-platform `SystemMemoryPressureEvaluator`, a disk-pressure vote, and (see below) an enterprise total-RSS vote — and dispatch "the most critical of all votes collected." This aggregation happens once, in the browser process.

**The one explicit whole-fleet memory budget found, and it's enterprise-only.** `EnterpriseMemoryLimitEvaluator` (`chrome/browser/memory/enterprise_memory_limit_evaluator.h:20-24`) "periodically receives updates on Chrome's current total resident set" — summed across the entire Chrome process fleet via `components/performance_manager/public/decorators/process_metrics_decorator.h`'s `ProcessMetricsDecorator`, which "adorns process nodes with performance metrics" on the PerformanceManager process graph — compares that sum against an IT-admin-configured byte ceiling, and casts a `MemoryPressureVoter` vote if it's exceeded. This is a genuine total-memory-across-the-fleet budget, not a per-process limit, but it is opt-in enterprise policy, not default consumer behavior — confirming even Chromium doesn't treat fleet-wide byte budgeting as necessary by default.

**A newer, more general "memory coordinator" primitive exists but is scoped per-process, not per-fleet.** `base::MemoryConsumer` / `MemoryConsumerRegistry` (`base/memory_coordinator/memory_consumer.h`, `memory_consumer_registry.h`; both dated 2025, i.e. actively evolving) let a subsystem register with a percentage-of-limit protocol (`OnUpdateMemoryLimit()` / `OnReleaseMemory()`) so "memory usage" can be coordinated "across all processes" per the class doc comment — but `MemoryConsumerRegistry::Get()` is explicitly documented as "the global registry for **the current process**" (`memory_consumer_registry.h:25-30`). So the actual cross-OS-process reach is indirect: the browser process's own consumers (e.g. `UrgentPageDiscardingPolicy`, which itself implements `base::MemoryConsumer`, `chrome/browser/performance_manager/policies/urgent_page_discarding_policy.h:26-29`) react to the aggregated signal and then act on *other* processes via IPC (discard/kill), rather than there being one shared budget object spanning OS process boundaries.

**Concrete discard/kill priority order, evidenced end to end:** (1) the idle spare renderer process is killed first — `SpareRenderProcessHostManagerImpl::CleanupSpares(SpareRendererDispatchResult::kMemoryPressure)` fires directly off the pressure callback (`spare_render_process_host_manager_impl.cc:998-1005`), gated by `kKillSpareRenderOnMemoryPressure`, with a `kSpareRPHKeepOneAliveOnMemoryPressure` feature to keep exactly one alive instead of zero — zero user-visible cost, since it hosts no content. (2) Prerendered (speculative, not-yet-shown) pages are next, via the `kPrerenderHostRegistry` listener. (3) The background-tab restore queue is throttled via `kBackgroundTabLoadingPolicy`. (4) The LRU cache of recently-used-but-hidden renderer processes (kept warm for fast back/forward) is trimmed via `kLruRendererCache`. (5) Under *sustained* pressure, `UrgentPageDiscardingPolicy` (`chrome/browser/performance_manager/policies/urgent_page_discarding_policy.{h,cc}`) actually discards a loaded, visible-in-tab-strip page, choosing the victim by `LifecycleUnit::SortKey` (`chrome/browser/resource_coordinator/lifecycle_unit.h:34-52`): ordered purely by last-focused-time, with the currently-focused unit pinned to `TimeTicks::Max()` so it is implicitly never chosen first — least-recently-focused background tab goes first, repeating on `sustained_memory_pressure_timer_` while pressure persists. (6) `OOMKillsMonitor` (`chrome/browser/memory/oom_kills_monitor.h`) only counts `/proc/vmstat`'s `oom_kill` field for telemetry after the fact — it is a backstop measurement, not a mitigation, meaning if the above don't relieve pressure in time the OS's own OOM killer is the final, Chrome-uncontrolled arbiter.

**Cross-process signal plumbing exists but is currently narrower than "all platforms."** `RenderProcessHostImpl::OnMemoryPressure` (`render_process_host_impl.cc:2945-2953`) forwards the aggregated level to each renderer child process via a mojo call, `child_process_->OnMemoryPressure(memory_pressure_level)` — but this is gated `#if BUILDFLAG(IS_ANDROID) || BUILDFLAG(IS_CASTOS)` with a `TODO(pmonette): Enable for all platforms` comment, i.e. desktop renderers currently do *not* get the browser-relayed signal this way. Renderer-side, `RenderThreadImpl::OnMemoryPressureFromBrowserReceived` (`content/renderer/render_thread_impl.cc:1773-1782`) forwards into `blink::RequestUserLevelMemoryPressureSignal`, and a `static_assert` block (`render_thread_impl.cc:247-258`) pins `v8::MemoryPressureLevel` to `base::MemoryPressureLevel` 1:1 (`kNone`/`kModerate`/`kCritical`), so V8's own garbage collector reacts to the same three-level signal. In the other direction, `RenderThreadImpl::SetPrivateMemoryFootprint` (`render_thread_impl.cc:1768-1771`) reports each renderer's own measured private-memory-footprint bytes up to its `RendererHost` in the browser process — so the browser process does maintain live per-process memory bookkeeping across the fleet, feeding the PerformanceManager graph and the enterprise evaluator's total-RSS sum.

## 3. Firefox's equivalent (Electrolysis/Fission process model and memory-pressure handling)

**The pool-size ceiling is a fixed pref, not RAM-derived.** `ContentParent::GetMaxProcessCount` (`dom/ipc/ContentParent.cpp:730-749`) reads `dom.ipc.processCount.<type>` (default 1) for most remote-process types, but routes the generic "web" content-process type through `GetMaxWebProcessCount()`, driven by the plain `dom.ipc.processCount` pref. `modules/libpref/init/all.js:1874-1881` sets that to 8 on release desktop builds, 4 under ASAN/TSAN, 1 under fuzzing; `mobile/android/geckoview/.../GeckoRuntimeSettings.java:792` sets the Android/GeckoView default to 2. None of these are computed from installed system RAM anywhere found in this checkout — a direct contrast with Chromium's `GetMaxRendererProcessCount()` formula in §1.

**Fission adds a second, still-small, separate pool rather than isolating everything.** `all.js:1896-1901`: `dom.ipc.processCount.webIsolated` = 4 on desktop, 1 on Android — this is the pool Fission's out-of-process cross-origin iframes draw from, layered on top of (not instead of) the generic 8-slot "web" pool that ordinary top-level navigations use. `toolkit/modules/E10SUtils.sys.mjs:24-35` defines the shared remote-type vocabulary (`WEB_REMOTE_TYPE = "web"`, `FISSION_WEB_REMOTE_TYPE = "webIsolated"`, plus `file`/`extension`/`privilegedabout`/`privilegedmozilla`/`webServiceWorker`, each capped at 1 process via the same `GetMaxProcessCount` mechanism), with a comment noting this vocabulary "must match the similar ones in RemoteTypes.h, ProcInfo.h... and ChromeUtils.cpp" — i.e. it's the canonical cross-language process-type taxonomy. Practical consequence: once more than 4 distinct origins simultaneously need Fission isolation on desktop, they start sharing those same 4 processes rather than each getting a dedicated one — a materially weaker isolation ceiling than Chromium's RAM-scaled cap (up to 82, or the 4096 MB → 24 / 16384 MB → 96 figures from §1) provides before *it* starts falling back to reuse.

**Process selection actively load-balances by tab count, not "new process until a limit is hit."** `ContentParent::MinTabSelect` (`ContentParent.cpp:794-840`) walks the existing pool (up to the type's max) and picks whichever process currently hosts the fewest live tabs/`BrowserId` keep-alives; it only returns null — triggering a brand-new process — once *every* existing pool member already hosts at least one tab and the pool hasn't hit its cap. This is the opposite default posture from Chromium's "new process per site instance, fall back to reuse only once the ceiling is hit" (§1): Firefox proactively packs unrelated origins into a small fixed pool from the very first tab, and reserves genuine per-origin isolation for the separate, smaller Fission pool layered on top.

**Memory-pressure detection reads real OS pressure data, not just a coarse level.** `nsAvailableMemoryWatcherBase` (`xpcom/base/AvailableMemoryWatcher.h:51-97`) is a platform-independent base class subclassed per OS (`AvailableMemoryWatcherWin.cpp`, `...Mac.cpp`, `...Linux.cpp`); the Linux implementation parses real-time PSI (Pressure Stall Information) straight from `/proc/pressure/memory` into a `PSIInfo` struct (`some_avg10/60/300`, `full_avg10/60/300`, `AvailableMemoryWatcher.h:19-33`) rather than reacting to one coarse OS-broadcast enum the way Chromium's `base::MemoryPressureLevel` does.

**The actual discard algorithm is a genuinely more elaborate, multi-factor ranking than Chromium's pure last-focused-time sort.** The watcher calls into `nsITabUnloader::unloadTabAsync()`, implemented by `browser/components/tabbrowser/TabUnloader.sys.mjs`. Hard exclusions get weight `NEVER_DISCARD` = 100000 and are never chosen: the currently selected tab, tabs in Picture-in-Picture, tabs playing audio, tabs using WebRTC, and private-browsing tabs (`criteriaTypes`, lines 32-40). Pinned tabs get a smaller `+2` deprioritizing weight rather than a hard exclusion. Tabs accessed within `browser.tabs.min_inactive_duration_before_unload` ms are skipped outright regardless of weight (line 28, `kMinInactiveDurationInMs`). The base sort is by weight ascending, then by `lastAccessed` ascending (`getSortedTabs`, lines 269-275) — the same recency heuristic as Chromium's `LifecycleUnit::SortKey`. But once ≥10 tabs are open (`MIN_TABS_COUNT`), Firefox layers two more reweighting passes the low-weight tabs (`adjustForResourceUse`, lines 455-516): tabs whose content lives in a process used by *no other tab* (`uniqueCount`) are favored for discard first, because discarding them is what actually frees a whole process's worth of memory (an explicit acknowledgment that in Firefox's packed-process model, most single-tab discards *don't* free a process at all); then tabs are further favored by an estimated per-tab memory share, computed by dividing each process's total RSS (`ChromeUtils.requestProcInfo()`) across its hosted top-level-tab/subframe count, weighting subframes at half a top-level tab's share (lines 470-481). Exactly one tab is discarded per unload attempt (`unloadLeastRecentlyUsedTab` returns after the first successful discard, line 336-342); the watcher re-invokes the whole ranking again if pressure persists — a reactive, incremental, single-victim-at-a-time loop, not a bulk eviction pass.

**No fleet-wide byte budget exists in Gecko.** Nothing under `xpcom/base/` or `browser/components/tabbrowser/` computes or enforces an absolute total-memory target for the browser; the watcher only reacts to the OS's/PSI's *relative* distress signal after the fact, discarding one tab at a time, with no equivalent of Chromium's `EnterpriseMemoryLimitEvaluator` total-RSS-vs-admin-ceiling check found anywhere in this checkout.

**Why Firefox runs fewer content processes, and the memory tradeoff it reflects.** The evidence across `dom.ipc.processCount` (a flat constant: 8 desktop / 2 Android, never RAM-scaled) and `MinTabSelect` (proactive load-balancing into that fixed pool from the first tab, not "new process by default") shows Firefox bounding process *count* first and letting isolation degrade gracefully as a consequence — unrelated origins routinely share one of 8 processes, with Fission clawing back isolation only for the cross-origin-iframe cases that specifically need it, and even then only into a separate 4-slot pool. Chromium inverts this: it bounds isolation *quality* first (one renderer process per `SiteInstance` by default) and lets process count grow as a consequence, reining that growth in via the RAM-scaled `GetMaxRendererProcessCount()` ceiling (§1) and reactive urgent-discarding (§2) rather than a small fixed pool, stepping back from full isolation only on Android and only below an explicit 1.9-3.2 GB RAM floor. Each renderer process carries fixed baseline overhead regardless of how little content it hosts — a JS engine heap and JIT code cache, IPC/mojo plumbing, base runtime pages — so Firefox's small fixed pool caps that per-process multiplier directly, while Chromium accepts a larger multiplier in exchange for stronger default cross-site memory-safety isolation and manages the resulting footprint after the fact.

## 4. Assessment: recommendations for BlueIce's multi-process fleet

**The site-isolation-vs-process-count tradeoff that dominates §1-3 doesn't map onto BlueIce's fleet the way it might first appear to.** `core` is a single process by design (plan §1: "It runs as a single process, kept deliberately low-memory and stable... the one thing in the whole system that must not crash") — BlueIce has no per-site or per-tab renderer pool to size at all, so Chromium's `GetMaxRendererProcessCount()` formula and Firefox's `dom.ipc.processCount` pref have no direct BlueIce analogue. What *does* transfer cleanly is the other half of both engines' machinery: how a small number of long-lived, mostly-singleton support processes get discarded/frozen/torn down under pressure, ranked by "how cheap is this to lose right now" rather than by a per-site pooling policy. That's the lens the rest of this section applies to BlueIce's seven named roles.

**`core` — always-resident, no change.** Structurally closest to Chromium's browser process (never itself discarded) merged with the one renderer instance BlueIce doesn't multiply per-site. Nothing found in either reference engine suggests treating the always-must-be-up process as an idle-teardown candidate; both engines' entire pressure-response machinery exists specifically to protect this tier by sacrificing everything else first.

**`extension` instances — the actual analogue of Chromium's renderer pool / Firefox's Fission pool, and currently under-specified for it.** Each extension instance is its own OS process (plan §1); `phase-9-extension-protocol/PLAN.md` currently has no idle-teardown or resource-governance open question at all. Recommend applying Firefox's bounded-pool philosophy over Chromium's uncapped-by-default one — cap concurrently-resident extension processes at a small fixed number and idle-teardown (not process-sharing: the plan's isolation guarantee — "an extension process crashing, hanging, or corrupting its own memory must be physically incapable of reaching core's address space" — must not be weakened to save memory) any extension process with no pending capability call for N minutes, respawning on the next `core`-to-extension IPC call. This is the direct BlueIce equivalent of Chromium killing its spare renderer first under pressure: an idle process holding no in-flight work is the cheapest thing in the fleet to give up.

**`mcp-server` (Phase 12) — the clearest on-demand-spawn candidate found, and it costs nothing to adopt.** Its own design sketch already states it "does not implement any browsing/download/transfer logic itself, only the translation" (`phase-12-mcp-server/PLAN.md:13`) — a stateless adapter has nothing to lose from not running while unused. Recommend: don't spawn at browser startup; spawn on the first inbound MCP connection attempt at a stable rendezvous point (the same "clients connect through a stable point, not to a specific instance" shape Phase 8 already designs for `core` hot-swap, `phase-8-live-core-hotswap/PLAN.md:18`), and tear down after some idle timeout with zero connected clients. This directly answers the task's own question — no, `mcp-server` does not need to run when no MCP client is connected — with no session-state cost, unlike every other process considered here.

**`downloads` (Phase 10) — idle-teardown is safe, but scoped to "no active or queued transfers," not "no history to show."** The phase's own design sketch already calls for a sidecar metadata file per in-progress download (URL, size, per-chunk completed ranges, `ETag`/`Last-Modified`, `PLAN.md:17`) specifically so a transfer can resume — which means in-flight state is already meant to be checkpointed to disk rather than living only in process memory. Recommend the process be torn down when idle (no active or queued transfers, no client requesting status) and respawned on the next `downloads`-directed IPC call — a new download request, a resume request, or `frontend` opening the downloads panel — with already-completed transfer history served from a small on-disk index `frontend`/`core` can read without the process running at all. Not eligible for teardown while any transfer is actively in-flight, obviously; "idle" here is a narrower bar than for `mcp-server`.

**`ai-gatekeeper` (Phase 7) — always-resident; explicitly not a teardown candidate, and this matters more than it looks.** Phase 7's own plan states the gatekeeper "must be a real enforcement point, not an advisor that can be silently skipped" and requires mandatory call-through before every risky action *and every incoming page* (`phase-7-local-ai/PLAN.md:30`, fail-closed per the resolved checklist item). The plan already flags an open question that on-demand spawning would make strictly worse: "if the gatekeeper process itself is down/unresponsive... does that count as flagged for fail-closed purposes too?" (`PLAN.md:79`). An idle-torn-down gatekeeper would turn cold-start latency into either a navigation-blocking stall on every first page after idle, or a fail-closed treatment of "still starting up" — worse than simply keeping it resident, since (unlike `mcp-server`/`downloads`) there is no meaningful "idle" state for a process that must review *every* page. Recommend the same always-resident tier as `core`, and note this explicitly as the one place where Chromium/Gecko's "discard the cheapest-to-lose thing first" pattern should *not* be imported, because BlueIce's gatekeeper has a correctness/security obligation neither engine's discarded caches or tabs carry.

**`ai-assistant` (Phase 7) — a real candidate, and the phase's own plan already gestures at it without committing.** `PLAN.md:58` already floats the assistant as "a good candidate for a larger local model, or even a fallback that only activates when no external AI agent is connected." Recommend formalizing that into idle-teardown after N minutes with no summarization/translation/organize request pending, respawned on next request — directly analogous to both engines cold-starting a torn-down spare/background process on next use; the cost is model-load latency, not correctness risk, since (unlike the gatekeeper) a slow-to-respond assistant only makes one interactive action feel laggy rather than leaving a page unreviewed. One concrete caveat grounded in Phase 7's own design: live translation substitutes translated text into the DOM before layout runs for as long as it's enabled on a tab (`PLAN.md:25`), so the assistant is not idle in any tab with live translation currently on — idle-teardown eligibility should be "no pending request AND no tab has live translation enabled," not request-idle alone.

**Phase 8 supervisor — always-resident by necessity, and its designed minimalism is already the right instinct.** It's the one process everything else connects *through* rather than to directly (`PLAN.md:18,28`), so tearing it down would break the indirection it exists to provide; the plan already designs it to be "simpler than core itself on purpose, so it's the least likely thing in the whole system to itself need updating" (`PLAN.md:17`) — a minimal, rarely-changing process is inherently cheap to keep resident, which is worth naming explicitly as a memory-conscious property the existing design already has, not a new requirement.

**Is there a case for an explicit total-memory budget/coordinator role, versus each process managing its own memory independently?** A narrow yes, but not a copy of either reference engine's heaviest machinery. Chromium's actual whole-fleet-RSS coordinator (`EnterpriseMemoryLimitEvaluator`) is enterprise-policy-gated in production Chrome, not a default consumer behavior — even Chromium doesn't treat live byte-for-byte fleet budgeting as necessary by default; most of its real memory response is the decentralized `MemoryPressureListenerTag` broadcast (§2) plus one browser-side urgent-discard policy. Firefox has no fleet-wide budget at all — purely reactive, one-tab-at-a-time discarding after the OS/PSI already signals distress. Given BlueIce's fleet is a handful of named, mostly-singleton roles rather than Chromium's potentially-dozens of same-type renderer instances, a full percentage-of-limit `MemoryConsumer`-style protocol (`base/memory_coordinator/`, §2) is more machinery than the process count justifies. The concrete, narrowly-scoped recommendation: let the Phase 8 supervisor — already being built for hot-swap, already the rendezvous point other processes connect through — also own (a) a registry of which of the on-demand-eligible processes (`extension` instances, `mcp-server`, `downloads`, `ai-assistant`) are currently resident and idle, and (b) a single OS-level memory-pressure listener (the direct analogue of Chromium's `AvailableMemoryMonitor`/`base::MemoryPressureListener` or Gecko's `nsAvailableMemoryWatcherBase` — polling available system memory, or subscribing to the OS's native signal where one exists, e.g. Linux cgroup PSI, which Gecko already reads directly from `/proc/pressure/memory`) that, on pressure, tears down whichever of those idle-eligible processes are currently resident before anything more drastic happens. "On-demand-eligible and currently idle" is BlueIce's equivalent of Chromium's "spare process" — a simpler, sufficient signal than a generic priority score, precisely because the fleet is small and named rather than large and homogeneous. This is deliberately advisory idle-teardown authority, not the budget-allocation/percentage-haggling machinery `MemoryConsumer` implies — BlueIce doesn't have Chromium's problem of hundreds of same-type consumers needing proportional shares. It is, concretely, the fix for the gap the plan already flags on its own: Phase 7's plan already has an open checklist item to "define the resource budget (memory/CPU ceiling) for each process" (`PLAN.md:102`, via per-process cgroups/Job Objects, `PLAN.md:74`) — that is a per-process ceiling, exactly the kind of thing the task description calls out as insufficient on its own; the supervisor's idle-teardown role is the minimal fleet-level complement to it, answering "how many of these ceilings are actually in use right now" rather than only "what is each one capped at."

## 5. User-selectable memory modes (added 2026-09-11)

### Product contract

BlueIce has three resource modes:

| Mode | Default | Memory policy |
| --- | --- | --- |
| **Performance** | Yes | No user-configured BlueIce or per-tab maximum. The existing host-pressure observer, cache trimming, and idle-sidecar teardown remain protective, best-effort measures. |
| **Recommended minimum-memory** | No; user must enable it | Each tab uses a low-retention soft target, but an inactive tab remains resident until its timeout. A timed-out tab is hibernated and releases its memory directly. There is neither a fleet hard cap nor a per-tab hard cap. |
| **Extreme memory** | No; user must enable it | A required BlueIce fleet limit and a required per-tab limit govern allocation admission, reclaim, and process containment. The active tab receives priority; timed-out tabs are reclaimed directly, while non-timed-out inactive tabs are reclaimed only when the hard budget needs room. |

Recommended minimum-memory mode enables the same per-tab accounting but gives each tab a soft target, not a maximum. The target is derived from the device/profile and active-tab count, shown to the user as an advisory value, and may be overridden only as an advisory preference. It selects low-retention behaviour at allocation time — no nonessential capture, streamed network bodies, small caches, and ordinary safe-point GC — but crossing it never by itself causes a memory-allocation failure, forced close, lifecycle reclaim, or OS group limit. In particular, a non-timed-out inactive tab keeps its live state; only a timed-out tab is hibernated to reclaim its memory. A foreground tab’s needed live DOM, script state, and committed page remain allowed to grow past the target; this mode is a best-effort minimization policy, not an inaccurate promise of a limit.

Extreme-mode settings require both positive byte values and reject `tab_limit_bytes > fleet_limit_bytes`. The stored profile also contains `recommended_minimum_timeout` and `extreme_timeout`, and validation rejects profiles where the former is not longer than the latter. The UI, CLI, and management API must identify the hard values as the BlueIce **fleet** maximum and the **per-tab** maximum, show the selected mode persistently, and display current, peak, reclaimable use, soft-target status, timeout state, and enforcement level. A planned launcher surface is `--memory-mode performance` (the default), `--memory-mode minimum`, or `--memory-mode extreme --memory-limit <bytes> --tab-memory-limit <bytes>`, with profile timeout settings; final flag spelling may follow the launcher's established configuration format.

Enabling extreme mode is a controlled transition, not an instant clamp. BlueIce first reports current use, reclaims safe caches, and refuses the transition if the requested limit cannot safely contain the running fleet. The first implementation may restart/reload the controlled launcher session so every child starts inside its resource group. A future live transition is allowed only after all existing children can be enrolled and accounting proves the requested budget is safe.

### Fleet boundary and OS enforcement

The fleet includes every first-party process the launcher creates: launcher, `core`, frontend, BlueJS, gatekeeper, assistant, extensions, downloads, MCP/automation/DevTools services, and API/SOAP workbench helpers. In extreme mode, a strict-mode child that cannot join the fleet accounting/enforcement group fails startup; it is never an untracked escape hatch. Independently launched external clients are outside the strict fleet cap and must be labelled as such.

Linux is the first strict implementation: the launcher creates one cgroup-v2 parent for the session, enrols all descendants, sets `memory.max` to the fleet limit, and sets `memory.high` below it as a preemptive reclaim/throttling boundary. `memory.current` and `memory.events` drive observability and early intervention. Linux documents `memory.max` as a hard limit which can cause cgroup OOM when reclaim cannot make room, while `memory.high` is a throttling/reclaim boundary rather than an OOM trigger; even a hard limit can have temporary overshoot. BlueIce must reclaim and reject work before the kernel becomes the decision maker. [Linux cgroup v2 memory controller](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

Windows uses a Job Object containing the complete managed process tree and `JOB_OBJECT_LIMIT_JOB_MEMORY`; its job-memory limit is the sum of committed memory for all processes in the job, and allocations that would exceed it fail. The UI must identify this committed-memory metric rather than presenting it as identical to Linux resident memory. [Microsoft Job Object limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)

On macOS, and on hosts where BlueIce cannot create the required OS resource group, extreme mode is an explicitly labelled **managed/accounted mode**, not a claimed hard fleet cap: BlueIce enforces its own allocation admission and reclamation but the operating system may still allow unaccounted allocations or terminate the process. The configuration screen must show the enforcement level before enablement. A strict-hard selection is unavailable on those platforms until equivalent, verified group enforcement exists.

### Per-tab accounting

Tabs share `core` and may share a BlueJS host, so a cgroup alone cannot enforce a per-tab maximum. Each `TabId` owns a `TabMemoryAccount { owned, reserved, soft_target, hard_limit }`; `hard_limit` is absent outside extreme mode. Shared processes use a `SharedFleetAccount` for resources that cannot truthfully be assigned to one tab. No subsystem may silently put tab work into the shared account to evade the tab policy.

Before committing memory, a tab reserves its attributed cost for DOM/CSS data, layout/paint/raster intermediates, frame/image buffers, network response bodies/buffers, BlueJS heap and compiled code, and automation/DevTools captures associated with that tab. The reservation is released or converted to owned use on completion. Global fonts, connection pools, runtime maps, protocol queues, and common caches are charged to `SharedFleetAccount`. The API/SOAP workspace has its own account beneath the fleet limit, rather than being charged to an arbitrary tab. BlueJS must carry the requesting `TabId` through allocation APIs; a process-global allocator total is insufficient for this policy.

In recommended minimum-memory mode, the same reservations make each tab's use visible and retain a low-footprint policy, but a `soft_target` crossing does not reclaim an inactive tab's live state before its timeout. In extreme mode, every allocation gate checks both the requesting tab's available hard budget and the remaining fleet budget; it prioritizes the active tab, then can reclaim non-timed-out inactive tabs only when a reservation needs room. The protocol needs `MemoryBudget`, `MemoryReport { current, peak, reclaimable, by_account }`, and `Reclaim { Moderate, Critical }` messages between launcher, core, BlueJS, and optional services. Frontend, MCP, and DevTools may expose aggregate/accounting status, but never response bodies or other sensitive payloads merely to explain a memory decision.

### Deterministic extreme-mode over-budget behaviour

Only when an extreme-mode reservation would cross a hard limit does BlueIce apply the following sequence and record the cause, account, action, and result:

1. Drop rebuildable work first: DevTools/API response previews, screenshots, inspection snapshots, and cache entries.
2. Trim shared and local caches, request aggressive BlueJS garbage collection, and tear down idle optional sidecars.
3. Ask the requesting tab to reclaim local data. If it still cannot reserve the amount, reject that operation atomically: Fetch/XHR reports a resource failure, script gets the defined out-of-memory/resource exception, and navigation keeps the previous committed page rather than partially replacing it.
4. Timed-out tabs have already been hibernated by the timeout policy. If a reservation still needs room, hibernate the least-recently-used eligible non-timed-out inactive tab after a truthful checkpoint/reload contract. The foreground tab is never silently discarded; its new expensive operation is rejected or aborted instead.
5. At an imminent OS hard-limit event, stop admitting expensive work and record the event. Kernel/Job-Object allocation failure is a containment backstop, not normal flow control.

### Verification boundary

Use deterministic fake-account tests for mode selection, reservation release, timeout ordering, and the rule that a background tab cannot evict the foreground tab or essential core services. Minimum-memory tests prove that an inactive non-timed-out tab remains resident and a target crossing does not reject a necessary allocation; its timed-out tab is hibernated. Extreme-mode tests prove the active tab has allocation priority, a timed-out tab is hibernated directly, and a non-timed-out inactive tab is reclaimed only when a hard-budget reservation needs room. Integration tests verify Linux cgroup membership and observed `memory.current`/`memory.high`/`memory.max` configuration when delegation is available, and Windows Job Object membership and limit setup on Windows. They must not induce actual OOM in CI. A strict-mode launch test fails when a required child is untracked; a managed/accounted-platform test verifies the explicit non-hard-cap status.

## 6. Tab-group, idle, and restart lifecycle (added 2026-09-11)

### Groups are policy scopes, not hidden shared allocations

A tab group is metadata and a scheduling/UX scope; it does not replace the per-`TabId` account or become a place to hide memory. `GroupMemoryView` displays the sum of its live tabs' owned/reserved/reclaimable values, with a separate, non-duplicated view of fleet-shared resources. A group may carry `MemoryPriority` and an explicit **Sleep group** action, so a user can park all eligible background tabs in it. Collapsing a group alone does not claim to have freed memory; it changes visibility and may lower its eviction priority, but a live tab remains charged until it is hibernated.

The first design deliberately has no independently configurable group hard cap: it would make a group another competing allocation authority without changing the fact that the page, BlueJS heap, and frame buffers belong to individual tabs. Extreme mode enforces the tab hard limit and the fleet hard limit; group priority is a tie-breaker only when a needed reservation may reclaim an eligible inactive tab. A later group soft target can be added as a fairness signal only if it is reported as the sum of member targets and never bypasses their accounts.

### Explicit tab residency states

| State | Retained in memory | Permitted transition |
| --- | --- | --- |
| **Live** | `Page`, DOM/CSS/layout/raster data, BlueJS realm, active network/task state, and its tab account. | The selected/working tab; ordinary execution. |
| **Frozen** | The same live state remains charged, except immediately reclaimable caches/artifacts. | Stops timers/new tasks at a safe point; reduces CPU, but is not represented as a major memory release. |
| **Hibernated** | No `Page`, BlueJS realm, frame buffers, in-flight request bodies, or tab-owned caches. Only a bounded restore descriptor remains. | Reopening creates a fresh live tab by reload; this is not transparent JS heap serialization. |
| **Dormant** | The same bounded restore descriptor, loaded from the session catalog after a restart; no runtime tab allocation. | Explicit user or automation activation creates a live tab and may navigate/reload. |

### Mode-driven expiry and reclaim order

For memory policy, **active** is the set of tabs currently presented in a frontend or doing controller-authorized work; it is deliberately a set, not a new global `TabManager` active-tab pointer, so human and AI observers may each have an active tab. **Inactive** means live but not active, with `now - last_active_at < timeout`. **Timed out** means that interval has elapsed. The stored profiles must enforce `recommended_minimum_timeout > extreme_timeout`; the documentation does not prescribe fixed durations.

| Mode | Active tab | Non-timed-out inactive tab | Timed-out tab |
| --- | --- | --- | --- |
| **Recommended minimum-memory** | Retain live state; use low-retention allocation choices. | Retain live state; do not lifecycle-reclaim/hibernate it merely for being inactive. | Hibernate directly at the next safe point and release its tab-owned memory. |
| **Extreme memory** | Highest reservation/reclaim priority; never the automatic reclamation target. | Keep it until a hard-budget reservation needs space, then consider it by LRU/group priority after cheaper reclaim. | Hibernate directly at the next safe point and release its tab-owned memory, independently of immediate demand. |

Frozen may still stop timers/new tasks at a safe point, but it remains charged and is never reported as the timeout memory recovery. A tab with a download, controller lease, debugger pause, unsaved form/edit state, active media, or a non-checkpointable task is temporarily ineligible; a timeout is recorded as pending and hibernation occurs at the next documented safe point. If extreme mode cannot make room without violating that protection, it rejects new work instead of corrupting state. An explicit Sleep group action may hibernate eligible members without waiting for their timeout.

### Restart without eager page allocation

The durable session catalog stores a bounded `DormantTab` descriptor — logical session-tab key, group membership, URL or blank state, title/icon metadata, viewport, and a truthful `restore_reason`. It does not serialize arbitrary DOM, JavaScript heap/closures, open network connections, or credentials to pretend a reload is a continuation. Any optional scroll/form restoration needs an explicit privacy and durability contract; the current Phase 16 plan has no navigation-history promise.

On startup, Recommended minimum-memory and Extreme memory modes restore this catalog as Dormant entries only. The tab strip/group list is visible, but BlueIce does not instantiate a `Page`, BlueJS realm, DevTools target, network request, or frame for a tab the user has not reopened. A fresh session in either mode uses a Dormant blank-tab descriptor as well, so opening BlueIce without ever opening a tab does not allocate an engine page merely to satisfy a default-tab convention. In Performance mode, the existing immediate default-tab behavior and a user's separate session-restore preference may choose eager restoration, but both must be disclosed as memory-costing behavior. `ListTabs` exposes the residency state and `ActivateTab`/a normal UI selection is the explicit reload boundary; automation/DevTools inspection of a Dormant tab must either activate it with controller authorization or return `TabNotResident`, never fabricate stale DOM.

`TabId` remains the monotonic runtime ID promised by Phase 16. The session catalog therefore uses a distinct persistent `SessionTabKey`, mapped to a new live `TabId` when a dormant tab is activated after restart; clients receive the mapping event rather than assuming a process-lifetime wire ID survived a new `core` process.

### Verification boundary

Test that collapsing a group alone releases no falsely reported memory, while Sleep group hibernates only eligible members and preserves group membership. Test that Frozen still reports live charges, Hibernated releases all tab-owned page/script/frame/network allocations, and a cold startup with only Dormant entries opens no network connection or BlueJS realm. Verify activation’s old-to-new session key/`TabId` mapping, a required reload, controller authorization, and that an ineligible background tab is preserved while extreme mode rejects the requesting operation instead.
