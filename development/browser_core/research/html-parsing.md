# HTML tokenizer/tree-builder architecture in Gecko and Blink

Findings from reading `../reference/gecko/parser/html/` (Firefox) and `../reference/chromium/third_party/blink/renderer/core/html/parser/` (Chromium/Blink) directly, focused on the questions Phase 2 needs answered before scoping an MVP HTML parser: how much of the HTML5 tree-construction algorithm is well-formed-document parsing vs. malformed-markup error recovery, how foreign content (SVG/MathML) is handled, whether tokenizer and tree builder are cleanly separable stages, and what else lives in "the HTML parser" beyond the spec's core two-stage algorithm.

## 1. Gecko's HTML parser architecture

Gecko's HTML parser lives entirely under `parser/html/`, and it is not hand-written C++: the directory contains a `java/` subdirectory (the translator itself) and a `javasrc/` subdirectory holding `Tokenizer.java`, `TreeBuilder.java`, `AttributeName.java`, `ElementName.java`, `Portability.java`, `StackNode.java`, `StateSnapshot.java`, `UTF16Buffer.java`, with `javasrc/README.txt` stating outright: "The .java files in this directory were placed here by the Java-to-C++ translator that lives in `parser/html/java/translator`... Changing these .java files is not worthwhile, as they will just be overwritten by the next translation." `nsHtml5TreeBuilder.h`/`.cpp` and `nsHtml5Tokenizer.h`/`.cpp` both carry the header comment "THIS IS A GENERATED FILE. PLEASE DO NOT EDIT. Please edit TreeBuilder.java instead and regenerate." This directly confirms the premise in the task brief: Gecko's HTML parser genuinely is the Validator.nu/html5lib-derived Henri Sivonen parser (the `nsHtml5*` prefix, the per-file "Copyright (c) 2007 Henri Sivonen" notices), machine-translated into C++ and still maintained by editing the Java source.

The tokenizer (`nsHtml5Tokenizer.h`, 4595 lines / `nsHtml5Tokenizer.cpp`, 1111 lines) is a single class holding ~78 named `int32_t` state constants (`DATA = 0`, `RCDATA = 1`, ... `COMMENT_LESSTHAN_BANG_DASH_DASH = 79`, `nsHtml5Tokenizer.h:65-234`) that correspond one-for-one to the WHATWG tokenization-state names, driven by one big dispatch method, `stateLoop(int32_t state, char16_t c, int32_t pos, ...)` (`nsHtml5Tokenizer.h:442`). The tokenizer never touches the DOM: it holds a `nsHtml5TreeBuilder* tokenHandler` (`nsHtml5Tokenizer.h`, protected field) and communicates purely through a handful of callback methods — `tokenHandler->startTag(...)`, `->endTag(...)`, `->characters(...)`, `->comment(...)`, `->doctype(...)`, `->eof()` (all called from `nsHtml5Tokenizer.cpp`, e.g. lines 296, 308, 246, 838, 831) — so the tokenizer/tree-builder split is a real interface boundary, not just a file split.

The tree builder (`nsHtml5TreeBuilder.h`, 600 lines / `nsHtml5TreeBuilder.cpp`, 4703 lines) keeps insertion-mode state as `int32_t mode` over another set of named constants: `IN_ROW=0, IN_TABLE_BODY=1, IN_TABLE=2, IN_CAPTION=3, IN_CELL=4, FRAMESET_OK=5, IN_BODY=6, IN_HEAD=7, IN_HEAD_NOSCRIPT=8, IN_COLUMN_GROUP=9, AFTER_BODY=12, IN_FRAMESET=13, AFTER_FRAMESET=14, INITIAL=15, BEFORE_HTML=16, BEFORE_HEAD=17, AFTER_HEAD=18, AFTER_AFTER_BODY=19, AFTER_AFTER_FRAMESET=20, TEXT=21, IN_TEMPLATE=22` (`nsHtml5TreeBuilder.h:210-243`). Note the gap at values 10 and 11: the spec's "in select" and "in select in table" insertion modes have no dedicated constants at all — `grep`-ing the whole tree builder for `IN_SELECT` turns up nothing; `case SELECT:` only appears as one branch of the *element-group* switch inside the `IN_BODY`-family handling (`nsHtml5TreeBuilder.cpp:1096, 1438, 2644`), meaning Gecko folds two of the spec's named insertion modes into `IN_BODY` plus inline current-node checks rather than modeling them as separate states. Tag dispatch itself is not done by string-comparing tag names inline; every `nsHtml5ElementName` carries a small integer "group" (`OTHER=0, A=1, BASE=2, BODY=3, ... TEMPLATE=66, IMG=67`, `nsHtml5TreeBuilder.h:71-207`) and the tree builder switches on `elementName->getGroup()`, so the giant "if the token is a start tag whose name is one of X, Y, Z" prose in the spec compiles down to a jump table over ~68 group codes rather than dozens of string comparisons.

## 2. Blink's HTML parser architecture

Blink's parser lives under `third_party/blink/renderer/core/html/parser/`, split cleanly across files rather than translated from another language: `html_tokenizer.h`/`.cc` (345/1945 lines), `html_tree_builder.h`/`.cc` (378/3287 lines), `html_construction_site.h`/`.cc` (336/1713 lines, the actual DOM-mutation layer the tree builder calls into), `html_element_stack.h`/`.cc` and `html_formatting_element_list.h`/`.cc` (the two spec-mandated auxiliary stacks), `atomic_html_token.h`/`.cc` (the token type), and `html_document_parser.h`/`.cc` (354/1877 lines, the orchestrator/owner). `HTMLTokenizer`'s `State` enum (`html_tokenizer.h:57` onward) has ~76 entries named identically to the spec's state names but in Blink's `k`-prefixed style: `kDataState, kRCDATAState, kScriptDataState, kTagOpenState, ... kCDATASectionEndState`. `HTMLTreeBuilder::InsertionMode` (`html_tree_builder.h:200-219`) has 20 entries — `kInitialMode, kBeforeHTMLMode, kBeforeHeadMode, kInHeadMode, kInHeadNoscriptMode, kAfterHeadMode, kTemplateContentsMode, kInBodyMode, kTextMode, kInTableMode, kInTableTextMode, kInCaptionMode, kInColumnGroupMode, kInTableBodyMode, kInRowMode, kInCellMode, kAfterBodyMode, kInFramesetMode, kAfterFramesetMode, kAfterAfterBodyMode, kAfterAfterFramesetMode` — and, exactly like Gecko, there is no `kInSelectMode`/`kInSelectInTableMode`: `ResetInsertionModeAppropriately()` (`html_tree_builder.cc:2019-2072`) switches over every HTML tag that has a dedicated insertion mode (`kTemplate, kTd/kTh, kTr, kTbody/kThead/kTfoot, kCaption, kColgroup, kTable, kHead, kBody, kFrameset, kHTML`) and simply has no `case HTMLTag::kSelect` — select-content handling lives inside `kInBodyMode` via explicit scope checks in `ProcessStartTagForInBody`/`ProcessEndTagForInBody`. Two independently-implemented, spec-following engines made the identical simplification here, which is a useful signal for what's genuinely load-bearing in the spec's insertion-mode list vs. what a competent implementation naturally elides.

The tokenizer/tree-builder split is structurally explicit at the owner level: `HTMLDocumentParser` holds `HTMLTokenizer tokenizer_;` as a plain value member and `Member<HTMLTreeBuilder> tree_builder_;` as a separate GC-managed object (`html_document_parser.h:306, 309`), and the "extra" subsystems are visibly bolted on beside them as their own optional members rather than folded into either core class: `std::unique_ptr<HTMLPreloadScanner> preload_scanner_`, `insertion_preload_scanner_`, and `HTMLPreloadScanner::BackgroundPtr background_scanner_` (`html_document_parser.h:311-315`). Foreign content is handled by `HTMLTreeBuilder::ShouldProcessTokenInForeignContent` / `ProcessTokenInForeignContent` (`html_tree_builder.cc:3062-3190`), which checks `HTMLElementStack::IsMathMLTextIntegrationPoint`/`IsHTMLIntegrationPoint` and the MathML `annotation-xml`+SVG special case, then routes through four free functions — `AdjustSVGTagNameCase`, `AdjustSVGAttributes`, `AdjustMathMLAttributes`, `AdjustForeignAttributes` (`html_tree_builder.cc:679-758`) — each backed by a `PrefixedNameToQualifiedNameMap` built from `svg_names::GetTags()`/`GetAttrs()`, `mathml_names::GetAttrs()`, `xlink_names::GetAttrs()`, `xml_names::GetAttrs()`. Notably, four camelCase SVG tag names (`altGlyph`, `altGlyphDef`, `altGlyphItem`, `glyphRef`) are manually added to the case-correction map with the comment "These tags aren't implemented by Chromium, so they don't exist in svg_tag_names.json5" (`html_tree_builder.cc:686-689`) — i.e. Blink still has to carry tokenizer-level knowledge of SVG elements it doesn't otherwise support, purely for spec-correct tag-name casing.

## 3. Where the real complexity lives

**Error recovery, not well-formed parsing, is the dominant cost, and both engines show this quantitatively.** Gecko's `nsHtml5TreeBuilderHSupplement.h` declares 48 distinct `err*()` methods (`errStrayStartTag`, `errUnclosedElements`, `errNoSelectInTableScope`, `errStartTagWithSelectOpen`, `errHtmlStartTagInForeignContext`, `errEndTagDidNotMatchCurrentOpenElement`, etc., lines 219-311) out of 116 total member functions defined in `nsHtml5TreeBuilder.cpp` — roughly 40% of the tree builder's named operations exist purely to name and react to one specific malformed-markup condition. Blink shows the same shape from the call-site side: `ParseError(token)` is invoked 85 separate times directly in `html_tree_builder.cc`. A parser that only had to accept well-formed markup (every element explicitly closed, no implied tag closing, no misplaced table/formatting content) would need almost none of this — the *tokenizer* state machine (turning bytes into start/end/text/comment/doctype tokens) is close to unavoidable complexity, but the *tree builder's* size is overwhelmingly the "what if the document is wrong" logic layered on top of a comparatively small well-formed-case core.

**The single most complex named algorithm in both trees is the adoption agency algorithm**, which exists solely to fix up misnested formatting elements like `<b><i>text</b>more</i>` — a real-world pattern nobody intentionally writes but that decades of hand-written HTML made unavoidable to handle. Gecko's `adoptionAgencyEndTag` (`nsHtml5TreeBuilder.cpp:3569-~3730`, ~160 lines, manipulating `listOfActiveFormattingElements` and a `bookmark` index) and Blink's `HTMLTreeBuilder::CallTheAdoptionAgency` (`html_tree_builder.cc:1755-2011`, ~255 lines) are both by far the largest single routines in their respective files. **Foster parenting** — redirecting misplaced content that appears directly inside `<table>` (before any `<tr>`/`<td>`) to just *before* the table in the tree — is the second major error-recovery subsystem, and it's pervasive rather than localized: Gecko has a `MayFoster`-suffixed variant of nearly every element/text insertion primitive (`appendToCurrentNodeAndPushElementMayFoster`, `appendVoidElementToCurrentMayFoster`, `insertFosterParentedChild`, `insertFosterParentedCharacters`, `nsHtml5TreeBuilder.h:446-525`), while Blink centralizes the same behavior behind `HTMLConstructionSite::ShouldFosterParent`/`FosterParent`/`AttachOrFosterParent` and a `RedirectToFosterParentGuard` RAII flag (`html_construction_site.h:144-228`) — same spec requirement, genuinely different implementation shapes, which means BlueIce is free to pick either without a "correct" precedent forcing one design.

**Foreign content (SVG/MathML) is a real, separable, moderately-sized subsystem, not something diffused through the whole tree builder.** In both engines it is gated behind one boolean check per token (`isInForeign()`/`ShouldProcessTokenInForeignContent()`) and, once true, routes to dedicated code (Gecko: the top of `startTag()`, `nsHtml5TreeBuilder.cpp:670-735`; Blink: `ProcessTokenInForeignContent`, `html_tree_builder.cc:3092-3190`) that does three things: (1) apply the "HTML breakout" list — a fixed set of ~20 element groups (bold/italic/font-with-color-etc./`div`/`p`/`br`/`table`/headings/...) that force a pop back out of foreign content even mid-SVG/MathML, (2) rewrite attribute names/namespaces for `xlink:*`, `xml:*`, `xmlns`, and MathML, and (3) restore camelCase for the handful of SVG tag/attribute names HTML's ASCII-lowercasing tokenizer would otherwise mangle (`feGaussianBlur`-style names). This is a bounded, well-isolated piece of the spec — exactly the kind of thing that can be cut wholesale for an MVP that doesn't need inline SVG/MathML, without touching the rest of the tree-construction logic, *provided* the cut is "don't implement the foreign-content insertion modes at all" (treat `<svg>`/`<math>` as unknown elements or skip them) rather than "implement them but skip error recovery inside them" — the breakout-list and namespace-adjustment behavior are what make partial support actually spec-correct, and a half-implementation would silently produce wrong trees on any page with an inline SVG icon.

**Beyond the tokenizer/tree-builder pair, both engines carry substantial additional machinery that is not part of the HTML5 tree-construction algorithm itself:** (a) *speculative/off-main-thread parsing* — Gecko's `nsHtml5StreamParser`/`nsHtml5Speculation`/`nsHtml5SpeculativeLoad` plus the `nsIContentHandle` double-indirection scheme documented at `nsHtml5TreeBuilderHSupplement.h:84-106` ("the off-the-main-thread code has an `nsIContent**` for each DOM node... a tree op is enqueued for later allocating an actual `nsIContent` object"), and Blink's `HTMLPreloadScanner`/`BackgroundHTMLScanner` (`html_preload_scanner.h/.cc`, `background_html_scanner.h/.cc`) plus `HtmlDocumentParserFastpath` — exist purely for performance/threading and have no bearing on parse *correctness*; (b) *`document.write` reentrancy* — Gecko's `nsHtml5Parser::mInDocumentWrite` flag with `mozilla::AutoRestore` guarding and comments about "multi-level document.write" (`nsHtml5Parser.cpp:228-425`), Blink's `HTMLParserReentryPermit` (`html_parser_reentry_permit.h`, referenced via `ReentryPermit()`/`ParserPauseFlag()` in `html_document_parser.h/.cc`) — a real subsystem, but one that only matters once the parser can be re-entered synchronously from script, which itself only matters once a scripting engine exists; (c) *encoding detection* — Gecko's `intl/EncodingDetector.h`, `intl/Encoding.h`, `dom/encoding/`, and the standalone `extensions/universalchardet/` charset sniffer, versus Blink's small dedicated `HTMLMetaCharsetParser` (`html_meta_charset_parser.h/.cc`, 81+149 lines) that pre-scans raw bytes for a `<meta charset>` tag before real decoding starts — encoding detection is consistently kept as its own small pre-pass in both engines, not entangled with the tokenizer state machine; (d) *named character references* — Blink's `html_entity_names.csv` has 2231 rows (matching the WHATWG spec's full named-character-reference table), and Gecko's generated `nsHtml5NamedCharacters.cpp`/`nsHtml5NamedCharactersAccel.cpp` implement the same table with an acceleration structure for fast lookup — a large, fully mechanical data table, not algorithmic complexity, but one an MVP has to consciously decide how much of to carry.

**Blink's own `HTMLDocumentParserFastpath` is the single most directly useful artifact in either codebase for scoping an MVP**, because Chromium engineers already did the "what's the smallest subset of HTML5 tree construction that still round-trips correctly" exercise for real, under real constraints, and left it fully commented (`html_document_parser_fastpath.cc:401-436`). It's a from-scratch recursive-descent parser used as a fast path for `element.innerHTML`/fragment parsing, restricted to a fixed tag whitelist (`a, b, body, br, button, div, footer, i, input, li, label, option, ol, p, select, span, strong, ul` — the `TagInfo` structs at lines ~591-745, roughly 19 tags), with explicitly documented restrictions: no auto-closing of tags, misnesting (e.g. nested `<p>`) causes bailout rather than fix-up, no custom elements or `is=` attribute, no duplicate attributes, restricted unquoted attribute syntax, `<table>` deliberately excluded "because of the complex re-parenting rules," `<img>` deliberately excluded because it would trigger an eager network load as a side effect of a fast-path attempt, any `\0` byte causes bailout, and character references are hand-inlined for only `&amp;`, `&lt;`, `&gt;`, `&nbsp;`, plus numeric references — anything else falls through to the full 2231-entry `ConsumeHTMLEntity` (`html_document_parser_fastpath.cc:1268-1300`), and only `;`-terminated references are accepted at all in the fast path (`ScanHTMLCharacterReference`, lines 1208-1227). Crucially, on any unsupported construct this fast path calls `Fail(...)` and the caller (`TryParsingHTMLFragment`) transparently falls back to the real, fully spec-compliant `HTMLTreeBuilder` — so this is a targeted optimization layered *on top of* full compliance, not a shipped subset of HTML support, but the restriction list is exactly the shape of restriction list an MVP-scoped, no-fallback parser would need to choose deliberately rather than accidentally.

## 4. Assessment: recommendations for BlueIce's MVP HTML parsing scope

**Keep the tokenizer/tree-builder split; it's validated by both engines as the right decomposition, and it's the right decomposition for testability independent of what upstream did.** Both Gecko and Blink maintain the boundary as a real interface (Gecko: `tokenHandler->startTag/endTag/characters/comment/doctype/eof`; Blink: `HTMLTokenizer` feeding `AtomicHTMLToken`s that `HTMLTreeBuilder::ProcessToken` consumes) even though the tokenizer's own state transitions are influenced by tree-builder state (both engines let the tree builder call back into the tokenizer to switch it into RAWTEXT/RCDATA/script-data modes for `<script>`/`<style>`/`<textarea>`/`<title>` — Gecko via `nsHtml5Tokenizer::start*` setters called from the tree builder, Blink via `parser_->tokenizer().SetState(HTMLTokenizer::kRAWTEXTState)` in `ProcessGenericRawTextStartTag`, `html_tree_builder.cc:3042-3047`). For BlueIce this means: build the tokenizer as a pure `&str`/byte-stream → token iterator with no DOM awareness, but give the tree builder an explicit, narrow way to push tokenizer-mode changes back (a `set_state()` call, not a shared mutable struct) — this keeps both stages independently unit-testable (feed the tokenizer a string, assert on the token stream; feed the tree builder a canned token sequence, assert on the resulting tree) exactly the way `html_tokenizer_test.cc` and `atomic_html_token_test.cc` are structured in the Blink checkout.

**The MVP tokenizer should implement close to the full spec state machine — this part is genuinely not optional complexity.** Unlike the tree builder, the ~75-80 tokenizer states aren't there to handle malformed markup; they're there to correctly delimit tokens in *well-formed* documents at all (attribute quoting variants, `<script>`/`<style>`/`<textarea>` raw-text modes, comment/DOCTYPE syntax, self-closing-tag syntax, CDATA in foreign content). A real page with `<script>if (a < b) { ... }</script>` or `<textarea>` containing `<` characters will silently corrupt without the RAWTEXT/script-data states, and these appear on essentially all real pages, not just edge cases. The one piece of the tokenizer that's legitimately optional for an initial cut is the CDATA-section states (`CDATA_START`/`CDATA_SECTION`/`CDATA_RSQB*` in Gecko, `kCDATASection*State` in Blink) and character-reference-in-attribute-value handling for the full spec-mandated set of legacy numeric-reference-without-semicolon quirks — CDATA sections are only reachable inside foreign content (which plan §4 can defer entirely per below), and Blink's own fast path already demonstrates that requiring `;`-terminated character references and hand-covering only `&amp;/&lt;/&gt;/&nbsp;/#numeric` explicitly, falling back to a full lookup only when needed, is an acceptable simplification that still parses real pages correctly (this is a genuine architectural precedent, not a guess: it ships in production Chromium today).

**Foreign content (SVG/MathML) is the cleanest, safest cut for an MVP scope, exactly as the task brief anticipated — but it must be an honest cut, not a partial one.** Since real-world "simple" pages that need to render text/forms/links essentially never rely on inline `<svg>`/`<math>` markup, and since the foreign-content algorithm is a bounded ~150-300 line addition gated behind a single `isInForeign()`-style check in both reference engines, BlueIce's MVP tree builder should simply not special-case the `svg`/`math` namespaces at all: treat `<svg>`/`<math>` and their descendants as ordinary (if unstyled/unrendered) HTML-namespace elements using the same insertion rules as any other unrecognized tag, and skip the HTML-breakout list, the attribute-namespace adjustment tables, and the integration-point checks entirely. This is safe specifically *because* it's total — the danger case the note above flags (a half-implementation that "renders wrong" on any page with an inline SVG icon) is avoided by not attempting foreign-content semantics at all rather than attempting them incompletely.

**Adoption agency and foster parenting are the two error-recovery algorithms real pages actually depend on even when the page "looks simple," and they're the ones to keep, not cut.** Misnested inline formatting tags (`<b>`/`<i>`/`<em>`/`<a>` etc. closed out of order) and content typed directly after `<table>` before a `<tr>` are common enough in hand-written and CMS-generated HTML — not exotic malformed-markup edge cases — that a parser lacking them will visibly misrender or drop content on ordinary pages, not just adversarial test cases. Both are self-contained algorithms (Gecko: ~160 and ~pervasive-but-mechanical lines; Blink: ~255 and ~centralized-guard lines) that can be ported close to verbatim from either reference without pulling in the rest of each engine's error-recovery surface. Everything else in the ~48/85-strong error-condition lists (Gecko's `err*()` methods / Blink's `ParseError()` call sites) is a long tail of increasingly rare malformed-markup shapes (stray end tags with no matching start tag, `<select>` inside `<select>`, doctype-related quirks-mode edge cases, frameset-related legacy handling) — implement the general "ignore an unexpected token, don't crash, keep parsing" fallback behavior the spec requires (open-elements-stack scope checks before every close, implied end-tag popping for `<li>`/`<p>`/table cells) and treat the *named*, spec-numbered error conditions as a backlog to fill in against real failing pages rather than something to pre-implement exhaustively.

**Everything outside the tokenizer+tree-builder pair is legitimately Phase-3-or-later, not Phase-2 MVP scope, and should be named as such rather than silently absorbed into "the parser":** speculative/background/off-thread parsing and preload scanning (pure performance, zero correctness impact — BlueIce can synchronously tokenize+build with no loss of spec fidelity); `document.write` reentrancy (only matters once JS execution exists and can call back into the parser mid-stream — irrelevant until Phase 3's scripting story is settled); full charset auto-detection (`universalchardet`-style statistical sniffing) — an MVP can assume UTF-8 or honor an explicit `<meta charset>`/HTTP `Content-Type` and skip statistical detection, since AI-agent-fetched content and most modern real pages declare UTF-8 explicitly; and the full 2231-row named-character-reference table, which can start as the handful Blink's fast path hand-covers (`&amp; &lt; &gt; &quot; &apos; &nbsp;` plus numeric/hex references) with the full table added later as a static data file once real pages are observed needing more of it. None of these change what "correctly parses well-formed real-world HTML" means — they change how fast, how JS-integrated, or how encoding-robust the parser is, which is precisely the line plan §4 draws between MVP and later phases.
