# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

**Phase 3 (Rust core engine skeleton) is done.** Every pipeline crate under `backend/core/` is a real implementation, end to end — HTML in, a paint-command display list out:

- `backend/core/dom` — the DOM tree (node identity, tree structure).
- `backend/core/html` — HTML tokenizer and tree builder (parses into `blueice-dom` trees).
- `backend/core/css` — CSS tokenizer, selector matching, and cascade (DOM + stylesheets -> per-element `ComputedStyle`, including a built-in UA stylesheet).
- `backend/core/layout` — block/inline layout (DOM + `ComputedStyle` -> an immutable `Fragment` tree with real box-model/line-breaking geometry).
- `backend/core/paint` — a `Fragment` tree + `ComputedStyle` -> a flat, ordered paint-command display list (background/border rectangles, text runs) — not pixels yet; actual rasterization is a per-platform Phase 4 `frontend` concern.
- `backend/core/engine` — wires the above into one `render(html, css, viewport_width) -> Frame` entry point, plus (Phase 4) a stateful `Page` type and `session` message loop for interactive use, and (Phase 16) a `TabManager` collection of `Page`s the session loop dispatches through.
- `backend/testing` — shared cross-stage test interface (fixture format + DOM dump serializer); see "Rendering-correctness fixtures" and "UI testing strategy" in `TEST_PLAN.md`.
- `backend/extension` (crate `blueice-extension-host`) — no longer a stub; see the Phase 9 paragraph below for what's actually built.

**Phase 4 (human-visible rendering path) is done** (see `phase-4-human-rendering-path/PLAN.md`). `core` and `frontend` are real, separate OS processes:

- `backend/ipc` — the control-plane protocol (`ClientMessage`/`ServerMessage` over a length-prefixed-JSON Unix domain socket) and the frame-plane (`blueice_ipc::shm`, real `mmap`-backed frame files).
- `backend/net` — HTTP fetching for navigation (`ureq`-based), plus (Phase 10) `blueice_net::download`: the segmented, resumable transfer engine — see the Phase 10 paragraph below.
- `backend/core/font` — the one place fonts are loaded and measured (bundled DejaVu Sans, plus a Noto Sans TC fallback face for CJK glyphs DejaVu lacks — `font_for_char`), shared by `blueice-layout` (real word-width measurement) and `blueice-raster` (glyph rasterization), so the two never disagree about how wide a run of text is.
- `backend/i18n` — `blueice-i18n`'s namespace/key UI-text lookup (Fluent-backed, `en` default + `zh-TW` today), per `phase-14-i18n-localization/PLAN.md`. Every UI-facing string (the credits screen, `frontend`'s window title) goes through this rather than being a hardcoded literal.
- `backend/mcp-server` — `blueice-mcp-server`, the completed Phase 12 standard-stdio MCP adapter. It wraps `blueice-ipc` (`navigate`/`get_page_representation`/`click`/`type_text`/`focus`/`scroll_into_view`/`highlight`/`screenshot`/`open_tab`/`close_tab`/`list_tabs`, Phase 16's `create_tab_group`/`set_tab_group`/`rename_tab_group`/`set_tab_group_color`/`set_tab_group_collapsed`/`close_tab_group`/`list_tab_groups`, Phase 10's seven transfer controls, and Phase 11's FTP/FTPS/SFTP `download_file` paths plus three non-secret local credential-removal tools) via the `rmcp` SDK rather than adding browsing or transfer logic of its own. Every browser tool takes an optional `tab_id` (Phase 16) with no MCP-server-tracked "current tab," matching `core`'s own no-single-active-tab design. Every page- or transfer-derived result is framed as untrusted data before it reaches the driving LLM. The MCP client owns this one-stdio-session process; tool discovery starts neither browser nor downloads, the first browser tool calls `CoreProcess::connect` (launcher rendezvous before private fallback), and the first download tool starts `downloads`. `tests/rmcp_stdio_client.rs` drives the compiled server with rmcp's official stdio client, including a real `about:credits` navigation.
- `backend/downloads` — `blueice-downloads`, the isolated process that owns downloads (Phase 10; see the paragraph below).
- `backend/launcher` — `blueice-launcher`, the supervisor role of `phase-8-live-core-hotswap/PLAN.md` (see that phase's own paragraph below for its now-built cutover/hot-swap mechanism); this bullet covers its earlier rendezvous-broker slice: a broker letting a human's `frontend` and an AI's `mcp-server` (or any other `blueice-ipc` client) share *one* running `core` instance and its `Page`s, instead of each observing a separate one. `core`/`session.rs` gained a `protocol_version` `Hello` handshake and per-request-ID reply correlation (`blueice_ipc::client_handshake`/`*_with_id`) for this, per Phase 1 §3's originally-deferred design; `SpawnedCore::spawn` satisfies core's handshake gate once on the launcher's own internal connection, so external clients' own `Hello`s just get answered rather than re-gating the shared session. The launcher starts `SpawnedGatekeeper` first on a unique private socket, passes it to v1 and every v2 cutover core, and owns its cleanup, making navigation review usable without a separately-run daemon. The launcher fans every external client's messages into that one connection and fans every reply back out to all of them, each client on its own channel and writer thread (a slow/non-draining client only ever delays itself, never the others' delivery). Also owns a second minimal first slice, the fleet memory supervisor: a policy-driven `ProcessRegistry` (`AlwaysResident`/`OnDemand`/`IdleTeardown`) plus a `sysinfo`-backed memory-pressure poll (`blueice_launcher::{supervisor, memory_pressure}`), with `core` and `ai-gatekeeper` registered `AlwaysResident` and `mcp-server` registered as a typed-but-not-yet-wired-up `IdleTeardown` slot — see `phase-8-live-core-hotswap/PLAN.md`'s own "Minimal first slice: fleet memory supervisor" section.
- `backend/core/raster` — `blueice-paint`'s display list -> actual RGBA8 pixels (`fontdue`-based glyph rendering).
- `backend/core/engine/src/bin/blueice-core.rs` — the `core` process binary: a Unix-socket server owning a `TabManager` (Phase 16's collection of `Page`s, one per open tab), driven by `blueice_engine::session`.
- `backend/frontend-reference` — the reference `frontend` binary (`winit` + `softbuffer`), verified manually in a real window (resize, click-driven navigation, no rendering defects) since GUI event loops can't run in headless CI.

**Phase 5 (AI representation output path) is done** (see `phase-5-ai-representation-output/PLAN.md`; the `protocol_version` handshake `phase-1-ai-representation-layer/PLAN.md` also decided was implemented once genuinely independent clients existed to need it — see `backend/launcher`'s entry above). `blueice_engine::ai_snapshot` extracts the Phase 1 accessibility-tree-shaped schema (`blueice_ipc::{AiSnapshot, AiNode, Role, ...}`) from the exact same `Page` state Phase 4's `render()` paints from, reachable over the same `blueice-ipc` control-plane protocol `frontend` already uses (`ClientMessage::GetRepresentation`/`ActOn`/`Highlight`/`Hover`, `ServerMessage::Representation`) rather than a separate channel. Elements are addressed by their stable `blueice_dom::NodeId` (`ActOn` resolves an ID to current bounds internally, never raw coordinates); a `Representation` and the `FrameReady` from the state change immediately before it always share the same `generation` number, the checkable version of "human and AI perceive the same render pass."

**Phase 16 (multi-tab and tab groups) is done** — `Page` remains one navigable context, while `core` owns a `TabManager` collection of them (`backend/core/engine/src/tabs.rs`). `ClientMessage`/`ServerMessage` envelopes carry optional `tab_id` (`None` = default tab), lifecycle commands create/list/close tabs, and every per-tab reply echoes the resolved tab. Each tab owns URL-based back/forward entries by default: `GoBack`/`GoForward` re-run the target URL through the normal gatekeeper/fetch path, so changed web content is current and a failed fetch leaves the history position unchanged. `blueice-core --history-snapshots` explicitly opts into retaining displayable `Page` snapshots instead, allowing an unavailable old URL to be restored locally. A new navigation clears only that tab's forward branch, and `GetHistoryState` reports button availability without introducing a core-global active tab. `frontend-reference` caches frames per tab and renders a graphical strip with frontend-local selection, enabled history controls, group color bars/collapse controls/new-tab/close actions, plus stdin controls for manual operation. Core-owned `TabGroup { id, name, color, collapsed }` state and `TabSummary.group_id` are exposed through create/assign/rename/recolor/collapse/close/list IPC and matching MCP tools; MCP also exposes `go_back`/`go_forward`, so AI and human observers share organization and history state without sharing an active-tab pointer. A resize eagerly relayouts live pages and any retained snapshots for the one physical content viewport.

**Phase 7 (local AI safety gatekeeper) is in progress** (see `phase-7-local-ai/PLAN.md`). `core` reviews every navigation (`Navigate`, a link-`Click`/`ActOn`'s resulting href, `OpenTab{url}`) in two stages — URL, then fetched HTML content — against `backend/ai-gatekeeper` before it takes effect, over a short-lived-per-check `blueice_ipc::gatekeeper` connection. This is genuinely concurrent: a background thread runs both gatekeeper stages plus the fetch, while the session poll loop keeps other tabs and clients responsive. A same-tab later navigation supersedes a stale one; an unreachable gatekeeper blocks fail-closed. In normal launcher use, `SpawnedGatekeeper` is started first on a private socket and that same live checkpoint is passed to v1 and every cutover v2; standalone core remains explicitly configurable with `--gatekeeper-socket`. `Page::apply_fetched` requires a privately-constructed, non-`Clone` `GatekeeperClearance`, so fetched HTML cannot be applied without both reviews. The independent deterministic rule-base now rejects local blocklist hosts, URL/page Unicode obfuscation, hidden prompt-injection-shaped content, executable downloads, and unsafe extension-action metadata; each rejection carries its compiled `RULESET_VERSION`, updated only through reviewed releases. A model-review layer, assistant agent, real-core extension-host integration, and broader wire-level enforcement remain unfinished.

**Phase 9 historical minimal-slice milestone** (superseded by the current status immediately below; retained for its original protocol rationale) (see `phase-9-extension-protocol/PLAN.md`'s "Wiring design (resolved 2026-09-08)"). Design is fully resolved: the capability list, the three-tier manifest/permission model, WASM as the implementation format, a two-layer versioning story (the existing all-or-nothing `PROTOCOL_VERSION`/`Hello` for framing, plus per-capability `[min, max]` version windows for capability content), server-side capability enforcement, and its high-risk Phase 7 review triggers (`network:intercept` and form/network-causing `dom:write`; purely read-only capabilities skip it). `backend/extension`'s former `todo!()` stub is now a real crate (`blueice-extension-host`) implementing that enforcement mechanism end to end: a new internal `blueice_ipc::extension` wire protocol (its own `ExtensionRequest`/`ExtensionReply` enums, a long-lived `Hello`-handshaked connection — a deliberate hybrid of the external client protocol's handshake and `blueice_ipc::gatekeeper`'s framing style, distinct from both), and an in-memory `ExtensionRegistry` that checks every capability-gated request against both a declared, successfully negotiated capability version and what the connected extension was actually granted, replying a structured `CapabilityDenied` on rejection rather than a silent no-op. `HelloAck { unsupported_capabilities }` reports unknown capabilities or an incompatible supported range while preserving compatible capabilities on the same connection. The host reviews a granted high-risk action through `CheckExtensionAction` over the real private gatekeeper protocol, uses bounded structured metadata rather than forwarding extension payloads, and fails closed on rejection or reviewer failure. This is a hardcoded single-extension minimal slice, deliberately scoped like `ai-gatekeeper`'s own first slice: one fixed `extension_id` granted `dom:read` only, so a `DomWrite` attempt is the concrete, real-subprocess-tested proof of server-side denial. Not yet done: the WASM runtime, manifest file parsing, a real non-spoofable (manifest-hash-derived) `extension_id` scheme, real `Page`/interception execution, and wiring any of this into the real `blueice-core` binary (this slice's enforcement runs standalone in `blueice-extension-host`, not multiplexed into `core`'s own session loop yet).

**Phase 9 implementation update.** The preceding historical milestone is no longer a current gap list: manifest-derived package identity, no-WASI WASM execution, authenticated core-host binding, and core-owned Page and declarative interception bridges are implemented and described in the current-status paragraph below. The remaining Phase 7 work is model review, an assistant agent, and broader wire-level enforcement.

**Phase 9 current status.** Core now validates a strict manifest/WASM package, derives the extension identity, enforces per-capability v1–v6 grants and Phase 7 review, serves core-owned representation reads, and supports only gatekeeper-reviewed explicit text-input, enabled-native-checkbox, enabled-native-textarea, selection-only named-radio, and single-select-option writes against live core state. Radio group membership is derived from core's live DOM; selecting a radio atomically clears the other radios with the same name and ordinary form owner, while disabled, unnamed, and externally form-associated controls remain unsupported. A v6 extension can read semantically represented `<select>`/`<option>` IDs and select one enabled option only when its owner is an enabled native single-select; core then atomically clears that select's other options. Multiple selects and disabled options/optgroups are rejected rather than approximated. Text-control payloads have a 4 KiB UTF-8 limit enforced by the WASM ABI, host protocol handler, and core session owner, including in manually connected development mode. `network:intercept` v2 adds one real but intentionally narrow effect: after review, an extension can register a 2 KiB-or-smaller canonical absolute HTTP(S) URL that core blocks before gatekeeper/fetch at the initial request or any later redirect hop. V3 adds `ClearNetworkBlockUrls`, a payload-free operation that can remove only the caller connection's own 64-rule set, with ordinary capability/version enforcement but no new gatekeeper review; disconnect cleanup performs the same removal. An in-flight navigation still uses the immutable live-rule snapshot it captured when it started. Every redirect target is URL-reviewed before core opens its connection, then only the final page goes through content review. There is no callback, ambient network handle, observation, header/body modification, or richer rule algebra. Both core and the standalone host create user-owned `0700` socket directories and bind `0600` extension listeners. With `--extension-host`, core generates a fresh 256-bit credential, starts `blueice-extension-host --connect`, accepts only `HelloAuthenticated` carrying that environment-only credential, and delays public frontend readiness until the child completes its handshake; a peer presenting only a matching manifest-derived ID is denied. The child waits on internal `RuntimeReady`/`RuntimeStart` until the accepted frontend has a live core session, then runs the exact validated package bytes as a fuel- and memory-bounded Wasmtime 49 `blueice_start` reactor with no WASI or ambient OS imports. Thereafter it pulls a core-defined `NavigationCommitted` event only after a gatekeeper-cleared navigation has committed and published a frame; each event gets a fresh bounded instance and only an opaque tab ID, while a 16-item non-blocking queue prevents extension latency from blocking core. It can only call bounded read/text/checkbox/radio/select/textarea/network-rule ABI functions that re-enter the authenticated core protocol. The current remaining work is broader safe DOM mutation semantics, broader declarative network semantics, and a richer lifecycle reliability/scheduling policy. The explicitly manual extension socket mode remains a protocol-development bearer-claim mode, not the authenticated production path.

**Phase 9 storage v1.** An extension declaring `storage` can use bounded get/set/remove operations against an in-memory bucket selected solely by its negotiated manifest-derived identity. Core owns the shared map, so the same extension can reconnect without losing process-lifetime state and another identity cannot name or observe its bucket. Guest code receives no filesystem path, persistence handle, or ambient OS authority; v1 uses ASCII identifier keys up to 256 bytes, UTF-8 values up to 16 KiB, and per-extension limits of 128 entries / 256 KiB. Manifest grant and v1 negotiation gate all operations; no gatekeeper action review is needed because the API cannot create a network action. Unit, Wasm ABI, real extension-host, and compiled-core reconnect tests cover the boundary. Durable storage is intentionally a later versioned design.

**Phase 9 optional-permission boundary.** An explicit `blueice-core --permission-control-stdio` mode now accepts bounded `Inspect`/`Grant`/`Revoke` requests only on the owning parent's private stdio pipe and only with a core-spawned authenticated extension host. It lists validated package identity, optional declarations, origin scopes, and live grants; unknown or runtime-ephemeral capabilities remain ungrantable. Revocation waits for the core's published-effect cleanup barrier; EOF or malformed transport withdraws grants. The extension-host child inherits neither side of this control pipe. A compiled core/host test proves deny/grant/revoke/EOF behavior on one live connection. Normal launcher operation does not enable this mode, and the reference frontend has no separately authenticated human approval action; user-facing optional consent and gesture-bound ephemeral grants remain open (see the Phase 9 plan).

**Phase 9 DOM-write v7.** The v1–v6 summary above is extended by `SetRangeInputValue { tab_id, node_id, value }`: a represented native range is a `Slider`, and its signed integer value is changed only after v7 negotiation and fixed-detail Phase 7 review. The extension never supplies `min`, `max`, `step`, or an attribute name. Core accepts a live enabled `<input type=range>` only when its integer constraints (or native defaults) validate the requested value; decimal constraints and `step=any` fail closed rather than being approximated. Unit, WASM ABI, actual host-subprocess, and compiled-core tests cover v7.

**Phase 8 (live `core` hot-swap)'s minimal-slice cutover mechanism is done** (see `phase-8-live-core-hotswap/PLAN.md`'s "Wiring design (resolved 2026-09-08)"). `blueice-launcher` can now swap the running `core` (v1) for a freshly-spawned one (v2) at runtime, with no already-connected external client ever dropped: a manually-triggered `ControlRequest::Cutover` (a new, launcher-internal control socket/protocol, `backend/launcher/src/control.rs`) captures v1's currently-open tabs (via a synthetic internal client of the broker itself — the same request-ID-based reply filtering `blueice-mcp-server` already established, reused here to pick one reply out of the broker's shared broadcast stream), spawns v2, replays those tabs into it directly (`Navigate`/`OpenTab`), health-checks the replay succeeded, then performs the actual swap — a generation counter distinguishes "v1's connection ended because we deliberately superseded it" from "v1's connection ended because something actually went wrong" (only the latter still ends the whole launcher, exactly as before this phase's work). Reload-based, not true state migration: no JS execution state exists yet, so replaying tab URLs is sufficient. A cutover is now single-flight for its full capture/replay/health-check/swap interval: an atomic RAII gate returns `ControlReply::CutoverBusy` to a competing request without changing v1. Single-attempt, fail-closed to v1 on any error — no retry policy yet. Found and fixed a real, previously-unnoticed bug along the way: the broker's `forward_client_to_core`/`broadcast_core_to_clients` were silently discarding `tab_id`/`request_id` on every relayed message (using the plain, non-`_with_ids` `blueice_ipc` functions and an id-less channel type), meaning multi-tab addressing was actually broken for any client connected through the shared launcher — fixed as a prerequisite for this phase's own request-ID-dependent cutover mechanism, and regression-tested independently. A cutover retries a transient failure up to three times (never touching v1 until one succeeds), and `blueice-launcher --auto-update-secs N` opts in to cutting over automatically when the `blueice-core` binary changes and stays unchanged for one further poll. The health bar is every replay message succeeding, a matching `ListTabs`, and a structural check that each replayed tab renders a node count comparable to v1's (a blank v2 is refused); it does not compare content or layout. See `phase-8-live-core-hotswap/PLAN.md`.

**Phase 10 (download manager)'s first slice is done** (see `phase-10-download-manager/PLAN.md`'s "Wiring design (resolved 2026-09-20)" and its `TODO.md`). Built to match Free Download Manager's core: `blueice_net::download` probes a URL with a one-byte ranged `GET`, fetches it in concurrent segments into a pre-allocated file with **dynamic re-splitting** (a connection that finishes early takes the back half of the slowest segment), retries with backoff, revokes stalled segments with its own watchdog (`ureq` has no idle-read timeout), and resumes from an atomically written sidecar only when a strong validator proves the remote file is unchanged — otherwise it restarts from byte 0 rather than splice two versions. The destination appears only when the transfer completes. A download needs a `DownloadClearance` from a two-stage, fail-closed gatekeeper review (`CheckUrl`, then a new `CheckDownload` after the probe) — a privately constructed, non-`Clone` token the engine itself requires, re-earned on every resume. `backend/downloads` owns the queue and lifecycle, reviews every start itself (never trusting a client, the MCP adapter included, to have asked), confines destinations to a download directory (a requested `dest` is relative, with no `..`, no component sanitizing would change, and no symlink escape), persists `transfers.json` so history and interrupted transfers survive a crash (they come back `Paused`, never auto-started), and serves `blueice_ipc::downloads` over a Unix socket with push subscriptions that keep the latest record per transfer. `blueice-mcp-server`'s thirteen download-related tools open every result with a one-sentence summary and then the full record — per-segment progress, retries, the last error, the gatekeeper's decision, and an event log saying *why* — framed as untrusted data, connecting to (and if need be starting) the downloads process only on first use. A human sees the same records in a built-in `about:downloads` page rendered by BlueIce's own engine, kept live through the session's poll tick (a tab on it is re-read about twice a second off-thread, re-rendered with the scroll position kept, and a fresh frame pushed only when the content changed), reachable from the reference frontend's `downloads` command; `download <url>` starts one. Tested down to a `kill -9` mid-download and to the compiled `blueice-mcp-server` speaking JSON-RPC over stdio. Not built: a scheduler, speed limits, multi-mirror downloads, cookies/authentication, human-facing pause/resume/cancel controls on the page (an agent can do all of it over MCP), navigation-triggered downloads, private-network URL policy (a known gap for the gatekeeper's rule base), and signal handling (a `SIGTERM` is recovered from like a crash).

**Phase 11 (transfer protocol clients) is done.** The shared `TransferBackend` has SFTP, anonymous FTP, and explicit-FTPS implementations. SFTP requires strict `known_hosts` verification and tries SSH-agent authentication, then a key selected with `blueice-downloads --sftp-private-key PATH` (whose passphrase has its own OS-keychain entry), then an OS-keychain password; credentials are opened only after host-key verification. Explicit FTPS uses `suppaftp` 12.0.1 with certificate/hostname validation and OS-keychain passwords. FTP's `REST` does not provide an end offset, so FTP-family downloads are verified single streams that discard partial state rather than unsafe segmented/resumed downloads.


**Phase 13 (BlueJS, the custom JavaScript engine) has a working AST→bytecode→VM engine covering nearly all of ECMA-262's core language and library surface** (see `development/browser_core/phase-13-bluejs-engine/PLAN.md` and `STRING_BUILTINS.md`). `backend/bluejs` exposes `parse`, `compile`, `compile_with_limit` and `Vm::execute`; execution never walks the AST. Stable heap-scoped handles, descriptors/accessors, String/Symbol keys, sparse arrays, boxed primitives, compiled functions/arrows/classes and captured binding cells use nursery/tenured GC with a managed-data budget. The String surface includes all 35 core prototype methods, three statics and 16 Annex B properties, Unicode 17 normalization/casing, five pattern protocols, standalone UTF-16 RegExp matching, callable replacements, iterators, spread/for-of and frozen tagged-template objects. Bound callbacks/constructors, instanceof with Symbol.hasInstance and RegExp.escape execute through the same VM. Classes are a real ClassDefinitionEvaluation implementation (derived-constructor `this`, private names/methods/static blocks, auto-accessors, one instance-field initializer function) rather than a subset, and the Stage 3 TC39 Decorators proposal (grammar, evaluation order, the `context`/`access`/`addInitializer` call protocol and `Symbol.metadata`) is implemented on top of it. Promise (capability records, all/allSettled/any/race/try/withResolvers/allKeyed/allSettledKeyed via the iterator protocol) was rebuilt on spec-shaped `PromiseCapability` records. General tail calls (a frame-replacing `TailCall` opcode, not just self-recursion) and `Function.prototype.toString` returning the exact original source text (a `SourceText` byte-range shared per parse, not a per-function copy) are both implemented, the latter including a lossless reversible encoding so `eval`/`Function`/`ShadowRealm` source containing an unpaired UTF-16 surrogate round-trips correctly through the Rust-`String`-based lexer. A generational-heap-aware `$262.createRealm()` cross-realm model exists (per-realm intrinsics/prototypes, `GetFunctionRealm`/`GetPrototypeFromConstructor`, foreign-object facades that forward `[[Get]]`/`[[Set]]`/other essential internal methods into the owning realm), now including a real "reverse membrane" (`Test262ReverseValue`, `vm/test262/reverse.rs`, reusing `shadow_realm.rs`'s `ACTIVE` reentrancy mechanism via the shared `vm/realm_reentrancy.rs`): a child realm can correctly re-enter a live parent-owned Proxy trap, callback or object. A round-trip-cache gap found while building it — a value crossing parent→child, mutated there, then crossing back out lost that mutation to `test262_import_foreign_value`'s round-trip identity cache, which unconditionally returned the original pristine value instead of the mutated stand-in — is now fixed: the one case that legitimately needs to see such a mutation (writing a freshly cross-realm-`Construct`ed TypedArray's bytes) bypasses the cache entirely via a direct real-object write (`Vm::test262_reverse_write_into_real_construction_result`) instead of fighting it, verified against both a hand-written regression and the real Test262 fixture that exposed it (`development/browser_core/phase-13-bluejs-engine/TEST262_ANALYSIS_REPORT.md` has the full mechanism). Observable object conversions, primitive setters, strict/sloppy String writes/deletes and custom constructor prototypes are covered. Each execute has fresh bindings; returned/thrown objects stay rooted until the next execution.

Runtime dispatch/native loops use fuel, strings and managed heap have byte limits, and call depth is bounded by the native stack actually left on the running thread, not a frame count (`Vm::enter_call` refuses with a catchable `RangeError` once `vm/native_stack.rs`'s `remaining_stack()` reports under a 256 KiB red zone, `vm/completion.rs`; that query is written in Rust alone with no assembly or C build step — the address of a local as the current position, the thread's lower bound asked of the OS once per thread via `libc` on Linux/macOS and `windows-sys` on Windows, and no bound on any other host; one debug-build JS call costs about 15 KB of native stack, so an 8 MiB stack allows roughly 500 nested calls, and the old 32-frame count remains only as the fallback where a host cannot report its stack; the margin is tested against `tests/call_stack_budget.rs`'s runaway-recursion patterns, where a 24 KiB margin aborted the process; the Windows branch is compiled but has never been run (`cargo check --target x86_64-pc-windows-msvc` only) and a 1 MiB main-thread stack is untested, and parser/compiler nesting and native data recursion that never pass through `enter_call` are not covered by this guard). Regex compilation/matching runs in the sibling `bluejs-regexp-worker` with a configurable operation deadline (default 250 ms) and a separate two-second startup bound; bytecode/AST/compiled regex storage and allocator overhead are outside the managed-heap budget. The pinned `regress` crate is a real, if imperfect, dependency limitation, not a stub: it cannot represent a raw lone surrogate in regex source text, and its non-`u`-mode Canonicalize and `u`/`v`-mode backreference matching disagreed with ECMA-262 on BMP/surrogate-pair edge cases. Those two deviations are now corrected in the wrapper layer, without forking or bumping `regress`: `regex_backrefs.rs` wraps each `\N`/`\k<name>` in a surrogate-pair-boundary guard, and `regex_canonicalize.rs` rewrites a non-`u` `/i` pattern to a case-sensitive pattern over ECMA-262 `Canonicalize` units matched against the subject mapped one unit to one unit (so capture ranges stay valid); a `v`-only pattern is also handed `u` so `regress` folds it as Unicode. Still using `regress`'s own folding: patterns with modifier groups (`(?i:...)`), and a few unrelated deviations recorded in `TEST262_ANALYSIS_REPORT.md`. Intl.Collator, Intl.Locale, its Locale-info queries, getCanonicalLocales, locale-sensitive String casing, Math constants/functions, abstract equality and property-presence are implemented; formatter constructors remain open. Test262 harness scripts share a classic-script global object; only `sta.js` and `assert.js` are native overrides now (matching the upstream harness's own observable behavior, differentially tested against it), while `propertyHelper.js` and `isConstructor.js` run their real upstream source, and the one declared range-parts `deepEqual.js` fixture uses a bounded native assertion, documented with its exact checked shape in the Test262 runner README. **Definition of Done** (full policy: `development/browser_core/testing/TEST_PLAN.md`): no design or feature counts as done merely because it's settled or compiles.

- **Develop test-first (TDD)**: write the failing test before the implementation that makes it pass — not tests bolted on after the feature is already written.
- It needs passing tests; where an end-to-end path through the feature's real public interface exists, that path must pass too — not just tests of internal modules.
- The public interface itself must be complete enough for tests to drive without reaching into `pub(crate)`/private internals.
- Real-implementation crates must clear the ≥90% line-coverage gate.
- **Once implementation is otherwise complete, do a dedicated test-review pass**: re-read the suite's actual content (not just pass/fail or the coverage number), fill in cases TDD's incremental cycles didn't surface, update any test whose expectation no longer matches intended behavior, and delete tests that no longer check anything meaningful.

## Core goal

BlueIce is a browser engine, written from scratch in Rust, built around one idea: a human user and an AI agent should perceive the same page state from the **same render pass**, instead of the common dual-track setup where a human uses a real browser and an AI drives a separate headless instance via external automation (e.g. Puppeteer/CDP). That dual-track approach is rejected for architectural reasons, not just performance:

- Anti-bot systems (Cloudflare, Akamai, PerimeterX) fingerprint headless/CDP Chromium and can serve it different content than a human sees.
- A separate driven instance has its own viewport/timing/JS state, so "what the AI saw" is only ever an approximation of "what the human saw."
- Any AI-facing capability (e.g. semantic tags alongside human-facing highlights) has to be a post-hoc hack in an externally-driven architecture; owning the render pipeline makes it a first-class feature instead.

This is not a clean-room implementation — Gecko (Firefox) and Blink/V8 (Chromium) source are read directly as technical reference and porting basis. See `development/browser_core/BROWSER_CORE_PLAN.md` for full detail.

Two concrete requirements follow from the core goal (plan §1) and apply across all phases:

- The AI must be able to show/hide the human-facing window at runtime without restarting the engine — same instance, same render pass, same JS state, regardless of window visibility.
- Every DOM node has an explicit, stable ID assigned at creation (not an array index or ephemeral pointer), so the AI-facing representation can reference elements reliably across mutations.

## Design-first workflow

Plans are drafted under `development/` *before* implementation starts, and updated as the design evolves — treat these as living documents, not historical records. Each major component gets its own subdirectory with a plan doc. Currently the only component is `development/browser_core/BROWSER_CORE_PLAN.md` (the engine itself).

**Settled**: which layer the human and AI representations are shared at (plan §3) — an accessibility-tree-shaped schema (role, state, provenance-tagged name, bounds) extended with `opacity`, `animating`, `occluded`/`occludedBy`/`occludedFraction`, and per-node `hovered`/`focused`, keyed by BlueIce's own stable `NodeId`. Resolved directly from how Gecko/Blink already do this in production (`research/accessibility-tree.md`), not from an independent validation exercise — check plan §3 for the current schema rather than assuming one of the original four candidates in isolation.

**MVP scope** (per plan §4) is deliberately narrow: a minimal HTML parse → DOM → CSS cascade → layout → paint pipeline, plus the shared human/AI representation layer. Explicitly out of scope for now: extension ecosystem, multi-tab state sync, full JS engine optimization, DevTools.

## Licensing (load-bearing, not boilerplate)

Project-wide license is MPL-2.0, chosen specifically because the project reads and adapts Gecko/Chromium source rather than clean-rooming:

- Files derived from Gecko **must** stay MPL-2.0 — this is an inherent MPL file-level copyleft obligation, not a project choice.
- Files derived from Chromium/Blink (BSD-3-Clause) are relicensed to MPL-2.0, but the original BSD copyright/disclaimer notice must be preserved verbatim in that file's own header — the project uses per-file headers only, no centralized `NOTICE`/`THIRD_PARTY_LICENSES` file. See `CONTRIBUTING.md` for the exact header templates (original code, Gecko-derived, Chromium/Blink-derived) before porting any file.
- BSD-3-Clause's binary-distribution clause is separate from the source-header requirement above and isn't satisfied by it: any distributed binary needs the Chromium notice reproduced in "documentation and/or other materials provided with the distribution" — i.e. a Help/About/Credits screen. Tracked as a Phase 4 checklist item (`development/browser_core/phase-4-human-rendering-path/PLAN.md`), since there's no UI to put it in yet.
- Wholly original code (the AI representation layer, project glue) uses MPL-2.0 for consistency only, with no derivative-work obligation.
- The license places no field-of-use/commercial restriction (that would violate the OSI Open Source Definition) — "no commercial activity" is a project stance, not something encoded in the license terms.
- MPL §2.1's patent grant only covers contributors' own contributions to this project, not unrelated third-party patents (codecs, GPU rendering, JIT techniques). This risk doesn't disappear at non-commercial stage.
- Do not use "Firefox", "Mozilla", "Chrome", "Google Chrome", or "Chromium" names/logos as BlueIce branding. Descriptive references ("BlueIce references Gecko's approach to X") are fine as nominative fair use.

## Phase 7 assistant update (2026-09-25)

The assistant is no longer only a plan. `backend/ai-assistant` (`blueice-ai-assistant`) serves translation, summarization, and data organization over the `blueice_ipc::assistant` protocol through an `InferenceBackend` trait: a loopback `llama.cpp`/Ollama/TGI backend built on the shared `backend/loopback-model` crate (also used by the gatekeeper, so the loopback-only rules exist once), an in-process `candle` backend behind a cargo feature (Qwen3 GGUF only; **real inference is unverified because no weights exist on the development machine**), and a racing `Race` backend for opt-in simultaneous mode. Live translation happens in `core` after the gatekeeper has reviewed the original HTML and before layout, retains the original text, and fails open to the original page; the AI snapshot carries `AiNode.original_name`. Summaries and organized data go to a built-in `about:assistant` page (escaped plain text, same render pass as any page). `blueice-launcher --assistant-settings` supervises the assistant on demand (it owns the public socket, relays connections, respawns a dead assistant, and enforces a resident-memory ceiling and a priority from outside); settings live in one validated, versioned file (`backend/assistant-settings`). Client controls exist over IPC, MCP (`set_translation_language`, `show_translation`, `summarize_page`, `organize_page`), and the reference frontend's stdin. Settings are edited only in the launcher-owned trusted window (F9 in the native frontend); an AI agent can only *propose* a change over MCP (`get_assistant_settings`, `propose_assistant_settings`, `assistant_settings_proposal_status`), a deterministic rule-base screens the proposal before the person ever sees it, and it takes effect — at once, restarting the assistant — only when the person approves that exact proposal. Still open: a manual check of the windowed frontend commands and the F9 panel. `phase-7-local-ai/PLAN.md` carries the authoritative checklist.
