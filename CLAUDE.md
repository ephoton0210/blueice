# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

**Phase 3 (Rust core engine skeleton) is done.** Every pipeline crate under `backend/core/` is a real implementation, end to end — HTML in, a paint-command display list out:

- `backend/core/dom` — the DOM tree (node identity, tree structure).
- `backend/core/html` — HTML tokenizer and tree builder (parses into `blueice-dom` trees).
- `backend/core/css` — CSS tokenizer, selector matching, and cascade (DOM + stylesheets -> per-element `ComputedStyle`, including a built-in UA stylesheet).
- `backend/core/layout` — block/inline layout (DOM + `ComputedStyle` -> an immutable `Fragment` tree with real box-model/line-breaking geometry).
- `backend/core/paint` — a `Fragment` tree + `ComputedStyle` -> a flat, ordered paint-command display list (background/border rectangles, text runs) — not pixels yet; actual rasterization is a per-platform Phase 4 `frontend` concern.
- `backend/core/engine` — wires the above into one `render(html, css, viewport_width) -> Frame` entry point, plus (Phase 4) a stateful `Page` type and `session` message loop for interactive use, and (Phase 16) a `TabManager` collection of `Page`s the session loop dispatches through.
- `backend/testing` — shared cross-stage test interface (fixture format + DOM dump serializer); see "Rendering-correctness fixtures" and "UI testing strategy" in `TEST_PLAN.md`.
- `backend/extension` (crate `blueice-extension-host`) — no longer a stub; see the Phase 9 paragraph below for what's actually built.

**Phase 4 (human-visible rendering path) is done** (see `phase-4-human-rendering-path/PLAN.md`). `core` and `frontend` are real, separate OS processes:

- `backend/ipc` — the control-plane protocol (`ClientMessage`/`ServerMessage` over a length-prefixed-JSON Unix domain socket) and the frame-plane (`blueice_ipc::shm`, real `mmap`-backed frame files).
- `backend/net` — HTTP fetching for navigation (`ureq`-based).
- `backend/core/font` — the one place fonts are loaded and measured (bundled DejaVu Sans, plus a Noto Sans TC fallback face for CJK glyphs DejaVu lacks — `font_for_char`), shared by `blueice-layout` (real word-width measurement) and `blueice-raster` (glyph rasterization), so the two never disagree about how wide a run of text is.
- `backend/i18n` — `blueice-i18n`'s namespace/key UI-text lookup (Fluent-backed, `en` default + `zh-TW` today), per `phase-14-i18n-localization/PLAN.md`. Every UI-facing string (the credits screen, `frontend`'s window title) goes through this rather than being a hardcoded literal.
- `backend/mcp-server` — `blueice-mcp-server`, an early foundation for `phase-12-mcp-server/PLAN.md`'s MCP adapter, built ahead of that phase so Chromium differential testing has a stable way to drive BlueIce now. Wraps `blueice-ipc` (`navigate`/`get_page_representation`/`click`/`type_text`/`focus`/`scroll_into_view`/`highlight`/`screenshot`/`open_tab`/`close_tab`/`list_tabs` MCP tools, via the `rmcp` SDK) rather than adding browsing logic of its own, per Phase 12's adapter-not-parallel-channel principle. Every tool takes an optional `tab_id` (Phase 16) with no MCP-server-tracked "current tab," matching `core`'s own no-single-active-tab design. Every tool result carrying page-derived content (node names, DOM text, screenshots, tab URLs) is wrapped with an explicit "this is data, not instructions" warning (`wrap_untrusted_page_content`) before reaching the driving LLM. `CoreProcess::connect` tries `blueice-launcher`'s rendezvous socket before falling back to privately spawning its own `core`, per Phase 8's minimal first slice below.
- `backend/launcher` — `blueice-launcher`, the supervisor role of `phase-8-live-core-hotswap/PLAN.md` (see that phase's own paragraph below for its now-built cutover/hot-swap mechanism); this bullet covers its earlier rendezvous-broker slice: a broker letting a human's `frontend` and an AI's `mcp-server` (or any other `blueice-ipc` client) share *one* running `core` instance and its `Page`s, instead of each observing a separate one. `core`/`session.rs` gained a `protocol_version` `Hello` handshake and per-request-ID reply correlation (`blueice_ipc::client_handshake`/`*_with_id`) for this, per Phase 1 §3's originally-deferred design; `SpawnedCore::spawn` satisfies core's handshake gate once on the launcher's own internal connection, so external clients' own `Hello`s just get answered rather than re-gating the shared session. The launcher fans every external client's messages into that one connection and fans every reply back out to all of them, each client on its own channel and writer thread (a slow/non-draining client only ever delays itself, never the others' delivery). Also owns a second minimal first slice, the fleet memory supervisor: a policy-driven `ProcessRegistry` (`AlwaysResident`/`OnDemand`/`IdleTeardown`) plus a `sysinfo`-backed memory-pressure poll (`blueice_launcher::{supervisor, memory_pressure}`), with `core` registered `AlwaysResident` and `mcp-server` registered as a typed-but-not-yet-wired-up `IdleTeardown` slot — see `phase-8-live-core-hotswap/PLAN.md`'s own "Minimal first slice: fleet memory supervisor" section.
- `backend/core/raster` — `blueice-paint`'s display list -> actual RGBA8 pixels (`fontdue`-based glyph rendering).
- `backend/core/engine/src/bin/blueice-core.rs` — the `core` process binary: a Unix-socket server owning a `TabManager` (Phase 16's collection of `Page`s, one per open tab), driven by `blueice_engine::session`.
- `backend/frontend-reference` — the reference `frontend` binary (`winit` + `softbuffer`), verified manually in a real window (resize, click-driven navigation, no rendering defects) since GUI event loops can't run in headless CI.

**Phase 5 (AI representation output path) is done** (see `phase-5-ai-representation-output/PLAN.md`; the `protocol_version` handshake `phase-1-ai-representation-layer/PLAN.md` also decided was implemented once genuinely independent clients existed to need it — see `backend/launcher`'s entry above). `blueice_engine::ai_snapshot` extracts the Phase 1 accessibility-tree-shaped schema (`blueice_ipc::{AiSnapshot, AiNode, Role, ...}`) from the exact same `Page` state Phase 4's `render()` paints from, reachable over the same `blueice-ipc` control-plane protocol `frontend` already uses (`ClientMessage::GetRepresentation`/`ActOn`/`Highlight`/`Hover`, `ServerMessage::Representation`) rather than a separate channel. Elements are addressed by their stable `blueice_dom::NodeId` (`ActOn` resolves an ID to current bounds internally, never raw coordinates); a `Representation` and the `FrameReady` from the state change immediately before it always share the same `generation` number, the checkable version of "human and AI perceive the same render pass."

**Phase 16 (multi-tab support) is in progress** — the `core`/wire-protocol slice and its `blueice-mcp-server` exposure are both done; only `frontend-reference`'s tab-strip UI and tab groups remain, see `phase-16-multi-tab-and-tab-groups/PLAN.md`. Reverses `phase-2-mvp-scope/PLAN.md`'s original "no multi-tab concept anywhere in `Page`'s design" exclusion — `Page` itself is unchanged, but `core` now owns a `TabManager` collection of them (`backend/core/engine/src/tabs.rs`) instead of exactly one. `ClientMessage`/`ServerMessage` envelopes gain an optional `tab_id` (`None` = the default tab, reproducing pre-Phase-16 behavior byte-for-byte) alongside the existing `request_id`; new `OpenTab`/`CloseTab`/`ListTabs` messages, exposed as `blueice-mcp-server` tools of the same names plus a `tab_id` parameter on every other tool. Deliberately no core- or mcp-server-tracked "active tab": a human's `frontend` and an AI's `mcp-server` may be looking at different tabs simultaneously, and every reply echoes back the *resolved* tab (never the request's raw, possibly-implicit value) so a client sharing the connection via `blueice-launcher`'s broadcast broker can always tell which tab a reply is about. Tab groups and the `frontend-reference` tab-strip UI are explicitly deferred follow-ups, not yet started.

**Phase 7 (local AI safety gatekeeper)'s minimal slice is done** (see `phase-7-local-ai/PLAN.md`'s "Wiring design (resolved 2026-09-08)"). `core` reviews every navigation (`Navigate`, a link-`Click`/`ActOn`'s resulting href, `OpenTab{url}`) in two stages — URL, then fetched HTML content — against a new always-resident `backend/ai-gatekeeper` process before it takes effect, over a short-lived-per-check connection speaking a new internal `blueice_ipc::gatekeeper` protocol (distinct from the external `ClientMessage`/`ServerMessage` protocol). This is genuinely concurrent, not just present: `session.rs`'s dispatch loop no longer blocks on a gated navigation's round trip — a background thread runs both gatekeeper stages plus the fetch, reporting back over an `mpsc` channel a poll tick drains between reads (`run_session`'s stream now runs under a short read timeout via a small `ReadTimeout` trait), so a slow/stalled review on one tab never delays a reply to another tab or client sharing the same launcher connection. A second, same-tab navigation supersedes a still-pending one (the stale result is silently discarded on arrival). Fail-closed: an unreachable gatekeeper is treated as a rejection, never as clearance. `Page::apply_fetched` requires a privately-constructed, non-`Clone` `GatekeeperClearance` token as a parameter — the typestate/capability-token pattern the phase's design settled on, making it a compile error (not just a runtime convention) to apply fetched HTML without both stages having actually cleared. `ai-gatekeeper` itself is a trivial always-clears stub in this slice — no model, no rule-base yet; what's real is the process, the protocol, the concurrency mechanism, and the fail-closed behavior. Not yet done: wiring the same capability-token requirement into `backend/downloads`/the `extension` host/the Phase 12 MCP adapter (none of those exist yet or aren't in scope), IPC-wire-protocol-level enforcement tied into Phase 9, and the real rule-base/AI review content itself.

**Phase 9 (BlueIce extension protocol)'s minimal slice is done** (see `phase-9-extension-protocol/PLAN.md`'s "Wiring design (resolved 2026-09-08)"). Design is fully resolved: the capability list, the three-tier manifest/permission model, WASM as the implementation format, a two-layer versioning story (the existing all-or-nothing `PROTOCOL_VERSION`/`Hello` for framing, plus a new per-capability `[min, max]` version window for capability content), server-side capability enforcement, and which extension actions should eventually route through Phase 7's gatekeeper (`network:intercept` and form/network-causing `dom:write`; purely read-only capabilities skip it). `backend/extension`'s former `todo!()` stub is now a real crate (`blueice-extension-host`) implementing that enforcement mechanism end to end: a new internal `blueice_ipc::extension` wire protocol (its own `ExtensionRequest`/`ExtensionReply` enums, a long-lived `Hello`-handshaked connection — a deliberate hybrid of the external client protocol's handshake and `blueice_ipc::gatekeeper`'s framing style, distinct from both), and an in-memory `ExtensionRegistry` that checks every capability-gated request against what a connected extension was actually granted, replying a structured `CapabilityDenied` on rejection rather than a silent no-op. This is a hardcoded single-extension minimal slice, deliberately scoped like `ai-gatekeeper`'s own first slice: one fixed `extension_id` granted `dom:read` only, so a `DomWrite` attempt is the concrete, real-subprocess-tested proof of server-side denial. Not yet done: the WASM runtime, manifest file parsing, a real non-spoofable (manifest-hash-derived) `extension_id` scheme, real per-capability version-window enforcement, the `CheckExtensionAction` gatekeeper-integration trigger list, and wiring any of this into the real `blueice-core` binary (this slice's enforcement runs standalone in `blueice-extension-host`, not multiplexed into `core`'s own session loop yet).

**Phase 8 (live `core` hot-swap)'s minimal-slice cutover mechanism is done** (see `phase-8-live-core-hotswap/PLAN.md`'s "Wiring design (resolved 2026-09-08)"). `blueice-launcher` can now swap the running `core` (v1) for a freshly-spawned one (v2) at runtime, with no already-connected external client ever dropped: a manually-triggered `ControlRequest::Cutover` (a new, launcher-internal control socket/protocol, `backend/launcher/src/control.rs`) captures v1's currently-open tabs (via a synthetic internal client of the broker itself — the same request-ID-based reply filtering `blueice-mcp-server` already established, reused here to pick one reply out of the broker's shared broadcast stream), spawns v2, replays those tabs into it directly (`Navigate`/`OpenTab`), health-checks the replay succeeded, then performs the actual swap — a generation counter distinguishes "v1's connection ended because we deliberately superseded it" from "v1's connection ended because something actually went wrong" (only the latter still ends the whole launcher, exactly as before this phase's work). Reload-based, not true state migration: no JS execution state exists yet, so replaying tab URLs is sufficient. Single-attempt, fail-closed to v1 on any error — no retry policy yet. Concurrent `Cutover` requests are serialized across capture, spawn, replay, health check and swap, so each observes the latest generation and has a unique v2 frame directory. Found and fixed a real, previously-unnoticed bug along the way: the broker's `forward_client_to_core`/`broadcast_core_to_clients` were silently discarding `tab_id`/`request_id` on every relayed message (using the plain, non-`_with_ids` `blueice_ipc` functions and an id-less channel type), meaning multi-tab addressing was actually broken for any client connected through the shared launcher — fixed as a prerequisite for this phase's own request-ID-dependent cutover mechanism, and regression-tested independently. Not yet done: automatic update-detection/scheduling policy, a bounded-retry policy, and structural per-tab `GetDom`/`GetRepresentation` health diffing (this slice's bar is lighter — every replay message succeeding plus a matching `ListTabs`).

**Phase 13 (BlueJS, the custom JavaScript engine) has a working AST→bytecode→VM engine covering nearly all of ECMA-262's core language and library surface** (see `development/browser_core/phase-13-bluejs-engine/PLAN.md` and `STRING_BUILTINS.md`). `backend/bluejs` exposes `parse`, `compile`, `compile_with_limit` and `Vm::execute`; execution never walks the AST. Stable heap-scoped handles, descriptors/accessors, String/Symbol keys, sparse arrays, boxed primitives, compiled functions/arrows/classes and captured binding cells use nursery/tenured GC with a managed-data budget. The String surface includes all 35 core prototype methods, three statics and 16 Annex B properties, Unicode 17 normalization/casing, five pattern protocols, standalone UTF-16 RegExp matching, callable replacements, iterators, spread/for-of and frozen tagged-template objects. Bound callbacks/constructors, instanceof with Symbol.hasInstance and RegExp.escape execute through the same VM. Classes are a real ClassDefinitionEvaluation implementation (derived-constructor `this`, private names/methods/static blocks, auto-accessors, one instance-field initializer function) rather than a subset, and the Stage 3 TC39 Decorators proposal (grammar, evaluation order, the `context`/`access`/`addInitializer` call protocol and `Symbol.metadata`) is implemented on top of it. Promise (capability records, all/allSettled/any/race/try/withResolvers/allKeyed/allSettledKeyed via the iterator protocol) was rebuilt on spec-shaped `PromiseCapability` records. General tail calls (a frame-replacing `TailCall` opcode, not just self-recursion) and `Function.prototype.toString` returning the exact original source text (a `SourceText` byte-range shared per parse, not a per-function copy) are both implemented, the latter including a lossless reversible encoding so `eval`/`Function`/`ShadowRealm` source containing an unpaired UTF-16 surrogate round-trips correctly through the Rust-`String`-based lexer. A generational-heap-aware `$262.createRealm()` cross-realm model exists (per-realm intrinsics/prototypes, `GetFunctionRealm`/`GetPrototypeFromConstructor`, foreign-object facades that forward `[[Get]]`/`[[Set]]`/other essential internal methods into the owning realm), now including a real "reverse membrane" (`Test262ReverseValue`, `vm/test262/reverse.rs`, reusing `shadow_realm.rs`'s `ACTIVE` reentrancy mechanism via the shared `vm/realm_reentrancy.rs`): a child realm can correctly re-enter a live parent-owned Proxy trap, callback or object. A round-trip-cache gap found while building it — a value crossing parent→child, mutated there, then crossing back out lost that mutation to `test262_import_foreign_value`'s round-trip identity cache, which unconditionally returned the original pristine value instead of the mutated stand-in — is now fixed: the one case that legitimately needs to see such a mutation (writing a freshly cross-realm-`Construct`ed TypedArray's bytes) bypasses the cache entirely via a direct real-object write (`Vm::test262_reverse_write_into_real_construction_result`) instead of fighting it, verified against both a hand-written regression and the real Test262 fixture that exposed it (`development/browser_core/phase-13-bluejs-engine/TEST262_ANALYSIS_REPORT.md` has the full mechanism). Observable object conversions, primitive setters, strict/sloppy String writes/deletes and custom constructor prototypes are covered. Each execute has fresh bindings; returned/thrown objects stay rooted until the next execution.

Runtime dispatch/native loops use fuel, strings and managed heap have byte limits, and calls have a 32-frame depth limit (a deliberately conservative bound: a 100-deep constructor chain needs on the order of 1.5 MB of native stack at roughly 14 KB per JS call, measured 2026-09-22, so raising it needs a byte-budget guard first, not just a bigger constant). Regex compilation/matching runs in the sibling `bluejs-regexp-worker` with a configurable operation deadline (default 250 ms) and a separate two-second startup bound; bytecode/AST/compiled regex storage and allocator overhead are outside the managed-heap budget. The pinned `regress` crate is a real, if imperfect, dependency limitation, not a stub: it cannot represent a raw lone surrogate in regex source text, and its non-`u`-mode Canonicalize and `u`-mode backreference matching disagree with ECMA-262 on a handful of BMP/surrogate-pair edge cases (`development/browser_core/phase-13-bluejs-engine/TEST262_ANALYSIS_REPORT.md` has the exact fixtures). Intl.Collator, Intl.Locale, its Locale-info queries, getCanonicalLocales, locale-sensitive String casing, Math constants/functions, abstract equality and property-presence are implemented; formatter constructors remain open. Test262 harness scripts share a classic-script global object; only `sta.js` and `assert.js` are native overrides now (matching the upstream harness's own observable behavior, differentially tested against it), while `propertyHelper.js` and `isConstructor.js` run their real upstream source, and the one declared range-parts `deepEqual.js` fixture uses a bounded native assertion, documented with its exact checked shape in the Test262 runner README. The binary-data family passes the pinned Test262 snapshot's `built-ins/{TypedArray,ArrayBuffer,SharedArrayBuffer,DataView,Uint8Array}` selections in full (`Atomics`: 774 of 778 modes passing, the other 4 `CanBlockIsFalse` modes excluded as a host `[[CanBlock]]` capability declaration rather than counted as a gap — BlueJS's `Atomics.wait` genuinely suspends the agent, so every `CanBlockIsTrue` mode already passes and a `CanBlockIsFalse` mode is inapplicable to that declaration), the module system passes `language/{module-code,export,eval-code}` in full, and three TC39 proposals beyond edition 17 (Immutable ArrayBuffer, `import defer`, `import.source()`) are implemented; `development/browser_core/phase-13-bluejs-engine/TEST262_ARCHITECTURE.md` holds the measurements and remaining gaps. Supporting language semantics that were previously an open subset — class/super, try/catch/finally completion values, eval-created bindings closing over their creator's scope, `arguments`/parameter environments — are now implemented; BigInt, proxy functions, complete realms (a general reverse-buffer-mirror mechanism symmetric to the forward direction's is not built; the round-trip-cache gap above is fixed only for the one case that needed it, a freshly cross-realm-constructed TypedArray's bytes), the event loop, browser/DOM wiring, shell/REPL and full Test262 conformance remain open. A real correctness gap found and left open, not yet BlueJS-specific: `vm/modules.rs`'s static-error discovery uses unordered `HashMap`/`HashSet`s for a module's dependency set, so which of two equally-valid `SyntaxError`s a cyclic module graph reports is nondeterministic across runs (`language/module-code/instn-resolve-order-src.js` passes either way, since Test262 doesn't pin the message, but the nondeterminism itself is real). The pinned inventory runner explicitly reports unsupported module/async hosts and harness sources that need unsupported grammar/APIs. `regress` and ICU are algorithm/data dependencies, not embedded JavaScript engines.

BlueJS has an opt-in **22,268-script Node oracle** (it agrees with Node on every script — three primitive-hook scripts asserting Node's legacy behaviour were removed because BlueJS follows ECMA-262 and Test262). Its current line coverage (`cargo llvm-cov -p blueice-bluejs`, Rust 1.95 on Ubuntu, 2026-09-22) is **108,834/121,558 lines (89.53%)**, with an 88% CI floor; the workspace measures 90.58% (155,626/171,819) against a 90% floor. The crate roughly doubled in size this pass (Promise/classes/decorators/tail-calls/source-text/cross-realm/surrogate-encoding work), which is why the percentage moved down from the prior 91.38% while the absolute covered-line count grew by about 50,000: both floors are still comfortably met, but this is not a 100% coverage claim. Current exact measurements, reviewed algorithms, edition-17/Node differences and limitations are recorded in the [String inventory](development/browser_core/phase-13-bluejs-engine/STRING_BUILTINS.md). The [Intl/deadline/Test262 report](development/browser_core/phase-13-bluejs-engine/INTL_CONFORMANCE.md) records the full inventory result. The [verified standards baseline](development/browser_core/research/js-conformance-baseline.md) distinguishes published ECMAScript 2026 from the living 2027 draft. These checks do not establish complete ECMAScript conformance.

**Test262 (complete unfiltered inventory, 53,582 files / 102,926 modes, pinned corpus `72faf8ec`):** on `feature/test262-remaining-failures` at commit `d33babc`, measured 2026-09-22 on macOS 26.6.2 on Apple silicon (Apple M4, `aarch64-apple-darwin`), with both adapter binaries freshly rebuilt from that exact commit before running: **102,859 / 102,926 (99.935%)**, unchanged from the prior 2026-09-22 figure measured at commit `9decbb3` on Ubuntu 24.04.4 LTS under WSL2 (that run predates `d33babc`'s new `excluded` status; the two runs' totals reconcile exactly, confirming `d33babc` only reclassifies 4 modes rather than changing engine behavior), and up from the 2026-09-21 figure of 99,897 / 102,926 (97.057%) recorded on `main` at commit `eaeb5c1`. Of the 67 non-passing modes, 63 are failures and 4 are `excluded` — a status `d33babc` added for a Test262 fixture flag that declares a host-capability assumption (`CanBlockIsTrue`/`CanBlockIsFalse` for `Atomics.wait`'s `[[CanBlock]]`) rather than a capability BlueJS actually lacks: BlueJS's `Atomics.wait` genuinely suspends the agent, so every `CanBlockIsTrue` mode already passes and the 4 `CanBlockIsFalse` modes (`built-ins/Atomics/wait/{,bigint/}cannot-suspend-throws.js`, 2 modes each) are inapplicable to that declaration and are never dispatched, not folded into "fail" or "unsupported". The 63 failures are classified in `TEST262_ANALYSIS_REPORT.md`: 22 need more instruction budget/wall time than a bytecode interpreter's default fuel gives a few heavy fixtures (DST-cache tables, `toSpliced`, a 100,000-live-object WeakMap chain); 19 are corpus problems, not engine gaps (a shared Annex-B strict-mode test harness runs its own "lenient" half through a `"use strict"`-prefixed direct `eval`, which cannot both be strict and prove sloppy-only behavior — verified independently against Node 24 running the same harness concatenation, which fails identically); 10 need the reverse-membrane cross-realm work above; 4 hit the 1 MiB managed-string limit by design (the corpus expects a catchable OOM, but a host resource limit is deliberately uncatchable here); 4 are the `regress`-crate RegExp limitations above; 2 hit the 32-frame call-depth limit; 1 is a spec-version conflict between an older Annex B fixture and Temporal-era block-function-hoisting wording (resolved in favor of the current spec text, which two `staging/sm` fixtures also require); 1 is a parser grammar gap (`for await` loop-body syntax rejection). This branch has not yet had a full cross-platform (Windows) re-run against `d33babc`, and the per-platform group/selection/coverage/oracle tables in `TEST262_{MACOS,LINUX,WINDOWS}_REPORT.md` still reflect the prior `9decbb3`/`eaeb5c1` figures — only the classification above was re-verified on macOS at `d33babc`. These are progress measurements, not a full-conformance claim.

**Phase 26 (ECMA-262 Temporal) is nearly closed against Test262** (see `development/browser_core/phase-26-ecma262-temporal/PLAN.md`; implemented in `backend/bluejs/src/vm/temporal/`, split by value type and operation with a 1,500-line-per-file rule). All eight Temporal value types plus `Temporal.Now` and `Date.prototype.toTemporalInstant` exist, with the ISO calendar and the 16 `AvailableCalendars()` non-ISO calendars, IANA time zones read from the same pinned `jiff-tzdb` bundle that `blueice-ecma402` uses, and the spec-shaped `DifferencePlainDateTime*` / `DifferenceZonedDateTime*` rounding pipelines shared by `until`/`since`/`round`/`total`. Time-zone equality compares ECMA-402 primary identifiers (`blueice_ecma402::primary_time_zone_identifier`, from a generated table tied to tz release 2026c). Measured 2026-09-21 by complete unfiltered inventories against the pinned Test262 corpus (`72faf8ec`): `built-ins/Temporal/` 9,210 / 9,210 (100.000%), `intl402/Temporal/` 4,058 / 4,058 (100.000%), the combined Temporal surface 13,268 / 13,268 (100.000%) and the whole of `intl402/` 6,714 / 6,714 (100.000%) on Ubuntu (macOS identical); every test tagged `features: [Temporal]` together (those directories plus 80 files elsewhere, e.g. `intl402/DateTimeFormat`, `built-ins/Date`, `staging/sm`) is 13,432 / 13,432 on both. The member set of every Temporal prototype, constructor, the namespace and `Temporal.Now` is pinned to the specification's own section headings by `backend/bluejs/tests/temporal_spec_member_inventory.rs`, written against `tc39/proposal-temporal` `spec/` on `main` (Temporal is Stage 4; the ECMA-262/402 merge PRs were not yet merged when checked, so that repository is the authority): this is why `ZonedDateTime` no longer has `getISOFields`/`toPlainMonthDay`/`toPlainYearMonth` (use `toPlainDate().toPlainMonthDay()`) and `PlainMonthDay` has no `month`. A zero UTC offset formats as the locale's `GMT`, not `GMT+0`: ICU4X drops CLDR's `gmtZeroFormat`, so `blueice-ecma402` (`date_time_format/zero_offset.rs`) restores it from the locale's `gmtFormat` pattern, exact for 761 of CLDR's 766 locales (`dz`, `ks`, `ks-Arab`, `tok`, `xnr` get the derived text). Re-measured 2026-09-21: `blueice-ecma402` line coverage is 94.42% (9,559 / 10,124) on Ubuntu and `blueice-bluejs` 91.38% (58,892 / 64,450), and the Ubuntu full-inventory run replaces the older 12,682 / 13,268 (95.583%) figure. `blueice-bluejs`'s tests `include_str!` the pinned Test262 checkout, so it must exist at `development/browser_core/reference/test262` (see that directory's README) before `cargo test -p blueice-bluejs` compiles. Test262 passing is not a claim of full spec conformance.

Build/lint/test commands (see `development/browser_core/testing/TEST_PLAN.md` for the full testing policy):

- Build: `cargo build --workspace --all-targets`
- Test: `cargo test --workspace`
- Lint: `cargo clippy --workspace --all-targets -- -D warnings`
- Coverage gate (crates with a real implementation must hold ≥90% line coverage; the placeholder `extension` process, the windowed reference frontend's `main.rs`, `mcp-server`'s `main.rs`/`server.rs`, and `ai-gatekeeper`'s `main.rs` -- process/transport wiring exercised by a real subprocess or MCP client, not headless-CI-reachable, with pure helpers/message-sequencing logic still unit tested (each crate's own `lib.rs` holds the gate) -- are excluded and only reported for visibility): `cargo llvm-cov --workspace --ignore-filename-regex 'extension/src/main\.rs$|frontend-reference/src/main\.rs$|mcp-server/src/main\.rs$|mcp-server/src/server\.rs$|ai-gatekeeper/src/bin/blueice-ai-gatekeeper\.rs$' --fail-under-lines 90 --summary-only`

All of the above run in CI on every push/PR to `main` (`.github/workflows/ci.yml`). Design documentation for both implemented and not-yet-implemented parts still lives under `development/` — keep it in sync as each phase's own Definition of Done, not as an afterthought.

**Definition of Done** (full policy: `development/browser_core/testing/TEST_PLAN.md`): no design or feature counts as done merely because it's settled or compiles.

- **Develop test-first (TDD)**: write the failing test before the implementation that makes it pass — not tests bolted on after the feature is already written.
- It needs passing tests; where an end-to-end path through the feature's real public interface exists, that path must pass too — not just tests of internal modules.
- The public interface itself must be complete enough for tests to drive without reaching into `pub(crate)`/private internals.
- Real-implementation crates must clear the ≥90% line-coverage gate.
- **Once implementation is otherwise complete, do a dedicated test-review pass**: re-read the suite's actual content (not just pass/fail or the coverage number), fill in cases TDD's incremental cycles didn't surface, update any test whose expectation no longer matches intended behavior, and delete tests that no longer check anything meaningful.

This applies to every phase's checklist, not only to crates that already meet it.

## Core goal

BlueIce is a browser engine, written from scratch in Rust, built around one idea: a human user and an AI agent should perceive the same page state from the **same render pass**, instead of the common dual-track setup where a human uses a real browser and an AI drives a separate headless instance via external automation (e.g. Puppeteer/CDP). That dual-track approach is rejected for architectural reasons, not just performance:

- Anti-bot systems (Cloudflare, Akamai, PerimeterX) fingerprint headless/CDP Chromium and can serve it different content than a human sees.
- A separate driven instance has its own viewport/timing/JS state, so "what the AI saw" is only ever an approximation of "what the human saw."
- Any AI-facing capability (e.g. semantic tags alongside human-facing highlights) has to be a post-hoc hack in an externally-driven architecture; owning the render pipeline makes it a first-class feature instead.

This is not a clean-room implementation — Gecko (Firefox) and Blink/V8 (Chromium) source are read directly as technical reference and porting basis. See `development/browser_core/BROWSER_CORE_PLAN.md` for full detail.

Two concrete requirements follow from the core goal (plan §1) and apply across all phases:

- The AI must be able to show/hide the human-facing window at runtime without restarting the engine — same instance, same render pass, same JS state, regardless of window visibility.
- Every DOM node has an explicit, stable ID assigned at creation (not an array index or ephemeral pointer), so the AI-facing representation can reference elements reliably across mutations.

## Design-first workflow

Plans are drafted under `development/` *before* implementation starts, and updated as the design evolves — treat these as living documents, not historical records. Each major component gets its own subdirectory with a plan doc. Currently the only component is `development/browser_core/BROWSER_CORE_PLAN.md` (the engine itself).

**Settled**: which layer the human and AI representations are shared at (plan §3) — an accessibility-tree-shaped schema (role, state, provenance-tagged name, bounds) extended with `opacity`, `animating`, `occluded`/`occludedBy`/`occludedFraction`, and per-node `hovered`/`focused`, keyed by BlueIce's own stable `NodeId`. Resolved directly from how Gecko/Blink already do this in production (`research/accessibility-tree.md`), not from an independent validation exercise — check plan §3 for the current schema rather than assuming one of the original four candidates in isolation.

**MVP scope** (per plan §4) is deliberately narrow: a minimal HTML parse → DOM → CSS cascade → layout → paint pipeline, plus the shared human/AI representation layer. Explicitly out of scope for now: extension ecosystem, multi-tab state sync, full JS engine optimization, DevTools.

## Licensing (load-bearing, not boilerplate)

Project-wide license is MPL-2.0, chosen specifically because the project reads and adapts Gecko/Chromium source rather than clean-rooming:

- Files derived from Gecko **must** stay MPL-2.0 — this is an inherent MPL file-level copyleft obligation, not a project choice.
- Files derived from Chromium/Blink (BSD-3-Clause) are relicensed to MPL-2.0, but the original BSD copyright/disclaimer notice must be preserved verbatim in that file's own header — the project uses per-file headers only, no centralized `NOTICE`/`THIRD_PARTY_LICENSES` file. See `CONTRIBUTING.md` for the exact header templates (original code, Gecko-derived, Chromium/Blink-derived) before porting any file.
- BSD-3-Clause's binary-distribution clause is separate from the source-header requirement above and isn't satisfied by it: any distributed binary needs the Chromium notice reproduced in "documentation and/or other materials provided with the distribution" — i.e. a Help/About/Credits screen. Tracked as a Phase 4 checklist item (`development/browser_core/phase-4-human-rendering-path/PLAN.md`), since there's no UI to put it in yet.
- Wholly original code (the AI representation layer, project glue) uses MPL-2.0 for consistency only, with no derivative-work obligation.
- The license places no field-of-use/commercial restriction (that would violate the OSI Open Source Definition) — "no commercial activity" is a project stance, not something encoded in the license terms.
- MPL §2.1's patent grant only covers contributors' own contributions to this project, not unrelated third-party patents (codecs, GPU rendering, JIT techniques). This risk doesn't disappear at non-commercial stage.
- Do not use "Firefox", "Mozilla", "Chrome", "Google Chrome", or "Chromium" names/logos as BlueIce branding. Descriptive references ("BlueIce references Gecko's approach to X") are fine as nominative fair use.
